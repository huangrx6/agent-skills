# 既有界面精修、组件评审与视觉性能核查

对已经上线或成型的界面做优化时，最高原则只有一条：**精修是提纯，绝不是披着优化外衣的偷偷重设计**。如果现有概念本身有根本问题，应明确指出并建议立项重设计，而不是在修补细节时悄悄换掉整套视觉世界。

---

## 一、精修铁律与 4 类系统漂移分类

动刀前，先通读项目已有的设计规范文档、样式 Token、共享基础组件与 2–3 个标杆邻近页面。把发现的每一处不一致先归类，再在**最窄的正确层级**修复：

| 漂移类型 | 识别特征 | 正确修法 | 错误做法 |
| --- | --- | --- | --- |
| **1. 缺 Token（Missing Token）** | 多个页面各自硬编码相近的阴影、圆角、灰阶或字号 | 提炼并命名可复用的语义 Token，再回填各处引用 | 只在当前页面又写死一个新十六进制色值 |
| **2. 重复造轮子（One-off）** | 局部手搓了自定义下拉、弹窗、开关或标签，与全站共享组件细节偏离 | 直接替换为设计系统已有的共享组件与标准变体 | 把手搓组件的 CSS 硬调成“看起来差不多” |
| **3. 概念错位（Conceptual Mismatch）** | 信息架构、保存方式（自动保存 vs 显式提交）、导航层级或披露模式与邻近模块矛盾 | 对齐全站心智模型与交互模式（必要时先与需求方确认） | 保留错位流程，只美化按钮颜色 |
| **4. 局部缺陷（Local Defect）** | 方向与组件没错，但缺状态、没对齐、间距松散或文案口径不统一 | 就地补全状态与精确微调，不动范围外代码 | 借题发挥顺手重构无关页面 |

> 约束：不要为一次局部特例过度抽象出全局组件，也不要放任真正复用的值继续散落硬编码。

## 二、5 级精修分诊顺序（Triage）

禁止在某个按钮圆角上雕花，却留下阻断主流程的硬伤。严格按以下 5 级先后推进，保持整条用户路径处于同一完成度水位：

1. **第 1 级（阻断与安全）**：任务无法完成、按钮不可点/被遮挡、误导性状态、数据丢失、键盘与无障碍路径彻底断裂；
2. **第 2 级（核心状态缺口）**：补齐 `loading`、`empty`、搜索无结果、`error` 与重试、`success`、`disabled` 及权限受限态；
3. **第 3 级（结构与系统漂移）**：修平流程心智不一致、视觉层级混乱、窄窗/矮窗断行裁切及上述 4 类设计系统漂移；
4. **第 4 级（视觉与动效精修）**：统一光学与数学对齐、间距节奏、图标线宽、明暗主题细节与克制可中断的动效；
5. **第 5 级（代码与资产收尾）**：清理调试输出、死样式、未用导入、多余临时类与因精修产生的重复代码。

## 三、全路径精修 5 维度核查清单

按真实用户从进入、操作、等待、报错到完成的完整路径逐项过筛：

1. **流程与层级**：术语、披露方式、路由与保存反馈与邻近模块一致；主任务与当前状态一眼明确，又不把所有元素拉成相同视觉重量；到达、转场、空态与错误恢复连成闭环。
2. **布局与排版**：对齐网格与 4px 间距体系；同时核查**数学对齐与光学对齐**；同角色字形全页统一；在移动端、中等宽度、宽屏与 200% 缩放下复验，绝不只盯着一张桌面截图修。
3. **色彩、图像与图标**：全面回归语义 Token；逐状态复核文本/控件/焦点对比度；全站图标同家族、同线宽、同视觉重心；图片锁定宽高比与 `alt`，杜绝加载跳动（CLS）。
4. **交互与全状态**：每个可交互控件具备清晰区分的 `default` / `hover` / `focus-visible` / `active` / `disabled` / `loading` / `error` / `success` 态，且交互态对比度高于静息态；不为了“显得改过”硬加多余动效。
5. **文案与源码 Diff**：术语、大小写、标点（真省略号 `…`、弯引号）与事实一致；收尾逐行审阅源码变更，确认无误伤范围外文件。

## 四、组件与资产交付评审规范

无论从设计稿落地还是重构共享组件库，在铺开整页实现前先过两道关：

### 1. 资产与代码边界评审（防“代码硬画复杂插画”）

- **先划清职责**：复杂写实材质、带透视/光影的插画与摄影图必须由独立图片/分层资产承担，绝不在代码里用笨拙 SVG 或上百行 CSS 渐变硬画；标准控件、排版、数据表、架构几何图与图标系统由结构化 HTML/CSS/SVG 实现。
- **可动部件独立分层**：如果一个视觉载体包含需要开合、滑动或替换内容的局部（如带透明窗口的画框、可滑动遮罩、独立开关门板），在资产拆解阶段就拆成「外框层 + 内容层 + 独立运动件」，而不是摊成一张死图。
- **首屏基准校准**：先高质量装配并校准首屏（含真实交互脚本与所有外部字体/图片依赖），确认视觉与交互达标后再向整页扩展；绝不通过临时删掉交互脚本来换取静态截图通过。

### 2. 共享组件完备度评审表

| 评审维度 | 必须回答并通过的检查项 |
| --- | --- |
| **语义与 API** | 是否使用原生语义元素（`<button>` / `<a>` / `<label>` / `<dialog>`）？是否支持受控与非受控（或清晰的 `defaultValue`）？变体数量是否收敛（优先 3–4 个高频变体而非十几种碎片）？ |
| **全状态矩阵** | `default`、`hover`、`focus-visible`、`active`、`disabled`、`loading`、`error`、`selected` 是否全部定义且在明暗双主题对比度达标？ |
| **键盘与读屏** | 完整支持 `Tab` / `Shift+Tab` / `Enter` / `Space` / `Esc` / 方向键（复合控件）？无文本图标按钮是否有 `aria-label`？异步状态是否有 `aria-live="polite"`？ |
| **容器与极端内容** | 放进 240px 窄侧栏和 1200px 宽主区是否均正常（优先 Container Queries）？传入 100 字标题、空字符串或 50+ 选项时是否优雅截断或内部滚动？ |

## 五、视觉与前端资源性能核查

性能是界面体验的硬组成部分。原则：**先度量真实瓶颈，改完复测前后数据，不盲目做无感微优化，也绝不拿无障碍换性能**。

### 1. Core Web Vitals 硬目标

| 指标 | 目标线 | 关键界面工程动作 |
| --- | --- | --- |
| **LCP（最大内容绘制）** | **< 2.5 s** | 首屏主图加 `fetchpriority="high"`、严禁给首屏图加 `loading="lazy"`；使用 WebP/AVIF 与匹配尺寸的 `srcset`；预连接 CDN（`preconnect`）并预加载关键字体 |
| **INP（交互到下次绘制）** | **< 200 ms** | 拆分长任务；延迟加载非关键重组件（图表、富文本编辑器）；受控输入框单次击键开销必须极低，优先非受控或轻量状态 |
| **CLS（累积布局偏移）** | **< 0.1** | 所有 `<img>`/`<video>` 声明显式 `width`/`height` 或 `aspect-ratio`；严禁在既有内容上方动态插入无预留空间的横幅；字体做好度量回退 |

### 2. 渲染、媒体与长列表高频卡点

- **消除布局抖动（Layout Thrashing）**：严禁在循环或渲染中交替读取几何属性（`getBoundingClientRect`、`offsetHeight`、`scrollTop`）与写入样式——必须**先批量读，再批量写**：

```js
// ❌ 反例：循环中读写交替，每轮强制同步重排
items.forEach((el) => {
  const h = el.offsetHeight;
  el.style.minHeight = `${h + 16}px`;
});

// ✅ 正例：批量读完再批量写
const heights = items.map((el) => el.offsetHeight);
items.forEach((el, i) => {
  el.style.minHeight = `${heights[i] + 16}px`;
});
```

- **大列表渲染（> 50 项）**：使用虚拟列表（如 `virtua` / TanStack Virtual）或对离屏项启用 `content-visibility: auto; contain-intrinsic-size: auto 64px;`，独立区块加 `contain: layout style`。
- **用压缩视频替代 GIF**：短循环演示动图优先用 `<video autoplay muted loop playsinline>`（或按需提供 H.264/WebM 源），并务必配套 `poster` 静态图及 `prefers-reduced-motion` 静态回退方案。
- **首屏外资源延后**：首屏以下图片设 `loading="lazy"`；重型图表与低频弹窗采用动态 `import()` 按需加载；移除未使用的 CSS 规则与冗余依赖包。
