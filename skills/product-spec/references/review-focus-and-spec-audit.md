# 全局约束、隐含失效与规格自审

写完产品规格初稿并不代表可以直接交给用户批准或交给研发开工。本文件融合了「愿景文档原则」「Global Constraints」「Review Focus 五大隐含失效模式」「独立构建者视角审稿（Builder Check）」与「6 维规格自审清单」，帮你在交出文档前拦下 80% 的下游返工。

---

## 1. 核心原则：规格是愿景文档，不是穷举清单

> **规格定义了软件「必须做什么」，而不是现实世界会丢给软件的每一种输入。规格对某个输入保持沉默，绝不等于允许该输入把程序弄崩、弄丢数据或让用户陷入死胡同。**

这一原则同时约束三个环节：
1. **写规格与交接时**：不能因为用户没提到「空列表」「切页串态」「快速连点」就视而不见；必须在 `Global Constraints` 和 `Review Focus` 中主动补全横切约束与隐含失效防线。
2. **研发拆解计划时**：`Review Focus` 里列出的每一类隐含失效，都要反向挂接到对应负责模块的验证用例中，而不只是挂在文档顶部当口号。
3. **最终评审定级时**：问题的严重级别取决于**「若按现状发布，理性用户实际承受什么后果」**，而不是「规格有没有逐字点名这个输入」。把导致真实用户数据丢失或界面卡死的问题标成「次要（因为规格没写）」，是在给规格打分，不是在给产品把关。

## 2. Global Constraints（全局约束）提炼规范

把整份规格中**所有横切、全局生效的硬约束**抽成一个单行清单，放在规格交接区和实施计划头部。每个下游模块与实施任务都隐式继承本节全部条款，避免散落在正文里被漏看。

### 提炼五类必查项
1. **平台、视口与运行下限**：最小支持窗口尺寸（如 `900×620`）、目标系统/浏览器版本、明暗主题、全键盘可达。
2. **依赖与外部边界**：禁止引入的依赖、离线可用要求、禁止读写的外部路径或遗留目录。
3. **数据与安全红线**：凭据存储与脱敏要求、渲染层序列化边界、禁止越界作用域反向推导、旧版配置无损保留。
4. **命名、术语与文案口径**：产品内唯一术语表、固定按钮文案、固定错误码或状态枚举值。
5. **性能与交互底线**：本地过滤响应上限、防抖时间、超时时间、禁止未捕获控制台异常。

### 写作铁律：精确拷贝，拒绝概括
- **反例（禁止）**：「遵守平台兼容性与安全规范，文案保持一致。」（废话，没有可核验值）
- **正例（推荐）**：

```markdown
## Global Constraints（全局约束）

- 最小视口 `900×620` 下所有主操作可见、无非预期横向滚动条，且明暗双主题对比度达标。
- 所有用户凭据仅保留在受保护后端存储，绝不明文序列化到前端状态或写入日志。
- 术语全篇统一使用「扩展（Extension）」，不使用「插件」「模块」混称；按钮文案固定为「恢复默认」「清空搜索」。
- 配置优先级严格遵循 `会话 > 项目 > 工作区 > 用户 > 全局`，严禁从较窄作用域反推改写较宽作用域。
- 升级加载旧版本配置（缺少 `sortOrder` 字段）时必须无损兼容并回退为 `enabled-first`，不得报错或覆盖未知字段。
```

## 3. 五大隐含失效模式（Review Focus）写法

在将规格交给实施或拆解计划之前，站在规格对面问自己：**「规格里没逐字写死、但最可能在实际使用中咬伤用户的 5 类输入或状态是什么？」**

### 编写规则
- 最多 **5 条**，按**真实发生概率与伤害从高到低**排序；
- 每条严格 **1 行**，必须同时包含两个要素：**「触发输入/条件」 + 「理性用户应得的预期行为」**；
- 写完之后，在进入实施计划时，**逐条把对应验证项挂接到拥有该逻辑的任务里**（绝不悬空）；
- 如果核查后确实没有未覆盖的隐含失效，显式写明「经核查，五大类隐含失效均已由对应 AC 与任务验证覆盖」，绝不能因为懒得查而留空。

### 五大高频维度与模板

```markdown
## Review Focus（五大隐含失效模式）

1. **顺序与切页干扰**：在项目 A 打开编辑面板修改一半后切换到项目 B 或关闭重开，面板必须完全重置为当前目标最新状态，绝不残留旧搜索词或把项目 A 的修改误写进项目 B。
2. **极值与特殊输入**：列表为 0 项、恰好 1 项、超过 100 项，或包含 80 字符无空格 URL / Emoji / `<script>` 转义字符时，界面仍保持安全折行、独立滚动与右侧按钮完整可见，不崩溃不越界。
3. **并发与中断竞态**：用户快速连续点击提交、快速键入触发多次异步查询，或在请求未返回前关闭弹窗时，必须防重提交、丢弃晚到的陈旧响应，且在途回调不得向已关闭界面报错。
4. **权限受限与依赖降级**：外部服务离线、超时（>10s）或接口返回 401/403/5xx 时，必须完整保留用户已填输入、就近给出可理解原因与恢复按钮，且不阻塞页面其他本地功能。
5. **历史存量与升级兼容**：首次载入缺少新增字段或含废弃枚举值的旧版配置时，必须按默认值平稳降级渲染，并在重新保存时无损保留无法识别的历史字段。
```

## 4. 独立构建者视角审查（Builder Check）

对于**完整项目规格**，在正式交给用户批准之前，必须执行一次「独立构建者审查」：模拟一位完全没参与前面讨论、且之后无法再找你问问题的资深构建者，拿着这份规格去制定实施计划，看哪里被迫去猜且猜错会酿成大错。

> 小改动短规格体量轻，直接交用户确认即可，无需走这一步；完整项目规格必须走。在告诉用户「正在整理正式规格」时，先说明会有一轮独立审稿，可能会带着极少量关键问题回来确认一次。

### 独立审稿提示词模板（有子智能体工具时派发给全新上下文）

将占位符替换为真实领域与文档路径，派发给全新子智能体（不带当前对话历史，彻底隔绝作者盲区）：

```text
你是一位经验丰富的 [领域角色，例如：资深全栈产品工程师 / 桌面客户端研发负责人]。
现在有人递给你一份产品规格文档，要求你据此制定可落地的实施计划。
你无法再联系文档作者，也看不到他们之前的聊天记录。

请完整阅读：[规格文档路径]

只报告那些「在开始规划实现前必须搞清楚的问题」：即文档没说清、你被迫去猜、而且一旦猜错就会实质改变产品行为或实施方案的地方。
每一条请写清：
1. 具体问题是什么；
2. 为什么不同答案会改变计划或最终产物。

请按重要程度从高到低排序。
跳过以下内容：
- 文档已明确声明「留给实现者自行决定」的部分；
- 任何经验正常的工程师按惯例即可安全决定、不会改变产品形态的小细节；
- 纯粹的措辞润色或字面挑刺。

如果没有重要缺口，直接回复：「无重要遗漏」。
```

> **无子智能体工具时**：不要跳过，显式切换为「陌生构建者」角色从头冷读一遍文档，逐段寻找被迫猜测的点。

### 问题三堆分拣法（严格只产生最多一轮追问）

收到构建者审稿反馈后，绝不原封不动全丢给用户，先按下面三堆彻底分拣：

| 分拣堆 | 判定标准 | 正确处理动作 |
| --- | --- | --- |
| **第一堆：已有答案** | 前序对话、现有代码或项目规范里其实已经明确，只是忘写进规格 | 直接补写进规格文档，**不打扰用户** |
| **第二堆：次要细节** | 合理构建者能自行拍板，且不会实质改变产品形态或用户体验 | 由你直接做出合理决定，写入规格并显式标为「作者决定（附理由）」，交付文档时附短清单供用户顺手过目 |
| **第三堆：仅用户能决** | 只有用户能拍板，且答案会实质改变范围、交互或核心验收标准 | 按重要度排序，汇总成**唯一一轮**简洁提问发给用户（带推荐项）；拿到回复后更新规格再正式交付 |

> **铁律**：构建者审查最多只向用户回抛这**一轮**高价值问题；绝不反复来回折腾三四轮。

## 5. 独立规格自审清单（6 维体检表）

在交出最终规格之前，用新鲜眼光逐项扫过以下 6 个维度；任何一项不过关，当场修正再发：

| 自审维度 | 要捕捉的缺陷形态 | 合格判据 |
| --- | --- | --- |
| **1. 占位词与空洞语句拦截** | 出现 `TBD`、`待定`、`待补充`、`适当处理边界情况`、`完善校验`、`体验更好`、`按需调整`、`支持常见异常` 等什么也没决定的废话 | 全文零占位词；所有真未定的项均明确放入「待确认假设」并附默认执行方案 |
| **2. 术语与逻辑自相矛盾** | 前面叫「扩展」后面叫「插件」再后面叫「模块」；前面说「关闭清空搜索词」后面 AC 写「保留上次检索」；`Out of Scope` 排除的项又出现在 AC 里 | 全篇核心名词、按钮文案、状态名唯一一致；范围、主路径、边界矩阵与 AC 零冲突 |
| **3. 孤立引用与悬空契约** | 正文提到了某个「高级设置弹窗」「错误码 E-102」「管理员角色」或「草稿箱」，但全篇从未定义其入口、结构或行为 | 规格里提到的每个界面元素、状态枚举、角色权限与外部依赖都有清晰归属或显式标注为既有能力 |
| **4. 不可测 AC 审计** | 随机抽 3 条 AC 问：「不懂代码的黑盒验收人员照着做，能毫无争议判 PASS/FAIL 吗？」若依赖主观感受或内部实现则不合格 | 每条 `AC-N` 均有明确前置条件、操作动作与外部可观测结果，且原始痛点 100% 映射到 `In Scope + AC` 或 `Out of Scope` |
| **5. 过度膨胀与越界写代码** | 小改动强行堆砌 8 个空洞章节；或在产品规格里替研发写死了具体 React hook、SQL 索引名、内部私有函数实现 | 体量与复杂度相称；只钉死用户可见行为、业务规则与外部契约，把内部代码结构留给架构与实施计划 |
| **6. 隐蔽拍板清零** | 规格里夹带了用户从未确认的默认阈值、删除护栏、排序规则或作用域覆盖策略，却写得像既定事实 | 所有作者补全的默认选择 100% 显式收录在「待确认假设 / 作者决定」清单中，交付时主动提醒用户核对 |

## 6. 交付规格时的标准收尾话术

完成自审与构建者检查后，提交规格文档给用户批准时应包含三要素：
1. **文档位置与核心摘要**（3–5 行说明这份规格最终锁死了什么）；
2. **作者自行拍板的次要决定短清单**（方便用户扫一眼确认，无需通篇猜哪些是自己说过的）；
3. **明确的批准请求**（例如：「请确认这份规格是否准确表达了你要的结果；确认后我将把它桥接为可执行实施计划，在这之前不会改动任何代码。」）。
