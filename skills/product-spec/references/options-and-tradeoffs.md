# 多方案权衡与裁剪

在理解用户「要什么、为什么」之后、动笔写完整产品规格之前，必须用**独立的一轮**把「怎么实现这个产品形态」的真实可行方案摊在桌面上。方案没定就写详尽规格，等于在还没选好地基时就开始画装修施工图。

---

## 1. 方案对比的触发与筛选纪律

### 何时必须给 2–3 个方案
- 只要需求存在多种合理交互形态、入口位置、数据归属或渐进演进路径，都应提出 **2–3 个真实可行的备选方案**。
- **先自行淘汰伪方案**：不要为了凑够 3 个方案而塞进明显违背用户目标、被现有架构否决或纯属稻草人的选项。留下的每个方案都必须足够具体，让读者脑海里能立刻浮现它的样子，且扎根于当前项目的真实结构。
- **仅存在唯一合理路径时**：不要硬编两个凑数方案。在同一轮明确说明「当前约束下只有这一条合理路径」，并用 1–2 句话交代为什么其他常见做法不成立，确认后再进入规格细节（若是小改动，可直接合并进短规格请求批准）。

### 方案粒度的边界
- 聚焦**用户可见的交互形态、职责边界、演进代价与工程体量**，不要在方案对比阶段提前陷入具体表字段、组件内部 hook 或低层实现细节（那些归架构设计与实施计划）。

## 2. 2–3 方案对比标准模板

将以下骨架用于方案定案消息，并最终保留精简版写入产品规格的「方案结论」一节：

```markdown
## 备选方案对比

为了解决「<一句话核心痛点>」，结合现有 <页面/模块现状>，以下 3 个方案均可行，取舍如下：

### 方案 A（推荐）：<方案短名，例如：就地轻量浮层 + 独立滚动与粘性底栏>
- **长什么样**：<2–3 句具象描述入口、交互主路径与核心反馈，必要时附 4 行文本草图>
- **收益**：<直接命中了哪条核心目标>
- **代价 / 限制**：<明确写出短板和需要配套的约束>

### 方案 B：<方案短名，例如：独立模态弹窗>
- **长什么样**：<2–3 句具象描述>
- **收益**：...
- **代价 / 限制**：...

### 方案 C：<方案短名，例如：新增独立设置子页>
- **长什么样**：<2–3 句具象描述>
- **收益**：...
- **代价 / 限制**：...

### 四维权衡矩阵

| 评估维度 | 方案 A（推荐） | 方案 B | 方案 C |
| --- | --- | --- | --- |
| **交互体验与路径** | 1 步就地完成，不打断当前工作流；高频切换极快 | 弹窗聚焦注意力，适合一次配多项；但高频打开有打断感 | 空间最宽裕；但跳转离开主工作区，路径偏深 |
| **改动与维护成本** | 低：复用现有容器与列表组件，仅补粘性搜索与滚动区 | 中：需新增弹窗状态机、焦点捕获与窄窗高度适配 | 高：涉及路由新增、面包屑、返回态同步与导航入口调整 |
| **演进风险** | 若未来需要单扩展复杂表单配置，浮层放不下，需二次跳转管理页 | 中等：可承载中等表单，但嵌套二级弹层易出焦点冲突 | 低：扩展性最强，但前期过度设计 |
| **可逆性** | **高（双向门）**：未来如需升级为管理页，入口可直接外链跳转，无数据迁移成本 | **中**：弹窗交互一旦养成习惯，后续改路由需迁移状态管理 | **低（单向门）**：新增顶层路由与导航项后，后续撤回影响用户路径记忆 |

**推荐理由**：当前最高频场景是「快速检索并勾选 1–2 个扩展后继续当前工作」，属于高频轻量操作而非深度配置。方案 A 改动最小、不打断主流程，通过「≥15 项显搜索 + 独立滚动区 + 粘性底栏『管理全部』入口」即可兼顾高数量与未来扩展（YAGNI，不为尚未验证的复杂配置需求提前引入新路由）。

你倾向按 **方案 A** 推进，还是选择 B / C？
```

## 3. 四维权衡矩阵评估指南

对比方案时，不要只写「优点/缺点」这种空泛标签，必须落实到以下四个硬维度：

| 维度 | 必须回答的核心问题 | 常见遗漏点 |
| --- | --- | --- |
| **交互成本** | 高频主任务需要几步点击/键盘操作？是否打断当前上下文？新手能否一眼发现？ | 只看首次好看，忽略每天操作 20 次的累赘感；忽略键盘流与窄窗 |
| **维护成本** | 复用多少现有组件与状态机制？新增多少状态同步点与回归面？ | 低估「双入口同步」「切页状态保活」「窄窗/主题适配」的长期维护税 |
| **演进风险** | 数量放大 5 倍、字段增加 2 倍、角色增加时，该形态在哪里会撞墙？ | 方案在 3 条测试数据时很美，到 80 条或长文本时直接崩坏 |
| **可逆性** | 如果上线后发现方向不对，改换方案的代价多大？是双向门还是单向门？ | 轻易改动持久化结构、公共 URL/导航路径或外部接口协议（单向门） |

### 不可逆决策（单向门）警报
凡涉及以下任一项，必须在方案对比中显式标红提醒，并在规格里补充兼容/回滚策略：
- 修改已有持久化数据格式或配置作用域覆盖规则；
- 改变用户已形成肌肉记忆的核心快捷键或顶层导航位置；
- 暴露给第三方或跨模块依赖的公共标识、事件名、错误码；
- 不可撤销的数据删除或批量覆盖行为。

## 4. YAGNI 严苛裁剪检查表

**YAGNI（You Aren't Gonna Need It）** 是防止规格从「精准解决痛点」膨胀成「大而全半成品」的第一道防线。在锁定推荐方案前，对每一个打算纳入 `In Scope` 的能力逐项过下面五问：

| 检查项 | 判断问题 | 处理动作 |
| --- | --- | --- |
| **1. 闭环必要性** | 删掉这项能力后，本期核心用户闭环还能跑通吗？ | 能跑通且无明显阻塞 → 移入 `Out of Scope` |
| **2. 真实证据** | 这是用户明确提出的痛点/数据证明的问题，还是作者臆想的「以后可能会用到」？ | 属于「以后可能用到」 → 坚决砍掉，写入后续演进备忘 |
| **3. 抽象提前量** | 是否为了「兼容未来未知类型」而现在就引入复杂配置面板、插件机制或通用引擎？ | 仅服务当前明确场景做最简表达；等第二个真实场景出现再抽象 |
| **4. 顺手优化边界** | 这是本次痛点必须改的，还是顺路看到的相邻老问题？ | 顺路老问题单记议题，不混入本期范围与验收 |
| **5. 收益/复杂度比** | 为了覆盖极低频 1% 场景，是否给 99% 主路径增加了额外控件、弹窗或维护分支？ | 优先保持主路径干净，低频场景交由更简洁的默认行为或文档说明 |

### YAGNI 裁剪正反例

| 原始想法 | 臃肿做法（反例） | YAGNI 裁剪做法（正例） |
| --- | --- | --- |
| 「扩展多了不好找」 | 一次加上：全文搜索 + 拼音首字母 + 标签分组 + 拖拽排序 + 收藏置顶 + 自定义文件夹 | 本期只做：名称/描述子串搜索 + 启用态置顶排序 + 独立滚动区；把「标签分组 / 拖拽排序 / 收藏」显式写入 `Out of Scope` |
| 「用户可能想撤销删除」 | 立刻设计完整的回收站页面、30 天自动清理定时任务和批量还原接口 | 本期仅做 5 秒可撤销 Toast（内存暂存或软状态），满足误删抢救闭环；完整回收站归入远期规划 |
| 「不同项目配置可能不同」 | 顺手做成 5 级继承树 + 配置模板导入导出 + 历史版本对比 | 只按当前已有的「全局 / 项目」两层做继承与一键恢复默认；模板与历史版本列入 `Out of Scope` |

## 5. 推荐理由论证写法

推荐方案不能只写「方案 A 更好」或「综合来看选 A」，必须给出一句**可被反驳的因果论证**，结构为：

> **场景特征（基于已确认目标） + 关键权衡取舍（放弃了什么换取什么） + 风险兜底机制（如何化解本方案的短板）**

### 弱论证 vs 强论证对比

| 弱论证（禁止） | 强论证（推荐） |
| --- | --- |
| 「推荐方案 A，因为体验更丝滑、开发更快、综合性价比最高。」 | 「推荐方案 A：用户在此入口的核心诉求是『2 秒内找到并开关 1 个扩展』，不打断主界面远比大表单空间重要；虽然浮层高度有限，但通过 15 项起显搜索 + 独立滚动区 + 粘性『管理』入口即可兜底 100 项场景，且保留未来跳转独立管理页的退路。」 |
| 「推荐方案 B，因为它功能最全面、扩展性最好。」 | 「推荐方案 B：当前目标包含跨字段联动校验与实时预览，内联展开在 900px 窄窗下必然挤压主栏；虽然独立抽屉增加了焦点与关闭态维护成本，但可一次性承载全部表单并支持 Esc 复位，避免把主界面改造成多层嵌套布局。」 |

## 6. 方案定案核对清单

在把方案消息发给用户、或将定案写入规格书前，逐条核对：

- [ ] 至少评估了 2–3 个真实可行的方案（或明确论证了为何仅存唯一合理路径），无凑数稻草人。
- [ ] 每个方案都具体到能想象出交互形态，且扎根于现有项目的真实页面与约束。
- [ ] 四维权衡矩阵已覆盖交互、维护成本、演进风险与可逆性，单向门决策已显式标出。
- [ ] 已执行 YAGNI 裁剪检查，所有「以后可能用到」的顺手功能已剥离到 `Out of Scope`。
- [ ] 推荐理由包含「场景特征 + 取舍 + 短板兜底」，不空喊主观口号。
- [ ] 若用户保留了方案选择权，已在方案轮停下等待确认，再进入完整规格编写。
