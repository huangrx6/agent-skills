# 实施计划桥接与执行交接

当书面产品规格已获用户**明确批准**，且准备进入研发实施阶段时，本规范负责把产品规格无损桥接为「一位从未见过本仓库、也未参与讨论的工程师拿到就能零歧义照做的实施计划」，并按清晰纪律完成执行方式交接。

---

## 1. 桥接前置检查（最后一道范围拦截）

动笔写实施计划前先做两项核查：
1. **规格批准核验**：确认用户已明确批准对应的书面规格（短规格或完整规格），而非只口头称赞过想法。
2. **多子系统再拦截**：如果规格里仍塞着多个彼此独立、可各自上线验收的子系统，**立刻叫停**，建议拆分成多份独立实施计划（每个子系统一份，各自交付可运行的软件），不在一份超长计划里混编多个子系统。

---

## 2. 文件归属地图（先锁边界，再拆任务）

在定义任何任务之前，先画出一张**文件归属地图**，把「新建哪些文件、修改哪些文件、每个文件的唯一职责是什么」钉死。这是系统分解决策真正落锁的地方：

- **单一清晰职责**：每个文件只承担一类明确职责，接口边界清晰，便于一次装进上下文里可靠阅读与修改。
- **按职责切分，不机械按技术层拆散**：总是一起变更的逻辑尽量内聚在相近目录；在已有仓库中尊重既定目录约定与命名规范（仅当待改文件已严重膨胀失控时，才在计划中纳入顺带拆分）。

### 文件归属地图模板

```markdown
## 文件归属地图

| 动作 | 路径 | 单一职责 |
| --- | --- | --- |
| 新建 | `src/features/extensions/filter-state.ts` | 纯函数：扩展搜索匹配、启用态置顶排序与关闭复位状态模型 |
| 修改 | `src/features/extensions/ExtensionPicker.tsx` | 接入粘性搜索栏、独立滚动容器、空态/无结果提示与键盘流 |
| 新建 | `spec/extensions/filter-state.spec.ts` | 覆盖搜索、高数量排序、特殊字符转义与切页状态复位的单元验证 |
| 修改 | `spec/extensions/picker-flow.spec.ts` | 覆盖 `AC-1` 至 `AC-5` 及 `Review Focus` 隐含失效的交互验证 |
```

## 3. 可独立验证的任务切分原则（Task Right-Sizing）

> **一个任务（Task）是「自带完整验证闭环、且值得由独立审稿人单独把关」的最小交付单元。**

切分任务时遵守以下三条硬边界：
1. **独立可验证**：每个任务结束时必须产出一个可单独运行验证并给出通过证据的交付物，绝不拆成「Task 1 写一半 UI，Task 2 再补逻辑」（Task 1 根本无法独立验收）。
2. **把杂项折进真正需要它的任务**：环境配置、小型脚手架、类型声明、配套文档不要单拆成空洞的「Task 0：准备工作」，直接折进首个需要它们的交付任务中。
3. **审稿人分割测试**：问自己「独立审稿人有没有可能合理地拒绝 Task A，同时批准相邻的 Task B？」——只有回答「会」，才在 A 与 B 之间切一刀。

## 4. 任务间 `Consumes / Produces` 接口契约块

当多个工程师或子智能体分别执行不同任务时，每个任务执行者可能**只看自己当前任务的说明书**。`Interfaces` 区块就是相邻任务之间唯一可信的对接契约，必须写死精确的函数名、参数类型、返回类型、事件名与状态/错误枚举：

```markdown
**Interfaces:**
- **Consumes**:
  - `src/features/extensions/types.ts` 中的 `ExtensionItem { id: string; name: string; description: string; enabled: boolean }`
- **Produces**:
  - `filterAndSortExtensions(items: readonly ExtensionItem[], query: string): ExtensionItem[]`（来自 `src/features/extensions/filter-state.ts`）
  - `SEARCH_SHOW_THRESHOLD = 15`（精确常量，来自规格 `AC-2`）
```

> **执行前跨任务接口预扫（Pre-flight Scan）**：在启动 Task 1 之前，逐一核对所有任务中 `Task M 的 Consumes` 与 `Task K 的 Produces` 是否逐字匹配（例如不能在 Task 2 定义 `clearFilters()`，而在 Task 5 写成 `resetAllFilters()`）。发现冲突立即以**已批准的产品规格**为最高权威裁决并统一，再开始执行。

## 5. 实施计划文档标准模板

### 5.1 计划头部模板

```markdown
# <功能名称> 实施计划

**目标（Goal）**：<1 句话概括本次构建交付什么>
**架构思路（Architecture）**：<2–3 句概括模块组织与核心数据流>
**技术栈（Tech Stack）**：<关键语言、框架与验证运行器>
**关联规格（Spec）**：<指向已批准产品规格的路径——计划由规格推导而来，执行者须同时读取两者>

## Global Constraints（全局约束）
- <逐字精确拷贝规格中的全局硬约束，每条一行；所有任务隐式继承>

## Review Focus（五大隐含失效模式）
- <逐条列出 5 类隐含失效模式（触发条件 + 合理用户预期），并标明由哪个 Task 的哪条验证用例钉住>
```

### 5.2 单任务结构模板（无歧义步骤粒度）

每一步只做**一个动作**，并带有一个可核验的 `Expected:` 结果，遵循 `RED（写失败验证）→ 验证失败 → GREEN（最小实现）→ 验证通过 → 提交` 节奏：

```markdown
### Task N：<模块/能力名称>

**Files:**
- Create: `src/features/extensions/filter-state.ts`
- Modify: `src/features/extensions/ExtensionPicker.tsx:85-140`
- Verify: `spec/extensions/filter-state.spec.ts`

**Interfaces:**
- Consumes: <精确签名与来源>
- Produces: <供后续任务依赖的精确函数名、参数、返回类型与常量>

- [ ] **Step 1：编写覆盖核心行为与边界的失败验证用例**

```ts
// spec/extensions/filter-state.spec.ts
it("ignores leading/trailing whitespace and sorts enabled items first", () => {
  const result = filterAndSortExtensions(sampleItems, "  alpha  ");
  expect(result.map((x) => x.id)).toEqual(["enabled-alpha", "disabled-alpha"]);
});
```

- [ ] **Step 2：运行验证确认按预期失败（RED）**
  - Run: `pnpm vitest run spec/extensions/filter-state.spec.ts`
  - Expected: FAIL，报错 `filterAndSortExtensions is not defined`

- [ ] **Step 3：在 `src/features/extensions/filter-state.ts` 中实现 `filterAndSortExtensions(items, query)`**
  - 做法提示：仅当签名与验证断言未能唯一决定做法时写 1 行思路（如采用哪种算法或库调用）；只有遇到规格定死的精确文案或复杂算法时才贴代码片段，不抄录显而易见的函数体。

- [ ] **Step 4：运行验证确认通过（GREEN）**
  - Run: `pnpm vitest run spec/extensions/filter-state.spec.ts`
  - Expected: PASS，所有断言通过且无控制台告警

- [ ] **Step 5：提交本任务改动**
  - Commit: `feat(extensions): add search filtering and enabled-first sorting`
```

## 6. 无歧义步骤粒度与计划篇幅比例检查

### 什么是「恰到好处」的步骤粒度
一个步骤合格的唯一标准是：**执行者照着读，只能写出唯一合理的一件事——无歧义，但绝不啰嗦。**

| 步骤类型 | 必须包含什么（执行者无法自猜的决策） | 禁止包含什么（过度或不足） |
| --- | --- | --- |
| **验证用例步骤** | 用例路径、用例名称、含规格精确数值/文案的断言代码 | 禁止只写「补齐相关边界验证」（什么都没决定） |
| **代码实现步骤** | 目标文件路径、精确函数/类型签名、规格定死的常量/文案、必要的 1 行做法说明 | 禁止把签名和断言已经唯一决定的常规函数体完整抄写一遍 |
| **命令核验步骤** | 精确执行命令 + 具体的 `Expected:` 通过/失败输出特征 | 禁止写「跑一下看看没问题」 |
| **跨任务引用步骤** | 直接引用上游任务的 `Interfaces` 契约名 | 禁止把上游任务的代码重复粘贴进下游任务 |

### 实施计划自审 5 项（交付前必跑）

写完计划后，对照产品规格用新鲜眼光逐项自查并当场修掉问题：

1. **规格覆盖率检查**：顺着产品规格的每一条 `In Scope` 与每一条 `AC-N` 往下点名，确认每条都能指到具体某个 Task；漏掉就补任务或补步骤。
2. **步骤空洞 / 抄录双扫**：抓出两类极端错误——一是「TBD / 适当处理异常 / 补充校验」这类决定为零的空话；二是大段复制粘贴常规业务实现代码的「代码抄录本」。两类都必须改掉。
3. **跨任务类型与签名一致性检查**：对照所有 `Consumes` 与 `Produces`，确认函数名、参数顺序、字段名、错误码和常量名全篇完全一致。
4. **Review Focus 挂接核查**：检查头部列出的 5 条隐含失效模式是否都已落入对应负责任务的验证步骤，而不是只写在计划开头。
5. **计划篇幅比例检查**：把计划总长度与产品规格对比——如果实施计划比它要实现的规格长出好几倍、且页面大部分被大段业务代码体占满，说明计划退化成了「提前写完的代码抄录本」；立刻将常规函数体收缩为「精确签名 + 精确常量 + 验证断言」，再确认每步依然零歧义。

## 7. 交付与执行方式交接

完成计划自审并保存后，将计划路径呈现给用户审阅。**等待用户确认计划符合预期后再开始实现。**

### 7.1 两种执行模式对比与推荐模板

如果用户此前尚未指定执行方式，在交接消息中直接给出清晰对比与基于本计划特征的**具体推荐**：

| 执行模式 | 工作方式 | 优势与代价 | 适用计划特征 |
| --- | --- | --- | --- |
| **子智能体逐任务驱动（Subagent-driven）** | 每个任务派发全新子智能体实现 + 独立审稿把关，全部完成后再做整分支终审 | 每任务干净上下文、逐关拦截缺陷，最稳妥；上下文与耗时成本较高 | 任务数较多（避免后期上下文压缩失忆）、单次线上失误代价高、或用户希望每步独立把关 |
| **当前会话顺序执行（Native / Inline）** | 当前会话按任务顺序逐一落地（配合进度账本与每步 RED→GREEN 验证），全部完成后由高能力独立审稿做整分支终审 | 成本最低、速度最快；任务间无独立审稿，依赖高确定性计划与终审兜底 | 任务边界清晰、计划规格详尽、总长度可控，或当前环境无子智能体能力 |

### 交接提问模板

```markdown
实施计划已完成自审并保存至 <计划路径>。请审阅计划内容是否完整覆盖你的需求。

确认后，你倾向采用哪种执行方式？
- **子智能体逐任务驱动**：每个任务独立上下文实现并逐任务审查，收尾再做整分支终审（最严谨，耗时与成本较高）。
- **当前会话顺序执行**：我在本会话按任务连续落地并维护进度账本，全部完成后做一次高规格整分支终审（更快更省）。

针对这份计划，我推荐 **<上述二选一>**，原因是：<一句基于本计划的具体理由：任务数量、任务间接口耦合度、以及出错代价>。

计划是否符合预期？我们按哪种方式开始执行？
```

> 若用户事先已指定执行方式，则只询问计划是否符合预期，确认后直接按其指定方式推进。

## 8. 顺序执行时的核心运行纪律（供执行阶段承接）

当采用当前会话顺序执行计划时，为了在不花逐任务审稿成本的前提下守住交付质量，必须严格执行以下六条纪律：

1. **隔离工作区与持久化账本（Ledger）**：
   - 在独立分支或隔离工作区中实施，未经用户明确同意不直接在主分支动手。
   - 用独立账本文件记录已完成任务、提交哈希与验证命令结果（防长会话上下文压缩后失忆重做已有任务）；压缩后以账本与 `git log` 为准，不凭印象。
2. **连续执行，不在任务间反复打断用户**：
   - 既然用户选择了顺序执行以节省精力，就连续推进所有任务，不要每做完一个 Task 就停下来问「要不要继续？」。
3. **遇冲突主动裁决并记账（Rulings, not stalls）**：
   - 遇到计划局部疏漏或接口细微偏差时，以**已批准的产品规格**为最高权威，按最小改动原则果断裁决，并在账本记下：`Ruling: <裁决内容> — <依据> — <猜错代价>`，然后继续推进。未经记账擅自偏离计划等于秘密拍板，严禁发生。
4. **仅四类硬停条件**：
   - 只有在遇到以下四种情况时才停下来请示用户：**不可逆或破坏性操作**、**安全敏感动作**、**工作区之外的外部副作用（如合并/推送共享分支/正式发布）**、或**计划严重错误以致每条前进路径都只能靠盲猜**。
5. **任务完成硬契约（Completion Contract）**：
   - 每个任务标记完成前，必须在本会话中拥有真实运行证据：所有验证用例均已跑过且亲眼读过输出、每个 `Expected:` 已逐条核对、所有偏差已记入 `Ruling:`、整任务最终验证命令实际通过。
6. **整分支终审与按效果重定级**：
   - 全部任务完成后必须跑一次整分支终审（优先派发高能力独立审稿，无子智能体工具时切角色自审并在收尾如实披露）。
   - 终审问题按**「真实用户承受的效果」**重新定级（不因规格沉默而把严重故障降级为 Minor）：**Critical / Important** 集中做**唯一一次** RED→GREEN 修复并通过全量验证；**Minor** 记入延期清单不擅自扩修。
   - 最终交付汇报必须完整列出：**所有 `Ruling:` 裁决清单（含猜错代价）** 与 **所有延期 Minor 清单**，确保替用户做过的每个决定都透明可见。

## 9. 交接前核对清单

- [ ] 书面产品规格已获用户明确批准，且不存在未拆分的多个独立子系统。
- [ ] 文件归属地图职责清晰，每个任务对应一个可独立验证的交付物。
- [ ] 跨任务依赖全部写死在 `Consumes / Produces` 契约中，且无命名或类型不一致。
- [ ] `Global Constraints` 与 5 条 `Review Focus` 已逐一挂接到负责任务的验证步骤。
- [ ] 步骤粒度无歧义且计划篇幅未沦为整份业务代码的抄录本。
- [ ] 已向用户提交计划链接与带具体理由的执行方式建议，等待确认后再动手写代码。
