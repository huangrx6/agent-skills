# 规格骨架与可复测 AC

把已对齐的目标、范围与方案落成一份「资深研发与黑盒验收人员不回头问原作者也能直接开工、直接验出通过或失败」的书面规格。好规格不是越长越好，而是每个决定都精确、每条验收标准都可复测、每个状态生命周期都无歧义。

---

## 1. 分段回放与确认节奏

在完整项目规格定稿前，不要憋一大段后一次性甩出 2000 字。采用**边收敛边回放（Play It Back）**的节奏：

1. **按主题分段回放**：每搞清一块（例如「定位与范围」「主路径与界面结构」「状态复位与边界」），立刻用 **200–300 字** 回述给用户确认，然后再问下一块。
2. **严格区分来源**：只有用户明确说过的才写为「已确定」；凡由你补全的默认值、文案或边界策略，一律标为「提案 + 理由」。
3. **涉及界面或流程先画文本草图**：凡用户要「看」的东西（页面、浮层、布局、状态流），把 5–10 行简洁文本草图放在描述旁，让对方一眼指出哪里不对。
4. **每段以纠偏问题收尾**：「这一段有没有哪条不对，或者漏掉了什么？」

## 2. 按体量选择规格模板

### 2.1 小改动：短规格模板（1 屏可读完）

适用于单组件/单接口、无跨模块副作用的小范围变更，无需独立构建者审稿，直接呈交用户批准：

```markdown
# <改动名称> 短规格

- **目标与原因**：<1 句痛点 + 1 句改动后达成的结果>
- **选定方案**：<2–3 句描述交互与行为>（未选 <方案 B>，因为 <1 句原因>）
- **范围边界**：
  - 本期做：<2–3 条核心项>
  - 本期不做：<1–2 条显式排除项>
- **核心边界与状态**：<空态 / 极值 / 关闭重开复位 / 错误恢复各 1 行>
- **验收条件**：
  - **AC-1**：给定 <前提>，当 <操作>，则 <可观测结果>。
  - **AC-2**：给定 <前提>，当 <操作>，则 <可观测结果>。
- **待确认假设（如无异议按此执行）**：<列出所有作者补全的默认项>
```

### 2.2 完整项目：标准产品规格模板

```markdown
## 2. 范围边界
- **本期做（In Scope）**：
  - ...
- **本期不做（Out of Scope）**：
  - ...（每条注明原因或归入哪一期）

## 5. 用户主路径与状态流转
1. **触发入口**：<从哪里进入、视觉/快捷键入口>
2. **核心主路径**：<步骤、即时反馈、文本草图或状态流转表>
3. **退出、切页与重开**：<关闭/切页/刷新/重启后的精确行为>
4. **状态生命周期契约**：<见下方第 5 节模板>

## 6. 边界与异常场景矩阵
（按需引用并落地边界矩阵，见同目录边界与异常场景规范）

## 7. 验收条件（Acceptance Criteria）
- **AC-1（核心主路径）**：给定 <前置条件>，当 <用户操作>，则 <可见反馈与状态结果>，且刷新/重开后 <持久化结果>。
- **AC-2（状态复位）**：...
- **AC-3（边界与极值）**：...
- **AC-4（异常与恢复）**：...

## 8. 已确认事实与待确认假设
- **已确认事实**：<用户明示或代码查实的客观事实>
- **待确认假设（作者提案，请确认）**：<每条附理由与默认执行策略>
```

## 3. Given / When / Then 编号 AC 写法

每条验收条件（Acceptance Criteria）都必须经得起**「黑盒验收测试」**：一个没读过源码的人，照着 AC 执行一遍，就能无争议地判定 PASS 或 FAIL。

### 编写铁律
1. **强制编号与命名**：采用 `AC-1（场景短名）` 顺序编号，方便设计、研发、评审和缺陷单精准引用。
2. **完整三段式结构**：
   - **给定（Given）**：明确初始状态、数据规模、权限角色或视口条件（如「已安装 25 个扩展且当前窗口宽 900px、高 620px」）。
   - **当（When）**：唯一、具体的用户动作或系统事件（如「输入不存在关键词 `zzz` 并按下回车」）。
   - **则（Then）**：所有外部可观测结果——界面文案/状态、列表内容、焦点位置、持久化变化与控制台无未捕获异常。
3. **一条 AC 只锁一个行为断言**：不要把「搜索 + 勾选 + 断网报错 + 关闭重开」揉进同一条超长 AC，否则部分失败时无法定位。
4. **数值与文案尽量钉死**：阈值（如 `≥ 15 项`、`5 秒撤销窗口`、`900×620`）、关键按钮文案、明确状态名直接写进 AC；不确定的值先标入「待确认假设」。

## 5. 状态生命周期（临时 vs 持久）契约

绝大多数桌面与 Web 工具的「怪异行为」，根源都是没说清一个状态应该活多久。每份含交互状态的规格必须明确填入下表：

| 生命周期层级 | 存活范围 | 触发清空 / 复位的事件 | 典型状态示例 |
| --- | --- | --- | --- |
| **临时态（Ephemeral）** | 单次浮层/弹窗/组件挂载期间 | 关闭弹窗、切换页面、按 `Esc` 退出 | 搜索关键词、筛选下拉展开态、列表滚动位置、悬停/高亮项、一次性内联校验报错 |
| **会话态（Session）** | 当前应用运行或当前工作区会话期间 | 重启应用、切换工作区/账号、显式清空 | 未提交的长表单草稿（若约定跨页暂存）、当前选中 Tab、本次会话已折叠的提示横幅 |
| **持久化态（Persistent）** | 写入本地存储或后端数据库，跨重启保留 | 用户显式修改、点击「恢复默认」或执行删除 | 开关启用状态、用户显式保存的配置项、自定义排序规则、已固定/置顶项 |

### 契约模板（直接写入规格第 5 节）

```markdown
### 状态生命周期契约

| 状态项 | 归属层级 | 关闭浮层/切页后 | 重启应用后 | 失败时回滚策略 |
| --- | --- | --- | --- | --- |
| 顶部搜索关键词 | 临时态 | 清空为空串 | 清空 | 不涉及持久化 |
| 列表滚动位置 | 临时态 | 回到顶部（0px） | 回到顶部 | 不涉及持久化 |
| 扩展启停开关 | 持久化态 | 保持已保存值 | 保持已保存值 | 接口失败时回滚至原开关状态并提示错误 |
| 自定义表单草稿 | 会话态 | 切换子页前弹窗提醒保存/放弃 | 丢弃未保存草稿 | 提交失败时**保留全部已填草稿**，绝不清空 |
```

## 6. 多层配置作用域在 UI 中的继承 / 覆盖表达规范

当产品存在多层设置（例如：**全局 / 系统默认 → 用户 → 工作区 → 项目 → 当前会话**）时，必须遵守以下三条铁律并在规格中写清界面表达：

### 作用域硬规则
1. **单向继承，优先级明确**：较窄作用域默认继承较宽作用域的生效值；仅当用户在较窄作用域显式修改时，才产生该层的覆盖值（Override）。
2. **严禁反向推导**：绝不能从较窄作用域（如某一个会话或单个项目）反推或悄悄改写较宽作用域（如用户或全局）的值。
3. **显式区分「未设置（继承）」与「显式设为与上级相同的值」**：或者明确约定将值改回上级相同时是否自动清除覆盖标记，避免日后上级改动时下级行为令人困惑。

### UI 四态视觉与交互规范

| 配置态 | UI 必须传达的信息 | 推荐控件与文案表达 |
| --- | --- | --- |
| **继承态（Inherited）** | 当前值来自哪一层、实际生效值是什么 | 控件呈现当前生效值，标签旁显示次级徽章「继承自：全局（或工作区）」，不显示重置按钮 |
| **覆盖态（Overridden）** | 本层已覆写上级、上级原值是什么、如何恢复 | 控件左侧/标签旁显示明确覆盖标记「当前项目已覆盖」，悬停或副文案可见原继承值，并提供一键「恢复继承」操作 |
| **锁定态（Locked / Policy）** | 被更高权威层强制锁定，本层不可改 | 控件禁用，附锁定图标与明确说明「已由管理员策略锁定为 <值>」 |
| **生效范围提示** | 本次修改影响哪些对象、何时生效 | 顶栏或保存区明确标注「当前编辑：项目 `<名称>`（仅影响本项目）」，需要重启或下一次请求生效时明示生效时机 |

### 作用域专项 AC 模板
- **AC-S1（继承显示）**：给定全局配置将 `超时期限` 设为 `30s` 且项目 A 未单独覆盖，当用户进入项目 A 设置页时，控件显示 `30s` 并标注「继承自全局」，无「恢复继承」按钮。
- **AC-S2（覆盖与隔离）**：给定上述前提，当用户在项目 A 将 `超时期限` 修改为 `60s` 并保存，则项目 A 标注「当前项目已覆盖」且显示「恢复继承」按钮；切换至全局设置与项目 B 时，两者仍为 `30s` 未受影响。
- **AC-S3（一键恢复继承）**：给定项目 A 已覆盖为 `60s`，当用户点击「恢复继承」，则项目 A 立即回落为全局值 `30s`，覆盖标记消失；此后全局改为 `45s` 时，项目 A 自动跟随变为 `45s`。

## 7. 规格与 AC 质量核对清单

- [ ] 规格体量与需求复杂度匹配（小改动 1 屏短规格，复杂项目走完整骨架）。
- [ ] 已写明 `Goals`、`Non-Goals`、`Anti-Goals` 与 `In / Out of Scope`。
- [ ] 所有 AC 均有顺序编号且符合 `Given → When → Then` 三段式，零主观模糊词。
- [ ] 所有涉及用户交互的状态均已归类到「临时态 / 会话态 / 持久化态」，无归属不明的状态。
- [ ] 若存在多层配置，已明确优先级顺序、禁止反向推导规则以及继承/覆盖/锁定/重置的 UI 表达。
- [ ] 所有非用户明示的默认细节已单列在「待确认假设」中。
