# 产品需求澄清与规格收敛

把模糊想法、用户反馈或零散诉求收敛成清晰、可复测、零歧义的产品规格，并在规格获批后无损桥接为可执行的研发实施计划。核心不是替用户猜答案，而是先弄清**真正要什么、为什么现在要、不做什么、如何判定通过**，让后续实现中的上百个细微决定都能沿着同一意图自然成立。

## 硬闸门：规格未确认前绝不进入实现代码

**在用户明确批准书面规格（小改动为短规格，完整项目为完整规格）之前，严禁进入任何实现动作。**

- **被拦截的动作**：编写业务代码、生成脚手架、安装依赖、建项目目录、修改既有逻辑，或直接调用编码实现流程。只读探索仓库、查文档、画文本草图与整理规格不受限。
- **「想法不错」不等于批准规格**：口头认可方向只代表通过方案选择，未写出、未获确认的书面规格永远不算过关。
- **仅有两个明确豁免**：
  1. **用户主动跳过澄清**：用户未主动要求讨论且接受你给出的「直接推进」出口，或明确指令「不用问了，按推荐直接做」——此时退出闸门，开工前用一行写明关键技术/方案选择再进入常规实现。
  2. **经同意的一次性探路（Spike）**：当极简原型是验证未知的最低成本手段时，经用户同意可做 Spike；必须明确标为一次性丢弃物，跳过完整计划与防护。**若用户决定保留 Spike 产物并继续演进，视为新需求，必须把学到的结论带回规格闸门重新收敛。**

## 需求收敛七关阶段闸门

需求收敛是一条严格有序的七关链路，上一关没有可核验出口，绝不跳入下一关：

| 阶段 | 核心动作 | 过关出口（可核验） | 未过关禁止越界 |
| --- | --- | --- | --- |
| **1. 探索上下文** | 只读查代码、页面心智、历史规范、数据归属与痛点证据 | 讲清「现状怎么运转、改动触达哪里」，区分已证实事实 | 禁空手发问、禁反问仓库已有事实、禁重开已定决策 |
| **2. 范围拆期** | 识别是否打包多个独立子系统，判定小改动 / 完整项目体量 | 锁定本期最小闭环（MVP）与后续分期顺序；体量中途膨胀即升级 | 禁把多个独立子系统硬塞进单份规格或单份计划 |
| **3. 关键提问** | 动机未明前用开放题；动机已明后每次聚焦 1–3 个高影响分歧给带推荐选择题 | 关键范围、主路径与核心取舍收敛；所有默认值入「待确认假设」 | 禁抛长问卷、禁在未知「为什么」前预设功能菜单引导 |
| **4. 2–3 方案权衡** | 独立一轮呈现 2–3 个真实可行方案，按四维权衡并做 YAGNI 裁剪 | 用户选定方案并留存弃选理由（或确认仅存唯一合理路径） | 禁跳过方案对比直接写长规格，禁塞入稻草人凑数方案 |
| **5. 分段规格确认** | 边收敛边按 200–300 字回放，配文本草图，落成完整骨架、边界矩阵与编号 AC | 书面短规格或完整规格经用户明确批准 | 禁把作者填补写成用户决定，禁保留主观模糊 AC |
| **6. 规格自审** | 完整项目交付前跑构建者视角审稿（三堆分拣、最多回抛一轮）+ 6 维体检 | 清零占位词、矛盾、孤立引用与不可测 AC；补齐 `Global Constraints` 与五大 `Review Focus` | 禁原样转抛审稿列表给用户，禁以「规格没写」纵容隐含崩溃 |
| **7. 计划桥接交接** | 规格获批后画文件归属地图、切独立可验证任务、锁 `Consumes / Produces` 契约 | 实施计划自审 5 项通过，用户审阅计划并确认执行方式 | 禁计划沦为代码抄录本，禁未经确认直接开工或主分支直写 |

## 场景判断表

动手前先对照下表决定本轮动作，既不机械走重流程，也绝不偷步跳关：

| 当前需求形态 | 判定路径 | 本轮唯一正确动作 |
| --- | --- | --- |
| 目标、范围、行为全明且无歧义的微调（如改固定文案、调单色值） | 无需规格收敛 | 核实上下文后直接给结论或交由实现流程，不强行拉长环节 |
| 用户已给详细背景/文档/旧规格，但动机未明或关键分歧悬空 | 标准收敛（有材料起步） | 先只读查代码；约 200 字回述理解 + 现状发现 + 冲突或更省路径，留一句纠偏入口，再只问 1 个最关键问题；未主动求讨论时文末附一行「或直接按推荐开工」出口 |
| 一句话想法或零散用户吐槽，目标尚空泛 | 标准收敛（从零起步） | 先轻量侦察现状，只抛 1 个直击最大分歧的开放问题并说明答案如何改变产物，不附选项菜单、不抛长问卷 |
| 一句话打包了 2 个以上彼此独立的子系统 | 先拆期再收敛 | 指出其中包含多个可独立上线验收的子课题，提出分期与 MVP 顺序建议，先只围绕第一期展开澄清 |
| 影响局限在单组件/单接口，现状清晰且只有唯一合理路径 | 快车道短规格 | 产出 1 屏短规格（目标、选定做法、为何不选更重做法、核心边界、2–4 条 AC、待确认假设），请用户一眼批准 |
| 复杂交互、跨模块状态、存量迁移或多人协作 | 方案权衡 → 完整规格 → 自审 | 先独立一轮做 2–3 方案权衡定案；再分段回放落成完整规格；交用户前跑构建者视角审查与 6 维自审 |
| 书面规格已获明确批准，准备投入研发实施 | 计划桥接交接 | 补齐 `Global Constraints`、五大 `Review Focus`、文件归属地图、独立可验证任务与 `Consumes / Produces` 契约，呈交计划并请用户选定执行方式 |

## 体量分级与产物契约

确认目标后用大白话定出体量档位（用户可随时覆盖）；若任务做到一半发现牵动存量迁移、并发竞态或多模块联动，**立刻叫停并升级档位**：

| 体量档位 | 必备规格产物 | 是否跑构建者审查 | 计划桥接方式 |
| --- | --- | --- | --- |
| **小改动** | 1 屏短规格（目标、方案与弃选理由、范围、关键边界、2–4 条 AC、待确认假设） | 否（直接交用户确认） | 可直接落成单任务或极简步骤清单 |
| **完整项目** | 完整产品规格（意图/非目标/反目标、范围、方案结论、主路径、状态生命周期、边界矩阵、编号 AC、事实与假设） | **是**（独立审稿 + 三堆分拣 + 6 维自审） | 产出完整实施计划（文件地图 + 独立任务 + `Consumes / Produces` + 终审交接） |
| **多子系统** | 先拆期清单（按价值闭环与独立可验收性排序） | 逐期按上述规则执行 | 每个子系统对应独立计划，绝不混编 |

## 提问、规格与交接核心铁律

### 1. 探索与方案阶段
- **只问能改变产物的分歧**：过程性小事（文件放哪、章节怎么排）自行决定并简述即可。动机未明用开放题；动机已明后每次聚焦 1–3 个高影响分歧，给带推荐项的选择题并说明取舍。
- **按表达判定实现权归属**：用户只谈业务结果时，技术实现权默认交给你，按已有技术栈拍板并在规格中单行标明「作者决定」；用户主动谈交互形态与取舍时，必用独立一轮给 2–3 方案（交互 / 维护成本 / 演进风险 / 可逆性）与 YAGNI 裁剪由其定夺。
- **事实与假设硬分离**：永远分列「已确认事实」与「待确认假设（默认按此推进）」。用户没听过的默认值就是他们无法否决的隐形拍板，必须公开亮明。

### 2. 规格与自审阶段
- **AC 与状态零歧义**：每条 `AC-N` 遵循 `Given（前置）→ When（操作）→ Then（外部可观测结果）`，彻底清除「丝滑、友好、清晰、合理、好用」等主观词。所有交互状态明确归入「临时态 / 会话态 / 持久化态」；多层配置作用域（如全局 / 用户 / 工作区 / 项目 / 会话）明确覆盖优先级与 UI 继承/覆盖/重置表达，**严禁从较窄作用域反推改写较宽作用域**。
- **边界必查九类场景**：0 项空态、搜索无结果、单条、20+/100+ 高数量、超长中英混排/URL/Emoji、切页/关闭/重开状态复位、快速连点与并发竞态、网络超时与 4xx/5xx 保输入恢复、破坏性操作护栏与存量数据兼容。
- **规格是愿景文档，不是穷举清单**：规格对异常输入保持沉默，绝不等于允许程序崩溃或丢数据。必须提炼精确的 `Global Constraints` 与 5 类最可能咬伤用户的 `Review Focus`，并将每条隐含失效反向挂接到对应负责任务的验证用例。
- **独立审稿三堆分拣**：构建者视角审稿发现的问题，按「已有答案直接补写 / 次要细节自行定案标注 / 仅用户能决汇成唯一一轮」分拣，绝不原样甩给用户，也不反复追问多轮。

### 3. 计划桥接与执行交接阶段
- **计划只记录「决策」，不抄录整段实现**：步骤做到「执行者只能写出唯一合理的一件事」即可（精确路径、签名、规格常量与验证断言）；若计划篇幅数倍于规格且充斥常规函数体，立即瘦身。
- **交接与顺序执行纪律**：保存并完成 5 项计划自审后，呈现计划路径并结合任务耦合度与风险推荐执行方式（子智能体逐任务驱动 vs 当前会话顺序执行），等用户确认后再开工。顺序执行时须在隔离工作区维护进度账本、连续执行不反复打断、遇小偏差按规格裁决并记 `Ruling:`、仅遇四类硬停（不可逆破坏 / 安全敏感 / 工作区外副作用 / 计划彻底断裂）才停下请示、收尾做整分支终审并按真实用户效果重定级。

## 反合理化清单

出现以下任何念头时立即刹车，它们都是绕过闸门或制造返工的典型借口：

| 偷懒念头 / 借口 | 真实后果与纠正铁律 |
| --- | --- |
| 「需求太简单，不用写规格直接改吧」 | 小改动最易在空态、关闭复位、窄窗和旧数据兼容上翻车。越简单越只需 1 屏短规格，2 分钟对齐省下 2 小时返工。 |
| 「先列个功能菜单让用户选，省时间」 | 预设菜单会强烈引导并掩盖真实动机。弄清「为什么」之前必须提开放题，让用户用自己的话描述场景。 |
| 「按常识填默认值就行，没必要写出来」 | 未说出口的默认选择等于替用户秘密拍板。全部写入「待确认假设」，让用户一眼能改或确认。 |
| 「先问用户比自己翻代码快」 | 反问仓库已有的事实会立刻消耗信任。提问前必须先只读查清现有代码、界面与历史规范。 |
| 「用户回了『听起来不错』，可以开工了」 | 口头认可方向不等于批准书面规格。未落字、未获确认的规格永远不可过闸。 |
| 「一次性 Spike 跑通了，顺手继续改吧」 | 探路原型没有边界与状态契约。要保留它就是新需求，必须把认知带回规格闸门重新收敛。 |
| 「写『体验丝滑、报错友好』大家都懂」 | 设计、研发与验收对主观词理解完全不同。每条 AC 必须落到黑盒可复测的 Given / When / Then。 |
| 「规格没提这种边界输入，出事不怪我」 | 规格沉默不是崩溃许可证。必须在 `Review Focus` 主动排查五类隐含失效，并按用户真实后果定级。 |
| 「计划里贴全量业务代码，执行者更省事」 | 计划比规格长出数倍且充斥常规函数体说明退化成了抄录本；只留路径、签名、常量与断言即可。 |

## 交付前硬检查清单

提交规格或完成实施计划交接前，逐条确认全部勾齐：

- **范围闭环**：已写明 `In Scope`、`Out of Scope` 与必要的 `Anti-Goals`，多子系统已拆期锁定首期 MVP。
- **方案留痕**：已记录考虑过的 2–3 个方案、四维取舍、选定方案及弃选理由（或论证唯一合理路径）。
- **AC 黑盒可测**：每条 `AC-N` 具备 `Given → When → Then` 可观测结果，零主观模糊词，原始痛点全覆盖。
- **边界与状态完备**：相关空态、无结果、高数量、长文本、切页/关闭状态复位、并发竞态、4xx/5xx 保输入恢复、破坏性护栏与存量兼容均已落地。
- **事实假设清晰**：所有非用户明示的默认项均显式单列在「待确认假设 / 作者决定」中。
- **自审与交接就绪**：完整项目已过构建者视角审查与 6 维体检；若桥接实施，已补齐 `Global Constraints`、五大 `Review Focus`、文件地图、`Consumes / Produces` 契约并等待用户确认执行方式。
