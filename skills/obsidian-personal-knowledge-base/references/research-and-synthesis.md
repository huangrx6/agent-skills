# 研究与综合

本文件只服务 `03 Resources` 中需要查资料、对比方案、解释技术主题或整理长期知识的任务。

## 工作目标

研究不是资料搬运。最终产物应回答：

- 事实是什么
- 这些事实之间怎么关联
- 对实际理解、使用或决策有什么影响
- 哪些结论来自官方或一手来源
- 哪些地方仍然不确定

## 研究顺序

| 阶段 | 要做什么 | 产出 |
|---|---|---|
| 定位问题 | 明确用户真正想理解或解决什么 | 主题边界、前置概念 |
| 确认事实 | 查官方文档、规范、源码、论文等一手来源 | 定义、保证、限制 |
| 补充实践 | 查看示例、issue、讨论、工程文章 | 常见用法、坑点、取舍 |
| 设计结构 | 判断写成一篇笔记还是一组笔记 | 标题、目录、拆分边界 |
| 综合写作 | 用自己的结构组织材料 | 可复用资源笔记 |

不要在只读到第一份材料后就写结论。材料不足时先标注缺口。

## 来源优先级

默认优先级：

1. 官方文档
2. RFC、规范、设计文档、源码、原始论文
3. 官方示例、GitHub issue、GitHub discussion
4. 高质量工程博客、文章、课程材料

来源冲突时：

- 事实判断以官方或一手材料为准。
- 二手材料用于理解背景、实践经验和取舍。
- 无法确认时写明“尚未确认”，不要把推测写成事实。

变化很快的主题需要关注资料时间、版本和维护状态。

## 结构决策

写之前先判断笔记边界。

| 情况 | 处理 |
|---|---|
| 单一概念，边界清楚 | 写一篇概念笔记 |
| 一个工具有安装、配置、使用、排障多个层次 | 拆成 MOC + 多篇子笔记 |
| 一个主题跨协议、实现、运维多个层次 | 按抽象层拆分 |
| 已有笔记宽而浅 | 保留概览，拆出可独立深入的子笔记 |
| 主题用于选型 | 写对比表和适用场景 |

不要为了显得完整而把多个层次塞进一篇笔记。能独立解释、独立验证、独立复用的内容，可以拆成独立笔记。

## 写作标准

资源笔记应采用“事实 + 关系 + 例子 + 验证”的结构。

推荐顺序：

1. 定义对象和边界
2. 说明它解决的问题
3. 建立核心模型
4. 展开关键概念
5. 给出实际例子或验证路径
6. 说明常见误区和失败表现
7. 列出参考资料

写作时避免三类弱内容：

| 弱内容 | 问题 | 改写方式 |
|---|---|---|
| 学习旁白 | 只描述阅读顺序，不提供知识 | 改成概念、机制、字段或动作标题 |
| 记忆口号 | 容易笼统，缺少条件 | 改成定义、约束、例外和验证方式 |
| 空泛评价 | 只说好坏或稳不稳 | 改成适用条件、风险和取舍 |

好的段落通常包含至少一个具体锚点：

- 一个服务或组件名
- 一个配置字段
- 一条命令
- 一段请求路径
- 一个输入输出关系
- 一个失败现象

## 示例要求

命令示例要说明：

- 前提环境
- 命令用途
- 关键参数
- 预期输出或状态变化

配置示例要说明：

- 配置属于哪一层
- 字段真实语义
- 默认值或修改后果
- 常见错误

请求路径示例要说明：

- 调用方
- 被调用方
- 协议或接口
- 数据如何变化
- 失败时卡在哪一层

## 技术准确性

对以下内容保持严格：

- API 字段含义
- YAML 或配置语义
- 命令参数
- 协议行为
- 版本相关能力
- 安全边界
- 性能或一致性保证

不能确认时，保留为待确认项，不写成结论。

## MOC 和编号

研究结果形成多篇笔记时：

- MOC 只做导航和范围说明。
- 每篇子笔记只有一个主要职责。
- 编号使用连续整数。
- 前置概念放在依赖它的主题之前。
- 重命名、拆分、重编号后同步修正 MOC 和附近链接。

MOC 不承担长篇解释；解释应进入具体子笔记。

## 图示提示词

图示用于解释结构、流程、边界或对比，不用于装饰。

提示词必须包含：

- 图要回答的问题
- 必须出现的节点
- 箭头方向和标签
- 关键字段或接口
- 明确省略的内容
- 视觉风格

默认视觉风格：

- Excalidraw 手绘风格
- 纯白背景
- 白底上很淡的浅灰细网格线
- 浅色系
- 少量手绘 icon

明确排除：灰色底色、深色背景、海报风、3D、商业宣传风。

## 图示类型选择

| 需要解释的问题 | 推荐形式 |
|---|---|
| 组件之间是什么关系 | 架构图 |
| 请求或数据怎么流动 | 流程图或时序图 |
| 多个方案如何选择 | 对比表 |
| 状态如何变化 | 状态图 |

如果表格比图更清楚，使用 Markdown 表格，不强行画图。
