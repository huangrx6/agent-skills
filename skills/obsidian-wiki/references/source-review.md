# 机制与源码解读

用于源码走读、架构说明、启动链路、协议实现等机制型笔记。目标不是逐段翻译代码，
而是让读者能解释：为什么需要这个设计、每一步多知道什么、结论由哪段代码支持。
文章结构仍由问题决定；以下是这类文章优先检查的顺序，不是固定章节。
结构与配图按 [学习笔记](resource-notes.md) 和 [写作规范](writing-conventions.md) 处理；
旧结论的修正按 [知识更新](knowledge-updates.md) 保留适用范围。

## 先给心智模型，再给源码

1. 从读者卡住的地方开始。先回答“为什么会有多个对象/多次调用/这一步”，
   不要先铺包清单、目录树和文件列表。
2. 用一个具体场景建立指代：一个目录、一次启动、一条请求、一份会话。
   抽象名词出现之前，读者要知道它在哪、由谁创建、什么时候失效。
3. 用一句话说清整体机制，再分阶段。阶段多时用表：
   阶段 / 已知信息 / 关键动作 / 产出 / 为什么不能合并。
4. 先讲“不这样会怎样”，再讲“代码怎么写”。设计动机和约束比函数名更值得记。
5. 源码放在心智模型之后。只引改变结论的片段；整段函数只在它本身就是解释对象时保留。
   片段后写“看什么/所以”，不要只贴代码让读者自己猜。
6. 名词第一次出现要落定义，复杂流程拆出输入、输出、状态变化和失败分支，
   关键代码给上下文和逐行解释。纯文字讲不清时，换表、图或最小例子。

## 把动作词分清

同一段链路里，至少区分：

- 读取/解析：文件被打开、`JSON.parse`、合并成对象。
- 加载：资源进入运行时（模块被 import、技能被登记）。
- 消费：调用方真的取值并控制行为。
- 执行：代码以当前用户权限运行。
- 写入：落盘，可能被信任状态拒绝。

不要把“读取了配置”写成“加载了资源”，也不要把“启动期用了一个值”写成“只读取了这个值”。
看到“只/唯一/从不/都”时先找反例：还有谁在读这份配置？启动界面、诊断、默认值回退算不算消费？
异常路径会不会绕过？

## 结论要有可复算的证据

- 关键结论给入口文件、函数/行号或文档链接；写清适用版本。行号会漂移，版本是结论的一部分。
- 区分“文档说”“源码显示”“我推断”“实际运行”。没运行就写“静态判断”，
  不把语法检查或文档核对写成行为验证。
- 绝对化措辞是结论，不是修辞。写“唯一/只/都/从不/第一次”前，
  检查调用点、默认值、回退路径和异常路径。
- 数字要能复算。例如“三次创建 = 六次读”要先数清每次 `create`、`reload`、
  状态翻转各读什么；数不清就写范围，不写精确数。
- 示例简化时标明省略了什么；伪代码不要伪装成可运行代码。
  路径示例要说明相对哪个基准目录解析，默认值要说明来自哪一层。

## 长度与跨篇一致

- 一篇只保留一条主叙述。启动链路、对象生命周期、请求链路不要互相抢主线。
- 用户先写出一版讲法时，保留他想要的顺序、例子和重点；只压缩重复与跑题，不换成另一套叙述。
  用户说“不清晰”时，优先重排因果和阶段，不是加更多定义。
- 同一机制在多篇出现时，事实、术语和结论要对齐，但每篇都要自包含：
  本文真正依赖的名词、流程和代码在本文讲清，不写“见另一篇”；用不到的背景不必补。
  可以用更紧的写法减少重复，不能靠省略关键解释来避免重复；
  冲突时先对齐事实，再分别改到每篇能独立理解本篇目标。
- 删重复例证和重复结论。开头、正文、结尾各说一遍同一句话，是长文膨胀的常见原因。
- 表格用于阶段、对照、优先级；长推理放回段落。代码块后说明它支持哪个判断。
- 详略按理解难点分配：简单处一句带过；名词、复杂流程、关键代码展开到读者能复述。
  不要用“篇幅短”换掉必要的中间步骤，也不要用“讲细致”把显而易见的内容铺满。
- 需要展开的失败路径、并发和安全边界不要为了短而删；能用一个例子讲清就不要三个。
- 文章长度服务于理解，不追求“覆盖所有源码”。读完后能解释关键判断，比逐函数注释更有价值。

## 审阅既有技术长文

先报告，再按授权修改。按这个顺序查：

1. 绝对化措辞：唯一、只、都、从不、第一次、必然。找反例和调用点。
2. 顺序与行号：步骤编号是否和源码调用顺序一致；初始化、启动、运行时这类阶段是否写反。
3. 路径与默认值：相对路径的基准、默认信任值、默认开关；示例值是否真的落在所说位置。
4. 跨篇一致性：同一机制在多篇里的次数、阶段名、结论是否冲突；
   冲突时对齐事实与术语。同时检查每篇是否依赖其他文章补全，
   发现“见另一篇”要补回本文或删除依赖，不能只改成 MOC 链接。
5. 动作词：读取、加载、消费、执行、写入是否混用。
6. 链接与锚点：重命名、标题变化后的入链；断链、重复标题和失效锚点。
7. 旧结论修正：保留旧说法成立的条件，不静默改掉；只在某个版本成立时写明版本，
   必要时留一句“原先为什么这么写”。

## 交付前

- 用不了解背景的读者视角复读：能否说出“为什么需要这一步”“每次多知道什么”
  “最终用的是哪一份”。
- 抽查 2–3 个关键行号、默认值和计数，确认没有因编辑漂移。
- 检查新增表格列数、代码块语言、链接目标；没看渲染就不声称视觉验收。
- 说明哪些是源码核对、哪些是静态推断、哪些未运行。
