# 工作材料的整理与改写

用于整理已有项目说明、会议纪要、周报等文字，或将用户给出的工作材料整理成可阅读的文档。
目标是让读者看懂事情的来由、已有结论及依据、还没解决的问题。这里按本次编辑目的选择内容，
不要求每篇都有背景、目标、进展、风险、行动项等完整栏目。

**边界**：这里只改已经存在的文字，不汇总工作项、不改状态和负责人、不生成周期周报。
要从需求与缺陷生成或核对周报、记录本周工作事实，用 `obsidian-work`；
数据源在 PingCode 时用 `pingcode-weekly`。用户只丢来一份草稿要求改顺，才算这次范围。

## 先判断读者需要看懂什么

结合用户请求和原文判断用途，再选择讲述顺序；上下文已清楚就直接整理。
例如，交接说明需要让接手人知道当前处境与接下来怎么做；方案讨论需要保留选择的理由和分歧；
周报需要让读者分清本周期发生了什么与下一步计划；资料入口则帮助找到正确页面。
这些用途可以组合，也可以只整理其中一部分。

先读目标文档与直接相关材料，找到值得保留的事实、个人判断、例子和引用。
可以调整顺序、合并重复、改写含混句子；用连贯段落解释因果，用表格比较方案或整理时间线。
已有标题和模板只供参考，保留有效信息与属性，不照着旧栏目补写空内容。
具体 Markdown 搭配见 [写作规范](writing-conventions.md)。

## 整理表达时，保留原话的确定程度

区分已发生的事实、讨论中的建议、已确认的决定和未来计划。精简口语不应改变归属、条件和语气：

- “小李说大概周五能做完”可整理为“小李预计周五完成”；不能变成已承诺的截止日期或完成结果。
- “会议确认由小王排查，周三反馈”应保留分工和反馈时间；记入纪要不等于修改任务主档或通知小王。
- “开发已提交，测试还没反馈”要保留两个阶段；不能概括成“需求已完成”。

只有结论而没有理由时，不补编理由。材料中的相反意见应保留归属；
没有后续明确决议或纠正依据时，不自行选出“最终决定”。

未知信息按用途处理：与这次文档无关的可省略；会影响理解、交接或行动的缺口在相关位置说明。
例如已决定推进却没确定负责人，可写“负责人待确认”；普通背景说明没写负责人，不必增设空字段。
材料未提风险只能说明尚未提供风险信息，不能据此声称“暂无风险”；也不必为此给每篇加风险章节。

## 有新材料时，更新对应事实

用户只要润色时，不顺带替换旧文中的事实。用户要求补充或更新时，找到新材料对应的原段落，
核对对象、时间和条件后再修订；重复材料不再追加一份。来源可以是相关记录或用户本次明确陈述，
以足够回查为准，不为每句话制造引用表。

当前项目说明可以按新的已知事实更新；会议纪要、实验记录和已发周报保留其当时的时间范围。
后来进展不能倒写成当时已经完成；若历史记录有误，在相应位置明确更正及依据。
相对日期能由已知会议日期确定时可转为具体日期，否则保留其语境，不用整理当天的日期替代事件日期。

## 文档与工作项怎样保持一致

已有分工、状态和行动项可以在纪要或周报中呈现，并链接对应工作项；
必要的摘要注明其时间范围。文档里的描述不另起一套需要持续维护的负责人和状态主档。
仅要求整理文档时，不据此拆建任务、改变负责人、关闭缺陷或同步外部平台。
如果用户同时明确要求这些操作，按实际请求另行处理；普通文档编辑本身无需依赖其他 skill。

用户要求从工作中提炼学习笔记时，提取能复用的解释或方法，保留原事件、条件和未验证之处。
单次成功可以作为经验或假设，不能直接写成普遍保证。

完成后对照原材料复读：独有信息是否丢失，建议是否被写成决定，计划是否被写成结果，
新旧时间范围是否混淆。交付说明整理了什么和仍影响使用的缺口，不再复述一遍整份文档。
