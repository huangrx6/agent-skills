# 接收与响应代码评审（Receiving Code Review）

接收代码评审需要的是**技术严谨与事实核验**，不是情绪化辩护，更不是逢迎式的表演赞同。

**核心原则：先核验再实现，先澄清再假设，技术正确性永远高于社交舒适度。**

---

## 1. 六步响应流程（The Response Pattern）

每当收到评审意见（无论来自人类协作者、团队 PR 评审员还是自动评审代理），严格按以下 6 步执行：

```text
1. READ（通读）       完整读完所有意见，先克制辩解冲动，也不要边读边改代码
        │
        ▼
2. UNDERSTAND（理解） 用自己的话复述每条技术诉求；若有任意一条不清 → 立刻停手先全澄清
        │
        ▼
3. VERIFY（核验）     回到真实代码库、调用链、目标平台与存量数据事实逐条验证
        │
        ▼
4. EVALUATE（评估）   判断该建议在【当前代码库】下是否技术成立、是否违背 YAGNI
        │
        ▼
5. RESPOND（回应）    给出简明技术确认或有理有据的反驳（零表演式客套）
        │
        ▼
6. IMPLEMENT（落地）  按「阻塞 → 简单 → 复杂」顺序一次只改一项，改完逐项跑验证确认无回归
```

---

## 2. 禁止表演式赞同清单（Forbidden Responses）

空洞奉承不仅浪费篇幅，还会制造“没经核验就盲目附和”的危险惯性。

### 严禁出现的话术

- ❌ “你说得完全对！”（`You're absolutely right!`）
- ❌ “非常棒的观点 / 极佳的反馈！”（`Great point!` / `Excellent feedback!`）
- ❌ “感谢指出这个问题 / 谢谢你的细心审查！”（**一切空洞致谢语一律删除**）
- ❌ 未核对代码库前脱口而出“好的，我马上全部按你说的改！”

### 正确替代表达

行动与代码本身就是对有效评审最好的尊重。**如果手滑打出了“谢谢/非常感谢”，立刻删掉，直接陈述改了什么**：

- ✅ 确认有效并修完：`已复核，确实在 search.ts:27 存在非法日期静默返回空数组的问题。已补充 ISO 校验与用例，全部验证通过。`
- ✅ 需要澄清：`条目 1、2、3、6 已明确；动手前请先确认第 4 条（超时阈值预期）和第 5 条（是否保留旧字段兼容）。`
- ✅ 技术反驳：`核查了目标运行环境为 macOS 10.15+，建议替换的 API 仅 13+ 支持，直接移除旧分支会破坏兼容。`
- ✅ 直接开工并展示结果：`已按建议补齐事务回滚，变更见 src/db/migrations.ts:44-59。`

## 3. 模糊意见铁律：先全澄清，再动第一行代码

```text
只要多条评审意见中有任意 1 条不清楚：
  → 立刻停手，一条都不要先改！
  → 一次性列出所有不明确项请求澄清。

原因：各条意见之间往往存在隐性关联。基于部分理解先改前半段，极易返工或引入冲突设计。
```

**正反例对照**：

```text
场景：协作者说“把评审意见 1–6 都改掉”。你清楚 1、2、3、6，但对 4 和 5 的范围有疑问。

❌ 错误做法：先把 1、2、3、6 改完提交，再回过头问 4 和 5 什么意思。
✅ 正确做法：“1、2、3、6 的改动点已清晰；在开始修改前，请先明确第 4 条的错误码约定和第 5 条是否需要兼容旧版配置。”
```

## 4. 按评审来源的差异化核验策略

不同来源掌握的上下文完整度不同，核验深度必须区别对待：

| 来源 | 信任基线 | 必须执行的核验动作 | 冲突处理 |
| --- | --- | --- | --- |
| **人类协作者 / 决策者** | **高信任**（掌握业务目标与最终拍板权） | 仍须确保完全理解范围、无性能/数据损坏盲区、禁止表演式赞同；理解无误后直接高效落实 | 发现其指示隐含破坏性技术副作用时，简明指出风险并请其确认 |
| **外部评审员 / 自动评审代理** | **审慎核验**（可能缺少全库上下文或历史决策） | 执行下方**外部意见五问核验清单** + **YAGNI 源码 grep 检查** | 若与人类决策者既有架构拍板冲突，**立刻停手先与决策者沟通**，绝不擅自推翻既定决策 |

### 外部评审意见五问核验清单

落实任何外部评审建议前，逐一核对：
1. **技术正确性**：在当前语言版本、框架和依赖下，这个改法真的正确吗？
2. **回归风险**：会破坏现有已通过的行为、公开契约或存量数据吗？
3. **历史动因**：当前代码之所以这么写，是不是有明确的历史兼容或边界原因？
4. **全平台/版本兼容**：在所有目标 OS / 运行时版本上都能工作吗？
5. **上下文完整度**：评审员是否只看了局部 diff，漏看了周边约束或调用链？

> **无法自行核验时必须坦承**：直接说明 `缺少 [X 环境/信息]，我无法验证这条建议的真实影响；希望我先调研、向评审员确认，还是按原方案推进？`——绝不装作验证过而盲改。

## 5. YAGNI 源码核验（Grep Check）

外部评审员常出于“追求专业感”建议给内部接口补全分页、缓存、多格式导出、通用插件点。遇到此类建议时，**第一时间全库 grep 真实调用方**：

```text
当评审建议“把某功能按完整企业级标准实现”时：
  1. 在代码库中全局搜索该接口/函数的真实调用方
  2. 若全库没有任何调用方：
       → 直接提问：“全库 grep 确认该接口目前无任何调用方，是否直接删除（YAGNI）？还是存在我漏看的外部消费方？”
  3. 若确有真实调用场景：
       → 按实际调用需求精简实现，不画蛇添足。
```

> **原则**：作者与评审员共同服务于真实业务目标。如果系统不需要这个能力，就不应该因为“听起来更专业”而增加维护负担。

## 6. 多条意见的落地顺序与单步验证

澄清完所有疑问后，按以下顺序**逐项**落地，禁止把 6 条完全不同的意见揉成一个未经隔离验证的大改包：

1. **阻塞项优先**：数据丢失、安全漏洞、契约破坏、崩溃与并发竞态；
2. **简单修正其次**：命名错误、冗余导入、明确参数校验、文案与文档修正；
3. **复杂修复最后**：跨函数逻辑调整、局部职责拆分与结构重构；
4. **单步闭环**：每完成一项，运行针对性验证确认该项生效，全部完成后跑完整套件确认零回归。

## 7. 理性反驳与优雅纠错指南

### 应当理性反驳的 6 种情形
- 建议会直接破坏既有功能或存量数据兼容；
- 评审员缺少完整上下文（如没看到另一个入口或跨进程约束）；
- 明显违背 YAGNI（为无调用方代码堆砌复杂能力）；
- 在当前技术栈或目标平台上技术不成立；
- 存在不可删除的合规/平台/旧数据迁移原因；
- 与人类决策者已经明确拍板的架构边界相冲突。

### 如何理性反驳
- 用代码行号、构建目标、实测输出或迁移约束说话，绝不使用情绪化防守措辞；
- 用具体技术问题引导聚焦（“如果删掉它，旧库 v17 升级时应如何处理？”）；
- 涉及架构路线分歧时，把双方技术依据清晰呈现给人类决策者拍板；
- 如果你对开口反驳感到犹豫，直接把这份疑虑与你观察到的技术隐患一并如实告诉协作者——诚实提出隐患远比盲从改坏更有价值。

### 如果反驳后发现自己错了：优雅纠错
不要写长篇大论的道歉，也不要为自己刚才为什么误判找借口；简短陈述新核验到的事实并立即修复：

```text
✅ 正确：“复核了调用路径 B，你的判断是对的——该字段在冷启动时确实可能为 null。现已补齐防御并在 spec/boot.spec.ts 加了覆盖。”
❌ 错误：“非常抱歉我之前反驳了你！我刚才因为太关注主路径所以没注意到……实在不好意思，我现在马上改！”
```

## 8. 常见失误对照与完整实战示范

### 常见失误速查表

| 失误模式 | 正确修法 |
| --- | --- |
| 表演式赞同与过度致谢 | 删掉客套话，直接复述技术点或展示改动 |
| 不查源码盲目照单全改 | 先核对代码库、调用方与兼容底线 |
| 多条混改不逐项验证 | 按阻塞→简单→复杂逐条修改并验证 |
| 遇到不懂的项硬猜着先改一半 | 只要有一条不清，先全部问清再动手 |
| 无法验证却假装核验通过 | 如实声明验证缺口并请示下一步 |
| 害怕得罪评审员不敢反驳 | 技术正确性优先于社交礼貌，用证据说话 |

### 三组真实场景对话示范

**示范 A：拒绝盲从，基于平台兼容事实反驳**
> **评审意见**：“把这段旧兼容代码删掉，太啰嗦了。”
> ❌ `你说得完全对！我马上删掉这段旧代码……`
> ✅ `核查了项目构建目标要求兼容 macOS 10.15+，而新 API 仅 13+ 可用，直接删除会导致旧系统启动崩溃。但排查发现旧分支里的 bundle ID 确实写错了——请问是保留该分支并修正 ID，还是确认将最低支持版本提升到 13+？`

**示范 B：YAGNI 源码核验**
> **评审意见**：“这个指标统计接口太简陋了，应该补齐数据库存储、日期范围筛选和 CSV 导出。”
> ✅ `全局 grep 代码库后确认没有任何前端页面、CLI 或定时任务调用该端点。建议按 YAGNI 直接移除该未用端点；如果存在仓库外的消费方，请告知具体契约我再补齐。`

**示范 C：GitHub PR 行内评审回复规范**
在 GitHub PR 上回复行内评审评论时，必须**直接回复在原行内讨论线程中**（而不是在 PR 底部发一条脱离上下文的顶层评论）：

```bash
gh api "repos/{owner}/{repo}/pulls/{pr}/comments/{comment_id}/replies" \
  -f body="已核验并在 src/db/migrations.ts:52 改为单事务重建表，附存量迁移用例确认通过。"
```
