# 系统化故障排查与四阶段调试

**核心原则**：动手修代码前必须先查明根因；只治症状就是失败。**违背流程的字面条款，就是违背调试精神本身。**

## 两条不可违背的铁律

```text
铁律 1：NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
       未完成第一阶段根因调查，禁止提出或实施任何修复。

铁律 2：NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
       未在当前轮次实际运行完整验证命令并亲眼确认输出通过，禁止宣称已修复或已完成。
```

### 适用范围与绝不跳过的时机

适用于一切技术异常：测试失败、线上故障、非预期行为、性能退化、构建失败、集成故障。

**以下场景尤其必须严格走完流程（绝不抄近道）**：
- 时间紧迫、线上告急（紧急时凭直觉乱猜只会越改越乱）；
- “改一行就能好”看起来显而易见（简单 Bug 同样有根因）；
- 已经试过一两次修复却没奏效；
- 对当前子系统机制还没有完全吃透。

---

## 四阶段完整流程与决策图

每个阶段必须达到成功判据后，才允许进入下一阶段。

```text
┌─────────────────────────────┐
│ Phase 1: 根因调查           │ 读全报错 → 稳定复现 → 查近期变更 → 跨边界插桩 → 逆向溯源
└──────────────┬──────────────┘
               ▼ 已明确 WHAT 与 WHY
┌─────────────────────────────┐
│ Phase 2: 模式分析           │ 找可工作样例 → 逐行读参考实现 → 列举全部差异 → 核对依赖假设
└──────────────┬──────────────┘
               ▼ 已定位精确差异
┌─────────────────────────────┐
│ Phase 3: 单假设最小验证     │ 写下单一假设 → 最小单变量改动验证 ──无效──▶ 回退并立新假设
└──────────────┬──────────────┘
               ▼ 假设被证据证实
┌─────────────────────────────┐
│ Phase 4: 根因修复与验证     │ 写最小失败复现用例 → 单一根因修复 → 跑新鲜全量验证
└──────────────┬──────────────┘
               ├── 全部通过 ──▶ 附新鲜验证证据交付
               └── 修复失败 ──▶ 统计已尝试次数：
                                • < 3 次：带新证据回 Phase 1 重查
                                • ≥ 3 次：触发【三连败停手闸门】质疑架构！
```

### 阶段速查表

| 阶段 | 核心动作 | 进入下一阶段的成功判据 |
| --- | --- | --- |
| **1. 根因调查** | 精读完整报错、稳定复现、核查近期变更、跨边界插桩、逆向数据溯源 | 说清 **WHAT（哪一层出错）** 与 **WHY（根因是什么）** |
| **2. 模式分析** | 找到同类正常代码、完整通读参考实现、列出全部细微差异 | 明确“正常路径”与“故障路径”的精确差异 |
| **3. 假设验证** | 形成单一书面假设、做最小单变量实验 | 假设被实测证实，或被推翻并回退重立 |
| **4. 实施验证** | 先建失败复现用例、做单一根因修复、跑新鲜全量验证 | 复现用例红→绿、无回归、有新鲜命令退出码证据 |

## Phase 1：根因调查（Root Cause Investigation）

**在提出任何修复想法之前，必须完成以下 5 步**：

### 1. 逐字精读错误消息与完整堆栈
- 不跳过任何警告与堆栈底部帧（真正的报错行常藏在堆栈中段或底层 cause 里）；
- 记录精确的错误码、文件路径、行号、运行时状态与参数值。

### 2. 稳定复现
- 确认触发所需的最小步骤；判断是 100% 必现还是条件偶现；
- 如果无法稳定复现，继续采集运行证据（日志、输入快照、时序），**绝不靠猜直接改代码**。

### 3. 检查近期变更
- 查看 `git diff` 与最近提交；
- 核对依赖版本变化、环境变量/配置变动以及本地与 CI/生产环境的差异。

### 4. 多组件跨边界诊断插桩（关键技法）
当系统跨越多层边界（如 `CI Workflow → 构建脚本 → 签名工具` 或 `前端 → IPC/API → 领域服务 → 数据库`）时，**先不要猜哪一层坏了**，而是在**每一个组件边界**同时插入诊断探针，跑一次直接定位断裂层：

```text
对每一个组件边界：
  - 打印进入该组件的数据、配置与关键标识
  - 打印离开该组件的数据与状态
  - 验证环境变量/上下文是否完整透传
只跑一次收集全链路证据 → 精确锁定坏在哪个边界 → 只深入排查那一层
```

**多组件流水线插桩示范（Shell）**：

```bash
# 第 1 层：CI Workflow 入口
echo "=== [Layer 1] Workflow 密钥是否存在 ==="
echo "SIGN_IDENTITY: $([ -n "${SIGN_IDENTITY:-}" ] && echo SET || echo UNSET)"

# 第 2 层：构建脚本子进程边界
echo "=== [Layer 2] 构建脚本环境变量 ==="
printenv SIGN_IDENTITY >/dev/null 2>&1 && echo "IN_ENV" || echo "MISSING_IN_ENV"

# 第 3 层：签名工具前置状态
echo "=== [Layer 3] Keychain 状态 ==="
security list-keychains
security find-identity -v

# 第 4 层：真实执行层
codesign --sign "$SIGN_IDENTITY" --verbose=4 "$APP_BUNDLE"
```

一次运行即可清晰看出断在哪一段（例如：密钥 → Workflow ✓，Workflow → 构建脚本 ✗，立即可锁死环境变量透传遗漏，而不会浪费两小时去猜签名证书坏了）。

**后端 API → Service → DB 跨层诊断插桩示范（TypeScript）**：

```ts
// 临时诊断探针（修复完成后必须清理）
console.error('[TRACE boundary:api->service]', { reqId, tenantId, rawLimit: req.query.limit });
const rows = await billingService.listInvoices({ tenantId, limit });
console.error('[TRACE boundary:service->db]', { reqId, returnedCount: rows.length });
```

### 5. 逆向追踪数据流
当报错发生在调用栈深处（如空目录、非法 ID、错误状态机值）时，沿调用链自下而上逐层追问“谁传入了这个坏值”，一直追到最初生成它的源头。完整五步逆向溯源法与前置栈追踪插桩见同目录下根因溯源专篇。

## Phase 2：模式分析（Pattern Analysis）

1. **寻找同代码库的可工作样例**：同一仓库里有哪些相似功能目前运行正常？
2. **逐行精读参考实现**：如果问题涉及特定协议、框架或库模式，把参考实现**从头到尾读完**，不要扫两眼就凭印象改造。
3. **穷举所有差异**：逐项对比“能跑的”与“报错的”之间每一处差别，无论多小——**绝不提前假设“这点差别不可能有影响”**。
4. **理清隐式依赖**：确认它依赖哪些前置初始化、配置字段、环境变量、时序顺序或全局状态。

---

## Phase 3：单一假设与最小验证（Hypothesis & Testing）

1. **明确写出单一假设**：用清晰句子写下来——“我认为根因是 X，因为证据 Y 说明了 Z”。拒绝模糊猜测。
2. **最小单变量验证**：做**最小改动**只检验这一个假设，绝不同时改两三个可疑点。
3. **验证与回退**：
   - 假设成立 → 进入 Phase 4 正式写复现用例并规范修复；
   - 假设不成立 → **立即回退本次实验改动**，根据新观察提出新假设，**绝不在错误改动上继续叠补丁**。
4. **不懂就直说**：遇到看不懂的机制，如实说明“我还不理解 X 的行为”，继续查源码或文档，绝不装懂硬蒙。

---

## Phase 4：实施修复、新鲜验证与三连败停手闸门

### 1. 先建最小失败复现用例
- 在改业务代码前，先写下能稳定复现原缺陷的最小自动化用例（如 `spec/billing-limit.spec.ts`）或最小复现脚本；
- 必须先亲眼运行确认它**因目标缺陷而失败（红）**。

### 2. 实施单一根因修复
- 只改根因本身，一次只解决一个问题；
- 禁止夹带“顺手重构”“顺手格式化”或无关优化。

### 3. 新鲜验证闭环（Gate Function）
在说出“已修复 / 测试通过 / 可合并”之前，严格执行 5 步验真闸门：

1. **IDENTIFY**：确定哪条命令能真正证明本次结论（单元测试、集成测试、类型检查、构建命令）；
2. **RUN**：在最终代码状态下**全新、完整地执行**该命令（旧运行结果作废）；
3. **READ**：完整阅读标准输出、退出码与失败计数；
4. **VERIFY**：确认输出确实支撑结论（回归用例还应确认回滚修复时会复现失败，防假绿）；
5. **CLAIM**：只陈述与实际输出严格一致的结论，绝不用“应该好了”“看起来没问题”代替实测。

### 4. 三连败停手闸门（3+ Failures Architectural Gate）

如果修复后问题仍在或引发新故障：**立刻停手计数**。

- **尝试次数 < 3 次**：带着新证据回到 Phase 1 重新分析，不得凭感觉硬撞。
- **尝试次数 ≥ 3 次：强制停手，禁止在未讨论架构前发起第 4 次修复！**

**识别架构本身已出错的 3 大信号**：
1. 每次修复都在系统另一处暴露新的共享状态、隐式耦合或回归；
2. 为了让补丁生效，被迫在多处塞入越来越复杂的特判 `if` 或大面积联动改动；
3. 每次修好症状 A，立刻衍生出症状 B。

**停手后必须向协作者提出架构重审 3 问**：
- 当前这个抽象/数据所有权设计在根本上还成立吗？
- 我们是不是只是出于惯性在死守一个错误的模式？
- 应该停下来重构底层边界，还是继续打无止境的补丁？

> 这不是“第 4 个假设还没猜中”，而是**底层架构与事实源出了结构性错误**。

## 红旗自检、协作者纠偏信号与反合理化对照表

### 红旗念头清单（一出现立刻停手回 Phase 1）

- “先快速打个补丁，以后再查根因”
- “先改改 X 试试看行不行”
- “把三个可疑点一起改了再跑测试”
- “跳过写复现用例，我手动验证一下就行”
- “大概率是 X，我直接修了吧”
- “我没完全看懂，但这样改应该能工作”
- “参考实现写了 X，我按自己感觉改写一下”
- 还没追踪数据流就直接抛出“主要问题清单与修复方案”
- 已经试了 2 次以上还在想“再试最后一次补丁”
- 每次修补都在别处冒出新故障
- 在未跑验证命令前脱口而出“应该好了 / 看起来没问题 / 搞定了”

### 协作者发出的纠偏信号

| 协作者的话 | 真正含义 | 立即动作 |
| --- | --- | --- |
| “那件事真的发生了吗？” | 你未经验证就在臆测 | 立刻去跑命令或查日志取证 |
| “这样做能让我们看到什么？” | 你缺少诊断插桩与证据采集 | 先加边界日志再跑一次 |
| “别猜了” | 你没弄清根因就在推修复方案 | 停手回到 Phase 1 查数据流 |
| “再深想一层” | 你只盯着症状，没质疑基本假设 | 审视架构与事实源设计 |
| “我们卡住了吗？” | 当前路线无效且在原地打转 | 核对尝试次数，触发架构复盘 |

### 调试与验证反合理化借口对照表

| 常见借口 | 残酷现实 |
| --- | --- |
| “问题很简单，不用走流程” | 简单 Bug 也有根因；按流程查简单 Bug 往往只要 2 分钟。 |
| “线上着火了，没时间走流程” | 系统排查比盲猜返工**快得多**；盲改只会制造二次事故。 |
| “先试这一下，不行再查” | 第一个补丁会污染现场与思维锚点，从一开始就要找根因。 |
| “等修好了我再补复现用例” | 未经先红验证的用例极易假绿，无法证明真的锁住了缺陷。 |
| “一次改多处更省时间” | 无法分辨哪处生效，且必然夹带多余改动与隐蔽新 Bug。 |
| “参考代码太长，我扫一眼照着改” | 一知半解几乎必然踩坑，必须完整读懂参考实现。 |
| “我看到报错点了，直接修掉” | 看到症状 ≠ 理解根因，报错点往往只是受害者。 |
| “再试一次就能好”（已失败 ≥ 2 次） | 三连败是架构错误的明确信号，必须停手质疑设计。 |
| “Linter 过了 / 上次跑过了，应该没问题” | Linter 不等于编译与运行验证；没有当前新鲜输出就不得宣称通过。 |

## 当完整调查证实“无代码根因”时

只有当你完整走完 Phase 1–3 后，确凿证据表明故障完全来自外部依赖抖动、瞬时网络或宿主环境时序，才按以下 4 步收口：
1. 记录全部排查过程与排除依据；
2. 针对性补齐容错机制（有界重试、明确超时、可行动错误提示）；
3. 增加脱敏后的结构化可观测日志与告警，便于下次出现时第一时间取证；
4. 牢记：**95% 被归结为“偶发/无根因”的案例，本质上都是调查尚未彻底。**
