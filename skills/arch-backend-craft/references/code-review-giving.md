# 发起与执行代码评审（Giving Code Review）

代码评审的核心目标是**在问题扩散成系统债之前拦截缺陷**。它不是礼貌走过场，也不是挑刺竞赛，而是基于真实源码阅读、严格对齐用户合理预期与工程底线的技术把关。

**核心原则：早评审、勤评审、只读审查、证据驱动、严重度校准。**

---

## 1. 评审触发时机与发起规范

### 何时必须发起评审

- **强制场景**：子任务驱动开发中每个任务完成后；完成重大功能或跨模块架构改造后；合并到主分支（`main`）之前。
- **高价值可选场景**：排查或设计陷入僵局需要新鲜视角时；大规模重构前建立基线检查时；复杂并发/安全/迁移缺陷修复后。

### 发起评审时的上下文纪律

1. **锁定精确 Git 范围**：
   ```bash
   BASE_SHA=$(git merge-base origin/main HEAD)   # 或单步提交：git rev-parse HEAD~1
   HEAD_SHA=$(git rev-parse HEAD)
   git diff --stat "$BASE_SHA".."$HEAD_SHA"
   git diff "$BASE_SHA".."$HEAD_SHA"
   ```
2. **只给精准上下文，绝不倾倒整个会话历史**：
   - 提供：实现了什么（Brief Description）、对应的规格/计划要求、精确的 `BASE_SHA..HEAD_SHA` 范围。
   - **原因**：把作者整段排查与思考历史倒给评审员，会让评审员被作者的思维惯性带偏；同时，作为协调者自己内联审大段 diff 会耗尽主上下文窗口，交由独立评审者（只看产物与规格）才能得到客观结论。
3. **禁止评审员再派生嵌套子评审员**：
   - 评审员必须亲自完成整份审查，不得再派生额外子代理“分担一半 diff”或“拿第二意见”；那会重复消耗成本且无权威性。
   - 如果 diff 实在过大，自行按模块分多趟读完，并在报告中说明分趟审查范围。

## 2. 三大评审铁律

### 铁律一：规格是愿景文档（The Spec Is a Vision Document）
需求规格只说明软件“必须实现什么”，永远不可能穷举软件上线后会遇到的每一种畸形输入、环境异常与边界组合。
- 对规格**未明写**的行为，以**一个理性正常使用者的合理预期**为标尺；
- **合理预期本身就是隐性需求，规格的沉默绝不是允许程序崩溃、丢数据或静默出错的许可证**；
- 发现此类问题时，按它对真实用户的实际伤害程度定级，而不是因为它“没写在规格里”就降级为 Minor 或放过。

### 铁律二：透明搁置清单（Declined to Judge）
在给出最终合并结论前，必须单列 `Declined to judge（暂不评判项）`：
- 逐行写出你本次审查时考虑过、但判定超出当前变更/规格范围而暂不裁决的事项，每条附一句理由；
- 执行者或决策者会对清单逐条拍板——**任何你搁置的疑点都不允许静默消失**；
- 若本次没有任何搁置项，显式写明「无」，表示你确实做过核查而非漏写。

### 铁律三：严格只读评审纪律（Read-Only Review）
评审期间对当前代码检出目录保持**100% 只读**：
- 严禁修改工作树文件、暂存区（index）、`HEAD` 或分支状态；
- 只使用只读命令（`git diff`、`git show`、`git log`、读文件）检查代码；
- 如果确需检出另一个历史版本对照运行，必须使用独立临时工作树（如 `git worktree add /tmp/review-<SHA> <SHA>`），并在结束后清理，绝不移动当前检出目录的 `HEAD`。

## 3. 六维度深度核查清单

逐一核对以下 6 个维度，绝不跳项：

| 维度 | 核心核查问题 |
| --- | --- |
| **1. 计划与需求对齐** | 是否完整覆盖规格/计划要求？如有偏离，是有依据的改进还是危险漂移？**若发现计划/规格本身存在缺陷，也应直接指出。** |
| **2. 代码质量与边界** | 职责分离是否清晰？错误处理是否显式完整（无静默吞错）？类型安全是否到位？是否在避免过早抽象的前提下保持 DRY？边界输入是否处理？ |
| **3. 架构与安全防线** | 单源事实与依赖方向是否健康？性能和扩展性是否合理？跨边界 JSON 是否洁净（无内部句柄/路径/凭据泄漏）？路径与外部输入是否防逃逸？ |
| **4. 测试与验证可信度** | 自动化用例是否验证真实行为（而非只测 Mock 自身）？异常与关键边界是否覆盖？需要集成验证的地方是否到位？是否有新鲜通过证据？ |
| **5. 持久化与生产就绪** | Schema 变更是否带版本号与事务原子性？存量数据与向后兼容是否保护？文档与配置是否同步？有无遗留调试代码或未释放资源？ |
| **6. 合理预期与盲区** | 超出规格字面之外：空输入、超大输入、并发重入、断网/超时、旧版本配置升级时，系统是否会优雅失败而非损坏数据？ |

## 4. 严重度校准规则与反合理化对照

不是所有问题都是 `Critical`。过度升级会消解评审公信力，过度宽容则会放行线上事故。

### 三级严重度精确定义

- **Critical（必须修复，阻断合并）**：真实 Bug、数据丢失/损坏风险、安全漏洞（路径逃逸、凭据泄漏、注入）、跨边界契约破坏、并发竞态、核心功能失效。
- **Important（应当修复，修复后推进）**：架构职责漂移、错误处理缺口、缺失合理预期校验、关键边界缺少验证、显著性能隐患、未说明的计划偏差。
- **Minor（建议打磨，不阻断）**：命名清晰度、魔法数字提取、局部可读性优化、注释与文档润色。

### 评审行为 DO / DON'T

- **DO**：先具体肯定做得扎实的部分（附 `文件:行号`，准确表扬能建立信任）；每条问题必附 `文件:行号` + `问题是什么` + `为什么重要` + `如何修复`；给出明确无歧义的最终结论。
- **DON'T**：没读完源码就说“看起来不错”；把风格偏好标成 Critical；给出空泛意见（如“改进一下错误处理”）；回避给出清晰结论。

### 发起评审时的常见借口反合理化

| 借口 | 现实 |
| --- | --- |
| “改动很简单，跳过评审直接合吧” | 很多高危事故恰恰来自“看起来很简单的 5 行改动”。 |
| “我自己扫一遍 diff 就够了，不派独立评审” | 作者自带思维盲区，且在主会话内联读大 diff 会挤占后续执行的上下文空间。 |
| “评审员需要看我全套聊天记录才懂背景” | 聊天记录会污染评审客观性；精炼规格 + Git 范围才是最干净的评判基准。 |
| “有几个 Important 先合了以后再补” | Important 未修就往后叠加新任务，债会指数级放大。 |

## 5. 标准评审报告模板与真实示范

### 评审任务派发模板（用于独立评审子代理）

```markdown
你是资深架构与后端代码评审员。请严格保持只读，对照需求与真实源码审查以下变更：

- **本次实现摘要**：[DESCRIPTION]
- **需求 / 计划**：[PLAN_OR_REQUIREMENTS]
- **Git 审查范围**：`[BASE_SHA]..[HEAD_SHA]`

必须遵守：
1. 规格是愿景文档：规格未明写但违背正常用户合理预期的行为，按实际影响定级。
2. 保持 100% 只读，不修改工作树、暂存区或分支；不派生子评审员。
3. 结论前单列 `Declined to judge`，逐行说明暂不评判的越界项及理由（无则写「无」）。
4. 按「亮点 → 问题（Critical/Important/Minor）→ 建议 → 暂不评判项 → 综合结论」输出。
```

### 标准评审报告真实示范

```markdown
### 亮点（Strengths）
- 数据库迁移使用显式线性版本号并在单事务内完成重建与外键校验（`src/db/migrations.ts:18-64`）。
- 核心解析与持久化路径均有真实存储验证，覆盖了空列表与重复键场景（18 条用例全通过）。
- 摘要服务对超时与上游 5xx 做了清晰分类并保留脱敏错误上下文（`src/services/summarizer.ts:85-96`）。

### 问题清单（Issues）

#### Critical（必须修复）
- 无。

#### Important（应当修复）
1. **日期筛选参数缺失格式校验，非法输入被静默吞成空结果**
   - **位置**：`src/services/search.ts:25-29`
   - **问题**：外部传入 `--since=2026-13-45` 时，`Date.parse` 返回 `NaN`，代码直接落入空区间查询返回 `[]`。
   - **影响**：用户误以为“没有匹配记录”而非“日期写错”，违背正常使用者的合理预期（虽规格未明写非法日期处理）。
   - **修复建议**：入口强校验 ISO-8601 日期格式与合法日历值，非法时返回 `INVALID_INPUT` 并附示例格式（如 `2026-05-01`）。

2. **CLI 包装脚本缺失 `--help` 入口**
   - **位置**：`bin/index-conversations.ts:1-31`
   - **问题**：未实现 `--help` / `-h`，使用者无法发现新增的 `--concurrency` 参数及安全上限。
   - **修复建议**：补充 `--help` 分支，输出参数说明、默认值与典型用法示例。

#### Minor（可选打磨）
1. **长耗时索引任务缺少进度反馈与魔法数字常量化**
   - **位置**：`src/services/indexer.ts:130`
   - **问题**：批量索引超过千条时无“已处理 X / Y”进度提示，且每 `100` 条刷盘的步长直接硬编码。
   - **修复建议**：提取命名常量 `FLUSH_BATCH_SIZE = 100`，并按批次输出脱敏进度日志。

### 改进建议（Recommendations）
- 后续迭代可考虑将排除目录规则收拢到工作区级配置中，避免在命令行反复拼接长参数。

### 暂不评判项（Declined to judge）
- `src/services/indexer.ts` 对超大单文件（> 500 MB）采用全量读入内存：超出本次索引元信息重构范围，建议单独立项改为流式分块读取。

### 综合结论（Assessment）
- **是否可合并**：修改后通过（With fixes）
- **核心依据**：主干架构、事务迁移与核心验证均扎实可靠；两条 Important 项（日期校验与 `--help`）改动半径极小且能直接消除用户静默踩坑风险，修复并复跑验证后即可合并。
```
