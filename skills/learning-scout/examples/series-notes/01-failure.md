# 先看一次真实失败

一个任务跑到一半进程被杀，重启后队列里的消息全没了。日志显示入队成功，落盘文件却是空的。

这篇只回答一个问题：**消息到底在哪一段丢的？**

## 一条链路分成三段

| 段 | 负责 | 断了会怎样 |
| --- | --- | --- |
| 入队 | 接收并确认消息 | 消息根本没进来 |
| 消费 | 取出并处理 | 消息堆积，延迟上升 |
| 落盘 | 持久化与恢复 | 重启后丢失 |

判断丢失位置，按这个顺序看：入队日志 → 消费记录 → 落盘文件。三段都有记录，才能对账。

## 一个最小复现

```python
# illustrative：内存队列，进程退出即丢失
queue = []

def enqueue(message):
    queue.append(message)      # 只在内存里
    return {"ok": True}        # 对调用方说成功了
```

这段代码的问题是：**确认与持久化不是同一件事**。`enqueue` 返回成功时，消息还没有落到任何持久介质上。

## 故障矩阵

| 症状 | 先查 | 常见原因 | 修法 |
| --- | --- | --- | --- |
| 重启后全丢 | 落盘文件是否存在 | 只有内存队列 | 增加持久化 |
| 部分丢失 | 写入是否 fsync | 只写页缓存 | 写入后 fsync |
| 重复消费 | 是否记录 ack | 消费后未确认 | 增加去重或幂等 |
| 顺序错乱 | 并发消费者数量 | 多消费者无序 | 单分区或按 key 路由 |

## 边界

- 内存队列适合可丢的任务（日志采样、缓存刷新）。
- 不是所有系统都需要持久化；先确认丢失的代价。
- 持久化会带来延迟与磁盘成本，不能免费获得。

## 核验说明

示例代码为 `illustrative`，未实际运行；链路划分依据通用队列模型，不针对某个具体产品。
