# 把消息写进磁盘

先定位丢失发生在“确认早于落盘”。这篇只回答一个问题：**怎样写，才算真的落下去了？**

## 原子替换

最常见的最小实现是“写临时文件，再原子重命名”：

```python
# illustrative：同一文件系统内原子替换
tmp = path.with_suffix(".tmp")
tmp.write_text(payload)
tmp.replace(path)
```

断电后，读者看到的要么是旧文件，要么是新文件，不会看到半个文件。

> [!warning] 前提
> `replace` 的原子性只在同一文件系统内成立；跨设备移动不是原子操作。

## 落盘顺序

1. 打开临时文件。
2. 写入内容。
3. `flush` + `fsync`，确保进入持久介质。
4. 关闭临时文件。
5. 原子重命名到目标路径。
6. （可选）对目录 fsync，确保重命名本身持久。

第 3 步最容易被跳过：只调用 `write` 时，数据可能还在页缓存里。

## 恢复时做什么

启动时读取目标文件；不存在就当作空队列；存在但解析失败，保留原文件并报警，不要静默删除。

## 故障矩阵

| 症状 | 先查 | 常见原因 | 修法 |
| --- | --- | --- | --- |
| 断电后文件为空 | 是否 fsync | 只写页缓存 | 写入后 fsync |
| 文件半截 | 是否原子替换 | 直接覆盖写 | 临时文件 + rename |
| 重命名失败 | 是否跨设备 | 临时目录在别的挂载点 | 临时文件放同目录 |
| 恢复后重复 | 是否记录已处理 | 无 ack | 幂等或去重表 |

## 边界

- 单机文件队列适合低吞吐；高吞吐要换日志型存储或消息中间件。
- `fsync` 每次都调用会显著降低吞吐；可以按批次折中。
- 原子替换保证“不半写”，不保证“不丢”——还需要确认时机正确。

## 核验说明

示例为 `illustrative`；`os.replace` 的原子性依据 POSIX rename 语义，未在断电环境实测。
