# 笔记骨架：按用途起步

写之前先选骨架，再按内容删减。不要为了“齐全”保留空节，也不要为凑行数注水。

## `concept`：建立心智模型（参考 220–400 行）

```markdown
# 标题：一个判断，不是名词

一个具体故障、反例或问题。结尾必须回到它。

## 1. 它解决什么问题

一句话定义 + 它不解决什么。

## 2. 最小模型

用 3–5 个节点画出链路，配一个日常类比。

## 3. 一个最小例子

完整但最小；标 illustrative / tested。

## 4. 常见误解

错误直觉 → 正确说法，2–3 条。

## 5. 边界

什么时候不适用，3 条。

## 6. 参考资料

读了什么、跑了什么、哪些是推断。
```

## `mechanism`：讲清怎么工作（参考 320–520 行）

```markdown
# 标题

一个“看起来正常但结果不对”的现象。

## 1. 分几层

每层回答的问题、断了会怎样（表格）。

## 2. 主流程

5–8 步编号，每步：做什么 → 看到什么 → 说明什么。

## 3. 对象与状态

| 对象 | 谁创建 | 持有什么 | 不持有什么 | 谁写 | 生命周期 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

## 4. 关键数据结构 / 协议

字段表 + 不变量（哪些字段必须一致）。
区分源数据、派生视图、持久化增量、请求投影；不要只写“由 X 算好”。

## 5. 失败模式

故障矩阵：症状 / 先查 / 原因 / 修法，至少 6 行。

## 6. 边界与反例

3 条。

## 7. 版本敏感点

哪些行为随版本变化。

## 8. 参考资料
```

## `practice`：教会使用（参考 320–520 行）

```markdown
# 标题

一个配置错、命令跑不通或结果不对的现场。

## 1. 先看完整示例

完整文件或完整命令序列，逐字段/逐行解释。

## 2. 操作步骤

5–10 步，每步带预期结果与判据。

## 3. 参数与选项

表格：字段 / 默认值 / 什么时候改。

## 4. 故障矩阵

症状 / 先查 / 原因 / 修法，8–12 行。

## 5. 边界与反例

3 条；写清不该用的场景。

## 6. 版本敏感点

## 7. 参考资料
```

## `source-review`：读懂源码（参考 450–650 行）

```markdown
# 标题

一个只有读源码才能回答的问题。

## 1. 数据结构

关键 type/interface 全文 + 字段逐条解释 + 不变量。

## 2. 主调用链

5–12 跳，每跳 `file:function` 与职责。

## 3. 核心函数精读（两处）

20–40 行代码 + 逐块解释 + 为什么这样写。
代码要覆盖计算、写入、重放/读取、请求投影；只贴构造函数不算讲清对象。

## 4. 所有权与表示对账

对象表 + 声明/实现、增量/全量、源/视图三组对账；列出所有注入点与触发时机。

## 5. 错误、中断、并发

各自独立成节，引用具体行。

## 6. 复杂度

引决定复杂度的行，给 O() 与触发条件。

## 7. 设计替代方案

两个“如果换成 X 会怎样”。

## 8. 可迁移结论

3 条，每条挂到一处代码。

## 9. 参考资料

读过的文件、核对过的行号、未验证点。
```

## 通用检查

- 开场的问题在结尾有答案。
- 按主题选择：能用一个完整示例讲清就不拆；有失败面时给故障矩阵；有适用边界时给三条。
  主题不需要时说明原因，不为凑数补节。
- 没有跨篇引用，没有个人环境路径。
- 代码与结论标明状态（tested / illustrative / pseudo）。
- 核验声明写清未验证的部分。
