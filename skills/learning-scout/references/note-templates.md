# 笔记骨架：按用途起步

写之前先选骨架，再按内容删减。不要为了“齐全”保留空节，也不要为凑行数注水。

## `concept`：建立心智模型（参考 220–400 行）

```markdown
# 标题：一个判断，不是名词

一个具体故障、反例或问题。结尾必须回到它。

## 它解决什么问题

一句话定义 + 它不解决什么。

## 最小模型

用 3–5 个节点画出链路，配一个日常类比。

## 一个最小例子

完整但最小；标 illustrative / tested。

## 常见误解

错误直觉 → 正确说法，2–3 条。

## 边界

什么时候不适用，3 条。

## 核验说明

读了什么、跑了什么、哪些是推断。
```

## `mechanism`：讲清怎么工作（参考 320–520 行）

```markdown
# 标题

一个“看起来正常但结果不对”的现象。

## 分几层

每层回答的问题、断了会怎样（表格）。

## 主流程

5–8 步编号，每步：做什么 → 看到什么 → 说明什么。

## 关键数据结构 / 协议

字段表 + 不变量（哪些字段必须一致）。

## 失败模式

故障矩阵：症状 / 先查 / 原因 / 修法，至少 6 行。

## 边界与反例

3 条。

## 版本敏感点

哪些行为随版本变化。

## 核验说明
```

## `practice`：教会使用（参考 320–520 行）

```markdown
# 标题

一个配置错、命令跑不通或结果不对的现场。

## 先看完整示例

完整文件或完整命令序列，逐字段/逐行解释。

## 操作步骤

5–10 步，每步带预期结果与判据。

## 参数与选项

表格：字段 / 默认值 / 什么时候改。

## 故障矩阵

症状 / 先查 / 原因 / 修法，8–12 行。

## 边界与反例

3 条；写清不该用的场景。

## 版本敏感点

## 核验说明
```

## `source-review`：读懂源码（参考 450–650 行）

```markdown
# 标题

一个只有读源码才能回答的问题。

## 数据结构

关键 type/interface 全文 + 字段逐条解释 + 不变量。

## 主调用链

5–12 跳，每跳 `file:function` 与职责。

## 核心函数精读（两处）

20–40 行代码 + 逐块解释 + 为什么这样写。

## 错误、中断、并发

各自独立成节，引用具体行。

## 复杂度

引决定复杂度的行，给 O() 与触发条件。

## 设计替代方案

两个“如果换成 X 会怎样”。

## 可迁移结论

3 条，每条挂到一处代码。

## 核验说明

读过的文件、核对过的行号、未验证点。
```

## 通用检查

- 开场的问题在结尾有答案。
- 至少一个完整示例；至少一张故障矩阵；至少三条边界。
- 没有跨篇引用，没有个人环境路径。
- 代码与结论标明状态（tested / illustrative / pseudo）。
- 核验声明写清未验证的部分。
