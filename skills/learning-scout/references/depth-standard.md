# 笔记深度规范

这份文档决定“一篇笔记算不算写透了”。渲染器只能检查结构和链接；深度必须由写作者保证。

核心原则：**笔记是交付物，HTML 是入口。** 学习者最终读的是 `notes/*.md` 渲染出的页面，不是计划 JSON，也不是资源清单。链接只是依据，不能代替讲解。

## 一、每篇独立成篇

- 一篇笔记只回答一个问题，标题就是这个问题或判断。
- 不引用同系列的其他篇（不写“见第 3 篇”“见另一篇”“其他笔记”）。导航由 `index.html` 负责；
  同一篇内部的“上一节”可以，但要写清是哪一节。
- 不假设读者读过前一篇；确实需要的前置概念用一两句话补齐，用不到的基础不补。
  独立成篇不等于从零讲起。
- 开头提到的场景、故障或问题，必须在结尾回收。

## 二、按用途定深度

| 用途 | `kind` | 参考长度 | 默认检查项 |
| --- | --- | --- | --- |
| 建立概念 | `concept` | 220–400 行 | 心智模型、类比、边界、一个最小例子 |
| 讲清机制 | `mechanism` | 320–520 行 | 分层、分步流程、数据结构/协议、失败模式 |
| 教会使用 | `practice` | 320–520 行 | 完整示例、逐字段解释、操作步骤、故障矩阵 |
| 读懂源码 | `source-review` | 450–650 行 | 真实代码（带位置）、调用链、不变量、替代方案 |

这些数字是**参考区间，不是配额**。同一个 `kind`，主题窄可以更短，材料多可以更长；
判断合格与否看的是右侧“默认检查项”，不是行数。主题确实不需要某一项时，
可以省略并说明原因。长度只用来提醒两件事：

- 明显低于区间（不足参考下限的六成）：大概率缺了完整示例、失败模式或边界，先补内容，不要靠加形容词凑。
- 明显高于区间：检查是否在重复同一结论，或者一篇里塞了两个目标，考虑拆篇。

源码篇例外：代码段数与代码总量是硬要求（见下文），因为那是“读源码”这件事的本体。

## 三、默认结构

不是每篇都要把所有项凑齐；下面这些是默认检查项，按主题取舍，不为凑结构补空节。
格式细节（frontmatter 键、编号、段落长度、参考资料写法）见 [成文风格](house-style.md)，
那套约定来自本机 53 篇已成稿笔记的实测。

1. **开场锚点**（正文第一段，不编号）：一个具体场景、一句判断或一个反例。不要从定义开始，
   也不要写“本文介绍……”。
2. **编号章节**：`## 1. …` 到 `## N. …` 连续，一节只回答一个问题；需要分叉时用 `### 2.1`。
   插入新节就重排编号，不留 `1. 2. 4.`。
3. **机制或分层**：它由哪几层组成、每层回答什么问题、哪一层断了会出现什么症状。
4. **完整示例**：一份完整配置、一段完整代码、一次完整命令序列。逐行或逐字段解释，不要只给片段。
5. **操作或判断步骤**：编号 5–10 步，每步写“做什么 → 看到什么 → 说明什么”。
6. **故障矩阵**：症状 / 先查什么 / 常见原因 / 修法。至少 6 行。
7. **边界与反例**：什么时候不适用；三个常见误解。
8. **版本敏感点**：哪些行为会随版本变化，当前基线是什么。
9. **参考资料**（最后一节）：`## N. 参考资料`，3–8 条 `- [标题](URL)`，优先官方文档、
   原始论文和源码仓库。实测 53/53 篇都有这一节，平均 7.9 条。
10. **核验落点**：frontmatter 写 `reviewed_at`，或在正文说明读了什么、跑了什么、哪些是推断。
   不必单独开一节「核验说明」——实测没有一篇这么做。

## 四、示例的标准

- **完整**：配置文件要能直接保存使用；命令序列要能从头跑到尾。
- **可核对**：外部事实给出版本与日期；源码引用给出文件与行号。
- **可替换**：人名、路径、密钥、主机名用占位符（`<provider>`、`/path/to/project`），不写作者自己的环境。
- **有解释**：每个示例后面必须有一段“这段在演示什么、为什么这样写、换个写法会怎样”。
- **标状态**：代码标 `tested` / `illustrative` / `pseudo`；没跑过就写清楚。

## 五、机制要写到“能复述”

判断一篇机制笔记是否合格，用这三个问题：

1. 读者能不能不看笔记，画出这条链路的 5 个关键节点？
2. 链路上每个节点失败时，症状是否不同、能否定位？
3. 有没有至少一个“反直觉但真实”的细节？

如果三个都答不上，说明还停在名词解释。

### 5.1 机制解释的六问

出现“X 由 Y 计算 / 持有 / 注入 / 每次请求前处理”这类句子时，不能停在动词。
至少回答六件事：

1. **源是什么**：哪份数据是 source of truth？配置对象、会话文件，还是运行时内存？
2. **派生视图是什么**：哪些值是从源重放、渲染或查询出来的？同名 getter 可能一个是“应该发什么”，
   另一个是“已经记录什么”。
3. **持久化表示是什么**：落盘或传输时存的是完整对象，还是 `sections`、`toolsAdded` 这类增量？
4. **请求投影是什么**：发出去前又经过哪些过滤、折叠、替换或重排？
5. **谁在什么时点写、读、消费**：是 run 开始、turn 结束、请求前，还是事件回调里？
6. **哪些层只声明、哪些层真执行**：给模型看的工具声明和运行时执行的函数往往不是同一份数据。

把这六问压缩成一张表或一条时序，不要用“由某个类算好”概括三个对象、四个时点。

### 5.2 对象与注入点

机制篇至少给一张对象表：对象 / 谁创建 / 持有什么 / 不持有什么 / 谁负责写 / 生命周期。
如果链路里有回调、钩子、中间件或事件订阅，再给一张注入点表：

| 注入点 | 何时触发 | 输入 | 产出 | 谁消费 |
| --- | --- | --- | --- | --- |

只有构造函数或 `subscribe` 不够。读者要能看到“变化在哪一刻进入系统、以什么形式落盘、
下一次请求又从哪读出来”。

### 5.3 绝对化措辞要对账

写“唯一 / 只 / 都 / 从不 / 纯函数 / 永远”之前，先列出所有调用点、回调和异常路径。
“依赖注入”不等于“纯函数”；“一个订阅”不等于“唯一反向通道”；
“每次请求前算好”可能实际分成 run 开始、turn 结束、请求前三个时点。
找不到反例才保留绝对化措辞，并写明版本和范围。

## 六、源码笔记的额外要求

- 至少 8 段真实代码，总代码行 120 以上；单段 10–40 行。
- 每段代码前写“看什么”，后写“所以”；代码块首行标 `path:line`。
- 至少两个核心函数整段精读，逐块解释，不允许只贴不解释。
- 关键类型/接口列全字段，并写出不变量（哪些字段必须一致）。
- 代码要覆盖“计算 → 写入 → 重放/读取 → 请求投影”的完整路径。
  只贴构造函数、只贴 `subscribe`、只贴类型定义，不足以解释对象如何工作。
- 给对象所有权表和表示对账：源数据、派生视图、持久化增量、请求投影分别是什么；
  声明的工具与可执行工具是否是同一份数据。
- 绝对化措辞逐条对账：列出所有注册点、回调位、写入点与异常路径，再决定是否保留“唯一/只/都/从不”。
- 主调用链 5–12 跳，每跳给出函数与职责。
- 错误、中断、并发、复杂度各自独立成节。
- 至少两个“如果换成 X 会怎样”的替代方案。
- 结论必须挂到具体代码位置，不写泛泛的“设计很优雅”。

## 七、禁止的写法

- 提纲式：每节两三行，读完只知道名词。
- 链接堆：把“去看这篇”当讲解。
- 环境实录：把作者自己的路径、密钥、会话数据写进示例。
- 跨篇引用：用“上一篇/下一篇/见第 N 篇”组织内容。
- 无依据断言：写“性能更好”“更安全”却不说在什么条件下、凭什么。
- 假精确：编造版本号、日期、行号、API 名称。

## 八、发布前自检

- [ ] 长度在参考区间附近；偏离时能说清是“主题窄”还是“缺内容”。
- [ ] 开场的问题在结尾有答案。
- [ ] 至少一个完整示例，能直接照做；主题不需要完整示例时，说明用什么替代。
- [ ] 有失败面时故障矩阵不少于 6 行，且每行的“先查什么”是可执行的；
      没有失败面时说明为什么省略。
- [ ] 有适用边界时给三个边界或反例；不适用场景单一时可减少，但要写清。
- [ ] 没有跨篇引用、没有个人环境信息。
- [ ] 每个外部结论有来源，每个源码结论有位置。
- [ ] 核验声明写清了未验证的部分。
- [ ] 删掉任意一节，读者会少一个可执行动作——否则那节是填充。
