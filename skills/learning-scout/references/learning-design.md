# 学习设计：从路线到系列

一条好路线不是课程目录，而是让学习者**知道自己在哪、下一步做什么、什么时候算过关**。
v2 把这套东西落成“一组独立笔记 + 一个入口页”。

## 一、先定承诺，再定篇目

承诺是一句可验证的话：

> 学完能从一个失败样本定位问题，并改出一条能跑的链路。

不要写“掌握 RAG”“精通 React”。承诺决定篇目数量和深度：承诺越具体，篇目越少、越深。

## 二、篇目是叙事节拍，不是章节复制

常见节奏：

| 节拍 | 作用 | 产物 |
| --- | --- | --- |
| 失败现场 | 用一个真实故障建立动机 | `concept` 篇：讲清问题边界 |
| 最小闭环 | 跑通一次能工作的链路 | `practice` 篇：完整示例 + 步骤 |
| 机制拆解 | 解释为什么这样设计 | `mechanism` 篇：分层、流程、失败模式 |
| 源码或规范 | 把行为落到实现 | `source-review` 篇：代码 + 调用链 |
| 迭代 | 在真实约束下改一次 | `practice` 篇：故障矩阵 + 取舍 |

不是每个主题都要五段。30 分钟的计划可以只有两篇；系统学习 8–12 篇也正常。

## 三、一篇一个目标

每篇写一个 `goal`，用“能做什么”表述：

- 好：能指出消息在哪一段丢的；能写出原子落盘的 20 行代码。
- 差：了解队列；熟悉持久化。

如果一篇里出现两个互不依赖的目标，拆篇。拆篇的判断标准：**读者能不能只用这一篇完成一件事？**

## 四、独立性优先

- 不假设读者读过前一篇；确实需要的前置概念用一两句话补齐，用不到的基础不补。
  独立成篇不等于从零讲起。
- 不写“见上一篇”“下一节会讲”。需要关联时，在入口页的篇目卡上写一句“建议顺序”，而不是在正文里互相指。
- 术语第一次出现就给定义；同一概念不要换三个名字。
- 正文用通用 Markdown，不依赖 Obsidian 双链或库内附件；图片与外部链接在发布后要能独立访问。

独立成篇的代价是少量重复；收益是任何一篇都能单独发给别人、单独导入知识库、
单独发布到博客或公众号、单独修订。

## 五、练习与自测

- 整条系列至少一次真实动手（`practice`），步骤写成 `do / expect / check`。
- 每篇 1–3 道自测题，至少一道问“为什么/下一步会怎样”，不要全是定义回忆。
- 复习卡只放能独立回答的问题；正面不泄露答案。
- 不假装是完整 FSRS：1 / 3 / 7 天只是轻量间隔。

## 六、资源与视频的位置

- 资源是依据，不是讲解。正文负责解释，链接放在对应结论旁边。
- 每篇 0–2 个视频；视频不能替代文字讲解。
- 视频选择、核验与内嵌规则见 [视频](video-sources.md)。

## 七、长度与节奏

按 `kind` 定长度（见 [笔记深度规范](depth-standard.md)）。一条经验：

- 30 分钟计划：2–3 篇，长度按内容定（参考 200–400 行），只保留一条主线。
- 一周计划：4–6 篇，其中至少两篇 `practice`。
- 一个月计划：8–12 篇，允许一篇 `source-review` 和一篇“暂时不学”的边界说明。

如果某篇写到 600 行还没讲完，通常是目标不单一，拆。

## 八、入口页的职责

`index.html` 不是装饰，它承担四件事：

1. 给出顺序与篇目目标，让读者知道先读哪篇。
2. 记录进度（本机），让中断后能继续。
3. 汇总视频与动手任务，避免散落在各篇。
4. 给出核验日期与来源，说明哪些没有验证。

正文不负责导航，入口页不负责讲解。
