# 内容质量：让人真的学会，而不是看起来很全

这份文档约束 `paged` 笔记的正文。渲染器只能检查结构和转义；下面这些判断必须由写作者做。

## “全面”指覆盖必要概念，不是覆盖所有 API

一条路线的范围要能被一句话说清。例如：

> 覆盖 `create_agent` → middleware → `StateGraph` → checkpoint 的主链路；不覆盖所有 integrations、部署和多 Agent。

判断是否全面，用“学完能否完成承诺的产物”来检查：

- 前置概念是否补齐？不会 Python 类型注解的人，读工具 schema 会卡住。
- 核心对象是否都有定义？model、message、tool、middleware、state、checkpoint、thread。
- 机制链是否连得起来？输入 → 模型 → 工具 → 状态 → 下一轮 → 停止。
- 边界和失败模式是否讲了？什么时候不该用、常见错误是什么。
- 是否有验证方式？练习、测验、trace、eval 至少有一种。
- 是否明确“不覆盖什么”？不把一条主路线伪装成完整课程。

## 每一页的内容合同

一个 `section` 至少回答下面四件事，最好六件都回答：

1. **是什么**：一句话定义，第一次出现的缩写要展开。
2. **为什么重要**：它解决什么问题；不解决什么问题。
3. **怎么工作**：输入、关键步骤、输出；如果有循环，写清退出条件。
4. **最小例子**：代码、消息轨迹、图或伪代码；标注 `tested / illustrative / pseudo`。
5. **常见误解**：一个错误直觉 + 正确说法；放在阶段页或正文旁注。
6. **依据**：官方文档、源码、论文或维护者文章；正文先讲，链接放旁边。

正文不要写成“先看这篇，再看那篇”。链接是依据，不是讲解。

## 清晰度的检查

- 每页只回答一个核心问题；标题就是这个问题或判断。
- 先给心智模型，再给源码细节；不要在读者没有地图时扔 2,000 行代码。
- 术语第一次出现时给定义；同一概念不要换三个名字。
- 代码块要说明“这段在演示什么”，并标出是否实际运行。
- 例子要最小：能说明一个机制即可；不要用 100 行代码证明一句话。
- 重要结论旁边放依据；关键限制不要藏在最后一段。
- 用“因为 → 所以”的连接词，不用“众所周知”“显然”。
- 读完一页，读者应该能用自己的话复述，而不是只记住文件名。

## 阶段页和复习

- 每个阶段至少有一个 `teach_back`：让学习者不看笔记讲 2–3 分钟。
- 每个阶段 1–2 个 `misconceptions`：写“错误直觉”和“正确说法”，不要写“注意一下”。
- `quiz` 至少包含一道“为什么/下一步会怎样”，不要全是定义回忆。
- `review` 卡片只放能独立回答的问题；正面不要泄露答案。
- 术语超过 8 个时加 `glossary`；前置门槛明显时加 `prerequisites`。

## 来源和不确定性

- 每个 section 至少一个 `sources`；整条路线必须有 `sources.verified_at`。
- 视频只核验元数据时写明“元数据核验”，不要评价讲得好不好。
- 代码没有实际运行时标 `illustrative` 或 `pseudo`；不要写“已验证”。
- 版本敏感的内容写清版本/日期；不确定就写“截至某日”，不要假装永恒。
- 发现链接失效或 API 变化时，先修内容，再更新核验日期。

## 发布前自检

- 一个完全新手能否从第 1 页读到最后一页，不需要外部搜索才能理解？
- 每页是否有一个明确的“带走”？
- 每个核心结论是否有一个可点的依据？
- 每个阶段是否有一次动手和一次回忆？
- 是否明确说明了范围和不覆盖的内容？
- 是否把示例代码的状态说清楚了？
