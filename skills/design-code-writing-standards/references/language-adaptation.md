## 基本原则

主规范定义语义和质量目标；语言附录定义具体大小写、工具、文件布局和语法规则。

发生冲突时，优先级通常为：

1. 编译器、运行时和协议强制要求；
2. 语言官方或事实标准工具；
3. 框架明确约定；
4. 仓库已自动化执行的规则；
5. 组织通用偏好。

不得为了跨语言“统一外观”破坏语言生态惯例。

## 通用实施步骤

每种语言附录至少确定：

- 格式化器及检查命令；
- 静态分析器和严重级别；
- 命名大小写；
- 文件名与目录规则；
- 导入排序；
- 公共 API 文档格式；
- 测试命名和目录；
- 生成代码位置；
- 依赖和锁文件；
- 最低支持版本；
- CI 质量门禁。

## 语言基线

| 语言 | 建议基线 | 最低支持版本（示例） |
|---|---|---|
| Java/Kotlin | 类型 PascalCase；成员遵循语言惯例；使用统一格式化器和静态分析；包名小写；避免无意义 `Impl` | Java 17 LTS / Kotlin 1.9 |
| Go | 以 `gofmt` 为格式事实来源；导出名称和注释遵循 Go 约定；包名简短清晰；错误处理使用语言惯例 | Go 1.21 |
| Python | 遵循 PEP 8 与项目选定格式化/检查工具；模块和函数 snake_case；类型 PascalCase；明确类型检查范围 | Python 3.11 |
| JavaScript/TypeScript | 统一格式化器和 lint；变量/函数 camelCase；类型/类 PascalCase；启用严格类型配置和未处理 Promise 检查 | Node 20 / TS 5.x |
| C# | 遵循 .NET 命名与分析器约定；公共成员 PascalCase；局部变量 camelCase；异步方法按生态使用 Async 后缀 | .NET 8 |
| C/C++ | 使用项目统一格式化和静态分析；头文件边界、所有权、生命周期和未定义行为规则必须明确 | C++17 / C11 |
| Rust | 使用标准格式化和 lint 工具；所有权与错误类型遵循生态惯例；避免无必要 `unsafe` | Rust 1.70 |
| SQL | 统一关键字大小写、缩进、对象命名和迁移规则；禁止字符串拼接生成不受控查询 | 由数据库版本定 |

表中只提供起点，最终规则必须与项目实际工具一致。

## 项目级覆盖

项目可以覆盖：

- 行宽；
- 缩进宽度；
- 文件命名；
- 目录布局；
- 测试命名形式；
- 注释主要语言；
- 文件头法律要求；
- 允许或禁止的特定模式；
- 质量阈值。

覆盖必须：

- 写入版本化配置；
- 可由 CI 检查；
- 说明偏离默认规则的原因；
- 不与上层安全和兼容性要求冲突。

## 禁止做法

- 仅在 Wiki 写格式规则而不提供工具配置；
- 同一仓库使用多个互相冲突的格式化器；
- 以个人 IDE 配置作为团队规范；
- 把一种语言的命名机械应用到另一种语言；
- 为满足规则大量禁用检查而不说明原因；
- 复制过时的网上样式指南而忽略当前工具链；
- 将生成代码与手写代码使用同一人工评审标准。
