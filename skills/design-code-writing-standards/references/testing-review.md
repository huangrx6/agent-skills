## 测试要求

至少覆盖：

- 正常行为；
- 边界和空输入；
- 无效输入和失败路径；
- 状态转换；
- 并发与重复执行；
- 时间、时区和精度；
- 资源释放；
- 权限与安全边界；
- 兼容性；
- 性能关键路径的基准或容量条件。

测试应验证可观察行为，不与私有实现过度耦合。

## 测试代码规范

- 测试名表达条件、行为和结果。
- 测试独立、确定、可重复。
- 不依赖执行顺序、真实时钟、公共互联网和共享生产数据。
- 使用固定随机种子或可注入随机源。
- 不用任意 `sleep` 等待异步结果。
- Fixture 和 Builder 应提升意图，不隐藏关键输入。
- Mock 只用于清晰边界，避免把整个实现复制成调用序列断言。
- 断言失败信息应能定位差异。
- 测试数据必须虚构并满足安全要求。
- 示例代码应纳入编译或测试。

## 代码评审重点

评审必须同时检查：

- 设计是否适合当前系统；
- 功能是否正确；
- 是否存在更简单方案；
- 命名和术语是否清晰；
- 复杂度和依赖是否合理；
- 注释是否解释原因并保持准确；
- 公共 API 和文档是否更新；
- 安全、并发、资源和性能风险；
- 测试是否有效；
- 代码是否符合自动化样式规则。

评审意见针对代码，不针对个人。阻塞意见应说明风险和原因；纯偏好建议标记为非阻塞。

## 自动化质量门禁

CI 应至少执行适用项目的：

- 格式检查；
- 编译和类型检查；
- 静态分析；
- 单元与集成测试；
- 依赖和许可证检查；
- 安全扫描；
- 生成代码一致性检查；
- API 或 Schema 兼容性检查；
- 覆盖率变化或关键路径覆盖；
- 文件头和目录策略校验。

质量阈值应防止新增问题，不鼓励为数字而写低价值测试或注释。

## 变更管理

- 变更应小而聚焦，便于理解、评审和回滚。
- 重构与行为变更尽量分开。
- 提交或 PR 描述说明问题、方案、风险、测试和迁移。
- 不把无关格式化覆盖整个仓库与功能变更混在同一提交。
- 公共 API、数据格式和数据库变更必须说明兼容策略。
- 重大设计模式或新抽象应记录替代方案和选择理由。
- 临时豁免必须有责任团队、原因和退出条件。

## 发布验收

存在以下情况时不得批准：

- 格式或静态检查只能在个人机器通过；
- 文件头元数据与 Git/构建事实冲突；
- 新增公共 API 缺少文档或兼容说明；
- 设计模式只增加间接层，没有明确变化点；
- 存在硬编码密钥或真实敏感数据；
- 并发与资源生命周期不明确；
- 测试依赖睡眠、执行顺序或外部不稳定服务；
- 注释与实现不一致；
- 生成代码被手工修改且无法重复生成；
- 变更过大，评审者无法可靠理解关键风险。
