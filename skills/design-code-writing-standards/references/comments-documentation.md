## 注释目的

注释应补充代码本身无法清楚表达的信息，主要回答“为什么”“受什么约束”“风险是什么”。

优先通过更好的命名、类型、结构和测试让代码自解释；注释不是糟糕设计的补丁。

## 必须注释的内容

以下内容无法通过代码和类型直接表达时，应添加注释或文档：

- 非显然的业务规则和历史兼容约束；
- 算法选择及关键复杂度；
- 安全假设、权限边界和敏感数据处理；
- 并发所有权、锁顺序、线程安全和可重入性；
- 单位、精度、舍入、时区和编码；
- 外部协议的特殊限制；
- 有意保留的看似冗余代码；
- 临时兼容方案的退出条件；
- 公共 API 的副作用、失败、幂等性和资源生命周期。

## 禁止或避免的注释

禁止：

- 逐行复述代码；
- 与当前实现不一致的陈旧说明；
- 注释掉的历史代码；
- 个人抱怨、责备或不专业内容；
- 密码、密钥、真实客户数据和内部敏感地址；
- 仅写“修复 bug”“临时处理”而不说明原因；
- 用注释替代缺失的验证、类型或测试。

代码发生变化时，相关注释和文档必须在同一变更中更新。

## 公共 API 文档

公共类型、函数、模块和配置项应根据语言约定提供文档。

文档至少说明适用内容：

- 目的和使用场景；
- 参数语义、单位和约束；
- 返回值和空值语义；
- 可预期失败；
- 副作用与幂等性；
- 线程安全或异步语义；
- 资源所有权与释放方式；
- 最小可运行示例；
- 兼容性或 `since` 信息。

不要重复类型系统已经完整表达的内容。文档必须面向调用方，而不是描述内部实现步骤。

## TODO 与 FIXME

TODO/FIXME 必须可追踪：

```text
TODO(PROJ-123): 在旧客户端下线后删除兼容分支。
FIXME(PROJ-456): 当前算法在百万级数据下退化，替换条件见基准测试。
```

要求（格式为强制，应配套 lint 规则自动校验追踪标识存在）：

- 关联事项编号、链接或仓库认可的追踪标识；
- 说明原因、风险或退出条件；
- 不使用个人姓名作为唯一责任信息；
- 高风险临时方案应设置截止条件或发布门禁；
- 已完成事项及时删除。

可自动化：在 CI 中拦截无追踪标识的 TODO/FIXME，例如 ESLint 的 `no-warning-comments`（限定 `TODO\(\w+-\d+\)`）、Checkstyle 的 `TodoComment`、Bandit 等。

## 示例与文档测试

- 示例应可复制、可运行，并使用安全的虚构数据。
- 示例代码应纳入编译、测试或文档测试。
- 不展示过时 API、弱加密、不安全 SQL 或硬编码凭据。
- 复杂行为优先提供最小示例和边界示例。
- 文档中的命令、配置和输出应与支持版本一致。

## 语言与维护

- 一个仓库应明确注释和文档的主要语言。
- 标识符通常使用英文，业务术语可在词汇表中建立中英文映射。
- 面向外部用户的文档应支持必要的本地化。
- 评审注释应讨论代码和设计，不评价个人。
- 无法通过注释讲清的复杂代码，应优先重构。
