# 完成前验证门控

**何时读取**：准备宣称“测试已通过 / Bug 已修复 / 构建成功 / 任务已完成”，或即将提交代码、发起 PR、进入下一阶段任务、验收子代理产出之前。

## 核心原则与铁律

> **证据永远先于声明。**
> **违背规则的字面，就是违背规则的精神。**

```text
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
没有本轮新鲜的验证证据，绝不做出任何完成或通过声明
```

如果你在**最后一次代码修改之后**还没有真实执行对应的验证命令并完整阅读其输出，你**无权**宣称它通过。

## 五步门控函数（Gate Function）

```text
在做出任何状态声明或表达满意之前（BEFORE claiming any status）：

1. IDENTIFY（识别）：哪一条完整命令能直接证明这个声明？
2. RUN（执行）：在最终代码状态下新鲜、完整地执行该命令（不复用旧结果）
3. READ（阅读）：逐字读完完整输出，核对退出码与失败/跳过计数
4. VERIFY（核验）：输出是否无可辩驳地证实了声明？
   - 若否 ──▶ 带着真实输出如实汇报当前失败或阻塞状态
   - 若是 ──▶ 带着真实证据（命令、退出码、通过数）陈述声明
5. ONLY THEN（然后才说）：此刻才允许发出完成声明

跳过任何一步 = 伪造验证，而不是验证
```

## 宣称 vs 真正证明对照表

| 你想作出的声明 | 真正充分的证明 | 绝不充分的伪证据 |
| --- | --- | --- |
| **测试通过** | 新鲜执行的测试命令完整输出：退出码 `0`、0 失败、0 未预期跳过 | 改之前跑过一次、“应该能过”、只跑了单个文件 |
| **Lint 干净** | Linter 完整运行输出：0 error（及符合约定的 0 warning） | 只抽查了改过的几行、凭肉眼推断 |
| **构建成功** | 真实构建命令输出：退出码 `0` | Linter 通过了、开发日志看着正常 |
| **Bug 已修复** | 针对原始症状的复现测试/步骤新鲜通过 | 改了代码、逻辑上“看起来修了” |
| **回归测试有效** | 完整走完红-绿反证闭环（修前必红、修后转绿） | 只在修复后跑绿过一次 |
| **子代理已完成** | 亲自核对 VCS diff 并独立复跑验证命令 | 只听子代理口头汇报“已完成” |
| **需求全部满足** | 对照原始需求/验收项逐行勾选核验每条产物与缺口 | “测试全绿了，所以需求做完了” |

## 五类关键验证模式

### 1. 测试通过

```text
✅ [新鲜运行全量测试命令] [亲眼确认：34/34 passed, 0 failed, 0 skipped, exit 0] → “全量测试 34/34 通过”
❌ “现在应该通过了” / “代码看起来没问题”
```

### 2. 回归测试红-绿反证法

如果回归测试是在补漏阶段写出来的，必须反证它真的能拦住原 Bug：

```text
✅ 写测试 → 跑（绿） → 临时回退修复代码 → 跑（必须红灯且错因匹配原 Bug） → 恢复修复代码 → 跑（绿）
❌ “我已经补了一条回归测试”（从未见过它失败）
```

### 3. 构建与类型检查

```text
✅ [运行 build / typecheck] [确认 exit 0] → “构建与类型检查通过”
❌ “Lint 全绿，应该能编过”（Linter 不代替编译器与打包器）
```

### 4. 需求完整性

```text
✅ 重读原始需求与约束 → 列出逐项清单 → 逐条对照证据核验 → 如实汇报已达标项与残留缺口
❌ “单测全绿，阶段完成”
```

### 5. 子代理 / 协作者产出验收

```text
✅ 收到子代理汇报 → 查看 git diff / 实际改动文件 → 亲自跑验证命令 → 按实测结果汇报
❌ 照单全收子代理的“一切成功”总结
```

## 完整伪完成借口反驳表

| # | 常见借口 | 工程真相 |
| --- | --- | --- |
| 1 | “改完这行小改动，应该能过了” | “应该”不是证据——立刻重跑验证命令。 |
| 2 | “我对这处改动很有信心” | 主观信心 ≠ 客观证据。 |
| 3 | “就这一次别重跑全量了” | 没有“就这一次”的例外。 |
| 4 | “Linter 已经通过了” | Linter 不是编译器，也不是测试运行器。 |
| 5 | “子代理已经说它跑过了” | 独立核验 diff 与命令输出，绝不转述未经证实的声明。 |
| 6 | “太累了，赶紧收工吧” | 疲惫不是跳过门控的理由，恰恰是最容易漏掉低级错误的时刻。 |
| 7 | “只跑我改的那个子模块就够了” | 局部通过不证明跨模块契约未受损；范围限定交付改动，不限定验证范围。 |
| 8 | “我换了个说法，没说‘全部通过’” | 规则约束一切暗示成功的措辞与同义表达，精神与字面同等有效。 |
| 9 | “我只加了一行日志/注释/格式调整，不用重跑” | 任何改动都可能引入语法错误、断行问题或触发快照/校验失败；最后一次编辑后必须新鲜重跑。 |
| 10 | “那条旧测试本来就不稳/过时了，先 skip 掉交差” | 掩盖失败等于把缺陷带进主干；要么修根因，要么先和人确认契约变更后精确更新断言。 |

## 红旗信号（Red Flags —— 立刻停手核验）

发现自己正准备说出或做以下任何一件事，立刻停住并先跑验证命令：

- 句子里冒出“应该（should）”、“大概（probably）”、“看起来（seems to）”
- 还没运行验证就开始欢呼或表态（“太好了！”、“完美！”、“搞定！”、“已完成”）
- 未经新鲜验证就准备 `git commit` / `git push` / 提 PR
- 盲信子代理或协作者的“成功”口头汇报
- 用单文件或局部检查代替项目全量验证
- 念头里出现“只破例这一次”
- 感到疲惫只想尽快结束对话
- 任何在未跑验证前就**暗示**正确或完成的表述

## 严禁弱化断言、删用例与 `skip` 规范

遇到既有测试失败时，**严禁**采取以下破坏性捷径：
- 把精确断言放宽成空洞断言（如把 `toEqual({ code: 400, field: 'email' })` 弱化成 `toBeTruthy()` 或 `toBeDefined()`）；
- 删掉报错的断言行或整条旧用例；
- 给失败用例加上 `.skip` / `xit` / `@unittest.skip` / `@pytest.mark.skip` 来凑出“全绿”；
- 在不理解根因的情况下盲目更新快照（snapshot）盖过差异。

### 既有测试失败的三步合规处置

1. **先判归因**：这是新改动引入的**真实回归**，还是需求明确要求的**有意契约变更**？
2. **若是回归**：保持测试不动，修复生产代码直到新旧测试全绿。
3. **若是有意契约变更**：明确指出受影响的旧契约与变更依据，把旧测试更新为同样精确的新契约断言（而非删掉或弱化），并在交付说明中显式列出变更点。
4. **若遇到与本次无关的既有失败或受限无法执行的检查**：绝不隐瞒、绝不假装全绿——在报告中**点名列出失败用例、原始错误与未覆盖边界**。

## 适用时机

以下一切节点均强制触发本门控：
- 任何形式的成功/完成/通过/已修复声明之前
- 任何表达满意或积极状态判断之前
- 提交代码、创建 PR、标记任务完成之前
- 切换到下一个任务之前
- 向子代理委派或验收子代理结果之时

规则不仅覆盖固定短语，也覆盖所有**同义改写、委婉暗示与隐含已完成语义的表达**。
