# 批量迁移与排期实战

来源：一次真实迁移的实测记录——两个项目、871 个工作项（史诗/特性/故事三层）、
23 个迭代、逐日排期与批量分配，全部在真实租户的默认 scrum 模板上验证。

## 迭代字段按类型可用，且属性表看不出来

- 用户故事：`workitem update SAN-3 --sprint "Sprint 11"` **成功**，详情回读迭代已挂上。
- 特性 / 史诗：同样命令返回 **400 code=100355**「'properties'中的部分属性在此类型工作项上不存在」。
- `list workitem_properties --project X --type story|feature|epic` **都不列「迭代」**——
  属性表不能用来判断迭代可用性；要确认就拿一条目标类型的项试单条 update。

结论：**迭代挂到用户故事这一层**（scrum 惯例也如此）；特性/史诗只给起止时间。

## bulk-update 的退出码不代表逐条成功

实测：`bulk-update --ids <两条故事> --sprint Sprint 11` 退出码 **0**，输出却是
「✓ 已更新 0 条 / ✗ 2 条失败」。混合批次（特性+故事）里只要含不支持该属性的类型，
整批全部失败，同样 exit=0。

- 批量写之后**解析输出里的「已更新 / 失败」条数**，不能只看退出码；
  脚本重定向输出时别只 tail 两行，失败信息可能埋在中段。
- 批内 id 必须同项目；含多种类型时先确认该属性对每个类型可用，否则按类型分批。
- 实测可靠与不可靠：`--assignee`、`--priority` 走 bulk 可靠；`--sprint` 走 bulk
  没有成功案例（静默失败）→ 迭代批量迁移用「并行单条 update」。

## fill-dates 的兜底会写错日期且不报错

fill-dates 推导顺序：迭代 → 子项汇总 → 创建时间 → 完成时间 → 项目日期 → 兜底。
如果迭代挂载静默失败（见上节），fill-dates 退到「创建时间作开始 / 子项或项目日期作结束」，
把错误日期**安静地写进去**。实测 514 条被写成 start=创建日、due=史诗截止。

- 跑 fill-dates 前先抽查两三条「迭代是否真的挂上」（单条详情或 `workitem show`）；
- 跑完核对故事日期是否等于其迭代起止；错值要用显式 `update --start/--end` 覆盖
  （fill-dates 只补缺失，不纠正已有值）。

## 大批量写入的三条路线（实测耗时）

| 路线 | 适用 | 速度 |
| --- | --- | --- |
| `create-plan --file plan.json --yes` | 一次性建整棵树 | 快；预检全树后深度优先直建，实测单文件 500 节点可行 |
| `bulk-update`（单属性单值 ≤100 id） | assignee / priority 等单字段 | 每批 100 条约 1-4 分钟（含预读），2 并行稳定 |
| 并行单条 `workitem update` | 多字段一次写（如迭代+起止） | ~0.75s/条（5 并行，504 条 376s） |

- 单条 update 约 2s，大头是 CLI 进程启动；4-5 个并行 worker 实测未触限。
  配额红线：企业每分钟 200（免费版）、单接口每秒 30，写操作响应头会带出剩余量。
- 真实组合：故事迁移（迭代+起止三字段）并行单条；负责人/优先级用 bulk。
- 超时被杀后：这些写操作全部幂等（同值重写无副作用）。先读当前状态算差集、只补差集，
  不要盲目重放整批。

## 迭代只有 create / update，没有 delete

- 重排周期：`sprint update --project X --sprint 旧名 --start … --end …` 直接改日期。
- 多余迭代收纳：`sprint update … --name "(备用)Sprint 14" --status completed`，
  列表沉底且明确未使用。
- `bulk-update` 没有 `--project` 参数；两个项目有同名迭代时 `--sprint 名字` 有歧义风险，
  先 `list sprints --project X` 拿迭代 id 再操作（单条 update 带项目内编号则按项目解析）。

## 排期：让迭代内的任务有先后顺序

用户常要求「任务不要全部同起同止，要有先后顺序」。做法（实测 774 条故事）：

1. 特性按构建顺序装箱到迭代：特性不跨迭代，容量按 CFP/周期控制
   （装箱容量从低到高试，直到迭代数 ≤ 目标周期数）；
2. 迭代内故事按顺序把 CFP 分摊到工作日：`第 i 条起始日 = floor(前缀 CFP 占比 × 工作日数)`，
   结束日同理，保证结束 ≥ 起始；同日多条任务可接受（任务数多于天数时不可避免）；
3. 特性起止 = 旗下故事 min/max，史诗 = 旗下特性 min/max；父项日期**不会被服务端自动覆盖**，
   可放心显式写；
4. 节假日（如元旦 1/1）从工作日序列剔除。

效果：周迭代内故事起始日有 5 种（周一到周五各一批），先后顺序一目了然。

## 迁移后的校验闭环

- 期望值做成 `(迭代名, 起, 止)` 三元组，与读回值全量对比，**差集清零才算完成**；
  对比脚本注意故事是三元组、特性/史诗是二元组，形状要统一，否则永远不等。
- 日期读回格式有两种：**列表接口**给 ISO 字符串或 `null`；**单条详情**给
  `{date: 秒级时间戳, with_time}`。校验代码要兼容两种。
- 全量拉取用 `api --method GET --path /v2/pjm/workitems --param project_id=…
  --param page_size=100 --param page_index=N` 分页（page_size 上限 100、page_index 从 0 起）。
