# 需求拆分与录入

把一段需求落成 PingCode 工作项时，描述是交付物的一部分，不是标题的附注。
史诗、特性、用户故事、任务、缺陷都要能让没参加讨论的人直接开工或验收。

## 层级

```text
史诗 Epic        为什么做、业务目标、范围边界、成功指标
  └─ 特性 Feature  提供什么能力、覆盖哪些场景、明确不做什么
       └─ 用户故事 Story  谁在什么场景下要什么、输入输出、验收标准
            └─ 任务 Task  具体怎么实现、改哪里、怎么验证
```

缺陷 Bug 单独挂在合适的史诗/特性/故事下，不硬塞进任务层级。

一个工作项只写一件事。标题用“动词 + 对象 + 结果”，不要写“优化”“完善”“处理一下”。

## 描述模板

所有类型至少写清下面这些内容；没有信息的项标“待确认”，不要编造。

```text
背景：为什么要做，当前哪里不满足。
目标：完成后谁得到什么结果。
范围：包含什么；明确不包含什么。
验收：可观察、可复现的通过条件。
依赖/风险：前置工作、外部系统、未决问题。
证据：相关链接、附件标题、截图说明。
```

按类型补充：

| 类型 | 必须补充 |
| --- | --- |
| 史诗 | 业务目标、目标用户、范围边界、成功指标、下属特性 |
| 特性 | 能力描述、典型场景、包含/不包含、跨端影响、验收口径 |
| 用户故事 | 角色、场景、输入/输出、主流程、异常流程、验收标准 |
| 任务 | 实现步骤、涉及模块、完成定义、验证命令或检查项、依赖 |
| 缺陷 | 环境/版本、复现步骤、期望结果、实际结果、影响范围、证据 |

用户故事示例：

```text
背景：运营需要按文件类型查看解析失败原因，目前只能逐条打开任务。
目标：在任务列表按文件类型筛选，并显示最近一次失败原因。
范围：包含 HTML/Markdown/PDF；不包含批量重跑。
验收：
1. 选择文件类型后，列表只显示该类型任务。
2. 失败任务展示错误码和一句可读原因。
3. 无匹配结果时显示空状态，不报错。
依赖/风险：错误码字典由解析服务提供；旧任务可能没有错误码。
证据：见附件《任务列表筛选-设计稿.png》。
```

任务示例：

```text
背景：列表接口目前不支持 file_type 过滤。
目标：新增 file_type 查询参数，保持旧请求兼容。
范围：只改列表查询；不改解析器。
验收：
1. 不传 file_type 时行为不变。
2. 传非法值时返回 400 和明确错误信息。
3. 单测覆盖有值、无值、非法值。
实现：解析 query → 校验枚举 → 拼查询条件 → 补单测。
依赖/风险：前端筛选器与接口同版本发布。
证据：见附件《列表接口字段说明.png》。
```

长描述先用文件写，再传给 CLI：

```sh
python3 skills/pingcode/scripts/pingcode.py workitem create \
  --project PROJ --type story --title "按文件类型筛选解析任务" \
  --description-file ./story.md
```

`create-plan` 的节点同样支持 `description` 和 `description_file`。整棵树先预览，确认后再建：

```sh
python3 skills/pingcode/scripts/pingcode.py workitem create-plan --file plan.json
python3 skills/pingcode/scripts/pingcode.py workitem create-plan --file plan.json --yes
```

## 负责人

创建时尽量明确三选一；不写会按未分配处理并提示，不要靠默认值猜：

- `--assignee 张三`：按姓名/ID 解析成真实用户；重名会报候选。
- `--assignee @me`：当前登录人；需要用户令牌。
- `--unassigned`：明确先不分配（`--assignee none` 同义）。

`create-plan` 可以给顶层 `--assignee` / `--unassigned`，应用到所有没写负责人的节点；
节点自己的 `assignee` 优先。已有工作项要补负责人，用
`workitem bulk-update --ids … --assignee 张三`。

## 起止时间

每个工作项都要有开始/结束时间。录入时优先用现成来源，不要留空：

1. 给了 `--sprint`：自动继承迭代的开始/截止。
2. 给了带日期的 `--parent`：自动继承父项日期。
3. 项目本身有起止日期时：继承项目日期。
4. `create-plan`：子项有迭代日期时，父项自动取最早开始/最晚结束；父项有日期时，
   子项没有日期也会继承。
5. 都没有时：显式给 `--start/--end`，或先跑
   `workitem fill-dates --project X` 预览，再 `--yes` 回填。

`fill-dates` 的推导顺序是：迭代日期 → 子项汇总 → 创建时间作开始 → 完成/关闭时间作结束
→ 项目日期 → `--start/--end` 兜底。只补缺失的一侧，不覆盖已有日期。

CLI 在仍然缺日期时会提示；`fill-dates` 默认预览，`--yes` 才写。

## 截图附件

用户提供截图时，按“先建工作项，再上传附件，最后回链描述”的顺序处理。
`create-plan` 不支持附件字段，不要假装它在建树时一起上传。

1. **确认来源**：只使用用户明确提供的截图；确认本地文件存在。聊天里的图片先保存为
   本地文件，拿不到路径就请用户提供。不要从网页抓图代替，不要把临时链接写进描述。
1. **选挂载点**：整体方案/范围图挂史诗或特性；交互/流程细节挂用户故事；实现细节挂任务；
   缺陷现场图挂缺陷。一张图只挂最相关的一个工作项，避免重复。
1. **脱敏**：截图含令牌、客户数据、内部地址时先提醒用户脱敏；未确认前不上传。
1. **上传**：每个工作项单独执行，标题写清用途。

```sh
python3 skills/pingcode/scripts/pingcode.py workitem attach PROJ-12 \
  --file ./任务列表筛选-设计稿.png \
  --title "任务列表筛选-设计稿"
```

1. **核验**：确认附件出现在该工作项下，再更新描述里的“证据”段。

```sh
python3 skills/pingcode/scripts/pingcode.py workitem attachments PROJ-12
```

1. **回链**：在描述里写附件标题，不写本机绝对路径：

```text
证据：见附件《任务列表筛选-设计稿.png》。
```

多张截图分别上传，标题不要重名。上传失败时报告工作项编号、文件路径和错误，
不要把“已创建工作项”说成“截图已附上”。树形创建中途失败时，只给已成功创建的
工作项补附件，未创建的节点留在剩余计划里继续处理。

## 建前检查

- 标题是否具体到对象和结果。
- 描述是否包含背景、目标、范围、验收、依赖/风险、证据。
- 父项类型是否允许当前子类型。
- 负责人、迭代、优先级、起止时间是否在用户给定范围内。
- 用户提供的截图是否已确定挂载点和脱敏状态。
- 长描述是否用 `--description-file`，避免 shell 转义丢失换行。
- 树形创建是否先不加 `--yes` 预览过。
