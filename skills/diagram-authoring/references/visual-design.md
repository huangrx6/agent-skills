# 技术图的视觉审查

技术图的美感来自清楚的阅读路线、稳定的语义编码和合适的信息密度。
脚本负责几何计算，作者仍需判断“这张图让谁理解什么”。以下是审稿方法，不是额外 schema。

## 先决定读者要看到的关系

标题说明图的主题或结论，避免只写“架构图”。明确边界与观察层级：
组件依赖、调用时序、部署拓扑不能未经解释混在一张图里。
同一张图的节点尽量处于相近抽象层；确需跨层时用分组和明确标签解释。

一张图可以有多个支撑点，但第一眼应能找到入口、主链与重点。
普通节点维持 normal，关键节点才用 primary，异常状态才用 critical。
把所有节点强调会消除层级。大小、留白、形状、位置和颜色应共同表达层级。

## 节点与文字

- 标签用可辨识的短名；detail 放接口、职责或必要限定。术语前后一致。
- 不用极长字段名把节点撑成横条；需要保留原标识符时放说明或附图。
- 形状有含义：数据存储用 cylinder、判断用 diamond；同语义保持同编码。
- 图标帮助辨认，不代替文字。通用图形不要借用特定云厂商 logo，以免引入错误技术含义。
- 在最终观看尺寸审查中文、英文、数字与标点。不能因为导出图像像素大，就认定字够大。

## 边与分组

线型和标签应回答“谁向谁做什么”。虚线只用于约定的异步/可选关系，不能为装饰随意变化。
箭头方向要符合源材料；双向关系可用两条有区别的边，但不要为了规避布局问题倒转业务含义。

尽量让主链清楚，次要边退后。交叉或长回路确实必要时给足解释，
复杂到需要逐条找线时拆视图。组框表示真实边界；组内不应夹入无关节点，
组标题不承担整段正文。

## 风格选择

沿用用户指定的视觉方向，或根据用途直接选择。工程文档重辨识与稳定，
讲解图可更轻松，打印稿要在灰度下仍分得清。用户授权自行决定时不要强制二次选题。
只有方向取舍会明显改变成品时，才用同一结构生成对比预览。

颜色由 palette 的语义档位派生；不要在文档复制 kind→色值表。
配色变了仍需检查文字与背景对比、主次比例和图标辨识。
品牌图标如须保持原貌，注意默认 auto 会调整部分颜色与笔触，详见 [图标](icons.md)。

## 审稿顺序

1. 缩到最终展示大小，确认入口、重点、阅读顺序与最小文字可读。
2. 对照 spec 和来源逐项看节点、边、方向、标签、分组，确认没有漏画或错误归属。
3. 检查密集区：连线穿框、标签叠线、区域标题、长说明、图标与文字的间隔。
4. 看全图是否存在空洞与拥挤并置、无意义的巨大回路、多个同等强度的焦点。
5. 只修导致问题的内容或实现，重导出后复查受影响区域与整体。

自研 preview 可加快结构检查，但最终以真实渲染为准。没有视觉检查能力时，
交付中写明只完成了哪些程序检查，不推断“看起来一定没问题”。
