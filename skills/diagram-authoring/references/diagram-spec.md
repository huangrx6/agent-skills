# 内容层契约与设计系统

规格文件（`*.diagram.json`）是模型的输出。**这里定义一个原则：能被机械校验的东西，只有一处定义。**

## 允许写的字段

```jsonc
{
  "type": "architecture",           // 必填，决定布局策略（见 SKILL.md 的策略表）
  "title": "鉴权链路",               // 可选，图标题
  "direction": "LR",                // 可选，仅 LR / TB；那三种算法里，只有分层用得上它
  "detail": "standard",             // executive | standard | diagnostic
  "visual": "auto",                  // 可选，见下方"视觉方向"；不写 = auto
  "groups": [                        // 可选：区域（一整个色块 + 顶部标题，见下）
    // { "id": "boot", "label": "装配与启动校验", "level": "tint",
    //   "style": { "stroke": "dashed" } }   ← style 只覆盖这一个区域
  ],
  "style": {                        // 可选：五组样式轴，见下方"样式轴"；不写就是默认
    "fill": "hachure",              // hachure 斜条纹 | cross-hatch 网格 | solid 实心
    "stroke": "shape",              // shape 听形状的 | solid | dashed | dotted（只管框）
    "corners": "shape",             // shape 听形状的 | sharp 直角 | round 圆角
    "line": "sketch"                // straight | sketch | rough（粗糙度 0/1/2）
  },
  "nodes": [
    {
      "id": "auth",                 // 必填，稳定 ID（来自领域名，不是序号）
      "label": "鉴权服务",            // 必填，节点标题
      "kind": "security",           // 必填，必须是色板文件里的键
      "shape": "cylinder",         // 可选，必须在本文件的形状表里（不写就按 kind 取默认）
      "emphasis": "primary",       // 可选，muted | normal | primary | critical（不写 = normal）
      "icon": "Database",           // 可选，素材库里的项名（见 references/icons.md）
      "group": "edge",              // 可选，必须指向已声明的 group
      "detail": "login / token",    // 可选，一行次要说明
      "rank": 2,                    // 可选，强制第几层
      "pin": "left"                 // 可选，仅 left / right / top / bottom
    }
  ],
  "edges": [
    { "from": "web", "to": "auth", "label": "POST /login", "kind": "sync" }
  ],
  "cards": [                       // 可选：图下方的结论卡（见下）
    { "title": "写入路径", "items": ["订单先落库再入队", "队列消费者异步扣库存"] }
  ]
}
```

`rank` 与 `pin` 是**唯一的两个"位置类"字段**，且都只是**约束**：布局算法在满足它们的前提下自动排其余节点。
它们存在的理由：完全自动布局是主线，但确实会有人想"这个节点我想放最左边"。给一个方向约束就够，
**给坐标就是把空间计算推回给模型。**

### `rank` 必须**严格递增**（沿边的方向）

边只能从低 rank 指向高 rank，而且**必须真的增大**。把 `uc_qa(3) → uc_ret(3)` 放同一层，
布局会直接拒绝，并把**全部**矛盾节点列出来（不是只报第一条）—— 实测过，一眼就能看出
是哪几条边在闹。

推论：**往返关系要占两层**。"HTTP 直调的一级"和"用例之间调用的一级"是两件事，
挤在一层会被拒；拆成 rank 3 / rank 4 之后就自然了。同层的并列关系用**同 rank 且无边**表达。

### `cards`：图下方的结论卡

**支撑性细节放卡片，不堆进图里。** 一张图塞不下也不该塞的解释性清单（回滚策略、
安全要点、术语表）放图下方的便签卡：虚线框 + 极轻填充 + 标题 + 条目，两个后端都支持。

```json
"cards": [
  { "title": "写入路径", "items": ["订单先落库再入队", "队列消费者异步扣库存"] },
  { "title": "回滚", "items": ["扣库存失败进入死信", "人工核对后重放"] }
]
```

- 字段封闭：`title`（非空）+ `items`（至少一条非空字符串）；写了空卡直接报错，
  不静默不生效（与 group 同一条规矩）；
- 卡片**不参与布局**（与标题同一条规矩）：内容算完之后才落在图下方，
  不会把任何节点推开；几何与断行在 `layout.card_rows`，两个后端同一份推导；
- 字号沿用现有两档：标题 16（节点档），条目 12（说明档）—— 不新造字号档；
- 行宽先按**自然**断行宽度（`CARD_WRAP_UNITS`）打包，再在行内**平分内容宽**
  （上限 `CARD_MAX_W = 480`）：卡片撑成栅格、行数降下来（实测样张 7 行 → 3 行）；
  宽度不够平分时退回内容宽（内容比排版优先）。

### `groups` / `group`：**区域**（一整个色块 + 顶部标题）

声明一个 group，再把节点指向它，图上就会出现**一个圆角矩形区域**：
交叉网格填充 + 顶部居中的标题，压在节点下面。这是图上**唯一的整片颜色** ——
节点受颜色预算限制（§9），单点关注撑不起画面，区域才是"哪里是一块"的表达。

```json
"groups": [
  { "id": "boot",  "label": "装配与启动校验（fail-closed）", "level": "tint" },
  { "id": "guard", "label": "异常兜底", "level": "critical" }
],
"nodes": [ { "id": "load", "kind": "plain", "label": "load_settings", "group": "boot" } ]
```

- `label` 写在区域顶部，在**标题带里挑一个不被连线穿过**的位置（实测：居中会被
  进入该区的竖线穿过，端到端夹具一次报出两个区域标题被穿）；
- `style` 可选：**只覆盖这个区域**的样式轴（`fill` / `stroke` / `corners` / `line`），
  没写的轴继承顶层 `style`。要「节点实线、区域虚线」就靠它 —— 顶层 `style` 是全局的，
  表达不了"只改这一块"；
- `level` 可选，默认 `tint`（极轻的一片）。`critical` 用来圈"这一段是异常路径"；
- 区域框由成员节点的**实际包围盒**算出来（四周留白 + 顶部标题带），
  所以一定框得住它画的每一个节点，标题也不会压到节点；
- **标题按区域的宽度断行**（字号在 `layout.REGION_LABEL_SIZE`，比节点标题大一步）：
  宽度 → 断行 → 行数 → **标题带高度**。所以"标题比区域宽"在构造上不可能发生，
  区域自然变高而不变宽。行数定下来之后还会在**同一行数**里挑最均衡的一版——
  贪心会给出 `…× 执行 × 物 / 化对齐`（从词的中间切开），收窄一档就能断在空格上：
  `三真源：完成 = 期望 / × 执行 × 物化对齐`；
- **标题最多两行**（`layout.REGION_TITLE_MAX_LINES`，判断不是推导）：超过就报失败，
  建议缩短标题或把这一区拆成两块 —— 和节点那边「标签超过最大断行档位」同一类。
  标题带是用来给区域起个名字的，不是拿来放一段话的；
- **声明了却一个节点都没指向它 → 直接报错**（`EMPTY_GROUP`）：那种"写了没生效"
  的静默失败最难查，所以不让它静默；
- **区域之间不许部分重叠**（`check_layout` 的 `region` 检查）：要么分开、
  要么一个完全包住另一个（分区里再圈一块是正当用法）。部分重叠时图上看不出
  谁包着谁，区域就不表达任何东西了 —— 这条是判失败，不自动缩框：缩框不是盖住
  成员就是把成员排除在外，两种都是在骗。

⚠️ 区域**不改变布局**：节点位置由 rank / 边决定，区域是照着结果画的。
所以"把节点挪到一起"要改的是分组归属或 rank，不是区域。

### 样式轴：五组 `style.*`

颜色之外，"怎么画"还有五组档位 —— 前四组就是 Excalidraw 原生的设置，
第五组 `icons` 是本项目自己的（图标颜色策略）：

| 轴 | 取值 | 作用范围 | 默认 |
| --- | --- | --- | --- |
| `fill` | `hachure` 斜条纹 / `cross-hatch` 网格 / `solid` 实心 | 节点 + 区域 | **`hachure`** |
| `stroke` | `shape` 听形状的 / `solid` / `dashed` / `dotted` | **节点 + 区域**（不管连线） | `shape` |
| `corners` | `shape` 听形状的 / `sharp` 直角 / `round` 圆角 | 节点 + 区域 | `shape` |
| `line` | `straight` / `sketch` / `rough`（roughness 0 / 1 / 2） | 节点 + 区域 + 连线 | `sketch` |
| `icons` | `auto` 多色保留 / `ink` 一律单色 / `native` 原样保留 | 只影响图标 | **`auto`** |

四条需要注意的：

1. **默认不是实心**。用户的要求是"尽量不要用实心的颜色"—— 斜条纹把浅色画成一组细线，
   整体更轻更透，一屏十几个框不会糊成一片色块。要实心就显式写 `"fill": "solid"`。
2. **`stroke` 只管节点和区域，不管连线**。连线的虚实是**语义**（虚线 = 异步 / 可选，
   见 §7）—— 让样式轴去改它会把语义一起改掉。
3. **`shape` 这个档位是"显式覆盖"的对手**。不写 = 保留形状自己的定义
   （`note` 天生虚线框、`rect` 天生直角、`capsule` 靠圆角定义自己）；
   写了就是明确要覆盖，包括把 capsule 变成普通直角矩形。
4. **未知的轴、未知的取值都判失败**（`BAD_STYLE_AXIS` / `BAD_STYLE_VALUE`），不 fallback。
   和颜色同一条规矩：程序补的默认值当然合法，那校验就自己绕过自己了。

`line` 的 `(roughness)` 数字是 Excalidraw 的 sloppiness：0 = architect（正常直线）、
1 = artist（轻微手绘）、2 = cartoonist（更明显的手绘）。

### 没有区域的时候怎么表达层

区域是后加的，下面这套仍然有效，而且**不依赖区域**：

1. **层级**用 `rank` 表达（每个节点写自己的层号）；
2. **层头标签**用一个 note 形状的节点表达：`kind` 取 `plain`、`shape` 取 `note`、
   `emphasis` 取 `muted`、给它那个层的 `rank`、再配 `pin: top` —— 它就是那一列/那一层的列头。

## 刻意不存在的字段（不要"顺手加"）

这一节是防未来迭代的。每一项都有前作 `draw-excalidraw` 的实证：

| 不存在 | 为什么 | 前作的实证 |
| --- | --- | --- |
| `nodes[].x` / `y` / `width` / `height` | 模型会填数字，而且填的是"看起来合理但总差一点"的那种 | 前作 schema **有这四个字段**，且 `layout.engine: "manual"` 会**直接用填的坐标** |
| 任意 hex 颜色 | 只写语义角色，颜色查表 | 前作有 **3 套可选主题**，且不校验颜色是否在板内 |
| 字号 | 跟容器档位联动，不单独设 | 前作有 **5 档且带区间**（28-32 / 18-20 / 16-18 / 12-14）——区间 = 自由度 |
| `layout.nodeSeparation` / `rankSeparation` | **布局参数只属于脚本**。schema 里放着，模型就会去填 | 前作 schema **有这两个参数**，但 SKILL.md 的修复动作里**一条都没提** |
| 画布宽高 / 绝对边距 | 同上 | 前作有 `marginx` / `marginy` 硬编码 |

## `shape`：形状与语义有关，且和 `kind` **正交**

| `shape` | 形状 | 什么时候用 | 文字装得下需要的倍数 |
| --- | --- | --- | --- |
| `rect` | 矩形 | 普通步骤 | 1.0 × 1.0 |
| `round` | 圆角矩形 | 服务、模块（默认） | 1.0 × 1.0 |
| `capsule` | 胶囊 | 消息、队列、事件 | 宽 + 两端弧线真正侵占的量（几何算出，约 2~3px） |
| `ellipse` | 椭圆 | 人、角色、外部实体 | √2 × √2 |
| `diamond` | 菱形 | 判断、条件分支 | **2.0 × 2.0** |
| `cylinder` | 圆柱 | 数据库、存储、持久化 | 高 + 顶盖 |
| `note` | 虚线便签 | 外部系统、边界之外的东西 | 1.0 × 1.0（虚线区分，不改几何） |

`kind` 不给 `shape` 时的默认：`client`→`ellipse`、`data`→`cylinder`、`async`→`capsule`、
`external`→`note`、其余→`round`。

### 为什么 `shape` 不折进 `kind`

因为它们是**两个正交的轴**：`kind` 说的是“这是什么角色”（决定颜色），`shape` 说的是
“它在图里长什么样”（决定几何）。流程里的一个“判断”节点，语义角色就是 `service`，
但形状必须是菱形 —— 折进 `kind` 就只能把 `kind` 拆成 `service` / `service_diamond` /
`service_ellipse`… 组合爆炸，而且颜色跟着一起变，是错的。

### 为什么形状是几何、不是样式

上表最右列不是装饰。“文字在构造上不可能溢出形状”这条不变量靠它成立：
**盒子的尺寸 = 文字尺寸 × 形状的倍数**。菱形里能放下文字的只有它的内接矩形（一半宽一半高），
所以 120px 宽的标题必须塞进 240px 宽的菱形 —— 这不是审美选择，是几何约束。

所以形状**会改变布局**，不只是换个 `type` 字段。实测：加形状后节点面积涨 4~27%。

### 未知 `shape` 判失败，**不 fallback**

和未知 `kind` 同一条规矩：报错并列出允许值。回退到 `round` 上一眼看不出来，
但会让“形状与语义有关”这个不变量静默失效。

## `detail`：信息量档位（顶层）

这个字段曾经是**空壳** —— 校验器认它，`layout` / `check_layout` / `emit` 一处都不读，
而 SKILL.md 的硬规则表里写着「信息量用 `detail` 控制」。现在按那句话字面的意思实现：

| `detail` | 节点次要说明（`detail`） | 用户写的边标签 | 边的 kind 说明 |
| --- | --- | --- | --- |
| `executive` | 只留 `emphasis: primary / critical` 的 | 丢掉 | 不补 |
| `standard`（默认） | 全部 | 全部 | 不补 |
| `diagnostic` | 全部 | 全部 | **自动补**（只补**非默认 kind**：数据 / 异步 / 可选） |

- 它**会影响布局**：少了那行字，节点盒子就该变小 —— 尺寸与落笔用的是同一份判据
  （`layout.shows_node_detail`），不是"文字少了盒子还那么大"。
- 不写 = `standard` = 实现之前的行为，所以任何既有规格都不受影响。
- `diagnostic` 的那一列是自动补的：用户自己写了 `label` 就听用户的，自动的从不越位。
- **默认 kind（`sync`）不补标签**：实线 + 箭头方向已经说明了“同步调用”，再写一遍是
  零信息量 —— 密集图上一片区域会出现四五个重复的“同步调用”（用户原话：“太拥挤了看着”）。
  判据是「这条边**不是**默认那一种」，而不是「它是不是虚线」：`data` 也是实线，
  但光看线分不出“调用”与“读写”，所以照样补。默认值只有一处定义：
  `palette.DEFAULT_EDGE_KIND`（线型与标签共用它，免得两处各自写一个字面量）。

## `emphasis`：视觉重点（层级 + 尺寸 + 线宽）

`emphasis` 不直接给颜色，它**在视觉层级上上下挪一档**：

| `emphasis` | 层级 | 尺寸倍数 | 描边宽 | 什么时候用 |
| --- | --- | --- | --- | --- |
| `muted` | `neutral` | **0.94** | 1.0 | 背景设施、边缘模块、次要分支 |
| `normal` | 随 `kind`（默认 `neutral`） | 1.00 | 1.5 | 默认。不写 `emphasis` 时就是这一档 |
| `primary` | **`accent`** | **1.06** | 2.5 | 这张图的视觉中心 |
| `critical` | **`critical`** | **1.03** | 2.5 | **真的异常 / 危险 / 失败路径** |

**尺寸倍数很小，这是有意的**（§13）：要的是层次，不是海报式跳跃。
实测（#114）这个幅度在整图尺度上几乎看不见 —— 所以它**不承担焦点**，
焦点仍由颜色和位置决定。它乘在**形状盒子**上（同形状等比放大，图形仍然成立），
而枢纽加长、图标加宽那些**固定像素**的追加量不跟着倍数走
（见 `layout.boxes_from_spec` 的尺寸链）。

`emphasis` 改的是**层级**，不是颜色本身：颜色仍然只由方向的层级表派生。

颜色本身由 `palette.fill_for(kind, emphasis)` / `stroke_for(kind, emphasis)`
从**主题的层级表**派生，没有第二份颜色表。

### 为什么不用尺寸表达重点

`visual-design.md` 里把“更大的尺寸”列为建立视觉重点的手段之一，但**这里刻意没做成**：
尺寸会进尺寸链（文字 → 盒子 → 坐标），改它就得重新验证 12px 最小间隙那一套阈值，
而“哪几处必须一眼看到”这件事本身不需要动几何。

**这一条后来被改了**（§11/§12 明确要求“视觉层级首先由空间、尺寸、线条、留白和构图决定，
其次才由颜色”）：颜色大幅退出主次之后，尺寸必须接上。现在 `emphasis` 会同时改层级、
尺寸倍数、字号步数与线宽 —— 代价（重新验证间隙阈值）已经付过一次，实测六张图的
穿节点与压线一处没变。

### 为什么重点往“更实”走，而不是“更深”

浅色主题的底色是浅的。在浅底板上“更深 = 更重”读不出来，但**“更有颜色 = 更重要”**很清楚——
所以 `primary` 是把填充往自己的描边色拉一点（同时描边加粗），而不是压暗。

### 未知 `emphasis` 判失败，**不 fallback**

同 `kind` / `shape`：报错并列出允许值。回退到 `normal` 上一眼看不出来，
但会让“视觉重点”静默消失 —— 那正是 P6（所有节点长得一样）重新长出来的方式。

## 图标（`icon` 字段）

`icon` 写素材库里的**项名**，不放条目内容 —— 库是几 MB 的第三方文件，不进规格也不进仓库。
取值合法性与使用方式见 `references/icons.md`。

**它是第一个外部尺寸来源**：节点盒子会为图标加宽，所以尺寸链上多了一项不是我们算的数。
那一节（`validation.md` 第六节）已经按约定更新过。

只校验"是个非空字符串"（素材库里有没有这个名字要到出图时才知道，那里才有库）。
库没给却指定了图标 → **明确报错**，不静默忽略。

## 视觉方向（`visual` 字段）

`颜色 = 派生(视觉方向 + seed)` —— **不是模板，是有审美锚点的自适应系统**。

一个方向只定义**两个色相**（`accent` + `critical`）与画布 / 墨色，其余颜色全部派生 ——
所以"一张图最多一个主色系"是**构造上的事实**。详见 `visual-design.md` 的 2.0 节。

| `visual` | 气质 | 适合 |
| --- | --- | --- |
| `auto`（**默认**） | 按图类型 + 用户意图自己挑 | —— |
| `botanical` | 自然 / 植物 / 温度 | 架构、关系图、知识体系 |
| `editorial` | 杂志 / 精炼 / 高对比 | 产品架构、方案、展示型图 |
| `fresh` | 轻盈 / 春夏 | 流程、产品、轻量知识图 |
| `coastal` | 清透 / 海风 | 数据流、网络、流动关系 |
| `night` | 墨夜 / 深色 | 深色场景、复杂架构 |

`mood` 是**用户的原话**（如"做得有点春天的气息"）。**用户意图优先于图类型** ——
说了春天就不该因为 `type=architecture` 强行走 editorial。

**Seed 不进规格**：它是内部的审美锚点（每个方向 1~2 个，名称如 `spring` / `sea-air`），
由 AUTO 挑，不是需要用户理解的配置。

未知方向名**判失败，不 fallback**：静默换方向会变成"我写了 A 出来的是 B"。
**旧名（`soft-light` / `morandi` 之类）也判失败** —— 它们代表的正是被否掉的灰蓝企业风，
映射过来只会让人以为改动没生效。

## 另一种失败：参数存在，但没人调用

前作最有价值的教训不是"它没想到间距参数"，而是**它想到了、写进了 schema、却没有写进修复动作**。
它的修复清单全是"改内容"（拆节点／缩短标签／换 direction／降细节／换布局参数），最后一条是
`set layout.engine to elk` —— **换引擎**。

> **设计里有正确的旋钮不够，还得有规则强制"先转旋钮，而不是先动别的"。**

所以本 skill 的做法是把旋钮**从规格里拿走**，放进脚本，并让脚本自己转（见 `validation.md`）。

## `kind` 与颜色（唯一真相源）

`kind` 是**封闭枚举**，取值表就在 `palette.py` 的 `DEFAULT_KIND_LEVELS`，校验器从那里读。

| `kind` | 语义角色 | 默认层级 |
| --- | --- | --- |
| `client` | 用户 / 客户端 / 浏览器 | `neutral` |
| `service` | 服务 / API / 进程 | `neutral` |
| `data` | 数据库 / 持久化存储 | `neutral` |
| `async` | 消息队列 / 缓存 / 事件通道 | `neutral` |
| `security` | 鉴权 / 网关 / 密钥 | `neutral` |
| `external` | 外部系统 / 第三方 / 不受控边界 | `neutral` |
| `plain` | 流水线步骤 / 状态 / 普通模块 / 叶子 | `neutral` |

**⚠️ 全都是 `neutral`，这是刻意的**（§2.0 的第二条解耦）：**没有任何角色默认拿到强调色**。
一张图里有五个 `service` 是常事，`kind` 说"这是什么角色"，**不说"它有多重要"** ——
谁是重点由**每张图**通过 `emphasis: primary` 决定。这张表在早期版本里写过
`service → accent`、`data → tint`（那是"每个角色各指一档"的旧设计），已作废。

**这张表里没有颜色，只有层级** —— 颜色住在主题的层级表里（见上面的"主题"一节）。
这个文件里**一个十六进制色值都不写**：颜色只有一处定义，复述一次就会漂移一次。
（这条现在有机械检查兜着，见 `validation.md`。）

角色的数量**不设上限** —— 加一个角色只是让它指向已有的 5 个层级之一，
**不会**多出一个颜色。`plain` 就是这么来的：没有它的时候，流水线步骤和状态机状态
只能硬套 `service`，于是整张图变成强调色（实测 75%）。

### 未知 `kind` 判失败，**不 fallback**

这是硬要求，不是洁癖。fallback 到默认色的后果是：

> 它会悄悄绕过"颜色必须落在色板内"这条校验 —— **因为程序补的默认色当然合法**。
> 校验通过了，但语义已经错了。

所以未知 `kind` 与"颜色不在板内"**同一档：直接失败，阻塞输出**。

## 画布与视觉风格

画布与视觉风格的规格只有这一处定义（**唯一真相源**）—— 别处复述一次就会漂移一次。

| 项 | 规格 |
| --- | --- |
| 背景 | 纯白 |
| 网格 | 白底上很淡的浅灰细网格线 |
| 线条 | Excalidraw 手绘风格，不做“整齐化”处理 |
| 配色 | 只走上面的 6 色语义色板，全部为浅色 |
| 字体 | CJK-safe 那一档（native scene 的 `fontFamily: 2`） |
| 图标 | 按需启用，只取图形（素材自带的文字会缩到看不清，见 `references/icons.md`） |

**明确排除**：灰色底色、深色背景、海报风、3D、商业宣传风、装饰性插画、为了显得丰富而添加的重复图。

排除项不只是审美偏好——它们都会破坏“这张图是拿来理解系统的”这个前提：
深色底色会压掉浅色色板的区分度，3D 与海报风会让结构信息退到视觉噪声之后。

### 宽度模型（结构沿用前作；拉丁常数已按实测换掉）

```text
加权单位 = Σ(字符权重)
  中文 / 全角（cp >= 0x2e80、假名、谚文） → 1.00（实测精确，偏差 0.0%）
  可打印 ASCII                         → 查 _ADVANCE 表（Helvetica 实测前进宽度）
  其它（带重音字母、西里尔、emoji……）       → 1.00（表里没有的按最宽估）
宽度 = 该行加权单位 × fontSize
```

CJK 的 1.00 沿用前作 `util.mjs`，并用真实字体量过 —— 全角字符的前进宽度就是精确的 1.0 em。

**拉丁的 0.56 被实测推翻了。** 它是个“平均字符宽度”式的单值启发式，对最需要准的标签偏得最厉害：

| 标签 | 0.56 的估计 | 实测 | 偏差 |
| --- | --- | --- | --- |
| `MQ` | 1.12 | 1.61 | **−30.5%** |
| `CPU` / `DNS` | 1.68 | 2.11 | **−20.4%** |
| `DB` | 1.12 | 1.39 | **−19.4%** |
| `HTTPS` | 2.80 | 3.28 | **−14.6%** |

而这些恰恰是架构图里最常见的缩写。**偏窄 = 容器比真实文字小 = Excalidraw 自己换行把容器撑高、
整个布局随之偏移**，所以换成了查表，并一律**向上取整**（估宽只是多留白，估窄会毁掉布局）。

> **原则：别人失败经验里的具体数值值得复用，但要拿实测复核。**
> “它没被推翻”当时只是没人去量，不等于它经得起量。

前作的文字溢出，**主因仍然是耦合而不是精度** —— 见下一节。

### 尺寸档位与「断行宽度 ← 容器宽度」的耦合（前作真正的病灶）

前作**有正确的宽度模型**，但 `wrapText(maxUnits = 22)` 里的 22 是**写死的**，与容器的尺寸档位无关：

```text
22 单位 × 16px = 352px，而容器可能只有 140px 宽  →  文字溢出
```

**所以本 skill 的耦合方向是反的：先定断行宽度，容器宽度由它算出来。**

| 档位 | 断行宽度（加权单位） | 典型用途 |
| --- | --- | --- |
| `S` | ≤ 10 | 短标签、外部系统 |
| `M` | ≤ 16 | 常规服务节点 |
| `L` | ≤ 24 | 带 `detail` 说明的关键节点 |

**档位由“标题与说明中更长的那个”决定**（说明折算到节点字号后再比），**说明的断行宽度也按字号比折算** —— 所以两者用的是**同一条像素宽度**。
旧规矩只看标题，实测的后果是用户截图里那种：说明长的节点框停在 S 档，说明挤成 120px 的窄列断了 8 行（还有长标识符被拦腰截断）。改成同宽之后同一批节点是 2~3 行（宽 120→384px）。

```text
容器宽度 = 档位单位数 × fontSize + 2 × 内边距
容器高度 = 实际行数 × fontSize × 行高 + 2 × 内边距
```

**这样文字在构造上就不可能溢出容器。** 于是 `validation.md` 里的"文字溢出"检查性质变了 ——
它不再是"发现溢出"，而是**一致性断言**：如果它报了，说明尺寸推导和实际落笔之间有不一致（一个 bug），
不是内容问题。这条差异是有意保留的：前作正是栽在这个耦合上。

档位由**加权长度自动选择**，不由模型指定。超过 `L` 的断行宽度 → 报告建议拆节点或缩短标签。

### 字号：3 档 + 一个强调步数

| 层级 | 字号 | 说明 |
| --- | --- | --- |
| 图标题 | 24 | 只有 `title` 用 |
| 节点标题 | 16（`primary` 档 **17**） | `label`、组标签 |
| 次要说明 | 12 | `detail`、边标签 |

重点档的字号大一步（§14）—— 注意它**从 `measure` 走进去**，盒子顺着尺寸链跟着变大；
不是在落笔时改 `fontSize`，那样盒子与实际文字就对不上了。
`detail` 不跟着放大：辅助说明本来就该更小（§14）。

**固定值，不给区间。** 前作给的是区间（28-32 / 18-20 / 16-18 / 12-14）—— 区间就是"让模型自己判断"，
而它不该判断这个。字体族固定用 CJK-safe 的那一档（native scene 里的 `fontFamily: 2`）。
