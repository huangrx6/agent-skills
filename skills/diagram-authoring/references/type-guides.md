# 六类技术图的专属审稿规则

选定类型后只读对应段。各段标题里的默认方向只是起手值，可用规格中的 `direction` 覆盖。
图型名是语义承诺，不是画几个类似形状就算实现。专用时序/泳道/ER 图当前尚未支持。

## 方向：LR 还是 TB

先看读者怎么读、图放在哪里，再看图型默认值：

- **LR（从左到右）**：横向流水线、阶段推进、分支并排、16:9 幻灯片/宽屏；
  架构图里并列的调用者也适合横向展开。
- **TB（从上到下）**：纵向步骤、层级深且每层窄的依赖、窄栏文档或移动端阅读。
- 用户说“横着/竖着”时直接采用，不再让用户猜默认值；方向不改变先后、依赖或状态事实。
- 主轴预计超过两屏时先拆图或换方向，不靠缩小字号硬塞。

`flow`/`dependency` 的默认 TB 最容易被误当成唯一选项；横向流水线或幻灯片场景应显式写 LR。
同一画布内需要横竖混排时，见 [混合方向](mixed-direction.md)；不要用单图 `direction` 硬掰。

## architecture：组件与边界（默认 LR）

默认横向展开组件与调用链；调用层级很深或载体是窄栏文档时可改 TB。

读者应知道组件职责、系统边界及一条重要连接路径。节点用组件名，边说明实际连接语义。
运行时调用、部署归属、代码依赖若混用必须明确图例或拆图。groups 只表达平面真实边界；
不能因想对齐而造分组，也不能把多层网络范围压成一层后称完整网络架构。
代码层/模块不是独立进程；包含 API 与多个 worker 的服务端范围不能未经依据称为单一进程边界。
同一条边不要同时混用 TCP 连接发起方向与消息流向。投递和消费属于不同语义时分别表达，
不能为少画一条线而合并成单向箭头，再在卡片里解释为双向。
并列的调用者应考虑并列摆放；一串竖排节点容易让读者误以为存在串行调用，仍须以真实连线为准。

## dependency：谁依赖谁（默认 TB）

依赖层级深时 TB 更自然；模块面很宽、跨层边多或横屏展示时可改 LR。

统一 from=依赖方、to=被依赖方，若来源采用其他约定须在说明明确并一致执行。
保留真实循环，不把布局内部的断环处理解释成业务依赖消失。包依赖与运行调用不是同一件事。
rank 表达有依据的层级，不能用它倒转事实。多父、跨层依赖正常，不改成脑图假装简单。

## flow：动作与结果（默认 TB）

纵向步骤用 TB；横向流水线、阶段门、多分支并排或 16:9 幻灯片可改 LR。
方向只改变排布，不把并行分支伪装成串行步骤。

节点写动词短语；diamond 用于实际判断。每个出向判断结果应可区分，不能两条都写“处理”。
正常完成、失败恢复、人工介入只画来源存在的部分。分支不足两条时先核查，不自动补“否”。
不同节点间的回边可以表达恢复；动作与状态不能为了美观混成一套。

## state：同一个对象的状态（默认 LR）

状态少、转移链横向可读时用 LR；状态多且转移链长时可改 TB 或拆成多张生命周期图。

节点写状态名，边写事件，可按 `事件 [条件] / 动作` 组织标签。等待不是未标注空白；
取消与失败含义不同就分开。强调重要状态不代表自动识别了终态。
当前只支持不同节点间的回边；不支持自环、原生开始/终止伪状态或并行状态区。
遇到这些需求应明确限制，选用能满足要求的其他工具，不能伪造额外状态凑图。

## mindmap：单根主题树（径向）

第一个节点作为根，边从父到子。每个非根只有一个父节点；同层节点保持相近抽象程度。
多父、循环或知识交叉联系需要 dependency/network。根只有一个不等于其他节点都能到达，
检查孤立子图。不要把顺序流程画成放射主题图。

## network：对等互连（力导向）

节点是对等实体，边是已证实的互连；图中距离不代表延迟，大小不代表容量。
force 布局可能有交叉，不为 showcase 过关删真实边。关键枢纽可强调，其他节点保持中性。
有明确主路径或层级时优先 architecture/dependency。

## 构件与审稿

标题陈述主题或结论，节点主标签标识对象，detail 提供必要限定，边标签表达关系；
长解释放 cards，不能把所有关键事实移到卡片后留下空壳图。
字体和尺寸交给现有生成器，按 [观看场景](output-presets.md) 检查缩放后的可读性。

语义检查命令：`python3 scripts/check_semantics.py system.diagram.json --json`。
它检查可观察遗漏，不验证事实；发现提示后对照来源解释或修复，不自动删改图。
