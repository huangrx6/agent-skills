# 校验与自动调参

这一节的存在理由，是前作 `draw-excalidraw` 最大的一处失败：

> 它的 `lint.mjs` **只有 1474 字节**。你要的四项校验里**只有"重叠"一项存在**
> （阈值 4px、只 warn），**连线长度 / 文字溢出 / 色板越界三项完全不存在**。
> 而且全部结果是 `warn` / `info` —— **没有一条能挡住输出**。报了什么也不影响结果。

---

## 一、十三项校验 + 质量两档

实现在 `scripts/check_layout.py`（分层与坐标在 `scripts/layout.py`）。“哪项失败动哪个参数”
也和校验写在同一个文件里 —— 拆成两个文件，那张表就会裂开。

| # | 检查 | 阈值 | 级别 | 可自动修？ |
| --- | --- | --- | --- | --- |
| 1 | 包围盒间隙 | **相邻元素间隙 < 12px** | 阻塞 | ✓ 调 `nodeSeparation` |
| 2 | 连线长度 | **< 24px** | 阻塞 | ✓ 调 `rankSeparation` |
| 3 | 文字超出容器 | 任何溢出 | 阻塞 | ✗ 这是脚本的 bug |
| 4 | `kind` / 颜色越界 | 任何越界 | 阻塞 | ✗ 这是内容错误 |
| 5 | 边交叉数 | `> 边数 / 2` | **软**（报告，不阻塞） | ✓ 调 `barycenterRounds` |
| 6 | 连线穿节点 | 任何穿过（两端节点除外） | 阻塞 | ✓ 调 `nodeSeparation` + `rankSeparation` |

| 10 | 区域标题溢出 | 标题宽过区域 / 断行与尺寸对不上 / 标题块压成员 | 阻塞 | ✗ 这是脚本的 bug |

| 13 | 桌面可读性 | 图宽 >960px 时最小字投影 <6px | **软**（只告知） | ✗ **不进调参** —— 加大间距只会更宽；修它靠拆图/折行/降层 |

### 质量两档：standard / showcase（quality_profile）

- **standard（默认）**：上表原样 —— 软项报告不阻塞，与历史行为一致；
- **showcase（交付档）**：调参循环照常先跑；试尽后把结构类软项（#5/#6/#8/#9/#11/#12）
  **升级为阻塞**，有残留就不出图。#13 与 icon 不升级 —— 前者是告知，后者是选型问题，
  卡住它们不会让图变好。

关键实现约束（`Outcome.promote`）：升级发生在调参循环**之外**的拷贝上 ——
直接在循环里升级会把“可调”变“阻塞”，调参循环对软项失明，白转四轮。
这是 `test_tuning_uses_raw_outcome` 钉着的性质。

### JSON 回执（`--json`，供机器消费）

`check_layout.py --json` / emit 失败时的 stderr 输出结构化诊断（修复回执）：

```json
{ "code": "layout/gap", "severity": "error",
  "message": "a ↔ b —— 间隙 4px，下限 12px",
  "subject": {"check": "gap", "where": "a ↔ b"},
  "evidence": {"gapPx": 4, "minPx": 12},
  "suggestedFixes": ["拆节点，或把相关节点归入同一主题分开画。"] }
```

与「模型写坐标」那类渲染路线相比，本 skill 的回执有两点刻意差异：

1. **suggestedFixes 里不出现参数名** —— 与人读报告同一条硬规则（`_assert_no_param_names`
   连回执也钉着）；
2. **不给坐标建议** —— 「模型写坐标」的路线里坐标是模型写的，脚本算个更好的还回去；
   我们的坐标是脚本推导的，模型不该拿坐标，也就不该收坐标。证据给“量到了什么/阈值是多少”。

### 路线节奏（route rhythm）：为什么不设独立检查（审计记录）

同类渲染器的路线节奏门分两档：任意段 ≥8px（微段下限）、内部折段 ≥16px（拐弯下限）。
本 skill 的 #2（任意可见段 ≥24px，阻塞 + 可调）**严格强于两者的并集** ——
所以不另设“微段/内部段”两条检查：同一件事只留一处定义，重复的检查只会让
两张表各自漂移。若未来 #2 改成区分端点段与内部段（放宽到同类工具的宽容度），
再回来把这一节改成真正的分档表。

### #8 / #9 / #11 也是后加的（连线形状出了问题之后）

这三项以前**根本不在这张表里**，于是“报告全绿”与“图看着难受”可以同时成立。

`#11` 的来历最直白：一份 25 节点的竖版流程里，一条边（`registry → validate`）
被折了 **10 次** —— 在 x≈1330 与 x≈2200 之间来回横跳三次 —— 而当时的九项校验
一项都不管折点数。用户指着它说「为什么这里的高度不能大一些呢，非要拐个弯」。
把那一刻的候选表打出来，根因**不是排序**而是**没得选**：直线候选穿 2 个节点、
车道候选穿 1 个，只有那条“折 10 次但拐点落在预留行/列上”的候选是无冲突的。
所以修了两处（都已在 `layout.py`）：

1. **排序键**（`_path_rank`）里档位加上“超出 `BEND_TOLERANCE` 的折点数” ——
   一条路要么折得少，要么就别想靠档位占便宜；
2. **新增候选**（`_sidestep_candidates`）：**逐个障碍让开** —— 碰到一个就从它边上擦过去，
   越过再继续。旧的车道候选只给“障碍**整体**包围盒外侧”两个位置，而障碍分散在不同层时
   这个包围盒跨了两千多像素高，贴着它走反而撞上别的节点。

效果：那条边 10 折 → 4 折（改走一条 240px 外的空车道）；7 个夹具 + 那张真实图共
96 条边，合计折点从 `{0:47, 2:42, 3:1, 4:5, 10:1}` 变成 `{0:50, 2:39, 3:2, 4:5}`，
**穿节点与交叉数一条都没变差**。
实测：7 张自带规格里有 5 张存在连线重合（最长 225px，`order→user` 与 `order→cache`
画在同一个 x 上），而报告一条都没报。

- **#8 连线重合**：两根线共线、区间重叠 → 图上就是**一根线**，信息直接丢了。
  生成侧现在有 `layout._spread_lanes` 主动错开车道，但那是尽力而为（挪进节点、
  压短相邻段就回退），所以还需要这一项把剩下的如实报出来。
  定为**软项**的理由与 #5 同：空档太窄时确实可能分不开，那是空间不够，不是内容错了。
- **#9 连线斜段**：分层图里每条边都有正交候选，出现斜段说明**那段路真的过不去**。
  它以前不在表里，生成侧于是把一条 1475px 的斜线当作“避开 3px 毛刺”的合理选择
  （排序键当时把毛刺排在斜段前面）—— 用户的原话是“为什么这么直着过去，这不对吧”。
  现在生成侧改成“斜段优先于毛刺 + 毛刺就地并掉”，这一项负责兜住剩下的。
  只查 LR / TB：径向与力导向的连线**就该是**两点直辐条。

### #6 / #7 也是后加的（区域做出来之后）

- **#6 连线穿节点**：`nodes_hit_by_polyline` 一向排除**两端**节点（端点在边界上，贴着边不算撞）——
  于是「从源的底边出去却往上走、整个人从盒子里穿过去」这种路一直是合法的，图上就是一条线
  从框里冒出来。现在**穿过自己两端节点的内部**也算（把盒子往里收 1px 再判），
  并且「端口朝着下一站开」（`_port_faces`）从根上消掉了这一类。
- **#7 区域重叠**：区域是"一块连续的东西"，两块**部分重叠**时图上看不出谁包着谁；
  框里**夹着非成员**更严重 —— 那个节点看起来"属于这一区"，是**语义错误**。
  完全包含（分区里再圈一块）是允许的。**这条是判失败，不自动缩框**：缩框不是盖住
  自己的成员就是把成员排除在外，两种都是在骗。实测它在真实使用里一次报出 20 条
  （折段把 3 个区域劈开了），并抓出过一处夹具里的真语义错。

### #10 区域标题：两条性质不同的失败共用一个 check

这一项是用户拿截图来问「这种块的 title 会溢出」之后加的 —— 当时**没有任何检查
在量区域标题**：一个 368px 的标题画在 324px 的可用宽度里，两头各冒出去 22px，
而报告一条都没报（标题宽度压根没进过任何尺寸链）。

现在尺寸链是**构造性**的：

```text
区域宽度（由成员节点定） → 断行 → 行数 → 标题带高度
```

所以前一类失败不该发生：

- 标题比区域宽 / 断行与尺寸对不上 / 标题块压到成员 → **脚本内部不一致**，
  **不给内容建议**（让它去“缩短标签”是白千）。
- 标题被断成 **超过 2 行** → **内容问题**，建议缩短标题或拆区域。

一个 check 里放两种性质的失败，`Issue` 的 docstring 里早就写明这是允许的
（文字溢出就是同一个情况）；关键是报告那句话说的是哪一种，而不是共用一个名字就混为一谈。

> **上限 2 行是判断，不是推导**（写在 `layout.REGION_TITLE_MAX_LINES` 上）：
> 标题带是用来给区域起个名字的，不是拿来放一段话的。它和节点那边
> 「标签超过最大断行档位就判失败」是同一类内容级问题。

### 为什么 #6 是“阻塞”而 #8 / #9 是“软项”

判据不是“难不难看”，而是**这句话说的是不是同一个东西**：

- #6 说的是“这条线穿过了那个**节点**” —— 节点在图上有语义，穿过它就是**读错**。
- #8 / #9 说的是“这条**线本身**画得不对” —— 语义没错，只是不好看（何况
  它已经有生成侧在主动避免）。

两类都可调参（加间距 → 空间富余 → 绕行/分道才推得开），只是**一个挡输出、一个不挡**。

### 为什么 #1 是"间隙 < 12px"而不是"重叠"

前作检查的是 `boxesOverlap(a, b, 4)` —— **容忍 4px 重叠**。但"看起来挤"和"重叠"是两回事：
两个框相距 2px 在视觉上就是糊在一起了，而它不报。所以这里检查的是**最小间隙**，
且默认阈值取 12px（这个数需要真实使用后校准，见下方"已知局限"）。

### 为什么 #5 是软阈值

**零交叉不是总能达到。** 边交叉最小化是 Sugiyama 里唯一不 trivial 的部分，
把它当硬门会导致：为了过门而把节点排成不可读的形状，或者干脆卡死。

它的真正作用不是"门"，是**仪表盘** —— 前作没有这个指标，所以层内排序质量差**只能靠人眼看出来**
（"这几根线绕得很奇怪"）。有了它，排序算法好不好是可观测的。

**报告必须给出交叉的是哪几条边**，只有计数没法定位问题。

### #3 和 #4 走不到自动调参

- **#3 文字溢出**：按 `diagram-spec.md` 的耦合方向（容器宽度由断行宽度算出），文字在构造上不可能溢出。
  所以它一旦报，说明**尺寸推导与实际落笔之间有不一致** —— 是脚本 bug，不是内容问题。报告必须这么说。
- **#4 越界**：未知 `kind` 或颜色不在板内，是规格写错了，改参数没用。

自动调参循环处理 **#1 / #2 / #5 / #6 / #8 / #9**（#3 / #4 / #7 / #10 走不到调参 ——
改参数对它们没有任何作用）。

### #1 和 #3 是“后置断言”，不是“内容体检”

坐标是从间距参数算出来的（`layout.py` 的 `assign_coordinates`），字号与容器宽度是同一份
`text_metrics` 量出来的。后果是：

| 校验 | 为什么在今天的推导下构造上不可能失败 |
| --- | --- |
| #1 元素间隙 | 同层节点恰好相距一个节点间距，跨层恰好相距一个层间距 |
| #3 文字溢出 | 容器宽度由断行宽度反推，两者同源 |

所以它们一旦报，报的是**脚本内部不一致**（推导与实际落笔不符），不是内容问题 ——
报告必须这么说，否则模型会去干“缩短标签”这件没用的事。

留着的意义是：以后加了分组折叠、或者换掉坐标推导方式时，这两条会立刻变成真实的门。

> **“它从来不报”不等于“间隙被量过了”。** 这一点必须写下来 —— 否则下一个人
> （或下一轮的我）会以为有一道实测防线在守着，而实际上那条路径今天是跑不到的。
> 同理，#1 对应的自动调参路径今天也**不会被触发**。

## 二、自动调参：由脚本完成，中间不经过模型

```text
layout(参数) → 校验 ──通过──→ 输出
                 │
                 ├─ 只有 #1/#2/#5 失败，且轮次未耗尽
                 │     → 对应参数按固定步长递增 → 重跑
                 │
                 └─ 轮次耗尽，或命中 #3/#4
                       → 出报告
```

### 谁在调这个参数（设计上必须钉死的一条）

**是脚本，不是模型。**

如果让模型读报告、判断"我该把 `nodeSeparation` 从 70 调成 90"，那和前作的病根是**同一件事** ——
只是把"模型猜坐标"换成了"模型猜间距"，换了个变量名：模型依然在做它不擅长的空间判断，
只是判断对象从每个节点的具体坐标退化成一个全局标量。风险小很多，但**没有归零**。

配套的两条设计：

1. **布局参数不出现在 schema 里**（见 `diagram-spec.md`）。规格里没有旋钮，模型就没有旋钮可拧。
   前作把 `layout.nodeSeparation` / `rankSeparation` 放在 schema 里，却**没有任何一处告诉模型去用它** ——
   既敞开着被误填，又没进修复动作。
2. **报告里不出现参数名。** 一旦报告写"建议调大 rankSeparation"，参数选择权就又回到模型手上了。

### 参数的选取规则（固定，不是判断）

| 失败的检查 | 动的参数 | 初始值 | 步长 | 上限 |
| --- | --- | --- | --- | --- |
| #1 间隙不足 | `nodeSeparation` | 70 | +20 | 4 轮 |
| #2 连线过短 | `rankSeparation` | 120 | +30 | 4 轮 |
| #5 交叉过多 | `barycenterRounds` | 4 | +4 | 12 |
| 同时多项 | 各自按上表递增 | — | — | — |

初值 **70 / 120** 直接取自前作 `layout.mjs` 里 Dagre 的默认值。

> **原则：别人失败经验里的具体数值（阈值、间距、比例）值得复用；他们的架构决策不值得复用。**
> 数是真实验证出来的，架构是假设出来的。前作被删了，但它踩过的这两个数不用重新猜。

## 三、报告该说什么

报告**只在脚本无法自动收敛时**出现，内容是固定的三段：

```text
1. 已尝试的参数探索（证明参数空间已经走过）
   例：节点间距 70 → 90 → 110 → 130，层间距 120 → 150 → 180（共 4 轮）

2. 仍然失败的项 + 具体位置
   例：3 处间隙不足：redis ↔ auth（4px）、db ↔ user-service（7px）、web ↔ auth（2px）

3. 只给内容层面的建议
   例：拆节点 / 缩短标签 / 降低 detail / 调整 rank 分层（**不是**"移进分组"—— 分组字段不产生效果，见 `diagram-spec.md`）
```

**必须包含第 1 段。** 不加的话，模型或人会立刻去建议"调一下间距" —— 而那段存在的意义就是
证明那条路已经走过了。这是一个措辞层面的约束，但它决定了整个循环会不会退化回前作。

**报告中绝不出现：** 参数名、"建议调大某某"、任何坐标。

### 命中 #3 / #4 时的报告措辞

| 命中 | 报告应说 | 不应说 |
| --- | --- | --- |
| #3 文字溢出 | "这是生成脚本的内部不一致（测量与落笔不符），不是你内容的问题" | "请缩短标签" —— 那是在让模型替脚本背锅 |
| #4 越界 | 列出越界的 `kind` 值 / 颜色值，以及色板里允许的取值 | "会用默认色代替" —— 那正是最危险的静默 fallback |

## 四、已知局限（写在这里，避免下次重新发现）

**阈值目前没有真实数据校准。** 侦察到的事实：

| 证据 | 值 |
| --- | --- |
| vault 里 Excalidraw 图 | 1 张（2026-07-30） |
| 最近 30 天 | 0 张 |

所以 12px / 24px / 交叉阈值都是**依据前作数值与常识设的起点**，不是实测出来的。

### 写测试时踩到的坑：改完代码，测试还在报旧值

`importlib` 按文件路径加载脚本时**会写 `__pycache__`**。用脚本做变异验证
（改坏源码 → 确认测试变红 → 还原）时，如果还原用的是 `shutil.copy`，还原后
文件的 mtime 可能**比 `.pyc` 还旧**，Python 就继续用旧字节码 ——
测试报的是**上一次变异的值**。

实测：源文件里写的是 `2.0`，加载出来是 `1.5`，两个用例一起红，看起来像
“还原没生效”。验证方式：直接加载模块把那行值打印出来，与源文件对比。

```bash
find . -name __pycache__ -type d -exec rm -rf {} +
```

**这条对变异验证的结论是有杀伤力的**：如果缓存脏了，“测试变红”可能来自上一次变异，
“还原后变绿”也可能是假绿 —— 于是整轮验证都在自欺。所以变异验证的前后都要清。

### 例外：交叉数这一条我改错过一次，量完就撤了（2026-09-14）

那天我想给 #5 按图型分岔：分层图阈值收到 **0**，理由写的是"分层图里 0 交叉是能做到的"。
量完 28 份规格 / 456 条边就撤了 —— 因为**#5 量的不是"线有没有撞在一起"**。

它量的是**相邻层之间的位置反序对**（层内 A 在 B 前面、下一层反了过来），
那是**层内排序质量的仪表盘**。同一批图里那张 43 条边的依赖图：**反序对 8、几何相交 0**
—— 路由把反序的那几条各自绕开了，肉眼一处交叉都没有。按 0 报的后果是：
在**一张看起来毫无交叉的图**上报 8 处，还建议"拆节点、调换两个节点的先后位置"，
让人去修一个眼睛看不见的东西。**这比不报更糟。**

两个口径必须分清，别再互相顶替：

| 口径 | 谁在量 | 量的是什么 | 实测（28 份规格 / 456 条边） |
| --- | --- | --- | --- |
| 层内反序对 | `crossing_pairs` → #5 | 层内排序质量（软阈值 边数÷2） | 0 ~ 8 |
| 几何相交 | `geometric_crossing_pairs` | **画出来的折线真的相交** | 全库 **3 处**，全在力导向/径向 |

所以「线不要遮挡线」今天在分层图上是 **0 违反**；而那 3 处都在两种"交叉属于形状本身"的
布局里（径向的兄弟节点绕着父节点排、力导向没有层可依）。
**几何相交目前没有独立的校验项** —— 这条记在这里，别再拿反序对顶替它。

真正在管间距的不是 12px，而是布局参数 `nodeSeparation = 70` —— 它决定同层节点至少
隔 70px。12px 只是在那之上的**地板**：参数被调得很小、或未来换了算法时它才会响。

**所以这轮校准的产出是"不改数，改说法"**：

- 12px / 24px **保持不动**，但不要把它们当成"我在控制间距"的手段 ——
  控制间距的是布局参数，这两个是保护网。
- 交叉数的软阈值同理：它**没报过** ≠ 它没用，而是还没遇到真会报警的图。
  网状图 14 条边里 4 处交叉，看着是合理密度，不该报 —— 方向是对的。
- **什么时候才该动这三个数**：出现一张"阈值没报、但人眼看着挤"的图。
  在那之前调它们只是在拟合这六张样本。

顺手量到两件值得记的事：

1. 六张图里最小的"非零间隙"都出现在**同层相邻节点之间**，值就等于 `nodeSeparation`
   —— 说明间距是布局参数的直接产物，中间没有东西在偷偷压缩它。
2. 最短的边都在 `rankSeparation` 决定的方向上（跨层边），值 ≈ `rankSeparation`
   （120~171，视绕行而定）—— 同一件事在主轴上的版本。

改动只需动本文件与 `text_metrics.py` / 布局脚本里的常量，不涉及架构。

## 五、这四条校验保证不了什么

不重叠、连线够长、颜色在板内、无溢出 —— 这四条能保证图**不出错**，
但保证不了图**好看、结构一眼能看懂**。而那恰恰是当初提这个需求时最在意的体验。

所以验收不能只看校验全绿。**最低要求：生成几张真实的图，用眼睛看一遍。**
校验脚本能说“没有一处是坏的”，说不了“这张图讲清楚了”—— 这两件事的强弱差得远。

这条不是口号：Wave 4 完成后必须真的看过图、并把结果记进上面的校准表，才算验收。

## 六、这两个断言的前提，什么时候会失效

**#1 元素间隙**与 **#3 文字溢出**之所以“构造上不可能失败”，前提是**尺寸只有一个来源**：
容器宽度来自断行宽度，断行宽度来自 `text_metrics`。

> **这个前提已经被触发过一次，机制按预期工作了。** 加入节点形状（`shapes.py`）时，
> 包围盒不再等于文字尺寸 —— 菱形里能放字的只有内接矩形（半个包围盒）、
> 椭圆是内接矩形的 √2 倍。于是 `TestSizeSourcePremise` **立刻失败**，
> 而它失败的消息写的就是“尺寸来源变了，先回来改这一节，再去改代码”。
> 实际做法也就是这个：**先改完本节，再改测试。**
>
> 更新后的尺寸链（每一步都由本 skill 自己算，所以“单一来源”仍然成立）：
>
> ```text
> 文字 → text_metrics.measure（断行、容器宽高）
>      → shapes.box_for（形状包围盒）
>      → layout.assign_coordinates（坐标）
> ```
>
> 现在还多了一步同样的"自己算"：**× 强调的尺寸倍数与字号步数**（§11/§14），
> 见 `layout.boxes_from_spec`。它仍然是我们自己算的，所以单一来源没被破坏。

### 第二次触发：图标（`icons.py`）—— 这次**真的**进来了一个外部来源

> **“尺寸只有一个来源”这个前提，从加入图标这一版起不再成立。**
>
> 图标的宽高来自那个 `.excalidrawlib` 文件 —— 不是我们量的。这是第一次有
> **外部数据直接决定画出来的东西有多大**（前面所有步骤都是我们自己算的）。
>
> 更新后的尺寸链，最后一项带来源标注：
>
> ```text
> 文字 → text_metrics.measure
>      → shapes.box_for
>      → + 图标尺寸（来自素材库文件，**外部**）
>      → layout.assign_coordinates
> ```
>
> 于是 #1/#3 的性质变了：#3「文字溢出」仍然是后置断言（文字那一半还是我们自己算的），
> 但 **#1「元素间隙」开始可能真的报出来了** —— 盒子被图标撑大之后，同层节点可能挤在一起。
> 这不是 bug，是这个断言第一次真的在干活。
>
> ⚠ 还有一件值得记的事：**`TestSizeSourcePremise` 这次没有自己失败**，
> 因为没有任何 fixture 用了图标 —— 一个只在“用到新功能时”才显现的前提变化，
> 现有测试是看不见的。所以这次是**主动**去改的，而不是等它响。
> 教训：新功能引入新来源时，别等测试报警，直接去看第六节这一节。

### 第三个尺寸来源：渲染器本身

**如果哪天引入真正的“外部”尺寸来源（尺寸来自我们控制不了的地方），这个前提才真会失效。** 现在剩两类：

| 外部来源 | 现状 | 后果 |
| --- | --- | --- |
| **渲染器**（Excalidraw 按真实字体重新断行） | 已实测，见下一节 | #1/#3 退化为“真实的门” |
| **图标库**（库里的图标自带固有宽高） | **已实现**（`icons.py`） | 盒子为图标加宽之后，同层节点可能挤到一起 —— 那时 #1 会真的报出来 |

图标这个来源落地之后 **#1 仍然没有触发过**（实测最小间隙 70~170px，见上面的校准复盘），
说明"盒子被撑大"的幅度还远没有撞到地板。它会在什么情况下真的响，目前**还不知道** ——
这正是校准复盘里那条"还没有被现实检验过"的具体含义。

注意区分：**“多算了一步”不算外部来源**（形状就属于这种，依旧是我们自己算的），
**“尺寸来自别人给的东西”才算**（图标就是这种）。

这条**不靠“到时候记得回来检查”**。这个前提由校验守着：它一旦不成立，校验会红 —— 而那**不是**“快改这条校验”的意思，
而是“尺寸来源变了，先回来改这一节，再去改代码”。

### 第二个尺寸来源：渲染器本身

上面那条断言只在**我们自己的流水线内部**成立 —— 它保证“尺寸在脚本里只有一个来源”。
但它管不了另一件事：

> 容器绑定的文字（`containerId` 非空）在 Excalidraw 里是**由 Excalidraw 自己按真实字体
> 重新断行**的。`text_metrics` 的字符宽度表是**推算**（Helvetica 实测 + 向上取整），不是同一个计算。

所以渲染器是**第二个尺寸来源**，而且不在我们控制之内。如果它断行比我们算的多出一行，
Excalidraw 会把容器撑高，布局随之偏移 —— 间隙保证也就不再成立。

这一条**无法靠脚本自查**：本 skill 的输出是 JSON，不是像素。只可能通过
**看一张真实渲染的图**发现。这也是为什么第五节把“用眼睛看一遍”写成硬性验收条件，
而不是可选项。

减轻手段（不是闭合）：`emit_excalidraw.py` 把断行结果直接写成文字元素里的显式换行，
而不是把一长串丢给 Excalidraw 去折 —— 少给渲染器一点自由发挥的空间。

### 已实测（2026-09-12）：这个风险在现有样本上**没有被实现**

方法：用浏览器加载**真实的 `@excalidraw/excalidraw` 包**（与 excalidraw.com 同一份代码），
`exportToSvg()` 渲染我们的场景，再把渲染结果挂进 DOM 量每个文字块的真实 bbox。

| 样本 | 我的预测内容宽 | Excalidraw 实宽 | 行数 |
| --- | --- | --- | --- |
| 10 个全角字 | 160 | **160** | 1（一致） |
| 17 字中文长标题 | 384（容量） | 272 | 1（一致） |
| `ABCDEFGHIJ`（宽大写） | 160（容量） | 101 | 1（一致） |
| `abcdefghijklmnop` | 160（容量） | 125 | 1（一致） |
| `订单服务 Order Service v2.1` | 256（容量） | 202 | 1（一致） |
| 两张真实图里的 14 个文字块 | — | 全部 ≤ 预测 | 全部 1 行 |

**两个结论：**

1. **CJK 精确**：Excalidraw 渲染的全角字符前进宽度就是 1.0 em（10 个字量出 160px @16px）。
2. **拉丁偏宽的那一侧是安全的**：因为我改成向上取整，实测总是 ≤ 预测，
   Excalidraw 不需要额外换行 → 容器不会被撑高。

### 已实测（第二次，2026-09-12）：**整条流水线**在真实 excalidraw.com 里渲染正确

上一次验的是"文字宽度算得准不准"（数据在上两节）。这一次验的是**整张图**：
把生成的 `.excalidraw` 用 `scripts/open_excalidraw_com.py` 在**官方 excalidraw.com** 里打开
（没有模拟、没有自己写的渲染器），逐项核对。

样本：一张六节点的架构图，刻意把新加的能力都用上 —— 标题、`emphasis: primary`、
椭圆 / 圆柱 / 胶囊三种形状、**两个嵌入的素材库图标**、带标签的虚线边、多个分散锚点。

| 验的东西 | 结果 |
| --- | --- |
| 标题 | ✓ 渲染在内容上方居中 |
| `emphasis: primary` | ✓ 填充明显更深、描边更粗 |
| 椭圆 / 圆柱（含顶盖）/ 胶囊 | ✓ 形状都对 |
| **嵌入的素材库图标** | ✓ 在官方应用里正常显示（这条同时验证了复制元素时的 id 与引用重映射） |
| 箭头锚点分散 | ✓ 同一节点上的几条边从不同落点出发 |
| 虚线 + 边标签 | ✓ 标签落在线的外侧，没有压线 |
| 遮挡 / 溢出 | ✓ 都没有 |

**这条结论的意义**：在此之前，"图看起来对不对"全部依赖我们自己的 PIL 预览
（`dev-tools/preview.py`）—— 它是自研的、只是近似，而且**已经骗过我一次**
（只认得矩形，椭圆节点直接不画还不吭声）。现在"能在官方应用里打开并核对"
这条路径有了，目视结论才有第二个来源。

**边界**：这是**一张**图的逐项目视核对，不是自动化的逐元素比对；
形状的**手绘质感**与字体仍是近似 —— 预览验证得了布局与结构，验证不了这两样。

### 这次核对之后又抓到一类"预览与真实渲染不一致"

用户看着真实渲染提出"为什么图标这么靠左、和文本间距是不是太大了"。查下去发现：

**绑定到容器的文字，官方会把它水平居中于容器并重算位置 —— 我们写进 `.excalidraw`
的 x 只影响自己的预览。** 两边的约定不一致时，预览会画出一张**真实渲染里不存在**的图。

具体经过：第一版按"图标贴左内边距、文字在剩余区域居中"算，写出的文本中心比节点中心
偏右 19px（173.6 vs 154.7）。预览照这个画，看起来正常；真实渲染把它拉回中心，
于是成了"文字居中、图标丢在左边"。

**这类不一致和前面那几种不一样**：以前是"算错了"或"没画"，这次是**两边对同一个字段的
语义理解不同**。所以对策也不同 —— 不是改渲染器，而是把**官方的约定**写死进自己的算法
（文字一律摆在容器中心），并将其作为结构性不变量：标题盒偏出所属节点就会被判为文字溢出。
现在预览和真实渲染在这件事上是一致的。

另一个推论也值得记：既然文字位置不在我们手里，"图标 + 文字整体居中"**在绑定前提下
做不到**。能做的只有"图标紧贴可见文字的左边"。**验的是可见文字的边，不是文字盒子那条边** ——
按盒子对齐会让间距凭空多一截（这正是用户说的"间距太大"）。

> ⚠️ **这条推论已被下面的 2026-09-16 条目修正**：绑定确实居中不了（仍成立），
> 但"做不到就忍了"这个结论错了 —— 带图标的节点改成**自由文字**就能精确居中。
> 当时否掉解绑的理由是"拖动时文字会留在原地"，那是没考虑**分组**。

### 2026-09-16：图标节点解绑让"整组居中"，卡片改成平分宽度（用户反馈驱动）

两个真问题都不是靠调数值解决的，而是换了做法：

**一、图标 + 文字整组居中。** 用户拿着一张大图问"图标和文本，不应该居中吗？"。
用官方导出量出来：绑定文字被渲染器钉在容器中心，我们只能把图标贴在可见文字左边，
整组重心**偏左 (图标宽 + 间隔)/2 = 19px**（实测；300px 宽节点上 6%）。
做法：**带图标的节点，标签解绑**（`containerId: None`，自由文字位置由我们定），
形状 / 图标 / 标签**同挂一个 groupId** 补偿编辑器里的拖动。
实测确认：自由文字写 145.6，官方导出就是 145.6（不被重算）。
代价已写明：改标签不会自动重排 —— 所以**只给带图标的节点用**。

连带改了两处判据/接口：

- "有没有 groupIds"这个认节点的旧判据作废，改成**按 id**（`node-<nid>`，`<nid>` 从
  `title-<nid>` 反推）—— 带图标的节点形状自己现在也挂着组号。
- `test_diagram_fixtures.measure` 的 `labels` 那一桶显式排除 `title-` / `detail-`：
  图标节点的标签解绑后会落进"自由文字"，而它们其实在节点里面。

**二、卡片太窄、行数太多。** 用户原话"这换了那么多行，就不能框宽一点吗，还显的大气"。
旧做法是卡片按**内容宽**缩，窄条里挤 5~7 行。现在**行内平分内容宽**
（上限 `CARD_MAX_W = 480`；宽度不够平分时退回内容宽）—— 卡片撑成栅格、
行数降下来（实测样张：同一段内容 7 行 → 3 行）。

**三、顺带定下来的两个事实（都实测，不是推测）：**

- 官方导出的**倍率两条路不一样**：PNG 走 `config.scale`，SVG 走
  `appState.exportScale`；PNG 传 `appState.exportScale` 会被**默默忽略**
  （出来的是 1 倍图）。留白**两条路都在 `config.padding`** —— `appState.exportPadding`
  被官方包**默默忽略**（实测：设 32 与不设，PNG 都是 3282×1895；改成 `config.padding: 32`
  才是 3410×2023，正好多 2×32 图内单位）。而官方两个默认不一样：
  **PNG 默认 0（贴边）、SVG 默认 10** —— 不显式传就会贴着边框。
- `@excalidraw/utils` 0.1.4 起**只发 ESM、无 UMD**，且签名是 `{ data, config }`
  两段式（传错就是 `Cannot read properties of undefined (reading 'elements')`）。

**四、验证手段升级：** 新增 `dev-tools/export_excalidraw.py` —— 用**官方**
`@excalidraw/utils` 的 `exportToBlob`/`exportToSvg` 在无头 Chrome 里出 PNG/SVG。
这是**渲染器自己画的图**，不再依赖我们的模型，所以上面三条都能拿它复核；
但"好不好看、讲没讲清楚"仍然只能人看（三档声明不变）。

### 2026-09-16（当晚第二次）：说明文字一直在窄列里断行，而且根本没被画出来

用户拿另一张局部截图（同一批节点）再说了一次："如果一个框中文本较多，直接将框设置的
稍微宽一些，不要一直换行换行的，很难受"。拿官方导出复核后是两个独立问题，**都不是调参数能解决的**：

**问题一：说明列比框窄一大截。** `measure()` 里两处叠加：

1. **档位只看标题**（旧注释写着"detail 是次要行，宽不够时跟着断行，不反过来撑大容器"）；
2. **说明按标题的单位数断行** —— 同一串单位数在 12px 下只画出 16px 的 75%，
   于是 384px 宽的框里，说明只占 120px（且长标识符会被 `_force_break` 拦腰截断）。

改法：档位由 **max(标题单位数, 说明折算到节点字号的单位数)** 定；说明断行宽度 =
`break_units × 节点字号 / 说明字号`，两者共用同一条**像素**宽度。实测（同一批真实节点）：

| 节点 | 旧列宽 | 新列宽 | 旧行数 | 新行数 |
| --- | --- | --- | --- | --- |
| 死租约接管 + 双 CAS | 120px | 384px | 8 | **3** |
| 任务级 max_attempts | 120px | 384px | 5 | **2** |
| IR / 索引 / 资产清理 | 120px | 384px | 6 | **2** |
| CapabilityRouter + 容量 | 192px | 384px | 4 | **2** |

顺手把标题/说明也都换成**均衡断行**（同行数挑最均匀的一版）：贪心断行的末行出现过
单字（"…三项都匹配才接" / "受"），与卡片那边同一个毛病。

**问题二（更严重）：说明在真实渲染里根本没被画出来。**
场景 JSON 里 `detail-*` 元素齐全、位置也对，但官方导出只画标题。原因：
**一个容器只能有一个绑定文字**，Excalidraw 取第一个（标题），第二个（说明）不渲染。
我们自己的预览会把两个都画出来 —— 又一条"预览与真实渲染不一致"，而且这条安静了很久：
`detail` 从实现起就没在真实 Excalidraw 里出现过，测试只查 JSON（元素在、引用对）就全绿了。

修法：有说明的节点，**标题与说明一起自由放置**（`containerId: None`）+ 与形状/图标同组
（理由：两个绑定文字还会互相压住 —— 标题被拉回容器中心，说明按我们算的位置落在旁边）。
新增两条测试：`test_detail_produces_a_second_text`（断言不再绑定）+
`test_no_container_has_two_bound_texts`（**场景级不变量**，把这类错误从“只能渲染发现”
变成“提交前就拦住”）。

**问题三：行首出现标点。** 修完前两条后新截图里第二行以「；」开头 —— 中文排印不允许
（避头尾/禁则）。实现放在 `_tokens` 后面：不能落行首的标点黏到前一块、不能落行尾的引号
黏到后一块（黏成不可拆 token，**宽度不变**，所以尺寸链不受影响）。

**问题四（上一条修复自己引入的）：图标越出左边框。** 用户接着发来一张带红框的截图：
图标跑到框外面去了。根因是 `emit_excalidraw.node_elements` 里算"可见文字宽度"时：

```python
visible_w = max(标题行 + 说明行) × text.font_size   # ← 说明行也被乘了 16px（它实际是 12px）
```

说明行宽在问题一的修复里变宽了（同一批行数 8→2），这个 33% 的高估就顶破了框宽，
图标被推到边框外面。复算那个真实节点：旧公式可见宽 432px（框只有 428px）
→ 图标左边界 **−30.3px**（正好是截图里越界的量）；按每桶自己的字号算之后是 **+23.7px**。

**同一个问题还错了一次方向**：第一版修法是在 emit 里给图标加一道**钳位**
（`icon_left = max(算出值, 框左边 + 4)`）—— 溢出确实没了，但图标被推到文字底下，
看起来像"这个节点没有图标"。用户当场指出："你这相当于溢出的直接不给icon了……
你应该考虑的是将框弄的自动适配宽度而不是删除icon"。

**正确的方向是让框适配内容**，而不是让图标将就框：`layout.boxes_from_spec` 里加上下限
`宽 ≥ 内边距×2 + 图标宽 + 间隔 + 可见文字宽`，于是图标的位置算出来**必定**在框内，
不需要任何钳位。教训：**钳位是在掩盖约束冲突，不是在解决它** ——
位置放不下时，该改的是尺寸链上游，不是把元素挪到不显眼的地方。

教训很具体：**"可见宽度"这种跨字号的量必须按桶分别算**。新增两条测试：
`test_icon_stays_inside_even_with_a_long_detail`（同时卡"无说明"与"长说明"，只测前者是漏的）
与 `test_visible_width_uses_the_detail_own_font_size`（说明长短不同时图标↔文字间隔应当一样）。
两条在旧公式下都会失败 —— 已复算确认。

**这一轮的方法论收获：** 四个问题里有两个（说明不渲染、行首标点）**只有真渲染才看得见**，
自研预览一个都抓不到；而第四个是"改完一处、另一个量跟着错"的典型（跨字号乘法），
只有把不变量写成测试才拦得住。官方导出工具是前一天才接的，接上的第二天就抓到了第一条 ——
这就是"第二档要做成渲染器自己的图"的价值，比再多写十条 JSON 断言都值。

### 2026-09-16（当晚第三次）：图标风格不一致 —— 素材原风格被照抄进来了

用户指着一张图说"图标风格不一致啊"：同一张图里几个图标是**粗黑实心**，另几个是
**细线描边**。根因不在选型，在 `icons.place()`：

```python
if original.get("strokeWidth"):
    new["strokeWidth"] = round(original["strokeWidth"] * scale, 2)   # 照抄 + 按缩放改
```

两件事同时错：

1. **照抄素材的描边粗细与颜色**：素材是不同作者做的，同一个库里都能出现
   `strokeWidth: 1` 与 `: 4` 混用，颜色有的纯黑、有的深灰 —— 一张图里自然两套语言；
2. **按 `scale` 缩放描边**：看着"更忠实素材"，实际让 22px 的小图标与 44px 的大图标
   粗细不同 —— 又是一层不一致。

改法：`place()` 落笔时统一 —— 描边一律 `ICON_STROKE_WIDTH = 2.0`（与内置 sigil 同一档）、
颜色一律用**所属节点自己的描边色**（图标与它所在的框同色）、粗糙度统一、填充保留
"实心/空心"但换成同一个墨色；**不再按 scale 改描边**。
实测同一张图内混用内置 sigil 与素材库图标：四个图标的 `strokeWidth / strokeColor /
roughness / fillStyle` 完全相同，墨迹高都恰好 36.0px（节点高的 39%）。

**实心也要统一**（第一版只改了描边，结果"整块填黑"的图标依旧突兀）：大块实心
（面积 > 图标包围盒的 25%，`ICON_SOLID_MAX_SHARE`）一律转空心，**小面积实心保留**
—— 那是设计细节（点、箭头头部；我们自己的 `queue` 就是三个点），一刀切会把点削成圈。
阈值是判断，不是推导，写在一个常数上。

**颜色：第一版一刀切压单色，又被用户指出来**（原话："品牌 logo 会被压成单色……
这个能优化吗，有时候图标带颜色也挺好看的"）。改成按素材性质分两种待遇：

- **多色素材**（≥2 个可见颜色）= 作品 → **保留配色**。但加了可读性约束：
  每个颜色与画布的对比度须 ≥ 3:1（WCAG 非文本图形），不够就**保留色相按 10% 一档往墨色混**，
  混到够为止 —— 实测某云厂商的橙（对比度 2.04）被压暗后到 3.37，仍是橙色但读得清；
  同一个 logo 里的深蓝（12.96）因为已经够清楚，原样不动。
- **单色素材** = 线描图形 → 换成节点墨色（与图纸同一套语言）。

策略开关是新增的第五组样式轴 `style.icons`：`auto`（默认）/ `ink`（严格单色）/ `native`
（原样保留，不管对比度）。未知取值照样报错 —— 与未知 `kind` 同一条规矩。
"压到可读"的实现落在 `palette.readable_on`（颜色与对比度的唯一真相源），
`icons.py` 惰性调用它，不在自己家再写一份混色。

**代价（剩下的）**：实心风格图标会变空心；`native` 档下品牌色可能读不清 ——
后者是显式选择，文档里写明后果自负。

**方法论**：这条和前面三条是同一类 ——"把第三方内容原样搬进来"本身就是 bug 源。
凡是**外部来源**（素材库、渲染器、字体），都要问一句"它的哪些属性必须被我们改写"。

### 2026-09-17：draw.io 官方命令行导出**首次实测**（本机装上了 draw.io）

之前这条一直是"未实测"（开发机没装桌面版，文档里写着"不作为基线能力"）。用户装上之后
直接实测，一次通过：`-x -f png -o out.png -s 2` 出图正确，PNG 1778×892（场景 889×446 @2x），
标题 / 节点 / 带标签箭头 / 圆柱 / 卡片的粗体与项目符号全部正常。

顺带量出三条**容易踩的坑**，都按官方 `--help` 核对过：

1. **`--crop` 只对 PDF 有效**（官方："crops PDF to diagram size"）。对 PNG 传它**静默无效** ——
   实测产物与不加时**字节完全相同**。工具改成遇到这种组合直接报错（"看着成功其实没生效"
   是本项目最不能接受的失败模式）。
2. **`-t/--transparent` 常常看不出效果**：它本身有效（SVG 里确实成了 `background: transparent`），
   但去不掉**图里那块底色** —— 我们 emit 时刻意写了 `background="…"`（不写底色导出不稳定）。
   工具在回执里提示这件事，不让你拿到"以为透明其实不透明"的图。
3. **`-b N` 每边只加 0.75×N 图内单位**（实测 16→12 / 32→24 / 64→48，72dpi 换算）。
   工具的 `--border` 替用户换算过，写 48 就是每边 48。
4. **但官方把 border 分得不均**（实测，scale 2）：总量对（每轴 +2B 图内单位），落地却是
   左/上 ≈1.31×B、右/下 ≈0.69×B —— `--border 16/32/64` 的右/下分别只有 11.5/22/43.5
   图内单位。挤不挤看的是**最紧的一边**，所以工具默认 **48**（最紧 ≈33 图内单位，
   ≈1.4 × 图内内边距 22~24），而不是跟着官方默认 0 走。

另有一个交付上有用的发现：**`-e/--embed`** 把图嵌进产物（PNG/SVG/PDF），导出的图片
还能在 draw.io 里打开继续改（实测 SVG 里能搜到 `mxGraphModel`）。

**方法论**：这次实测再一次说明"没实测过的能力不要在文档里写成能力"。写"未实测"是对的
（没假装），但**装着机器就该去实测** —— 实测成本只有几分钟，换来的是三条真事实。

### 这个结论的**边界**（别当成已经穷尽）

- 样本是 2 张图 + 5 个边界用例。不是穷尽测试。
- `fontFamily` 固定为 2（normal）。**换字体族的话这条结论作废** —— 不同字体的前进宽度差别很大。
- 浏览器里 `document.fonts` 是空的（Excalidraw 自带字体没加载），实测值来自系统
  Helvetica 类的回退字体。它在 macOS 上与真实观感一致，但在别的平台上未必。
- **反过来说**：这条结论真正成立的原因是“宁可估宽”这个不对称选择，而不是“我们算得准”。
  如果哪天有人为了让框更紧而把系数调小，这个风险会立刻回来。
