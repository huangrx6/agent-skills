# 布局体系：现状、缺口、参考标准、路线

这份文档回答一个问题：**布局 / 信息层级 / 留白 / 图形语言 / 图表 这五块，我们
现在是什么状态，该借谁的规则，以及哪些是"加一层"、哪些必须"重构"。**

先给结论，再给证据：

> **不需要重构。** 规范里最核心的那条原则 —— "不要让 LLM 决定 x=327，LLM 只决定
> 意图，程序负责精确布局" —— 本仓库**从第一版起就是那样做的**：spec 里根本没有
> x/y（`validate_spec.py` 的 `COORD_FIELDS` 把 `x`/`y`/`dx`/`dy`/`rot`/`width`/
> `height` 直接判错），坐标、字号、间距全部由脚本派生。
>
> 缺的不是"约束系统"，而是**判断一页好不好的那几把尺子**（焦点评分、间距体系、
> 图形参数、图表规则）。那些是**加法**，不是重构。

## 一、现状：布局到底怎么做的（实测，不是印象）

| 层 | 现在是什么 | 在哪 |
| --- | --- | --- |
| 画布 | **1600×900** 固定；`PAD_X/PAD_Y = 84/132`；页脚 52+24；正文带 132→824（占高度 77%） | `render.py` 的几何常量（**唯一来源**） |
| 版式 | **7 种 `type`**，每种是 `render.py` 里一个手写分支（`title` / `content-text` / `content-image` / `two-column` / `timeline` / `chart` / `end`） | `render.py` 699–781 |
| 字号 | 每个风格一套 `type` 阶梯（cover/subtitle/bullet/colTitle/…），外加 `bullet_tier()` **按条目数自动选小一档** | `style.json` 的 `type` + `render.py:102` |
| 间距 | **散在各 skin.css 里的手写值**，没有令牌、没有 ramp | `styles/*/skin.css` |
| 硬约束 | 越界 / 重叠 / 文字溢出 / 图被放大 / 图表成比例 —— 全部**阻塞**，靠真浏览器实测 | `check.py`（8 条） |
| 试排 | `fit.py` 把候选版式与各条目数档位摆进同一份产物渲一次、量一次，报实测溢出与占比 | `fit.py` |
| 层级/焦点/密度 | 刚加：文本预算 / 视觉焦点 / 内容密度 —— **提示级** | `hierarchy.py` |

**两处值得点名的发现：**

1. **`bullet_tier()` 是"缩字号第一"**：条目一多就自动选小档字号。规范第 12 条明确说
   "**绝对不要第一步缩字号**"，正确顺序是 精简 → 拆信息 → 换版式 → 拆页 → 最后才缩。
   现在 `hierarchy.py` 的预算提示里把**修复顺序**直接写进报错，等于把这条规矩补上；
   但 `bullet_tier()` 本身还在（它是"自动兜底"，不是"第一手段"）—— 见路线图阶段 3。
2. **我们的版式稳定产出明确的视觉焦点**：实测 demo 与压测 deck 每一页的"第一焦点
   领先第二名"都是 **90%+**（阈值取 25%）。这不是偶然 —— 标题永远是最大的文字，
   图/图表永远是最大的一块面积。所以焦点检查只在真出问题时才响。

## 二、五块 × 参考标准 × 我们缺什么

| 块 | 该借谁 | 我们已经有的 | 缺的 | 性质 |
| --- | --- | --- | --- | --- |
| **布局** | Fluent 2 的 Grid/Regions + Figma Auto Layout 的父子参数模型 | 固定画布 + 7 版式 + 实测校验 | 12 列网格、区域语义（header/content/aside/footer）、版式族 × 变体 | 加法 |
| **信息层级** | Fluent Typography + IBCS 的 Message 优先 | 风格级字号阶梯 + **刚加的**优先/焦点权重 | 显式 `priority` 字段（1~5）映射到字号/字重/明度/面积 | 加法 |
| **留白** | Fluent Spacing ramp + Auto Layout 的 padding/gap | 手写间距值（散在 CSS 里） | **间距令牌** + 关系规则（段内 < 模块内 < 模块间 < 章节间） | 加法（但要改 8 套 skin） |
| **图形语言** | Design Tokens（Fluent / Atlassian） | 每套风格自己的装饰（`decor` / `texture` 块） | 8 个形状参数（圆角/描边/阴影/表面/线型/几何/装饰密度/图标） | 加法 |
| **图表** | **IBCS 2.0 + ISO 24896:2026** + AntV | HTML 与 PPTX 都去掉了值轴、网格线与图例，数值标签外置 | 图表类型决策树、语义化配色（actual/plan/forecast）、标题即结论 | 加法 |

**参考体系的一条条要点**（都是公开可查的成熟约定，不是我们的发明）：

- **Fluent 2** 把 Layout 拆成 Grid / Spacing / Alignment / Regions / Baseline，
  并明确采用一致的 spacing ramp；它指出 **12 列**是常见且灵活的网格结构，
  Spacing 以 **4px 体系**为基础。
- **Figma Auto Layout** 值得借的是**它的实现逻辑**：父容器定义 direction / padding /
  gap / alignment / resizing，子元素内容变化时**自动重排**，而不是给每个元素写死坐标。
  —— 这正是我们 `fit.py` 在做的事（试排 + 实测），只是我们还没有"重排"这一步。
- **Design Tokens**（Fluent / Atlassian 都在用）：不要到处硬编码 `24px` / `#fff` /
  `radius=8`，先定义 Global Token，再定义带语义的 Alias Token。**我们的颜色与字号
  已经是这个结构**（`style.json` 里 `colorSets` + `type` 阶梯 + `fonts`），
  缺的是 **spacing 与 shape 两类令牌**。
- **IBCS** 是专门针对 reports / presentations / dashboards 的视觉沟通规则，
  其 §IBCS Message 原则要求标题传达**结论**而不是数据集名；
  时间序列横向排列、结构比较纵向排列；优先柱 / 条 / 线；
  标签尽量直接集成到图表里，**减少无意义的图例、坐标轴与网格线**
  （这几条我们在 HTML 与 PPTX 两侧都已经做了）。
  **ISO 24896** 是基于 IBCS 原则发布的商业报告视觉符号国际标准。

## 三、目标架构：照着规范长什么样

规范给的架构是对的，而且**我们已经在它的下半段**：

```text
内容 → 语义解析 → 页面类型判断 → 信息层级 → Layout Intent
     → 约束求解 → 视觉令牌 → 排版 → 视觉评分 → 自动修复 → 最终产物
      └────── 现在缺的是这一段 ──────┘  └── 后面这段我们已经有了 ──┘
```

具体该补的四层：

### 层 1：画布与安全区（规范第 3 条）

内部统一画布，不让业务代码碰 PPT 坐标。推荐**内部用比例（0~1）而不是像素** ——
因为要换画幅（16:9 / 4:3 / A4）时，比例只需重新映射一次。

```text
画布 1600×900（= 现在的值，不动）
安全区 左右上各 5%、下 8%（页脚要占位）→ 内容只出现在这 90%×77% 里
```

我们现在的 `PAD_X=84`（5.25%）、`PAD_Y=132`（14.7%）已经在安全区之内，
所以**这一层是"把已有常量命名成安全区"**，不是重算。

### 层 2：12 列网格（规范第 4 条）

```text
Margin 96 / Columns 12 / Gutter 24
元素宽度只许取整列：2 / 3 / 4 / 5 / 6 / 8 / 12 列
不允许 5.37 列
```

我们现在的 `content-image` 是 640px 图 + 820px 文，**折算下来是 5 列 / 7 列**，
本来就落在整列上 —— 所以这一层也是**把已有布局登记成网格坐标**，
好让新变体（左文右图 / 跨栏 / 出血）有共同的尺子。

### 层 3：区域语义（规范第 5 条）

```text
HEADER（标题区）/ BODY（正文区）/ ASIDE（图或图表）/ FOOTER（页脚）
```

**LLM 只输出 `{page_type, regions, priority}`，不输出坐标**；坐标由 Region Resolver
算。我们现在是"LLM 选 `type`，`render.py` 算坐标" —— 差的是**版式族 × 变体**这一层：

```text
page_type = content-image            ← 有限（7 种）
layout_variant = left_40 | left_50 | right_40 | full_bleed | overlap | editorial
composition = symmetric | asymmetric
visual_weight = high | low
```

这样既不会乱（页面类型有限），又不会每页一样（变体多）。这一层是**加法**，
但需要给 `render.py` 引入"变体表"，不是重写分支。

### 层 4：评分引擎（规范第 20 条）

规范给的权重表可以直接用。**但必须分清哪些能测、哪些是判断**：

| 项 | 权重 | 我们能不能测 | 现状 |
| --- | --- | --- | --- |
| 越界 / 重叠 | **硬约束** | ✓ 能测 | `check.py` 已阻塞 |
| 文本溢出 | **硬约束** | ✓ 能测 | `check.py` 已阻塞 |
| Grid 对齐 | 15 | ✓ 能测（元素左边缘是否吸附到列） | **缺** |
| 信息层级 | 15 | ✓ 半能测（焦点权重差距） | `hierarchy.py` 已做 |
| 留白 | 15 | ✓ 能测（密度占比） | `hierarchy.py` 已做 |
| 视觉焦点 | 10 | ✓ 能测 | `hierarchy.py` 已做 |
| 平衡度 | 10 | △ 能测（左右/上下质量分布） | **缺** |
| 内容密度 | 10 | ✓ 能测 | `hierarchy.py` 已做 |
| Style 一致性 | 10 | ✓ 能测（一套 deck 内的颜色/字号/间距是否来自同一风格） | 结构上天然成立 |
| 字号可读性 | 10 | ✓ 能测（字号 ≥ 门槛） | `check.py` 部分 |
| 装饰克制度 | 5 | △ 能测（装饰面积占比） | **缺** |

所以"评分引擎"不是从零写 —— **先把已有测项汇总成一个分数**，再补对齐 / 平衡 /
装饰这三项。低于阈值触发修复引擎（规范第 22 条），修复顺序**必须是**：

```text
1 删装饰 → 2 缩文字 → 3 调 gap → 4 调 padding → 5 改区域比例
→ 6 换版式变体 → 7 缩图 → 8 拆内容 → 9 拆成两页 → 最后才允许缩字号
```

这条顺序现在已经写进 `hierarchy.py` 的报错文本里（人唯一一定会读的那段字）✓

## 四、硬约束 / 软约束必须分开（规范第 21 条）

**这一条我们已经做到了**，而且方式正是规范说的那样：

| | 谁 | 失败怎么办 |
| --- | --- | --- |
| **硬约束**（越界 / 重叠 / 文字溢出 / 字号过小 / 图被放大 / 图表裁标签） | `check.py` **阻塞**（退出 1） | 必须重排。`deliver.py` 在 check 失败时直接中止 —— "把一份已知有问题的 deck 做成五种格式只是把问题复制五份" |
| **软约束**（焦点 / 密度 / 预算 / 对齐 / 平衡 / 风格一致） | `hierarchy.py` **提示**（永远退出 0） | 用于评分与建议。做成阻塞的话第一份正常的 deck 就被挡住，然后所有人开始忽略检查 |

## 五、路线图：分四步，标清性质与风险

| 阶段 | 做什么 | 性质 | 风险 | 依赖 |
| --- | --- | --- | --- | --- |
| **1（本轮已做）** | 文本预算 + 视觉焦点 + 密度 → 提示；修复顺序写进报错 | **加法** | 低（不改渲染） | — |
| **2** | **间距令牌**：`style.json` 加 `spacing`（8 档 ramp）+ 关系规则（段内 < 模块内 < 模块间 < 章节间）；skin 里的手写值换成令牌；加一条"间距必须来自 ramp"的检查 | 加法，**但要动 8 套 skin.css** | **中** —— 改了间距就改了全部产物的观感，必须逐套看图对比 | 阶段 1 |
| **3** | **版式族 × 变体** + `bullet_tier` 退位：把"缩字号"从第一手段改成最后手段（先试换变体、拆页） | **加法 + 局部重构** `render.py` 的版式分支 | 中 —— 变体要覆盖现有 7 版式的全部用例，否则既有 spec 会渲不出来 | 阶段 2 |
| **4** | **图形语言 8 参数** + **图表决策树** + **评分引擎与修复引擎** | 加法（图形/图表）、新增（评分） | 低～中 —— 图形参数只影响新风格；评分引擎先用现有测项汇总 | 阶段 3 |

**为什么把间距排在版式前面**：间距是**所有版式共用的**，先规范它，后面所有变体都
自动受益；反过来先做变体，会做出一批间距仍然靠手调的版式。

**为什么把 `bullet_tier` 退位排在阶段 3**：它现在承担着"内容多了别溢出"的兜底职责。
只有在变体与拆页能力到位之后，才能把它降级 —— 否则会出现"该缩字号的地方没人管"。

## 六、参考标准清单（要深入时看这些）

| 模块 | 主参考 | 具体借什么 |
| --- | --- | --- |
| 布局 | **Fluent 2 Layout** + **Figma Auto Layout** | 12 列 / 4px 基准 / Grid·Spacing·Alignment·Regions·Baseline 五件套；父容器定义 padding/gap/direction，子元素自动重排 |
| 信息层级 | Fluent Typography + IBCS Message | 字号阶梯是**层级**而不是"重要就放大"；图表标题要写结论 |
| 留白 | Fluent Spacing + Auto Layout 的 Padding/Gap | spacing ramp 只许取档位；间距表达**关系**（越近越相关） |
| 图形语言 | **Design Tokens**（Fluent / Atlassian） | Global Token → Alias Token；形状可替换而布局逻辑不变 |
| 图表 | **IBCS 2.0 + ISO 24896:2026** + AntV 数据可视化规范 | SUCCESS 框架；时间横向 / 结构纵向；去图例去网格；语义化配色（actual / plan / forecast） |
