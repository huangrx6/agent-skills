# 内容理解与论证

本篇指导作者从材料组织演示。内容关系先于页型选择，不定义运行时 schema，也不提供自动事实评分。
需要页序记录时见 [规划](planning.md)；仅使用结构化路线时读 [spec 字段](style-architecture.md)。

## 先确定这次演示要改变什么

从已有上下文确定观众、场合、观看距离、核心结论、页数/时间限制与输出格式。
缺少会改变论证的事实才询问；风格与授权已经明确时直接推进，不重复收集。

用一句话写希望观众读完理解、相信或决定什么。区分：

- 决策汇报：结论、证据、代价、建议与下一步。
- 技术评审：问题边界、约束、方案、权衡、验证与未决风险。
- 教学讲解：已有知识、概念、例子、推导与应用。
- 进展复盘：目标、结果、偏差、原因、修复与后续。

这些是起点，不能硬套成固定页序。已给定的用户结构优先，在必要处说明调整理由。

## 事实、推断与证据

提取原始材料里的事实、指标、实体、关系与限制；合并同义词前核对是否真的同一概念。
关键数字保留来源、期间、单位、统计口径和对照基准；推断或预测在文案中标清。
材料未提供的数字、客户案例、架构关系不能为了完整而补造。

发现冲突时，先判断版本、时间范围、样本或单位是否不同；仍不能解释就保留为待确认。
不要选一个更好看的数字，也不要用更强的因果措辞替代只存在的相关性。
图表的选取范围、尺度与比较口径应清楚；选取子集时标明范围，不通过省略改变结论。
“提升 20%”需要明确是相对变化还是百分点。

来源可在工作说明、讲稿或页脚保留。运行时没有通用 `source_ref` / `evidence_refs` 字段；
别把规划备注直接塞进闭合 spec。需要可见来源时用受支持的 caption 或正文表达。

以代码仓库为依据时，记录相应版本或提交、文件与必要位置。“来自当前主干”不足以追溯具体结论。
完全重新梳理时按 [资料边界](refined-workflow.md#重新制作与资料边界) 读取当前实现与事实文档，不能用旧 deck 或旧选型说明代替核实。
技术事实可先确定，页数与分章在试排中调整；不因先完成一份技术清单，就把其密度锁成每页必须塞下的内容。
区分业务阶段、进程角色、部署实例与队列的计数；图上形状数量不能替代统计口径。
条件分支和并行依赖不能无标注改成所有输入都经过的线性步骤；简化图需写明适用范围。
成功、降级、可检索与可交付可能有不同条件，核对状态定义与质量门禁后再写标题。

## 每页的工作

每页先确定一个主要讲解问题，再选择合适的表达。不要把原文的一个章节、一个表或旧稿的一页直接当成容量单位。
比较页、目录、图表总览或作品展示可以并列相关信息，但要能说明为什么需要同时看见。
标题可作判断、提问或主题索引，与正文共同建立阅读顺序。

在已有页序记录中简记“本页问题 / 视觉承担的关系 / 留在画面的短文 / 展开细节的去向”。
记这一行之前，先把本页每段过一遍[「该不该变成图」的判断](../references/images.md#什么时候把段落变成图)：
能指认“谁 → 对谁 → 什么关系”的段落，图承担；只剩判断与条件的，才留给文字。
这一步先于长文排版；若需要多个独立结论或几段解释才能讲清，优先拆成连续页。
没有页数上限时允许页数增长；有时长或页数限制时先收窄主讲范围，将参考细节放入附录或另交讲义。
拆页后保持实体、条件和前后关系可追踪，不将同一比较拆得无法对照。

| 需要表达 | 应保留的阅读关系 |
| --- | --- |
| 判断及其依据 | 先看见什么判断，随后怎样找到证据、条件与例外 |
| 同维度比较 | 对象共享哪些尺度，差异能否直接辨认，是否需要同时可见 |
| 数值趋势或构成 | 真实数值与图形编码对应，基准、单位和范围清楚 |
| 过程与变化 | 区分时间、因果、并行和条件分支，保持对象身份可追踪 |
| 界面或现场证据 | 先保全必要上下文，再决定是否局部放大，解释靠近对应细节 |
| 架构与依赖 | 实体、边界和关系准确，整体与局部的对应清楚 |

这些关系可以用不同画面表达：比较不必是双栏，过程不必是横向时间线，也无需把全部正文改写成条目。
图可以就是正文：例如能力矩阵用共享行列、符号与局部例外表达多对象差异，不再逐行复述；
一张带标签的剖面可以直接呈现层次与接口。先设计观众要读出的关系，再决定用可编辑图形、位图信息图或混合实现。
视觉参考中的手绘风格、字体和符号可以借鉴，模型名称、能力判断等事实需重新查证。
具体构图由内容与项目视觉方向共同决定，见 [构图](composition-principles.md)。
结构化项目才将表达映射到 [已有页型](style-architecture.md#deckspecjson)，不要把其有限接口当作通用设计词表。

## 编辑方法

先保全事实，再减少观众同一时刻要读的内容。讲解页优先由一个主图、就近短标签和必要条件组织，
解释关系已由图承担后，移除旁边同义长文。正文能简短表达就不再加复述式副标题、图注和底部总结。
长细节移入后续页、讲稿或可读附录；`notes` 不参与页面排版，用户要求必须看到的内容要有可见去向。

例如输入类型、分流规则、输出用途和完整参数表同时出现时，先分清“如何进入”“如何处理”“结果怎么用”几个问题。
可用带对象插图的分支流程解释路由，用另页说明输出用途，参数映射保留在参考页。
层次结构可让一次请求沿带标签的层间路径展开；模块全集、替换方式和失败规则按讲解需要分开。
这类拆分依据问题与关系，不固定页数，也不把所有材料都改成线性流程。

条目采用平行语法，优先具体对象、动作、指标；删除“全面赋能”“显著提升”等无证据空话。
来源措辞本来谨慎时，不能为标题有力改成确定性结论。不要为了填满留白增加无关内容。

信息过多时优先去重与拆讲，再调整图文组织；不要先锁定页数，最后靠缩字和挤间距收尾。

内容偏少时也有失败方式：正文在页脚上方 25% 以上就结束，整页会像"内容浮在上半"。
先把正文、行距或图放大一档，再考虑与相邻页合并；**不要用垂直居中把标题和内容拉开**——
居中只会把空白从底部移到标题与正文之间，阅读路径反而断了。
字号可以为更克制的视觉主动调小，但腾出的空间留给图像与呼吸，不继续填入新段落。可读性仍以实际观看尺寸判断。
版本、参数与长代码的去向按用途决定：汇报通常适合附录，技术讲解或速查材料可能需要在正文保留。
`render --contract` 只给容量估计，浏览器测量才判断实际越界；程序不会替作者完成语义拆页。

## 全篇复核

读者能否理解全篇的目的与推进；相邻页为何连接、哪些页可合并、哪里缺关键证据？
数值、实体名称、结论强度与原文一致吗？反例、约束、风险是否被保留？
页数与时长是否符合用户要求？收尾是否让观众知道下一步？

这些检查由作者完成，不能虚构自动评分或声称 check.py 已验证内容真实性。
制作中与 [视觉审稿](visual-quality.md) 一起复核；视觉重组若改变解释或比较关系，再检查对应内容，最终回读目标格式。
