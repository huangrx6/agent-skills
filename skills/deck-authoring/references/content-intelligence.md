# 内容理解与论证

本篇指导作者从材料组织 deck。它不定义运行时 schema，也没有自动事实抽取、事实核查或内容评分程序。
规划方式见 [planning.md](planning.md)，实际 spec 字段见 [style-architecture.md](style-architecture.md)。

## 先确定这次演示要改变什么

从已有上下文确定观众、场合、观看距离、核心结论、页数/时间限制与输出格式。
缺少会改变论证的事实才询问；风格与授权已经明确时直接推进，不重复收集。

用一句话写希望观众读完理解、相信或决定什么。区分：

- 决策汇报：结论、证据、代价、建议与下一步。
- 技术评审：问题边界、约束、方案、权衡、验证与未决风险。
- 教学讲解：已有知识、概念、例子、推导与应用。
- 进展复盘：目标、结果、偏差、原因、修复与后续。

这些是起点，不能硬套成固定页序。已给定的用户结构优先，在必要处说明调整理由。

## 事实、推断与证据

提取原始材料里的事实、指标、实体、关系与限制；合并同义词前核对是否真的同一概念。
关键数字保留来源、期间、单位、统计口径和对照基准；推断或预测在文案中标清。
材料未提供的数字、客户案例、架构关系不能为了完整而补造。

发现冲突时，先判断版本、时间范围、样本或单位是否不同；仍不能解释就保留为待确认。
不要选一个更好看的数字，也不要用更强的因果措辞替代只存在的相关性。
图表必须保留完整系列和尺度含义；“提升 20%”需要明确是相对变化还是百分点。

来源可在工作说明、讲稿或页脚保留。运行时没有通用 `source_ref` / `evidence_refs` 字段；
别把规划备注直接塞进闭合 spec。需要可见来源时用受支持的 caption 或正文表达。

## 每页的工作

每页先写一个主要结论，再选择能证明它的载体；不要先挑页型再往里面填无关内容。
标题尽量说具体判断，正文补原因、证据或限定，避免标题与列表重复同一句。

| 需要表达 | 合适载体 |
| --- | --- |
| 一个判断或短主张 | title / content-text |
| 两个对象的同维度比较 | two-column 或合适 chart |
| 数值趋势、构成、对比 | chart，按真实数据选图形 |
| 先后步骤、阶段 | timeline；复杂分支另做结构图 |
| 产品界面、现场证据 | content-image 接入真实截图/图片 |
| 架构、依赖、流程网络 | 结构化图工具生成外部图，并保留可编辑源 |

当前没有原生 table、复杂节点画布或代码页型；不能把“建议用表”当作渲染器已有表格能力。
必要时选择已有结构、合适外部素材，或明确实现范围，避免把整段信息硬压进双栏。

## 编辑方法

先保全事实，再做去重、短句化和层级化。段落可变为“判断 + 必要证据”，
长细节移入讲稿、附录或另一页。`notes` 不参与页面排版，不能把用户要求必须看到的内容藏进去。

条目采用平行语法，优先具体对象、动作、指标；删除“全面赋能”“显著提升”等无证据空话。
来源措辞本来谨慎时，不能为标题有力改成确定性结论。不要为了填满留白增加无关内容。

装不下时按顺序考虑：收短重复表述、降低单页任务、换更合适结构、拆页，最后才换较小字号档。
`render --contract` 只给容量估计，浏览器测量才判断实际越界；程序不会替作者完成语义拆页。

## 全篇复核

只读每页标题能否复述论证；相邻页为何连接、哪些页可合并、哪里缺关键证据？
数值、实体名称、结论强度与原文一致吗？反例、约束、风险是否被保留？
页数与时长是否符合用户要求？收尾是否让观众知道下一步？

这些检查由作者完成，不能虚构自动评分或声称 check.py 已验证内容真实性。
内容通过后再做 [视觉审稿](visual-quality.md)，最终回读目标格式。
