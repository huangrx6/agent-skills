# 配图、背景与素材回填

先明确图片帮助观众理解什么或形成什么视觉感受，再决定来源与处理方式。图可以直接承载页面的主要内容，而非只作文字旁的配饰。
主视觉、解释图、真实截图和背景承担不同任务；HTML/SVG 的精确图解同样是视觉表达，不必为了叫作“配图”另生一张图片。
完整新稿必须规划并交接配图；只有用户明确要求纯文字或局部文字编辑才免除相应步骤。
可以组合授权照片、原始截图、图表、生成图及精确的 HTML/SVG 解释层，不把某次项目的风格或色板写成全局默认值。
用户明确的素材限制持续有效，禁止 SVG 的 HTML 项目使用 `--raster-only`。

## 从页面到图像，再回到页面

1. **页面提出需求。** 在正文排满页面前，逐页写清图像承担什么、替代哪些文字、使用页、图位及主体与文字的避让位置。默认让各内容页有可解释的视觉主体；流程、机制、架构、比较与证据页尤其如此。结论过渡或完整参考表可不额外配图，但不能因文字已占满而放弃图。图位可跨栏、出血、局部放大、嵌入节点或作为背景，不默认每页右侧矩形框。
2. **先交可执行的配图 Markdown。** 默认由用户自行出图：按下方计划接口保存 image-plan.json，运行 `--brief` 生成 image-brief.md。内容决定画什么，设计记录决定媒介、材质、光线和色彩；每张完整提示词能独立复制，不依赖“同上”。同时把真实图位接到约定路径。这一步不以缺少生图工具为触发条件。
3. **按约定取得文件。** 用户将图片放到 Markdown 指定的目录和文件名，刷新后进入实际图文审阅。只有用户明确委托直接生图时，才改用当前可用且获授权的工具；仍保留提示词与目标路径，不绑定供应商。真实截图另说明采集位置与需要展示的状态，不能用生成图冒充现场、产品界面或实验结果。
4. **回填到原图位。** 核对路径，局部调整比例、焦点与背景层；不为了插图重写无关页面。新素材不覆盖仍需保留的原图。
5. **看实际页面。** 检查主体裁切、文字避让、背景衔接和生成瑕疵，再更新导出。文件合格与页面完成是不同状态。

已有素材先登记来源与用途，不为凑数重新生成；完整新稿仍需交付素材说明，说明哪些直接复用、哪些按提示词生成。
已有结构化 spec 继续用自己的请求合同及 `image_source.py --brief`，同样交付 `image-brief.md`，不重复维护两份计划。
尚未有 HTML 时可先交 Markdown，但明确图位尚未接入。

## 让配图承担解释，让背景参与构图

在现有 `design.md` 的页序中简记“视觉要解释什么 / 图片与 HTML 各负责什么 / 正文保留什么 / 背景怎么配合”。
这份记录覆盖封面与所有内页，不要求新增固定风格字段或另建一本设计手册。

- **封面**有专门设计的主视觉与背景关系：可以是排印海报、图形构成、场景、摄影或其组合，按参考安排焦点和安静区；不要求额外的大幅插画，也不固定标题与图片的左右位置。
- **内容页**围绕具体对象设计：过程展示对象如何变换及分支；机制展示剖面、状态或输入输出；比较让同一尺度下的差异可见；证据可用真实图像的局部放大与对应注解。选择服从内容，不是页型套餐。
- **背景层**要支持当前焦点和阅读路径：可用场景延伸、材质、图像局部、色域、渐变或空间层次。密集区域可以保持安静纯色，整体仍须有设计过的前后层次；不靠把一张壁纸铺遍全套交差。
- **文字与图分工**：图承担了位置、关系或变化后，正文留下判断、解释缺口及重要条件；完整参数、代码或清单可移入可读的附录。信息图可以包含标题、标签、图例与短注，甚至占据整页；问题是重复和负担，不是图里能不能有文字。把原段落截图再贴回页面，没有改善表达。

比较能力可以用共同维度的矩阵，符号区分支持、受限与不支持，条件紧邻对应单元；流程可以直接呈现分支和状态，
不必另用长表复述。先核实具体模型/版本/条件，参考图只用于学习表达，不能将其中的旧结论直接作为新项目事实。
精确标签与频繁更新的数据优先放在 HTML/SVG 层；用户需要完整位图信息图时可一体生成，逐项复核文字、符号与关系，
保留可更新的内容来源。矢量、位图、混合图按清晰度、编辑需求和实际工具选择，不设全局“图片禁字”。

功能图提示词需写清必须出现的对象、方向、顺序/并行、状态、边界与省略内容。可将对象插图嵌入流程节点，
或在整体图像上就近叠加精确技术名、数值、条件和箭头；它们共同构成一张解释图。
需要标签的位置和连接端点在图位设计时确定，避免出图后再挤入旁边的长表。
生成层不画文字不等于页面不能在图中标注；“无字隐喻图 + 另一栏完整说明”若没有减少解释负担，应重新构图。
图上节点已能辨认时，不再给每个节点添加重复图标；装饰用于识别对象和建立节奏，不虚构额外模块或连接。
检查解释图时暂时忽略旁边的说明：观众能否从图读出本页核心关系？若仍要逐段读正文才能理解，重做图的表达，不能仅增加图数或扩大图框。
需要生成器绘制关系时逐项复核，不能让模型自由补造架构。装饰图不能顶替功能图验收。

每页有视觉表达不等于每页新生一张大图。同一组对象素材可以复用、局部放大或逐步展开；复用项的 `pages` 写全实际使用页。
一页使用多个节点素材时各自登记路径和图位，提示词约定一致视角与尺寸感。按需取得素材，避免为图片数量制造无用文件。

同一项目的图片沿用已确定的媒介、质感、色彩与构图关系；每张再根据本页任务调整主体、视角和裁切。
把这些决定写进实际生成提示或选图条件，不能只写“符合整套风格”。可用参考图时按工具能力传入并记录用途，
仅有文字描述时不声称模型看过参考。取得图像后若关键质感或主体不符合方向，修改素材或构图再验证，
不要用统一滤镜掩盖不匹配。系列一致不要求同一主体、相同比例或每页同一位置。

## 配图与背景的设计边界

| 图像任务 | 内容依据 | 页面处理 |
| --- | --- | --- |
| 概念或情境主图 | 材料中的主体与含义 | 可以摄影、插画、3D 或其他媒介；不要默认居中或占满单栏 |
| 架构、流程与数据 | 核实的节点、关系、数值 | 优先保留可编辑标签；生成图同样要逐项复核事实 |
| 界面与现场证据 | 真实文件或授权素材 | 保全必要标注与上下文，不为了色板重绘证据 |
| 整页或局部背景 | 阅读路径与文字位置 | 决定图像、保护层与文字层的关系；不要求底栏或固定遮罩比例 |
| 透明主体 | 需要跨越色块或露出底层 | 请求真实 alpha，保留透明通道，检查边缘和底色融合 |

背景可以是纯色、图片、渐变或组合。文字覆盖图片时，先找低细节区域；必要时再调图片位置、局部遮罩或底板。
遮罩应解决实际对比问题，不统一铺黑。标题、正文与需要精确编辑的数据通常留在 HTML 层。

按最终图位及导出倍率确定目标像素。`cover` 填满图位会裁切，`contain` 保全原图会留边。
主体位置、文字安全区与透明需求写入提示词，实际 CSS 再落实 `object-fit` / `object-position`；
这些值不会因写进计划就自动改变页面。相同比例不证明主体没被切掉，文件尺寸充足也不证明标签清楚。

## 自由 HTML 的图片计划

`image_handoff.py` 不生图、不改 HTML。它生成完整交接说明，检查文件和声明页面的静态接入。
计划使用 schemaVersion: 1，顶层包含 project 名称与非空 images 数组。每项填写：

| 字段 | 含义 |
| --- | --- |
| id / pages / file | 稳定标识、实际使用页数组、项目内相对文件路径 |
| role / purpose | 图像职责与本页要解释的问题 |
| target_px / fit / focal | 目标像素 `[宽, 高]`、cover 或 contain、焦点 `[横向%, 纵向%]` |
| alt | 图像内容的替代描述 |
| prompt | 能独立复制的完整生成提示，按本项目对象、关系、媒介与构图编写 |
| source / source_note | 默认 generated；已有素材用 provided 并记录来源 |
| negative / negativeSpace / transparent | 按需填写排除项数组、文字安全区描述与透明背景布尔值 |

不提供固定色板、材质或主体的默认提示词；这些决定来自本轮视觉方案。

`file` 相对计划文件所在目录，`pages` 为真实使用页。比例从 `target_px` 推导，也可显式写一致的 `aspect`。
`source` 默认为 `generated`，需要完整 `prompt`；复用已提供的图片时写 `source: "provided"` 和 `source_note` 来源说明，
省略 `prompt`，其他图位字段保留。复用项必须已有合格文件才能通过交接，不能借“复用”登记不存在的图片。
`negative`、`negativeSpace`、`transparent` 按需要填写；不通过提示词字数判断质量。
透明图必须 PNG / WebP，检查器验证确有透明像素；这不证明抠图边缘合格。
复用素材按最大图位检查，并在所有使用页目检；不同比例的图位必要时采用不同素材。

```bash
python3 scripts/image_handoff.py --brief /project/image-plan.json --html /project/source.html
python3 scripts/image_handoff.py --handoff /project/image-plan.json --html /project/source.html
python3 scripts/image_handoff.py --check /project/image-plan.json --html /project/deck.html
```

`--brief` 创建 `image-brief.md`，包含使用页、图片目的、完整提示词、像素与比例、安全区、透明要求、目标路径与接入片段；不覆盖人工修改，新版本用 `--out briefs/v2.md`，交付时链接当前有效版本。
`--handoff` 检查 Markdown 确已生成、对应当前计划、包含逐图路径与完整提示词，且 HTML 图位接通；缺图允许待回填。
默认检查 `image-brief.md`，新版本用 `--document briefs/v2.md`。只改了 Markdown 中的提示词时同步计划，再生成有效版本；不覆盖用户修改。
该检查不判断功能图覆盖是否充分、背景是否设计或 CSS 下是否可见，这些必须逐页审阅。
`--check` 返回 0 为文件及所请求的静态接入通过，1 为缺失或不合格，2 为计划无效。
未提供 `--html` 只验文件；提供后还核对 `img src` 和页码，可用 `data-image-id` 对应计划。
静态检查不认证 CSS 背景、`picture/srcset` 或脚本换图，这些需浏览器另核对；也不证明图片可见。
背景图可用绝对定位的 `<img>` 配合叠层 CSS，从而保留明确资源路径。

缺图阶段，图位保持设计尺寸并显示可辨认的待素材状态；不能挪走图位、写入假成品图或以错误后备图永久替换目标路径。
核对 Markdown、计划及 HTML 指向同一文件。`--brief --html` 会在文档记录未接好的位置，但生成文档本身不等于接入通过。
用 `--check --html` 区分 `files_ready` 与 `bindings.ready`：待图时允许前者为 false，承诺“放入目录刷新即可显示”前后者必须为 true。
缺图稿标明待素材，不能把占位图算作成片；当前播放器/导出会等待图片，缺图造成的资源失败不能报成通过。
回填后刷新页面、重新截图并导出，已有 PDF/PPTX 不会自动更新。

## 结构化 spec 的兼容接口

`visual.kind` 使用 `none`、`data`、`evidence_image`，图位比例用 `visual.ratio`。
可选 `visual.imageBrief` 保存本图用途与提示词意图：`purpose`、`subject`、`style`、`composition`、
`negativeSpace` 为文本，`focal` 为 0–100 的 `[水平百分比, 垂直百分比]`，`transparent` 为布尔值，
`avoid` 为文本数组；全部按需填写，字段与校验以 `validate_spec.py` 为准。
不填时工具不代选摄影风格、色板、主体位置或透明需求。旧 hero 渲染器的真实标题遮挡仍须避让。

```bash
python3 scripts/image_source.py --brief deck.spec.json
python3 scripts/image_source.py --check deck.spec.json
# 使用已配置且获授权的后端时：
python3 scripts/image_source.py --generate deck.spec.json --provider-cmd '你的命令 --prompt {prompt} --out {out}'
```

`--brief` 生成 `image-brief.md` 与 `assets/requests/<槽位id>.json`，临时测量图不会成为交付素材。
请求 schemaVersion 2 兼容旧 v1：`target_px`、`aspect` 与 `requirements` 来自实际图位；
每个 requirement 保存 page / width / height / fit，复用图片按所有图位验收。
生成读取已填写的合同，不用模板覆盖提示词。未完成的占位提示词不得交付或提交生成。

后端优先使用 `--provider-cmd`，其次兼容内置 MiniMax（环境变量 `MINIMAX_API_KEY` 或 `MINIMAX_CN_API_KEY`，
可选 `MINIMAX_API_HOST` / `MINIMAX_IMAGE_MODEL`）；密钥不落盘。没有后端时转交完整提示词。
供应商默认尺寸不一定匹配图位，输出后仍检查有效采样、裁切和透明通道。

直接路径相对 spec；使用 `assets/manifest.json` 时，`image` 写 assetId，manifest 中 `file` 相对 `assets/`：

```json
{"schemaVersion":1,"assets":{"overview":{"file":"overview.png","source":"provided","note":"真实产品界面"}}}
```

spec 的图片 fit 与焦点在项目皮肤定义，默认仍是 cover。`--check` 临时渲染并量取每个实际槽位，
按 cover / contain 检查有效像素。原生 PPTX 会读取实测 fit / position，但复杂背景和效果仍须回读验证。
