# 图片：契约、提示词、验收

## 先盘点，再分派

**每页都要过一次**：这页靠什么立住？页面元素与配图不是"想到了才加"，而是**要决定的
一栏**（spec 的 `visual`，四档）。分派表：

| `visual.kind` | 这页要什么 | 谁做 | 落到哪 |
| --- | --- | --- | --- |
| `evidence_image` | 照片 / 插画 / 主视觉 / 现场图 / 界面截图 | **人出图**：`--brief` 给提示词（中文 + English）→ 你拿提示词去出图 → 放回目录 → `--check` | `assets/generated/`（manifest 登记） |
| `diagram` | 结构图 / 流程图 / 拓扑 / 架构 / 时序 | **<https://excalidraw.com/> 或 draw.io** 画好导出 PNG | `assets/diagrams/`（manifest 登记） |
| `data` | 图表（趋势 / 对比 / 构成 / 分档） | 工具链（G2，`chart` 版式 + `chart` 字段） | 产物里 |
| `none` | 纯文字立得住（结论 / 观点 / 读的页） | 不加 | — |

三条纪律：

1. **项目里已有的真实素材优先**：真实截图 / 真实报告样张 / 真实现场图，永远比生成的更像
   "这个项目自己"。先问"项目里有没有"，再问"要不要生成"。
2. **要图就给提示词 —— 图不由脚本手画。** 这条禁的是**方法**，不是某个格式：
   用代码把图一笔一笔画出来（SVG、`PIL`/`ImageDraw`、canvas、matplotlib 拼装饰图…）
   出来都一眼假，而且比「不加图」更糟：

   - 画出来的东西没有**纹理、光影、景深、材质** —— 那是照片与插画之所以像真的部分；
   - 图里的文字会**被烤成像素**：在 1280px 的画布上画 15px 的中文，再缩进 582px 的槽位，
     字比正文还糊；换一种语言得重画；改一个字要重跑脚本；
   - 更根本的是：脚本手画会把**版式烤进图片**（几行几列、哪块放标题）。而版式是这一层
     之外的东西 —— 坐标由壳算、内容写在 spec 里。烤进图里，就再也改不动、也进不了门。

   正当用途只有一个：**风格的装饰与几何**（decor / 网点 / 细线 / 编号），那是风格层
   的事（`decor`），不是配图。

   **谁画什么**（别越界）：

   | 东西 | 谁画 | 怎么来 |
   | --- | --- | --- |
   | 图表（bar/line/donut…） | **G2**（`chart.py`） | 数据驱动 —— 有数字就该它画 |
   | 装饰、网点、几何、编号 | **皮肤**（`decor` + `skin.css`） | 风格层声明 |
   | 版式与文字 | **壳**（`render.py` 算坐标） | 写 spec，不画图 |
   | 结构图 / 流程图 / 拓扑 / 架构 | **人**，在 excalidraw.com / draw.io 上画 | `visual.kind = diagram` |
   | 照片 / 插画 / 主视觉 / 现场图 / 截图 | **人**，拿 `--brief` 的提示词去出图 | `visual.kind = evidence_image` |

   一句判断：**图里要是出现了「版式」（卡片、分栏、页标题），那它就不该是图** ——
   那是一页 spec。
3. **纯文字页也要写 `{"kind": "none"}`**。"三条结论"确实不必配图 —— 但得是被**决定过**的，
   不是漏掉的。没决定的页 `check.py` 会点名。

## 图从哪来

这条流水线里，**图不由脚本生成**（下面说为什么），分工是：

> **脚本写契约与提示词 → 人出图 → 脚本再验一遍。**

## 为什么不是"脚本调生图模型"

不是因为难，是因为**分工反了**：

- 脚本真正知道的是——每张图**放进版面的哪个槽位**、那个槽位**实测多少像素**、
  **该风格的色板是什么**（提示词的色彩栏就来自它）。这些模型不会自己知道。
- "出一张好看的图"这件事，人拿自己顺手的模型做得比脚本去调一个陌生 API 好；
  而且没有一层 API key / 配额 / 供应商变更要维护。

所以默认路径是**交接**，不是生成。`--brief` 把契约与提示词写到一份文档里，
人拿它去出图，出完 `--check` 验一遍。

```bash
python3 scripts/image_source.py --brief your.spec.json      # → image-brief.md（提示词合同）
# …… 拿着 prompt 去出图，按文件名存到产物同目录 ……
python3 scripts/image_source.py --check your.spec.json      # 验尺寸 / 比例 / 在不在
# --brief 加 --json：把机读 brief 额外打到 stdout（给脚本消费）
```

`--brief` **不往 deck 里写任何图**：量槽位要用一块"尺子"（尺寸对、比例对），它活在
临时目录里，量完就消失。产物目录里的图永远只有人出的那一份 —— 脚本放一张"先占住"
的拼贴，就等于把一张不是设计的东西混进交付（实测踩过：跑完 `--brief`，图片目录里躺着
几张拼贴，没人替换它们就跟着交付了）。

**合同落在 spec 同目录（即 deck 项目），永远如此**：`--dir` 只说"出完图存哪"（脚本
自己不写），不会把提示词搬走 —— 那份合同是**要交给用户去执行**的东西，跟着临时目录走就等于
没产出。整份 deck（spec / 风格 / 素材 / 合同）都建在**项目目录**里，别建在 `/tmp`：
`--brief` 见到临时目录会当场说一声。

### 资产清单（manifest，§12 统一 Asset Pipeline 的入口 · v1）

spec 同目录放 `assets/manifest.json` 时，图文页的 `image` 写的是 **assetId**
（语义引用），编译（`deck.py::compile_spec`）按 §14 的优先级链把它解析成 `assets/<file>`（manifest 即
选择；generated / provided 的区分由 `source` 记录），Decision Trace 留痕，页对象
携带最终路径 —— 渲染器不见 assetId。没有 manifest 时 `image` 写相对路径
（相对 spec 所在目录）。清单 schema 封闭，违规即 ERROR：

```json
{"schemaVersion": 1,
 "assets": {"cover-photo": {"file": "generated/cover.png",
                            "source": "generated", "note": "主视觉"}}}
```

两条铁律的落点：**缺文件由 check 的「图片加载」门实测拦**（不猜存在性）；
**联网找图与脚本画图都禁止** —— content-image 缺 `image` 被 `validate_spec.py`
直接拦，文件缺失 / 太小 / 比例不对由 `image_source.py --check` 与 `check.py` 的阻断
拦。**产物目录里的图只能是人出的那一份**：`--brief` 量槽位用的尺子只活在临时目录里，
脚本一个字节都不往 deck 里写。

### 资产请求（requests，manifest 的上游合同）

`--brief` 除了人读的 `image-brief.md`，还在 spec 同目录给每个图槽位写机读的
`assets/requests/<槽位id>.json`（槽位 id 即 spec 里的 `image` 值，也用作 assetId）。
schema 封闭 v1：`{schemaVersion, slide, role, aspect, focal, negative_space, prompt,
required, note}`（`aspect` 是实测槽位宽高比，`prompt` 即契约里的中文提示词）。
先有请求、再出图：图回来后把选中的文件登记进 `manifest.json`，assetId 就用这个
槽位 id —— 请求说"要什么"，manifest 说"有什么"，管线闭环。

**该要就要，别嫌麻烦少要，多了也没事。** 这条在这里的含义是：`--brief` 不该因为
"图少"而显得多余 —— 一份 spec 有多少图位，就出多少份契约，逐张写全。反过来，遇到
**一张图都没有**的 spec，`--brief` 也不会甩一句"没有要出图的地方"就完事：它按版式
指出哪几页最可能该加图（纯文字页 ≥3 条的那种），由内容定要不要加。一页在讲
"某个东西长什么样 / 现场 / 对比"，就该有图；讲"三条结论"，就不必有。

另一条路仍然在，按需用：

| 路径 | 给谁 | 说明 |
| --- | --- | --- |
| `--brief` / `--check` | **默认** | 人出图；脚本给契约、给提示词、验交付 |
| `--provider-cmd` | 有 API 的人 | 用 `{prompt}` 与 `{out}` 占位的命令模板；**不过 shell**；不配就拒绝，没有降级产物 |

### 要图，就先把比例写下来（`visual.ratio`）

**声明了 `visual.kind` 要图，`ratio` 就是必填** —— 写 `"3:2"` / `"4:3"` / `"1:1"` / `"16:9"`。
不写下来等于没定：出图工具的默认比例各家不同（Midjourney 1:1、SD 看 sampler、
DALL·E 只认 prompt），而**槽位高度是按它算的** —— 出回来再改成本高得多。
`validate_spec.py` 会直接拦（`MISSING_RATIO`），格式不对报 `BAD_RATIO`。
没有 `visual` 声明的图页不受这条约束（那是老写法，按槽位缺省 3:2 走）。

### 比例规则：槽位定比例，图片只需"够宽 + 主体不贴边"

**生图工具出成 1:1 / 4:3 / 2:1 是常态**（提示词按不住比例：Midjourney 默认 1:1、
SD 看 sampler、DALL·E 认 prompt 不认参数）。所以比例**不是**一条要你重出图的规则 ——
渲染层按槽位处理：**高度由槽位比例（3:2）定**，多出来的部分按 `visual.kind` 处理：

| kind | 处理 | 效果 |
| --- | --- | --- |
| `evidence_image`（照片 / 插画 / 截图） | `object-fit: cover` | 按中心裁切，主体居中几乎无损 |
| `diagram`（结构图 / 流程图 / 拓扑） | `object-fit: contain` | 留边不裁 —— 图里每一笔都是信息 |

`visual.ratio` 就是那个槽位比例（`aspect-ratio` 由它给，默认 3:2）；皮肤的 `.imgwrap`
要改就覆盖 `aspect-ratio`。

**所以出图时主体必须留余量**：提示词的【限制】栏已经写死"主体收在画面中心 80% 区域内
（四周各留 ≥10%）" —— 因为裁切与留边都按槽位算，贴边的主体**一定**会被切掉。
出完图还有三条只能人眼看的自检（`--brief` 出的文档里也列了）：主体在不在中心 80%、
画面里有没有文字、结构图有没有被压扁。

于是 1:1 不会撑出页底、2:1 不会留出空洞，`--check` 也**不再把比例当问题**（只说明）。
真的需要重出图的只有两件：**宽度不够**（放进去一定糊）、**主要内容被裁到**（改成
`diagram` 走留边，或重出时把主体收进中心）。皮肤的 `.imgwrap` 要改槽位比例就直接覆盖
`aspect-ratio`。

## 契约里有什么

| 项 | 从哪来 |
| --- | --- |
| 文件名 | spec 里的 `image` 字段（同一个文件名用在多页时**合并成一条**） |
| 尺寸 | **实测槽位 × 2**（槽位宽由布局定：`.imgwrap{width:640px}` → 1280px） |
| 比例 | 3:2（**期望值，不是要求** —— 见下「比例规则」） |
| 透明通道 | 内容图**不需要**（整张不透明照片）；logo 那套另有路径 |
| 会被怎么处理 | **按原样使用**（不做后处理）；色彩与构图约束由提示词的对应栏承担 |
| 内容 | **留空给人填**（主体 / 场景 / 细节）。见下 |
| 提示词 | 中文 + English，两份都按同一套字段顺序给 |

### 三件容易做错的事（都踩过）

1. **同一张图用在多页时要合并**（按页列会让人对同一张图出三张、互相覆盖）。
2. **不能说"给文字留压字空间"**。我们的版式里文字是**独立一栏**（左文右图；
   唯一例外是 hero 变体 —— 满幅图 + 底部**实心**标题条（图高**按这一页要装的
   条目/图注算**：正文带 692 − 条目 − 图注 − 页脚净距 40，夹在 320~648；
   触到 320 就不再让 —— 那时该换版式或拆页，不是把图压成一条），条用 --text/--paper
   反转色对，对比度与正文同一个 token 保证，所以出图时**不需要**给标题留白区，
   标题条压在图上任意位置都成立），
   不是压在图上。写错了模型会交一张主体偏到一边、空掉半张的图。
3. **工具不许自己编主体**。把该页标题拼成"内容草稿"塞进提示词是
   **擅自补充事实**：条目往往在讲这份 deck 的叙事（"把现场图处理成两色…"），
   不是在讲画面里该有什么。「主体 / 场景 / 细节」三栏**留空**（写作 `〈…〉`），
   工具只把标题与条目列成**参考材料**放在提示词外面 —— 它读不到你脑子里的画面，
   就不该假装读得到。

## 提示词怎么组织：字段顺序就是优先级

每条提示词按**固定顺序**给十个字段：

```text
主体 → 场景 → 构图 → 镜头 → 光线 → 色彩 → 风格 → 细节 → 文字 → 限制
```

顺序本身就是信息：先让模型明白**画什么**（主体 / 场景），再明白**怎么画**
（构图 / 镜头 / 光线 / 色彩 / 风格），最后是**绝对不能错**（文字 / 限制）。
堆成一段的写法会让"不要细密纹理"这种约束把"主体是什么"淹掉 —— 而主体最优先。

每一栏只讲它该讲的事，不混着写：**构图不谈光线，光线不谈风格**。这是顺序能成立的
前提；混着写的话顺序就名存实亡了。所以风格那一栏给的是**可执行的视觉语言**
（"纪实摄影；克制平静、画面干净不杂"），不是风格文献的名字（写 Massimo Vignelli
对模型是噪音），也不夹规则说明。

冲突时按这个优先级裁决（左边赢）：

```text
你的明确要求 > 主体准确 > 文字与品牌准确 > 构图 > 场景 > 光线 > 风格 > 装饰细节
```

这条在本流水线里**真的会撞**：风格的强色相属于低优先级，不允许破坏构图与细节
（主体位置、负空间、形体是否清楚）—— 所以风格栏里明写"靠大块明暗和强形状立住"，
让它别压过构图。低优先级的不许破坏高优先级的。

### 谁知道哪些字段

| 字段 | 谁填 |
| --- | --- |
| 主体 / 场景 / 细节 | **人**（工具留空，写作 `〈…〉`） |
| 构图 / 光线 / 色彩 / 风格 / 限制 | 脚本。构图来自**实测槽位与版式**（图独立成栏、文字在旁边），色彩来自**该风格的色板**，光线与风格来自风格的**气质**档，限制来自**这条管线的约束**（与风格色板 / 构图冲突的观感项） |
| 镜头 | **默认不出现这一栏**：镜头参数只有能明显改善画面时才该加，而工具判断不了你这张图需不需要它 —— 给了"安全默认值"就等于**每次都加**，正好违反规则。要加就自己插一行，位置在【构图】与【光线】之间；契约里给了几个可抄的例子 |
| 文字 | 脚本。答案在**版面**上：画面里不要出现任何文字，说明文字由版面另排 |

**API 已经有的参数不要写进提示词**：尺寸、比例、数量、质量、seed 都单列在每张图的
「参数」栏里 —— prompt 里再写一遍只会在两者冲突时给出随机结果
（`3:2` 与 `1280x853px` 冲突时就是随机二选一）。

**限制项只列与这条管线相关的**：细线 / 细密网格或织物纹理 / 柔和渐变 / 低对比平光
（这四样与"按风格色板出图、主体清晰"冲突）、多个并列或重复主体、结构变形 / 过曝 / 裁切主体。
不堆"不要水印 / 不要额外人物 / 不要畸形手指"这类通用负面词 —— 与本任务无关的
负面词是噪音，还会挤掉真正重要的约束。

### 提示词里那条**管线特有**的约束

**没有制版后处理**（不做双色调 / 半调网点）—— 图按**原样使用**。
所以约束不来自"会被压成两墨"，而来自**提示词的色彩与构图栏**：

- 色彩栏钉住**该风格的色板**（主色 / 副色 / 纸色），让图与版面同源；
- 构图栏给**实测槽位与版式**（图独立成栏、文字在旁边、主体偏哪侧、哪侧留负空间）；
- 风格栏给**可执行的视觉语言**（"靠大块明暗和强形状立住"），不是风格文献的名字
  （写 Massimo Vignelli 对模型是噪音）。

这几条不写进去，模型会交一张很漂亮、却与版面不同源的图 —— 而**只有这条流水线的人
知道**该风格的色板与版式，通用提示词里不会有。

## 验收：`--check`

在**渲染之前**对着契约验，所以能在跑完整条流水线之前就告诉你"这张图你出小了"：

- 文件在不在（不在就说"还没出图"）
- 宽度够不够（契约是 1280px；小了这个尺寸的图放进版面**一定糊**）
- 比例对不对（版面按宽度缩放，比例差太多会撑高，撑高会撞页脚）

`check.py` 那条放大检查是**渲染之后**看产物的（它只知道有没有被放大）；
两者互补，不是重复。

> ⚠️ **`--check` 不许自己造图**：它只读 spec 与文件，不渲染任何东西 ——
> 检查器若自己造出该验的东西，就永远验不出"还没出图"（`--brief` 同理：它量槽位
> 的尺子只活在临时目录里，不落进 deck）。
