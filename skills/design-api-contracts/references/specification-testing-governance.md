## 契约事实来源

组织可采用 design-first 或 code-first，但必须有唯一发布契约：

- 版本化；
- 可机器读取；
- 与部署行为一致；
- 可生成文档；
- 可执行兼容性差异；
- 可关联服务版本和责任团队。

不得同时维护互不校验的手写文档、代码注解和独立 Schema。

## OpenAPI 规则

- 固定精确的 OpenAPI 规范版本。
- 新项目使用组织工具链已完整支持的当前版本。
- 每个操作拥有唯一、稳定的 `operationId`。
- `info` 包含名称、API 版本和必要联系信息。
- `servers` 不包含生产密钥或个人环境地址。
- 所有路径参数必须声明且为 required。
- 请求正文、成功响应、错误响应和相关 Header 全部建模。
- 安全方案和每个操作的安全要求必须明确。
- 使用 tags 组织领域，不按控制器类名自动生成。
- 复用 components 时确保语义真正一致。
- `deprecated`、`readOnly`、`writeOnly`、example 和 description 应准确。
- 不把自由文本文档作为缺失 Schema 的替代。
- 扩展字段使用稳定命名空间并记录用途。

OpenAPI 官方索引包含 3.2 与 3.1 等发布版本；版本选择必须结合当前工具链验证。

## Schema 与示例

- Schema 使用当前 OpenAPI 版本支持的 JSON Schema 方言。
- 明确 `additionalProperties` 策略。
- 所有示例必须通过 Schema。
- 请求示例、响应示例和错误示例相互一致。
- 复用示例时不得混入真实敏感数据。
- 二进制、multipart、streaming 和 webhook 使用对应契约能力。
- Schema 引用必须可解析，避免循环或跨仓库不可复现引用。

## 契约验证

CI 至少执行：

- YAML/JSON 语法检查；
- OpenAPI 规范验证；
- 组织风格 lint；
- `$ref` 解析；
- Schema 与示例验证；
- operationId 唯一性；
- 安全方案完整性；
- 破坏性变更差异；
- 生成代码一致性；
- 文档构建；
- API 目录元数据校验。

规范验证器不能发现所有语义问题，文字规范优先于辅助 Schema。

## 契约测试

至少包含：

- 提供方契约测试：实现符合发布契约；
- 消费方关键场景测试：调用方假设被记录和验证；
- 负向测试：无效参数、权限、冲突和限流；
- Schema fuzz 或属性测试：边界、未知字段和最大长度；
- 兼容测试：旧客户端对新服务、新客户端对旧服务；
- 示例测试：文档示例可运行；
- 回归测试：状态码、Header 和字段语义不漂移。

消费者驱动契约适用于多调用方协作，但不能替代提供方完整契约和安全测试。

## SDK 与代码生成

- SDK 从发布契约生成或校验。
- 生成器版本固定且可复现。
- 生成代码与手写扩展隔离。
- 不手工修改生成文件。
- SDK 版本与 API 版本的对应关系明确。
- 生成客户端必须实现未知字段、未知枚举、重试和超时的组织策略。
- 自动重试不得违反幂等性。
- 代码生成失败不得通过删除 Schema 约束来规避。

## API 评审

评审输入应包括：

- 业务目标和调用方；
- 资源模型；
- 操作与状态转换；
- OpenAPI/Proto/AsyncAPI 差异；
- 数据分类和授权；
- 幂等、并发和异步语义；
- 兼容性评估；
- 容量、限额和性能；
- 迁移和下线计划；
- 测试证据。

评审阻塞项必须关联明确风险，不以个人命名偏好阻塞。

## 生命周期治理

每个 API 必须有：

- 稳定名称和唯一标识；
- Owner 团队；
- 生命周期状态；
- 公开或内部分类；
- 数据敏感级别；
- 支持版本；
- 文档和契约位置；
- 依赖调用方；
- SLO 或服务承诺；
- 弃用与下线记录；
- 变更历史。

未登记、无 Owner 或无契约的生产 API 不得视为受治理接口。
