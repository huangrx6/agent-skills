## 选择原则

先看交互模型，再看组织已有能力。评估调用方数量和语言、内部还是公开、浏览器兼容、资源还是命令、单向还是双向实时、延迟吞吐、消息大小、是否需要离线重放、网关缓存能力、Schema 演进和团队运维成熟度。

禁止仅因为“微服务都用 gRPC”“前端都用 GraphQL”或“公司统一 REST”而忽略场景。

## 主风格对比

| 风格 | 最适合 | 优点 | 主要代价 |
|---|---|---|---|
| 资源化 HTTP / REST-style | 公开 API、资源生命周期、CRUD | 通用、易调试、代理缓存成熟 | 聚合读取可能多请求 |
| gRPC | 内部服务、低延迟、强类型 RPC、Streaming | Proto 强契约、代码生成 | 浏览器/公开生态门槛较高 |
| GraphQL | 多前端、聚合查询、字段需求差异大 | 客户端选择字段、统一图 | 成本攻击、N+1、缓存和 Schema 治理复杂 |
| SSE | 浏览器服务器单向推送、通知、进度 | HTTP 原生、自动重连 | 仅单向 |
| WebSocket | 聊天、协作、游戏、双向控制 | 全双工、低延迟 | 连接状态、背压、恢复复杂 |
| HTTP Streaming | AI 输出、日志流、逐块结果 | 仍保持请求响应模型 | 恢复和中途错误需定义 |
| Event / Pub-Sub | 异步解耦、多个消费者、重放 | 松耦合、吞吐高 | 重复、乱序、最终一致性 |
| Webhook | 跨组织异步通知 | HTTP 普及 | SSRF、签名、重试、重复 |
| JSON-RPC | 命令式工具 API、轻量内部调用 | 简单、transport agnostic | HTTP 语义利用少、类型弱 |

## 推荐组合

典型系统往往组合使用：

- 公开业务资源：REST-style HTTP + OpenAPI；
- 内部高频服务：gRPC；
- BFF 或复杂多前端查询：GraphQL；
- 浏览器进度/通知：SSE；
- 双向协作：WebSocket；
- AI/生成式输出：HTTP Streaming 或 SSE；
- 领域事实传播：事件总线；
- 合作方通知：Webhook；
- 运维或工具命令：JSON-RPC 或简单 RPC。

同一业务能力使用多个协议时，共享领域语义、身份、错误目录和兼容策略，但不要强行共享完全相同的传输模型。

## 不建议的统一化

避免：

- 用 POST `/execute` 承载所有 HTTP 操作；
- 为简单 CRUD 引入 GraphQL 只为减少端点数量；
- 为普通列表接口引入 WebSocket；
- 用 WebSocket 模拟可靠消息队列；
- 用事件总线实现需要即时同步确认的核心请求；
- 用 gRPC 直接暴露给缺乏支持的公开浏览器生态；
- 用 GraphQL Mutation 包装任意后端命令而不定义事务语义；
- 为“REST 纯度”加入对客户端无价值的复杂超媒体流程。

SOAP/WSDL、OData、WebTransport 等不在默认矩阵，仅在现有生态、合作方或专门业务明确要求时按需单独评估，不默认纳入新项目。

## 决策检查

1. 客户端需要资源、命令、聚合查询还是持续流？
2. 是否必须同步完成？
3. 是否需要服务端主动推送或双向通信？
4. 是否需要离线消费、重放或多个订阅者？
5. 客户端是否需要自主选择字段？
6. 是否需要强类型代码生成？
7. 浏览器、网关和运维平台支持什么？
8. 哪种协议的兼容与安全治理团队最成熟？
9. 复杂协议带来的收益是否覆盖运行成本？
