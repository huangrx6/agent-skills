# 敏感数据与日志安全

## 禁止记录

禁止记录：

- 密码；
- 访问令牌和刷新令牌；
- Cookie 与会话凭据；
- 私钥和签名材料；
- 完整支付卡或支付凭据；
- 完整政府证件号码；
- 原始数据库连接串；
- 默认情况下的完整请求头、请求体和响应体；
- 不必要的个人或客户数据。

## 处理策略

字段应根据数据分类选择：

- `DROP`：完全不记录；
- `MASK`：部分掩码；
- `HASH`：使用批准的不可逆哈希；
- `TRUNCATE`：限制长度；
- `ALLOW`：在明确用途和权限控制下记录。

优先采用允许列表，而不是先记录全部内容再尝试删除敏感字段。

## 用户可控文本

写入日志前必须：

- 限制长度；
- 规范化或转义换行；
- 删除不安全控制字符；
- 防止伪造日志字段或完整日志条目；
- 避免把未处理文本拼入 JSON、键值日志或模板。

## 请求与响应内容

只有在明确诊断需求、批准的数据分类和受控环境下，才可记录请求或响应内容。必须定义：

- 允许的接口或字段；
- 脱敏规则；
- 采样比例；
- 保留时间；
- 访问权限；
- 自动清理方式。

生产环境不得通过临时 DEBUG 开关绕过敏感数据规则。

## 删除权与个人信息

日志可能包含个人数据时，删除权（如 GDPR/个保法）应优先通过"默认不记 PII + 记录前匿名化"使删除权自动满足，而非事后重写：

- 默认不记录个人数据；确需记录时在写入前完成不可逆匿名化或哈希，使日志不再持有可识别个人信息；
- 明确哪些字段可被匿名化，哪些因审计或法律保留不可删除；
- 只有在无法事前匿名化且法律要求删除时，才考虑日志重写（字段级匿名化）或整行删除，并评估其对完整性和检索的影响；
- 重写或删除必须验证幂等性和范围，避免误伤他人数据；
- 法律保留期间的数据不响应普通删除请求，但应记录该请求。

## 错误消息

异常消息可能包含 SQL、路径、主机名、用户输入或依赖响应。写入日志前应进行安全评估；对外响应不得直接复用内部异常消息。

## 验证

敏感字段策略必须通过自动化测试、日志扫描或配置校验验证。仅依赖开发人员人工注意不构成控制措施。

## 告警与外部渠道

日志内容离开日志平台（告警通知、客服工单、导出分享）时仍须遵守脱敏规则：告警通知不得携带令牌、凭据、完整支付信息或不必要的个人数据。
