# 审计、采样与成本治理

## 审计日志分离

诊断日志与审计记录必须分开管理。

审计事件至少识别：

- 操作人或服务身份；
- 操作；
- 受保护资源；
- 结果；
- 时间；
- 相关策略、审批或权限上下文。

安全、资金、高权限和关键配置变更的审计记录不得因普通日志采样、磁盘清理或容量降级而丢失。审计保留、法律保留和销毁规则应单独配置。

### 审计降级模式

审计通道（审计存储、审计事件总线）故障或未装配时：

- 原则上不得阻断核心业务（审计是留痕要求，不是业务前置依赖）；
- 降级行为必须显式定义：例如降级为仅记录诊断日志，或写本地临时审计文件；
- 每次降级都必须产生一条可观测事件（如 `audit.sink_degraded`）并触发告警，禁止静默丢审计；
- 降级持续时间、丢失审计范围必须可追踪，恢复后补投或至少汇总丢失量；
- 合规要求不允许降级的场景（如支付、监管上报），审计必须使用独立高可靠通道，与普通诊断日志完全隔离。

## 日志量控制

高频成功路径优先使用：

- 指标和计数器；
- 延迟直方图；
- 聚合或周期汇总；
- 采样诊断日志；
- 重复错误限频。

逐请求 INFO、循环逐项日志和重复堆栈必须经过容量与成本评估。

### 日志量预算

为每个服务设置明确的日志量预算（如每实例每天 GB 数），并纳入容量规划：

- 预算按日志用途拆分（诊断/审计/安全）；
- 超预算时优先降级：降采样 → 关闭 DEBUG → 合并周期汇总，而不是直接截断 ERROR；
- 预算与成本治理由负责人定期核对，异常增长（环比突增）触发检查。

## 采样与限频

采样策略应明确：

- 适用事件；
- 采样方法和比例；
- 是否保留首个、最后一个或代表性样本；
- 是否按租户、错误码或依赖公平采样；
- 告警和事故期间的临时调整方式。

限频不得掩盖总量。被抑制日志应通过指标或汇总事件暴露数量。

## 动态日志级别

生产排查需要临时开启 DEBUG 时：

- 通过受控机制动态调级（配置中心、运维接口或平台能力），禁止生产硬编码 DEBUG；
- 动态调级必须有默认回退（如限定有效期、重启恢复默认级别），防止误开后永久 DEBUG；
- 调级操作应记审计（谁、何时、对哪个服务、调到什么级别）；
- 动态调级期间同步采样或容量保护，避免 DEBUG 打开导致日志量暴涨拖垮磁盘或平台。

## 访问与查询

根据用途和数据分类定义：

- 查询权限；
- 导出与共享限制；
- 跨区域或跨租户隔离；
- 高基数字段索引策略；
- 热、温、冷数据层级；
- 查询审计。

日志文件的轮转、压缩、保留和清理规则由 [rotation-retention.md](rotation-retention.md) 统一规定。

## 日志与告警联动

日志是告警的输入之一，需要定义：

- 从日志事件导出告警的规则（基于 `event.name` 或错误码，不解析自然语言消息）；
- 重复告警的聚合与抑制，避免 ERROR 风暴打爆通知渠道；
- 告警上下文附日志查询链接（按 trace_id 或 service.name+时间窗）；
- 告警通知内容不得携带敏感日志内容（脱敏后再进通知渠道）；
- 告警静默必须有上限和复核，防止长期静默掩盖故障。

## 日志平台故障

日志发送失败原则上不得导致核心业务失败。必须定义：

- 内存与本地磁盘缓冲上限；
- 队列满时的丢弃优先级；
- 背压策略；
- 平台故障指标和告警；
- 恢复后的有界排空速度；
- 审计日志的更高可靠性要求。

不得无限缓冲导致内存或磁盘耗尽。

## 可观测性分工

- 日志：离散事件和诊断上下文；
- 指标：聚合数量、速率、容量和延迟；
- 链路：单次请求的跨服务路径；
- 审计：主体对受保护资源的行为证据。

不要用日志替代所有其他信号。
