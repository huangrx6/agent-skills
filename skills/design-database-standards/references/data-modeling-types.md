## 建模原则

- 先写业务不变量、查询模式和生命周期，再建表。
- 一个表表达一个清晰实体/关系，不把无关字段塞进万能扩展表。
- 规范化是默认起点；反规范化必须有查询性能或一致性收益证据。
- 数据库约束负责保护跨进程、脚本、任务和多版本应用共同写入的数据。
- 不把展示层字符串直接当领域状态保存。

## 命名

- 库、schema、表、列、索引和约束使用统一命名风格；关系库默认推荐小写 snake_case。
- 表使用领域名词；单复数选择一种并保持一致。
- 不使用保留字、空格和需要频繁引用的特殊字符。
- 外键列名称应体现被引用对象，例如 `customer_id`。
- 布尔列命名成命题，例如 `is_active`、`has_access`。
- 时间列使用 `*_at`，仅日期使用 `*_date`；时长带单位或使用 interval/duration 类型。
- 金额、字节数等单位容易混淆时名称包含单位。
- 索引/约束名应可从错误和执行计划中识别用途。

## 主键与业务标识

- 主键用于稳定标识行，不承担可变化业务含义。
- 业务唯一键必须通过 UNIQUE 等约束真正落库。
- 对外 ID 可与内部主键分离，避免暴露递增规模、分片拓扑或重建风险。
- UUID、雪花 ID、自增 ID 的选择基于写入局部性、跨库生成、排序和安全需求，不设万能默认。
- 联合主键只在关系本身天然由多个不可变键组成且工具链可良好支持时使用。
- 不使用邮箱、手机号、用户名等可变字段作为主键。

## NULL 与默认值

- NULL 必须表示一种明确状态，例如“未知”或“不适用”。
- 必填业务字段设置 NOT NULL，并尽可能通过约束保证。
- 不用空字符串、0、1970-01-01 等魔法值代替 NULL。
- 默认值代表创建时真正的业务默认，不用于掩盖调用方遗漏。
- 数据库默认与应用默认必须一致，否则多写入路径会产生不同数据。
- 改变默认值不会自动改变历史行；迁移必须单独处理存量数据。

## 字符串与文本

- 长度限制基于业务和协议，而不是随意统一为 255。
- 标识、状态和短名称可有限长；正文使用数据库适合的大文本类型。
- 字符集统一 UTF-8/Unicode；排序规则和大小写敏感性必须与业务一致。
- 大小写不敏感唯一性要靠规范化值、函数索引或数据库支持实现，不能只在应用 `lower()`。
- 不把结构化列表塞进逗号分隔字符串。

## 金额与数值

- 金额使用 decimal/numeric 或最小货币单位整数，不使用 binary floating point。
- 保存货币代码，除非表业务域永远只有单一货币且由上层 Schema 保证。
- 精度、scale 和舍入规则必须与业务结算规则一致。
- 百分比明确是 0–1 还是 0–100。
- 计数、序号和容量选择能覆盖未来范围的整数类型。

## 时间与时区

- 时间点优先使用数据库的 timezone-aware timestamp 能力或明确统一 UTC。
- 仅日期用 DATE；本地业务时间和绝对时间不要混在同一字段。
- 需要地区时区规则时保存 IANA time zone，例如 `Asia/Shanghai`，不能只保存 UTC+8。
- `created_at`、`updated_at` 是否由数据库或应用维护必须统一。
- 不依赖服务器本地时区作为业务契约。

## 布尔、枚举与状态

- 布尔使用真正 BOOLEAN 能力，避免 `Y/N`、`0/1` 字符串混用。
- 枚举适合稳定小集合；频繁变化、需要元数据或动态配置时使用参考表/领域表。
- 数据库原生 ENUM 的可迁移性和变更成本必须评估。
- 状态列必须有合法值约束，并与状态机文档一致。
- 不把失败原因、动作类型和生命周期状态混在一个枚举。

## JSON 与半结构化字段

JSON 适合：

- 可扩展低频元数据；
- 外部原始载荷留存；
- 字段结构确实变化快且不参与关键关系约束。

不适合：

- 核心查询和关联字段；
- 必须唯一或外键约束的数据；
- 频繁按内部子字段过滤排序却没有明确索引策略；
- 用来逃避正常 Schema 设计。

JSON 字段必须定义最大大小、Schema/版本、敏感数据规则和索引方式。

## 审计与软删除

- `created_at`/`updated_at` 可用于业务追踪，但不能替代审计日志。
- `created_by`/`updated_by` 只在业务需要时保存，注意主体类型和隐私。
- 软删除只在恢复、审计或外部引用确有需要时使用。
- 软删除表必须解决唯一约束、默认查询过滤、索引膨胀、外键和最终物理清理。
- 不默认给所有表添加 `deleted_at`。
