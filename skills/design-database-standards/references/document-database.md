# 文档数据库附录（MongoDB 类）

仅在项目明确使用文档数据库时读取本文件。

## 建模

- 根据访问模式决定 embed 或 reference，而不是机械照搬关系数据库范式。
- 经常一起读取且生命周期一致的数据适合嵌入。
- 高频独立更新、多对多、无限增长集合通常适合引用。
- 文档大小有硬限制时，数组必须有增长上限。
- 即使数据库 schema-flexible，也应使用 Schema Validation 或应用契约约束关键字段。
- 不把“无 Schema”作为快速开发默认。

## 标识与一致性

- `_id` 与业务 ID 的关系明确。
- 唯一业务键创建 unique index。
- 单文档原子性是重要设计边界；跨文档事务只在确有必要时使用。
- 多文档事务有性能与运维成本，不能用于模拟所有关系型设计。

## 索引

- 索引基于真实 query shape。
- 联合索引顺序考虑 equality、sort、range 和实际执行计划。
- 每个索引都会增加写入和存储成本。
- wildcard index 不替代正常 Schema 和查询设计。
- 删除索引前可利用 hidden index 等功能验证影响（引擎支持时）。

## TTL 与生命周期

TTL index 可自动删除过期文档，但：

- TTL 删除不是精确时钟触发；
- 建 TTL 前若已有大量过期数据，可能产生突发删除负载；
- 应先批量清理存量并观察性能；
- 合规删除和归档仍需完整生命周期设计。

## 迁移

- 新字段提供安全缺省；
- 旧文档与新文档会长期并存，读取代码必须兼容；
- 大规模 updateMany 仍需限速、批处理、checkpoint 和监控；
- schema validation 收紧前先统计和清理历史异常文档。
