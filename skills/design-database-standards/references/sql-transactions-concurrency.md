## SQL 基线

- 所有外部输入使用参数化查询/绑定变量。
- 禁止拼接 SQL 处理用户输入。
- 生产查询显式列出需要字段；避免 `SELECT *` 造成 Schema 演进和网络浪费。
- SQL 应可追踪到业务操作，但日志不得打印敏感绑定参数。
- 避免数据库特定技巧散落业务代码；复杂特性封装并有测试。
- 数据类型比较保持一致，避免隐式转换导致索引失效。

## 查询与分页

- 所有可能增长的集合查询必须有上限。
- 分页必须稳定排序并带唯一决胜键。
- 大数据量优先 keyset/cursor pagination；深 OFFSET 需要成本验证。
- 查询条件、排序字段和 IN 项数设置上限。
- 避免 N+1；使用批量查询、JOIN 或 DataLoader 等适合方式。
- 避免无界 `COUNT(*)` 作为每页必需元数据，特别是大表复杂过滤。
- 对关键 SQL 保留 EXPLAIN/执行计划基准和数据规模假设。

## 写入与批量

- 批量写入设置单批行数、参数数和事务大小上限。
- UPSERT/MERGE 语义必须理解数据库实际并发行为。
- 唯一性依赖约束，不使用“先查后插”防重复。
- 更新语句必须有明确 WHERE；高风险全表 UPDATE/DELETE 设置保护门禁。
- 大删除优先分批，避免长事务、WAL/binlog 暴涨和复制延迟。

## 事务边界

- 事务围绕业务原子性定义，不围绕 controller/service 方法机械开启。
- 事务尽量短，只包含必要数据库工作。
- 禁止在持有行锁/表锁时调用不可控 HTTP/RPC、发送邮件或等待用户输入。
- 外部副作用使用 outbox、事务消息或补偿等模式协调。
- 明确事务传播和嵌套语义；不要假设所有框架 `nested` 都是独立事务。
- 事务失败后连接状态和对象状态必须正确清理。

## 隔离级别

隔离级别由业务不变量决定，需要理解：

- dirty read；
- non-repeatable read；
- phantom；
- lost update；
- write skew；
- serialization anomaly。

不要假设“更高隔离永远更安全且无代价”。

关键资金、库存、额度等不变量必须写出并发场景，并证明当前隔离 + 锁/约束能保护。

## 锁与死锁

- 尽量按稳定顺序访问多行/多表，减少死锁。
- 锁范围和持有时间必须最小。
- `SELECT ... FOR UPDATE` 等悲观锁只在确有并发冲突价值时使用。
- 避免对大范围结果加锁。
- 数据库 deadlock detector 终止事务后，只在事务可安全重放时重试。
- 锁等待必须有超时和监控。

## 乐观并发

适合冲突较低、不能长期持锁的更新。

常见方式：

```sql
UPDATE orders
SET status = ?, version = version + 1
WHERE id = ? AND version = ?;
```

要求检查受影响行数；0 行表示冲突或不存在，不得静默成功。

## 读副本

使用 read replica 必须承认复制延迟：

- 写后立即读是否允许旧数据；
- 登录、支付、权限等强一致读是否强制主库；
- session/read-your-writes 如何实现；
- replica lag 超阈值时如何降级；
- 报表查询是否可接受延迟；
- failover 后 DNS/连接池和事务语义如何恢复。

不要把所有 SELECT 自动发往副本而不定义一致性。
