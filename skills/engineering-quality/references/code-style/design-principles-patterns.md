## 设计优先级

设计质量的优先级：

1. 正确性和安全性；
2. 清晰性和可维护性；
3. 可测试性和可演进性；
4. 性能与资源效率；
5. 复用和抽象程度。

不得以类数量、接口数量或使用设计模式数量衡量设计成熟度。

## 基本原则

- **KISS**：选择能清楚解决当前问题的最简单设计。
- **YAGNI**：不为没有证据的未来需求建立复杂扩展点。
- **DRY**：消除真正的知识重复，不机械合并外观相似但变化原因不同的代码。
- **SOLID**：用于识别职责、替换、接口和依赖问题，不作为制造过多抽象的理由。
- 优先组合而非继承；继承仅用于稳定的“是一个”关系和可替换语义。
- 依赖倒置应用于变化边界、外部系统和难以测试的副作用，不要求每个类都有接口。
- 优先不可变数据、显式状态转换和受控副作用。
- 让非法状态难以表示，优先使用类型和值对象表达约束。
- 只抽象已出现且能证明共同变化原因的重复。

## 模式选择流程

使用模式前回答：

1. 当前具体问题是什么？
2. 哪个变化点或边界会持续存在？
3. 不使用模式的最简单实现是什么？
4. 模式减少了什么耦合、分支或重复？
5. 新增的类型、间接层和运行成本是什么？
6. 团队是否能从名称和结构识别该模式？
7. 是否有测试证明替换、扩展和失败行为？

无法回答时，先使用简单实现。

## 常用模式

### Strategy

适用于同一职责存在多种可替换算法或规则。

要求：

- 共同契约稳定；
- 调用方不依赖具体策略；
- 策略差异有独立测试。

不要仅为一个简单 `if` 创建策略层。

### Factory

适用于创建逻辑复杂、依赖运行时信息或需要隐藏具体实现。

不要建立只包装单个构造函数且无变化价值的工厂。

### Adapter

用于隔离第三方或遗留接口，将其转换为内部稳定契约。

适配器应承担协议转换，不应成为任意业务逻辑堆积点。

### Decorator

用于按组合方式增加横切行为，例如缓存、度量或权限检查。

必须明确顺序、重复应用和异常传播行为。

### State

适用于对象行为随有限状态变化，且条件分支已难以维护。

状态转换必须显式、可验证，并防止非法转换。

### Command

适用于把操作作为值进行排队、审计、撤销、调度或异步执行。

命令应表达意图，不直接携带不受控基础设施对象。

### Observer / Domain Event

适用于一个事实需要通知多个独立订阅者。

必须明确顺序、重复投递、幂等、事务边界和失败隔离。

### Builder

适用于构造参数较多、存在可选字段或需要分阶段验证不变量。

简单数据对象不应机械创建 Builder。

### Repository

用于隔离领域模型与持久化技术。

避免暴露任意 ORM 查询、通用万能 CRUD 或基础设施类型到领域层。

### Specification

适用于可组合、可复用的业务谓词或查询条件。

简单单次条件优先直接表达，避免过度对象化。

### Result / Outcome

适用于可预期失败需要作为显式值返回的场景。

程序缺陷仍应与预期失败区分，详细规则属异常处理层职责。

## 谨慎使用的模式

以下模式并非禁止，但必须有明确理由：

- Singleton：容易形成全局状态、测试隔离和生命周期问题；
- Service Locator：隐藏依赖并降低可测试性；
- Abstract Factory：可能造成大量平行类型；
- 通用 BaseService/BaseRepository：常把无关职责强行统一；
- 全局 Event Bus：容易隐藏控制流和失败；
- 多层 Facade/Proxy：可能只增加跳转而无边界价值；
- 反射驱动注册：降低可发现性和静态安全；
- 大型依赖注入容器自动扫描：需控制可见性和启动失败。

## 反模式

必须治理：

- God Object / God Service；
- 循环依赖；
- 贫血模型与业务规则散落；
- Shotgun Surgery；
- Feature Envy；
- Primitive Obsession；
- Boolean Blindness；
- Magic Number/String；
- 隐藏全局状态；
- 深继承树；
- 过度通用的 `utils`；
- 通过注释解释无法理解的复杂控制流；
- 为“以后可能需要”预留大量接口和扩展点。

## 模式验收

引入模式后必须验证：

- 职责比之前更清楚；
- 依赖方向更稳定；
- 分支和重复有所减少；
- 新增实现可独立测试；
- 失败、生命周期和并发行为明确；
- 没有把简单控制流变成难以追踪的间接调用；
- 文档说明了选择原因和替代方案。
