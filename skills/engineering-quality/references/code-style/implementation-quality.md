## 函数与方法

- 每个函数应承担一个可命名的完整职责。
- 函数长度不设跨语言硬阈值；当需要滚动、存在多层嵌套或难以命名时应重构。
- 参数应保持精简；多个相关参数使用值对象或配置对象。
- 避免布尔参数控制多个行为，优先使用明确方法或枚举。
- 返回值和副作用必须匹配名称。
- 查询和命令尽量分离。
- 复杂条件提取为有业务意义的命名表达式。
- 提前返回可用于减少嵌套，但不得破坏资源清理和事务语义。
- 不隐藏昂贵 I/O、重试或跨进程调用。

## 类型与数据

- 使用类型表达有效范围、单位、状态和所有权。
- 避免用字符串承载所有领域概念。
- 构造完成后对象应满足不变量。
- 优先不可变对象；可变状态必须限制作用域。
- 集合边界明确可变性和所有权，不无条件暴露内部集合。
- 时间使用明确类型和时区；金额使用精确十进制或最小货币单位。
- 序列化模型与领域模型可按边界分离，不让外部协议控制内部设计。

## 空值与失败

- 空值语义必须明确，不使用空字符串、零、空集合和 `null` 混合表示不同状态。
- 优先使用语言支持的可选类型、结果类型或明确异常。
- 不捕获后返回默认值掩盖失败。
- 不使用特殊数字或字符串作为隐式错误码。
- 详细异常分类、传播、统一响应、重试和超时属异常处理层职责。

## 副作用与资源

- 副作用集中在清晰边界。
- 文件、连接、锁、事务、流和订阅必须明确所有权与释放方式。
- 使用语言的作用域资源管理机制。
- 不在构造函数、属性访问器或普通 `toString` 中执行不可预期 I/O。
- 事务范围尽量小，禁止在长事务中执行不受控远程调用。
- 时间、随机数、环境变量和外部服务应可注入或替换以便测试。

## 配置与依赖

- 环境差异通过配置管理，不硬编码地址、凭据和部署参数。
- 配置必须有类型、默认值、范围校验和失败策略。
- 依赖声明保持最小，删除未使用依赖。
- 使用锁文件或构建系统保证可重复解析。
- 引入第三方依赖前评估维护状态、许可证、安全、大小和替换成本。
- 禁止复制来源不明或许可证不兼容代码。
- 公共依赖升级应经过兼容性测试。

## 安全

- 在所有信任边界验证输入，并在输出边界执行必要编码。
- 数据库操作使用参数化查询或安全 ORM 接口。
- 禁止硬编码密钥、令牌、私钥和真实生产凭据。
- 使用平台标准密码学和安全随机数，不自行设计加密协议。
- 权限检查靠近受保护操作，默认拒绝。
- 敏感数据最小化收集、传输、存储和暴露。
- 反序列化、文件路径、命令执行和模板渲染必须考虑注入风险。
- 依赖和构建产物应纳入漏洞与供应链检查。

## 并发

- 明确数据所有权和共享可变状态。
- 优先消息传递、不可变数据或受控同步。
- 锁顺序、可重入性和线程安全必须记录。
- 禁止在持锁期间执行不受控 I/O。
- 异步操作必须支持取消和超时。
- 不使用睡眠作为并发同步机制。
- 处理竞态、重复执行、乱序、饥饿和背压。
- 并发集合或原子操作不能自动保证整体业务不变量。

## 性能

- 先确保正确性和可读性，再依据测量优化。
- 评审明显的时间和空间复杂度风险。
- 为缓存、批处理、队列和缓冲设置容量与淘汰上限。
- 避免 N+1 查询、无界读取、重复序列化和不必要复制。
- 性能优化必须有基准、剖析或生产指标证据。
- 优化后的复杂实现应记录假设、输入规模和退化条件。
- 不为了微小局部性能牺牲公共 API 清晰性，除非数据证明必要。
