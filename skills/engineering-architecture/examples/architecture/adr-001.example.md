# NovaPay ADR-001：模块化单体 + 清算任务队列

- Status: Accepted
- Date: 2026-08-07
- Owners: 交易组
- Related: ADR-002（卡数据 token 化）

## Context

NovaPay 从零起步，团队 2 组 8 人，边界仍在演进。评审曾讨论直接上微服务，但交易与清算的独立扩缩、故障隔离需求尚未被数据证明；分布式事务和最终一致性成本会拖慢 4 个月 MVP。

## Architecture Drivers

- 功能驱动：交易受理、清算、对账、审计。
- 质量属性：受理 P99 ≤ 800ms；单可用区故障 2 分钟恢复；对账 ≤ 4 小时。
- 约束：8 人团队、4 个月 MVP、K8s 经验有限、监管留存 5 年。

## Decision

采用模块化单体，边界为交易/清算/商户/审计四个清晰模块，各自数据 Owner 与公开契约；清算走异步任务队列（Outbox + 至少一次投递 + 幂等消费）。不拆微服务。

## Alternatives

### 方案 A：模块化单体 + 队列（采纳）

- 优点：本地事务简单、MVP 快、调试成本低、边界可演进。
- 缺点：单部署单元，独立扩缩受限。
- 风险：模块规则不执行会退化为大泥球——用 ArchUnit 依赖检查 + 模块级测试治理。

### 方案 B：直接拆微服务（拒绝）

- 优点：独立扩缩、故障隔离。
- 缺点：8 人团队运维成本高、分布式事务复杂、MVP 延迟、边界未稳定。
- 风险：网络失败、最终一致性、多版本契约，收益未证实。

## Consequences

### Positive

- 4 个月 MVP 可交付；本地事务简单；清算队列解决削峰。
- 四个模块边界清晰，未来可单独演进为服务。

### Negative / Trade-offs

- 单部署单元限制独立扩缩——通过 worker 独立进程缓解清算扩缩。
- 需持续治理模块边界（依赖扫描）。

## Risks and Mitigations

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 单库容量不足 | 高 | 分区 + 归档 + 缓存；ADR-001 revisit 条件之一 |
| 模块边界退化 | 中 | ArchUnit 依赖规则 + 模块级测试 |
| 清算积压 | 中 | worker 扩缩 + 积压告警 |

## Validation

- 容量测试：单实例 QPS 满足 P99 ≤ 800ms。
- 故障实验：kill 一个 worker 实例，队列恢复消费。
- 模块依赖扫描：ArchUnit 验证单向依赖。

## Revisit Trigger

- 交易/清算出现独立扩缩需求且单体扩缩受限；
- 团队规模显著增长导致发布协调瓶颈；
- 单库容量达上限无法通过分区/归档解决。
