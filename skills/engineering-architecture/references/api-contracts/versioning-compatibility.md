## 兼容性原则

兼容性必须分别评估：

- 旧客户端调用新服务；
- 新客户端调用旧服务；
- 请求兼容；
- 响应兼容；
- 语法兼容；
- 语义兼容；
- 行为、性能和安全兼容。

“Schema 能解析”不代表行为兼容。

每次变更必须由自动差异工具和契约测试验证，并记录调用方影响。

## 通常兼容的变更

在满足约束时通常兼容：

- 新增可选请求字段，服务端不要求旧客户端提供；
- 新增可选响应字段，客户端忽略未知字段；
- 新增新端点；
- 放宽输入约束，但不破坏安全和语义；
- 增加新的可选过滤或排序能力；
- 增加新的错误类型，但调用方有通用未知错误处理；
- 增加新的事件订阅能力。

仍需检查：

- 生成客户端是否拒绝未知字段；
- 严格反序列化是否失败；
- 新字段名是否冲突；
- 响应增大是否突破限制；
- 新行为是否改变缓存、排序或权限。

## 破坏性变更

通常属于破坏性变更：

- 删除或重命名端点、字段、参数或枚举值；
- 改变字段类型、格式、单位、精度或含义；
- 把可选字段改为必填；
- 把可空改为不可空而旧数据可能为空；
- 收紧校验范围；
- 改变默认值；
- 改变分页顺序、游标语义或重复/遗漏保证；
- 改变状态码或错误码语义；
- 改变认证方式、权限范围或数据可见性；
- 改变同步操作为异步而无迁移；
- 降低限额、超时或保留期且调用方依赖旧值；
- Protobuf 重用已删除字段编号；
- 事件字段删除或语义改变。

破坏性变更必须发布新版本或提供兼容迁移层。

## 枚举与未知字段

新增枚举值在理论上是扩展，但常破坏穷举客户端。

要求：

- 客户端有 `UNKNOWN` 或默认分支；
- 服务端不把未知请求枚举静默映射为其他值；
- 枚举是否封闭必须写入契约；
- Protobuf 按其未知枚举和字段保留规则设计；
- 删除枚举值时先停止产生，再观察调用方，最后废弃。

响应客户端应忽略未知字段；请求端未知字段策略必须统一：

- 公共写 API 默认可选择严格拒绝以发现拼写错误；
- 需要代理转发或渐进升级的接口可选择保留未知字段；
- 选择结果必须写入契约和测试。

## 版本策略

原则：

- 兼容变更不应无意义提升主版本。
- 版本代表契约集合，不代表每次部署。
- 选择路径、主机、Header、媒体类型或 RPC package 版本之一并统一。
- 同一主版本内保持兼容。
- 不把日期当版本，除非组织采用有明确生命周期的日期版本策略。
- OpenAPI `info.version` 表示 API 描述版本；`openapi` 字段表示 OAS 规范版本，二者不得混淆。

常见路径版本：

```text
/v1/orders
/v2/orders
```

新主版本应有明确差异、迁移价值和下线计划。

## 弃用流程

弃用必须包含：

1. 标记被弃用的操作或字段；
2. 提供替代接口和迁移文档；
3. 通知已知调用方；
4. 发布弃用时间和计划下线时间；
5. 在契约中使用 `deprecated`；
6. HTTP 接口可使用标准 `Deprecation` Header；
7. 计划停止响应时可使用 `Sunset` Header；
8. 通过调用量、客户端版本和错误率观测迁移；
9. 提供测试环境或兼容验证；
10. 达到退出条件后才下线。

`Sunset` 时间不得早于弃用时间。

## 迁移与双轨运行

- 新旧版本并行期间明确数据一致性和功能差异。
- 使用适配层时，明确哪些语义无法完全兼容。
- 不让旧版本永久成为无责任人分支。
- 迁移文档提供字段映射、状态码变化和示例。
- 高风险变更可使用影子流量、双写校验或响应比较。
- 禁止在同一 URI 下按客户端身份返回语义不同且不可发现的契约。

## 下线验收

下线前必须确认：

- 已知调用方完成迁移；
- 流量达到组织阈值；
- 没有关键后台任务或离线客户端仍使用；
- 监控能识别残余调用；
- 支持和事故响应知道下线计划；
- 文档、SDK、示例和入口已更新；
- 回滚或临时恢复方案明确；
- 数据和审计保留符合要求。
