## gRPC 服务设计

- Service 和 RPC 名称表达领域能力，不映射控制器或数据库操作。
- 请求和响应使用独立消息，即使当前字段相同。
- 单项读取、列表、创建、更新、删除和自定义动作保持一致模式。
- 明确每个 RPC 的幂等性、权限、截止时间和最大消息大小。
- 不通过 metadata 传递应位于消息中的核心业务字段。
- 公共 RPC 避免返回内部存储类型或语言专属类型。
- package 名称和版本策略统一。

## Deadline、取消与重试

- 客户端必须设置 deadline；gRPC 默认可能无限等待。
- 服务端应检查取消并停止不必要工作。
- deadline 传播到下游，并扣减已消耗时间。
- 重试只用于幂等或有幂等保护的 RPC。
- Retry Policy 必须限制次数、退避和可重试状态。
- streaming RPC 的恢复点、重复消息和续传语义必须明确。

## gRPC 状态

使用 gRPC 官方状态语义，不创建重名但不同义的状态。

重点区分：

- `INVALID_ARGUMENT`：与系统状态无关的参数问题；
- `FAILED_PRECONDITION`：当前系统状态不允许执行；
- `ABORTED`：并发冲突或事务中止；
- `NOT_FOUND`：资源不存在；
- `ALREADY_EXISTS`：创建冲突；
- `DEADLINE_EXCEEDED`：截止时间耗尽；
- `UNAVAILABLE`：通常为临时不可用，但非幂等操作仍不能盲目重试；
- `INTERNAL`：内部不变量破坏；
- `UNAUTHENTICATED` 与 `PERMISSION_DENIED`：认证和授权。

业务错误细节与稳定错误码属异常处理层职责。

## Protobuf 兼容性

- 已发布字段编号永久保留，不得重用。
- 删除字段时使用 `reserved` 保留编号和名称。
- 不改变字段编号。
- 不把字段类型改成线格式兼容但语义不兼容的其他类型。
- 新字段优先 optional，并定义缺省行为。
- 不使用 required 破坏演进。
- 枚举必须有零值，通常为 `UNSPECIFIED`。
- 枚举值编号不得重用。
- `oneof` 变更需要评估字段存在性和旧客户端行为。
- 包、服务和消息重命名通常是破坏性变更。
- JSON 映射也属于兼容性范围，不能只看二进制线格式。

## 流式 RPC

必须定义：

- 客户端流、服务端流或双向流；
- 消息顺序；
- 每条消息和整个流的幂等性；
- 背压和缓冲上限；
- 心跳和空闲超时；
- 中断后的续传位置；
- 重复消息；
- 部分处理与最终状态；
- 取消和资源释放；
- 最大消息大小与频率。

不使用无界流隐藏缺失的分页或异步任务模型。
