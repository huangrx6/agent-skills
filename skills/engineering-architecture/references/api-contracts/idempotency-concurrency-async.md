## 幂等语义

幂等表示相同请求重复执行后，目标资源的预期状态和业务副作用不继续累积。

- GET、HEAD、PUT、DELETE 按 HTTP 语义应幂等。
- POST 默认不幂等，但可通过幂等键建立应用级幂等。
- PATCH 是否幂等取决于补丁操作；“将值设为 X”可幂等，“增加 1”通常不幂等。
- 幂等不保证每次响应字节完全相同，也不保证不记录访问审计。
- 文档必须声明可安全重试的操作和条件。

## 幂等键

适用于支付、下单、发货、创建任务等可能因网络重试重复提交的写操作。

必须定义：

- Header 或字段名称；
- 键的格式、最大长度和熵；
- 作用域，例如调用方 + 操作 + 资源；
- 保留期限；
- 是否绑定请求正文摘要；
- 同键不同请求的冲突行为；
- 首次处理中再次请求的行为；
- 完成后响应重放或状态查询方式；
- 数据隔离和防猜测要求。

推荐行为：

- 相同键和等价请求返回首次结果；
- 相同键但请求内容不同返回冲突；
- 处理中返回明确状态或同一操作资源；
- 键过期后行为必须文档化；
- 服务端不得依赖客户端永远不重复键。

## 超时与结果不确定

客户端超时、连接断开或 5xx 不能证明服务端写入未发生。

因此：

- 重试使用同一幂等键；
- 提供按幂等键或客户端引用查询结果的能力；
- 不让客户端通过盲目创建新请求规避未知结果；
- 对支付等高风险操作提供对账或状态确认；
- 网关超时与业务失败必须区分。

## 并发控制

避免丢失更新的推荐方式：

- ETag + `If-Match`；
- 显式 `version` 字段；
- 条件写入；
- 唯一约束和事务；
- 领域级命令序列号。

规则：

- 读取资源时返回版本标识。
- 更新时要求客户端提交版本条件。
- 条件不满足返回 412；要求条件但缺失可返回 428。
- 409 用于其他状态冲突。
- 不使用“最后写入者获胜”作为默认，除非业务明确接受数据丢失。
- 批量更新必须对每项或整批定义版本语义。
- 版本标识不得包含需要客户端解析的内部结构。

## 异步操作

长耗时或不可预测操作应返回 202 和操作资源：

```text
POST /exports
202 Accepted
Location: /operations/op_123
```

操作资源建议包含：

```json
{
  "id": "op_123",
  "status": "RUNNING",
  "progress": 35,
  "createdAt": "2026-08-07T03:59:00Z",
  "links": {
    "self": "/operations/op_123",
    "result": null
  }
}
```

状态至少区分：

- `PENDING`
- `RUNNING`
- `SUCCEEDED`
- `FAILED`
- `CANCELLING`
- `CANCELLED`
- `EXPIRED`

要求：

- 状态转换明确；
- 成功后提供结果资源；
- 失败后使用稳定错误码；
- 定义状态资源保留期限；
- 可提供 `Retry-After`；
- 进度字段必须说明是否精确；
- 不在 202 响应中暗示操作已成功。

## 取消与重试

- 明确哪些状态可取消。
- 取消请求本身应幂等。
- 取消成功不保证底层所有副作用回滚，必须说明补偿语义。
- 客户端轮询应使用退避和上限。
- 服务端重试不得造成重复业务副作用。
- 操作过期和结果清理后返回稳定生命周期错误。

## 回调与 Webhook

Webhook 契约必须定义：

- 事件类型和版本；
- 目标验证和所有权确认；
- 签名算法、密钥轮换和时间戳；
- 重放保护；
- 投递标识和幂等处理；
- 超时、重试、退避和最大次数；
- 顺序和重复投递语义；
- 响应码含义；
- 死信或人工重放机制；
- 敏感字段最小化。

回调不能作为唯一结果查询机制；调用方应能主动查询最终状态。
