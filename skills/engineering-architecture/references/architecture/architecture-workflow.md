## 第一步：建立上下文

开始设计前明确：

- 系统解决的业务问题；
- 主要用户和调用方；
- 上下游系统；
- 核心业务能力；
- 数据种类与敏感级别；
- 信任边界；
- 部署环境；
- 团队和所有权；
- 已存在的遗留约束。

先画 System Context。没有上下文时，不讨论微服务、消息队列、数据库或云产品。

## 第二步：识别架构驱动因素

只把会显著影响结构的需求提升为架构驱动因素，例如：

- 核心交易 P99 延迟；
- 峰值吞吐与增长；
- 可用性和允许停机；
- RPO/RTO；
- 数据驻留与合规；
- 强一致或最终一致；
- 独立部署频率；
- 多租户隔离；
- 离线能力；
- 外部合作方兼容期限；
- 团队规模与平台成熟度。

每个质量属性写成场景：

```text
来源 → 刺激 → 环境 → 目标 → 响应 → 可测指标
```

示例：

```text
高峰期单可用区故障
→ 订单创建流量继续进入
→ 系统在 2 分钟内恢复容量
→ 99.9% 请求不丢失
→ P99 在恢复期不超过 2 秒
```

## 第三步：形成候选方案

至少比较两个可行方案，除非存在明确平台或法规强制。

对每个方案评估：

- 复杂度；
- 交付速度；
- 独立部署；
- 数据一致性；
- 故障隔离；
- 性能；
- 成本；
- 安全；
- 运维；
- 团队认知负担；
- 迁移和退出成本。

优先能满足当前驱动因素的最简单方案。

## 第四步：验证关键风险

高风险决策使用 Spike、原型、容量测试或故障实验验证。

优先验证不可逆或昂贵假设：

- 单库是否能满足容量；
- 网络调用是否满足延迟；
- 消息顺序是否真的需要；
- 跨区域一致性能否接受；
- 某云服务是否存在锁定风险；
- 团队能否运维事件驱动或 Kubernetes；
- 数据迁移能否在线完成。

不要用 PoC 验证显而易见的语法和 SDK 用法。

## 第五步：记录决策

对架构显著决策写 ADR：

- Context；
- Decision；
- Alternatives；
- Consequences；
- Risks；
- Validation；
- Revisit Trigger。

ADR 记录“为什么”，架构图记录“是什么”。

## 第六步：持续验证

把关键架构约束转为自动检查：

- 禁止模块反向依赖；
- 禁止跨服务数据库访问；
- API/Schema 兼容检查；
- SLO 和容量告警；
- 架构依赖扫描；
- 数据分类和权限检查；
- 部署策略验证。

架构不是一次性评审。重大变化、SLO 持续不达标、团队边界变化或成本失控时重新评估。

## 常见失败方式

避免：

- 先选技术，再找问题；
- 一开始画几十张图；
- 只考虑正常流程；
- 只写“高可用、高并发”而没有数字；
- 把未来所有可能需求一次性设计进去；
- 用微服务掩盖模块边界不清；
- 只讨论代码结构，不讨论数据和部署；
- 只记录最终方案，不记录被拒绝方案；
- 架构评审没有风险、Owner 和退出条件。
