## 选择原则

架构风格是约束和权衡集合，不是产品清单。

选择时回答：

- 主要质量属性是什么；
- 哪些数据必须一致；
- 哪些部分必须独立部署；
- 哪些故障必须隔离；
- 调用关系是否需要同步；
- 团队能否运维该复杂度；
- 迁移和退出成本是什么。

## 模块化单体

默认优先项。

优点：

- 本地调用和事务简单；
- 调试与测试成本低；
- 部署路径简单；
- 便于业务边界演进。

风险：

- 模块规则不执行会退化为大泥球；
- 全局数据库容易形成隐式耦合；
- 单部署单元可能限制独立扩缩。

## 微服务

适用于：

- 业务边界稳定；
- 多团队需要独立交付；
- 部分能力需要独立扩缩；
- 故障隔离价值高；
- 平台、CI/CD、可观测性和安全治理成熟。

成本包括：

- 网络失败；
- 最终一致性；
- 多版本契约；
- 分布式追踪；
- 部署和配置管理；
- 数据迁移；
- 更高测试成本；
- 事件和重试治理。

不要把“拆得小”当作微服务目标。

## 分层与六边形

分层适合控制依赖方向；六边形/Ports and Adapters 适合隔离外部系统和框架。

规则：

- 领域核心不依赖数据库、HTTP 或消息框架；
- 端口表达业务需要；
- Adapter 负责协议转换；
- 不为每个简单函数制造五层转发；
- 层级数量由变化边界决定。

## 事件驱动

适合：

- 多消费者；
- 时间解耦；
- 削峰；
- 异步工作流；
- 数据变化传播。

代价：

- 最终一致性；
- 重复和乱序；
- Schema 演进；
- 调试困难；
- 失败恢复复杂。

事件只表达已经发生的事实。不要用事件隐藏同步业务依赖。

## CQRS

仅当读写模型存在真实差异时使用，例如：

- 读取形状和写入模型明显不同；
- 读扩展压力远高于写；
- 多种复杂读模型；
- 写模型需要严格领域约束。

简单 CRUD 不应采用 CQRS。

## Event Sourcing

只有在以下价值明显时考虑：

- 完整历史本身是核心业务资产；
- 必须重建过去状态；
- 审计和时间旅行查询有高价值；
- 领域适合事件作为事实来源。

必须处理：

- 事件永不可随意修改；
- Schema 演进；
- 快照；
- 重放成本；
- GDPR/删除要求；
- 副作用重放隔离。

审计日志需求本身通常不足以采用 Event Sourcing。

## Queue Worker

适合长耗时、批处理、异步通知和削峰。

明确：

- 队列容量；
- 幂等；
- 重试；
- DLQ；
- 背压；
- 任务超时；
- 任务状态。

## Serverless

适合事件触发、波动流量和低运维需求。

评估：

- 冷启动；
- 执行时长；
- 并发模型；
- 状态外置；
- 平台锁定；
- 成本随流量增长；
- 本地调试。

## 组合原则

真实系统可以组合多种风格，例如：

```text
模块化单体 + Queue Worker
微服务 + Event-Driven
HTTP API + 内部六边形架构
```

组合时必须说明每种风格解决的具体问题，避免模式堆砌。
