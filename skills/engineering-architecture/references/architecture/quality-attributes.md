## 写成可验证场景

使用六要素：

```text
Source / Stimulus / Environment / Artifact / Response / Measure
```

没有 Measure 的质量属性不能作为验收依据。

## 性能

至少明确：

- 关键操作 P50/P95/P99；
- 吞吐；
- 并发；
- 最大消息/请求大小；
- 批处理完成窗口；
- 后台积压恢复速度。

不要只写平均延迟。

## 可用性与可靠性

明确：

- SLO；
- 故障范围；
- RTO；
- RPO；
- 数据丢失容忍；
- 降级行为；
- 依赖故障处理；
- 计划维护。

高可用需要对应故障模型，例如：

```text
单实例故障
单可用区故障
数据库主节点故障
消息系统积压
外部支付不可用
```

## 可扩展性

明确：

- 当前容量；
- 12/24 月增长假设；
- 横向还是纵向扩展；
- 哪些组件独立扩展；
- 扩展触发指标；
- 数据分区策略。

不要为了“未来十倍流量”预先分布式化，除非增长有证据。

## 安全与隐私

在架构阶段定义：

- 信任边界；
- 身份；
- 权限；
- 多租户；
- 数据分类；
- 加密；
- 密钥边界；
- 威胁模型；
- 审计；
- 数据保留。

架构变更必须更新威胁模型。

## 可维护与可演进

衡量：

- 模块耦合；
- 构建时间；
- 部署频率；
- 变更影响范围；
- 技术栈数量；
- Owner 清晰度；
- API/Schema 兼容性；
- 技术债务退出计划。

## 可运维与可观测

必须考虑：

- 健康信号；
- Metrics；
- Tracing；
- Logs；
- Dashboard；
- Alert；
- Runbook；
- Debug 路径；
- 配置和 Feature Flag；
- 回滚。

## 成本

成本是架构属性。

评估：

- 稳态成本；
- 峰值成本；
- 单交易成本；
- 存储增长；
- 跨区流量；
- 第三方许可证；
- 运维人力。

优化成本不能破坏不可接受的可靠性和安全性。

## 优先级冲突

质量属性会冲突，例如：

- 强一致 vs 可用性/延迟；
- 隔离 vs 成本；
- 灵活性 vs 简单性；
- 安全控制 vs 用户体验。

必须记录优先级，而不是假设所有属性同时最大化。
