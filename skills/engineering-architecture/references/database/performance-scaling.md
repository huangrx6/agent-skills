## 性能基线

数据库性能优化必须基于：

- 真实 query shape；
- 接近生产的数据量和分布；
- P50/P95/P99 延迟；
- QPS/TPS；
- rows examined/returned；
- buffer/cache hit；
- I/O；
- lock wait；
- replication lag。

不要仅凭 SQL 长度或“有索引”判断性能。

## 执行计划

关键查询上线前应检查执行计划：

- 实际使用的索引；
- 估算行数与实际行数偏差；
- 全表扫描是否合理；
- 排序、hash、临时表；
- JOIN 顺序；
- 回表和随机 I/O；
- 参数选择性差异。

统计信息过期会影响优化器，应有自动分析/统计维护策略。

## 连接池

- 连接数不是越多越好；受数据库 CPU、内存和并发能力限制。
- 服务实例扩容时计算总连接上限。
- 设置连接建立、获取、查询、事务空闲超时。
- 连接泄漏必须可监控。
- serverless/大量短实例场景考虑代理或连接复用层。
- 不使用数据库连接作为通用线程池。

## 容量和增长

至少预测：

- 日增行数；
- 主表/索引大小；
- WAL/binlog；
- 临时空间；
- 备份容量；
- 归档容量；
- 复制容量；
- 峰值增长倍数。

设置磁盘和对象数量告警，并定义扩容提前量。

## 分区

分区适合：

- 时间范围删除/归档；
- 极大表的分区裁剪；
- 管理窗口和维护需求。

不应仅因“表很大”自动分区。

必须定义：

- 分区键；
- 新分区自动创建；
- 默认分区；
- 旧分区归档/删除；
- 跨分区唯一性；
- 查询是否真正命中分区裁剪；
- 分区数量上限。

## 分片

只有单实例/合理垂直扩展和分区已无法满足容量、地域或隔离目标时考虑。

必须解决：

- shard key；
- 热点；
- 跨 shard 查询/事务；
- 全局唯一 ID；
- rebalancing；
- 故障域；
- 数据迁移；
- 运维和备份成本。

分片是架构决策，不是 SQL 优化手段。

## 热点与缓存

- 识别热门 key、单租户和单行更新热点。
- 避免全局计数器成为锁热点；必要时分桶或异步聚合。
- 缓存需要定义一致性、TTL、失效、穿透和雪崩策略。
- 缓存不能成为数据库数据完整性的唯一来源。

## 维护

根据引擎实施：

- vacuum/analyze；
- statistics；
- index rebuild/reorg；
- table optimize；
- dead tuple/fragmentation；
- 慢查询归档；
- 长事务清理。

维护任务必须有资源预算，不能与业务峰值争抢 I/O。
