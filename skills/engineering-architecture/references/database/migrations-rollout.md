## 核心原则

数据库变更不得假设应用与 Schema 同步切换。

生产变更必须考虑：

- 新旧应用并存；
- 长连接和后台任务；
- 读副本；
- CDC/ETL；
- 离线脚本；
- 回滚后的旧版本应用；
- DDL lock 和 metadata lock；
- 表重写；
- WAL/binlog/redo 增长；
- 临时空间；
- 复制延迟。

## Expand-Migrate-Contract

默认流程：

### 1. Expand

增加兼容结构，不删除旧结构：

- 新增 nullable 列；
- 新表；
- 新索引；
- 新可选关系；
- 双读/双写能力。

### 2. Migrate

逐步迁移：

- 新写入使用新结构；
- 必要时双写；
- 批量回填历史数据；
- 对账与校验；
- 切换读取；
- 观察旧字段/旧表访问归零。

### 3. Contract

确认旧代码和任务全部退出后：

- 停止双写；
- 删除旧字段/表；
- 收紧 NOT NULL；
- 删除兼容索引或触发器；
- 删除旧 API/ETL 依赖。

## 常见变更

### 新增列

低风险起点通常是 nullable 无昂贵默认值，然后：

1. 应用兼容新列；
2. 回填；
3. 校验无 NULL；
4. 再加 NOT NULL；
5. 最后要求应用必填。

现代数据库对“常量默认值”可能有快速路径，但必须以实际版本官方文档验证，不能写死为通用规则。

### 删除列

1. 代码停止读取；
2. 代码停止写入；
3. 观察数据库访问和 CDC 消费；
4. 发布等待窗口；
5. 删除依赖索引/约束；
6. DROP COLUMN。

### 重命名列

生产系统不要直接 rename 作为唯一动作。优先新增新列 + 双写/回填 + 切读 + 删除旧列。

### 改类型/缩短长度

属于高风险变更：

- 验证所有现有数据可转换；
- 评估表重写；
- 新列迁移通常比原地改类型更安全；
- 双写、回填、校验后切换。

### 改唯一约束

必须先处理历史冲突，并评估并发写入窗口；不能“先清历史，稍后再加约束”而无保护。

## 大表 DDL

变更前必须记录：

- 表行数/大小；
- 写入 QPS；
- 预计扫描/重写量；
- 锁级别和持锁阶段；
- 可否 concurrent/online/in-place/instant；
- 临时磁盘需求；
- 复制延迟风险；
- 超时和取消行为；
- 失败后遗留对象；
- 业务低峰窗口。

DDL 必须设置合理 lock timeout/statement timeout（若引擎支持），防止意外长时间阻塞生产。

## 数据回填

回填程序必须：

- 幂等；
- 按主键/游标分批；
- checkpoint；
- 可暂停/继续；
- 限速；
- 设置每批事务上限；
- 监控 CPU、I/O、锁等待、复制延迟；
- 记录成功/失败计数；
- 对单行异常有隔离策略；
- 支持 dry-run/估算；
- 完成后有独立校验。

不要：

- 单事务更新数千万行；
- 使用无稳定排序的 OFFSET 扫描动态表；
- 在回填过程中同时做不可控外部请求；
- 仅通过“脚本跑完”判断正确性。

校验方式包括：

- 行数；
- checksum/hash；
- 聚合和金额对账；
- 随机抽样；
- 双读比对；
- 业务不变量查询。

## 索引与约束上线

- 大索引优先使用引擎支持的 concurrent/online 方式。
- 先构建索引再绑定 UNIQUE/constraint 仅在数据库明确支持时使用。
- 新约束可能扫描全表；可用 NOT VALID/online validation 等能力时分阶段执行。
- 创建失败后的 invalid index/临时文件要有清理方案。

## 部署顺序

每个迁移 PR 必须写出：

```text
DB Expand → App compatible deploy → Backfill → Verify → Read switch → Observe → DB Contract
```

若允许应用回滚，回滚版本必须仍能运行在 Expand 后 Schema 上。

## 失败、回滚与前滚

- 非破坏性迁移可提供反向 migration，但仍需验证数据语义。
- 破坏性 DDL 不依赖自动 down migration 恢复数据。
- 优先设计 forward fix。
- 必须明确“在何阶段还能安全回滚应用”。
- DROP 前确认备份/PITR 能覆盖恢复目标。
- 高风险发布需要 stop condition，例如复制延迟、锁等待、错误率超过阈值即暂停。

## 迁移工具规则

使用 Flyway/Liquibase/框架 migration 时：

- 迁移脚本进入版本控制；
- 已在共享环境成功执行的 versioned migration 不得随意修改；
- 校验 checksum；
- 顺序确定；
- 禁止应用实例并发重复执行无锁迁移；
- 大数据回填和 DDL 可拆成运维步骤，不强塞进应用启动 migration；
- migration 超时/失败必须阻止继续发布，而不是静默忽略。
