## 数据库约束

数据库必须保护关键不变量，尤其是：

- 主键；
- 唯一业务键；
- 必填字段；
- 可在单行表达的范围/状态规则；
- 必须存在的引用关系。

应用校验用于友好错误和业务流程，数据库约束用于最终一致性保护，两者职责不同。

## 唯一性

- 业务唯一性必须有 UNIQUE constraint/index，而不是“先查再插”。
- 联合唯一约束字段顺序应与语义和常见查询一起评估。
- 包含 NULL 的唯一语义因数据库不同，必须验证实际引擎行为。
- 软删除后的唯一键是否允许复用必须明确，可使用部分索引或有效状态字段等方式实现。
- 分区/分片环境下，唯一约束是否跨分区生效必须验证。

## 外键

现代工程实践默认不在数据库层使用外键约束，引用完整性优先在应用层保障。原因是外键在高并发写入、分库分表、微服务数据所有权和 DDL 迁移复杂度上带来显著代价。

不使用数据库外键时，必须在应用层通过以下方式保障引用完整性：

- 插入前校验父记录存在；
- 删除前校验无子引用（或按业务规则级联）；
- 定期对账发现孤儿数据；
- 使用唯一约束和非空约束保护单表内不变量（这些不因不用外键而放弃）。

仅在以下条件全部满足时，才考虑在单库内使用数据库外键：

- 确定不会分库分表；
- 写入吞吐和锁代价经测量可接受；
- 数据生命周期在同一数据库内管理；
- 对数据完整性有极高合规要求（如金融核心账务）。

若使用外键：

- 删除/更新行为必须显式选择 `RESTRICT/NO ACTION/CASCADE/SET NULL`，不依赖默认值。
- 禁止使用 `CASCADE` 级联删除作为主要数据清理方式（可能触发意外批量删除）。
- 大表新增外键要评估验证扫描和锁，可采用数据库支持的分阶段验证方式。

## CHECK 与领域约束

- 单行范围、正值、状态组合等可用 CHECK。
- 不在 CHECK 中依赖易变化外部数据。
- 复杂跨行不变量使用唯一约束、事务、锁或领域机制实现。
- 约束名称要能从报错快速定位业务含义。

## 索引设计原则

索引由实际查询模式驱动。每个索引要回答：

1. 支持哪个查询/约束？
2. 选择性和数据分布如何？
3. 排序是否能利用？
4. 写放大和空间成本是多少？
5. 是否与现有索引重复或被前缀覆盖？
6. 是否能从执行计划和指标验证收益？

不要：

- 为每个外键/状态字段机械加单列索引；
- 为低选择性布尔字段单独建普通索引而无查询证据；
- 为一个偶发后台查询牺牲所有写入成本；
- 创建大量相似联合索引。

## 联合索引

字段顺序由查询谓词、排序和数据库优化器行为决定。

常见考虑：

- 等值过滤；
- 排序；
- 范围过滤；
- 选择性；
- 左前缀可用性；
- 是否需要覆盖返回列。

不要把“选择性最高放最前”作为绝对规则；必须结合真实 query shape 和执行计划。

## 覆盖、部分和表达式索引

适用时考虑：

- covering/include 列减少回表；
- partial/filtered index 只索引活跃子集；
- expression/function index 支持规范化或计算条件；
- unique expression index 支持大小写不敏感唯一性。

这些能力依赖数据库产品和版本，必须放在引擎附录实施。

## 索引治理

- 建索引前记录目标 query、基准和预计数据量。
- 生产创建大索引使用数据库支持的 online/concurrent 能力并评估失败恢复。
- 定期审查未使用、重复和膨胀索引。
- 删除索引前观察使用情况，并利用 invisible/hidden index 等能力时先做试验（若引擎支持）。
- 主键、唯一约束和外键依赖的索引不得按“未使用”指标盲删。
- 索引变更纳入迁移脚本和回滚/前滚计划。
