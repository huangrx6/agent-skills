# 提交信息：规范怎么说，这个仓库怎么定

**判据在 `scripts/commit_style.py` 里，不在这份文档里。** 这份文档解释「为什么是这些判据」，
以及那些**规范其实允许、但很容易被误传**的地方。两者不一致时以脚本为准，并回头修这里。

规范原文：<https://www.conventionalcommits.org/en/v1.0.0/>

## 一、规范那 16 条

按条目号列，**加粗的是脚本会拦的**。

| # | 规则 | 脚本检查 |
| --- | --- | --- |
| 1 | **提交必须以 type 开头，后接可选 scope、可选 `!`、必需的冒号和空格** | ✓ |
| 2 | 新增功能用 `feat`（对应 SemVer MINOR） | 靠人判断 |
| 3 | 修 bug 用 `fix`（对应 SemVer PATCH） | 靠人判断 |
| 4 | **scope 可选，必须是被括号包住的名词** | ✓（空括号、含空格会拦） |
| 5 | **描述必须紧跟冒号和空格，且是简短总结** | ✓（空描述会拦） |
| 6 | **正文可选，但必须在描述后空一行** | ✓ |
| 7 | 正文是自由格式，可以多段 | 不检查 |
| 8 | **footer 可选，一行一个；token + `:` 或 `#` + 值** | 部分 |
| 9 | **footer 的 token 里用 `-` 代替空白**（`BREAKING CHANGE` 例外） | ✓ |
| 10 | footer 的值可以跨行 | 不检查（解析从后往前找） |
| 11 | 破坏性变更写在 type/scope 前缀里，或写在 footer 里 | 靠人判断 |
| 12 | **写成 footer 时必须全大写 `BREAKING CHANGE`** | ✓ |
| 13 | 写在前缀里时 `!` 必须紧贴在冒号前 | 不检查（形状对即可） |
| 14 | **`feat`/`fix` 之外的 type 可以用** | 见第二节：这是「我们的约定」不是规范 |
| 15 | **实现者不得把这些当作大小写敏感**（`BREAKING CHANGE` 例外，它必须大写） | ✓ 只在第 12 条上生效 |
| 16 | `BREAKING-CHANGE` 与 `BREAKING CHANGE` 同义 | ✓ |

### 第 15 条最容易被写反

「实现者**不得**区分大小写」的意思是：`FEAT:` **不算违规**。
你能做的只是提醒「同一个仓库里最好一致」—— 而那是**建议**，不是规则。
把它写成硬规则，等于在一个说「无所谓」的地方自己造了个错。

### 第 14 条同理

其它 type **可以用**。所以「type 不在清单里」是**本项目的约定**，不是规范违规。
脚本把两类结论分开标注（`规范 规则 N` / `本项目约定：…`）就是为了这件事。

## 二、这个仓库定的 type 表

上面 11 个，脚本里是封闭列表。

| type | 什么时候用 | 容易搞混的地方 |
| --- | --- | --- |
| `feat` | 加了对使用者可见的新能力 | 内部重构**不算** —— 那用 `refactor` |
| `fix` | 修了一个 bug | 修自己刚提交的 bug 也算，但更该用 `--amend` |
| `docs` | 只改了文档 | 代码注释如果起文档作用，也可以算 `docs` |
| `style` | 不影响语义的格式（空格、换行、格式化） | 改格式化工具配置 → 那是 `build` 或 `chore` |
| `refactor` | 既不加功能也不修 bug 的改写 | 顺手修了 bug → 拆成两个提交 |
| `perf` | 为了快 | 只是"看起来更快"没量过 → 用 `refactor` |
| `test` | 加或改测试 | 为了过测试而改源码 → 那是 `fix` |
| `build` | 构建系统、依赖清单、镜像 | Dockerfile、requirements、package.json |
| `ci` | CI 配置与脚本 | 本地跑的脚本 → `chore` |
| `chore` | 其它杂项 | 拿不准时的兜底 —— 但别什么都往里塞 |
| `revert` | 回滚某个提交 | 规范 FAQ 推荐的写法，配 `Refs:` footer |

**拿不准时的判断顺序**：① 先看这个改动**对使用者可见吗**（可见 → `feat`/`fix`；
不可见 → 其余）② 再看**影响面最小的是哪个** ③ 还是拿不准 → **拆成两个提交**，
而不是硬选一个。规范 FAQ 也这么说：「符合多个 type 时，回去拆成多个提交」。

## 三、不是规则、只是建议的三条

规范**没有**规定下面这些。脚本把它们标成「本项目约定：可读性提示」，不挡提交。

| 建议 | 为什么 | 规范怎么说 |
| --- | --- | --- |
| type 用小写 | 同一个仓库里一致 | 规则 15 说不得区分大小写；FAQ 说「any casing may be used, but it's best to be consistent」 |
| 主题行 ≤ 72 字符 | 超过之后 `git log --oneline` 会截断 | 规范没提长度 |
| 主题行末尾不加句号 | 多数工具链的习惯 | 规范没提 |

## 四、中文怎么写（合法，且不受限制）

规范**从头到尾没有限制语言**。中文描述完全合法，而且这个仓库的历史里绝大多数是中文。

写中文时注意两点：

1. **冒号必须是 ASCII 的 `:`** —— 全角 `：` 会违反规则 1（形状要求的是 terminal colon）。
   历史里真的出现过（`feat(管理端)：修改用户名`），脚本现在会拦住它并指名道姓。
2. **type 和 scope 保持英文** —— 它们是给工具读的枚举值，不是给人读的描述。
   `feat(管理端)` 可以，`功能: xxx` 不行。

一段合规的中文提交信息：

```text
fix(worker): PARSER_* 主备名修复 + 发包指纹加固

主备名之前写反，导致切换后仍在读旧实例；顺带把发包指纹加进构建产物名，
部署时能一眼看出跑的是哪一版。现场并发参数还没调完，见 #229。

Reviewed-by: 张三
Refs: #228
```

## 五、不适用这一套的提交

脚本会把它们标成「不适用」并放行（退出码 0）—— 它们不是手写的常规提交：

- 合并提交（`Merge branch …` / `Merge remote-tracking branch …`）
- `git revert` 生成的默认信息（`Revert "…"`）—— 想规范就用 `revert:` type
- autosquash 标记（`fixup! …` / `squash! …` / `amend! …`）

**为什么要放行**：如果把 `Merge` 也当成违规，挂了 commit-msg 钩子的仓库就没法合并了 ——
而那是两件事。

## 六、脚本边界（这里没做、别读成做了）

- 不判断 type 用得**对不对**（`feat` 还是 `fix` 是语义判断，机器只能看形状）。
- 不检查 `!` 的位置（规则 13）—— 形状对了就行。
- footer 只在**最后一段**里找：正文里出现 `Note: xxx` 这种句子很常见，
  一律当 footer 会造出一堆假报，而全是假报的检查会被忽略（包括它本来对的那部分）。
- 不校验历史提交 —— 这个脚本是给**将要提交的那条**用的。

## 七、怎么用

```sh
python3 scripts/commit_style.py --check "fix(api): 修正分页越界"
python3 scripts/commit_style.py --check-file .git/COMMIT_EDITMSG
python3 scripts/commit_style.py --template
```

退出码：`0` 合规或不适用，`1` 有规范违规。想把它挂成 `commit-msg` 钩子也行 ——
但**先确认那个仓库本来有没有钩子**（脚本 `git_guard.py bypass-hooks` 会告诉你）。
