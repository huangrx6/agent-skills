# 历史改写

先确定具体范围和预期：改信息、整理本地提交、恢复误操作，还是移除敏感文件。
普通修复不自动扩大为改写已发布历史。

`git_guard.py rewrite-history` 检查当前 HEAD 是否被本地远端跟踪引用包含；
它不是整个 rebase/filter 范围的共享性证明。检查范围内提交与目标远端，必要时刷新跟踪引用。
`--shared` 仅记录知情的共享改写，不替代用户授权。

| 目标 | 常见方式 |
| --- | --- |
| 改最后一条信息 | `git commit --amend`；会同时包含已暂存内容，先检查 index |
| 只改最后一条内容 | 暂存目标改动后 `git commit --amend --no-edit` |
| 整理一段本地提交 | `git rebase -i <base>`；核对范围与 edit/reword/squash/drop 的含义 |
| 整段历史移除文件 | 选择适合仓库的历史过滤工具；先在隔离副本验证，不默认套用 filter-branch |

执行前保留原引用；范围大或涉及敏感内容时保存隔离备份，并保护其中仍含有的敏感数据。
未提交内容不在 mirror clone 里，需单独保存。

完成后核验新旧提交及最终树：纯信息/结构整理时最终内容应一致；删除文件等内容改写时，
差异应恰好等于预期。再检查分支、标签和其他引用是否仍指向需要处理的旧历史。

确需更新远端时，先运行 `git_guard.py force-push --branch NAME --remote REMOTE`。
该 guard 不允许强推 main/master/dev 或检测出的基线分支，并保守阻断远端独有提交；
它不是自动完成任意共享历史迁移的工具。共享重写需要明确的迁移方案、授权与恢复点。
优先使用绑定预期旧 SHA 的 `--force-with-lease=<ref>:<sha>`，避免后台 fetch 改变默认 lease 的参照。

涉及凭据泄露时先撤销或轮换凭据；重写不能删除他人 clone 中的副本，也不能证明凭据未被使用。
给用户说明协作者需要如何同步，只有获授权时才发送通知或发布记录。
