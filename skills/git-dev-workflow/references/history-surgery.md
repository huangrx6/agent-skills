# 改写历史：什么时候值得，怎么不闯祸

## 先问一句：这条历史是共享的吗

**共享历史别改写** —— 除非你明确知道代价并且愿意付。判据是机械的：

```sh
git branch -r --contains HEAD        # 有任何输出 = 远端已经有这些提交了
python3 scripts/git_guard.py rewrite-history
```

`git_guard.py` 在"要改写的提交已在远端"时给 **BLOCK**；要走下去必须显式 `--shared`，
而且**报告里必须写明「这是一次知情的共享历史改写」** —— 因为别的 clone 不会自己知道，
他们的下一次 pull 会带来一次难查的冲突。

## 四种改写，按代价排序

| 手段 | 改了什么 | 什么时候用 |
| --- | --- | --- |
| `git commit --amend` | 只改**最后一条**提交 | 提交信息写错、漏了一个文件、刚提交就发现错了 |
| `git rebase -i <base>` | 改一段**本地**历史（改信息、合并、拆分、重排） | 提交太碎要合、提交信息不合规、顺序错 |
| `git filter-branch` | 整段历史重写（含文件内容） | 要删掉某个文件/凭据 —— **慢，且要手动清备份** |
| 强推 | 把改写后的结果覆盖远端 | 上面几条做完之后的收尾 |

改写的**动笔顺序**永远是：本地先改 → 看一遍 → 再动远端。

## 手顺

### 1. 先备份（真的做，不是心里想）

```sh
git clone --mirror . /tmp/备份-$(date +%Y%m%d-%H%M%S).git
```

`--mirror` 会把所有分支与引用一起拷走，出事了能整块换回去。这个仓库的主人做过一次脱敏
重写，就是先备再用 —— 备份是**唯一**能兜住"改写做坏了"的东西（reflog 救不了改写类事故，
因为它记的是引用移动，而改写会移动一大堆）。

### 2. 确认工作区干净

```sh
git_state.py            # 未提交那一行必须是 0
```

带着未提交改动做 rebase，那些改动会被卷进冲突里 —— 而它们是你**唯一**没有副本的东西。

### 3. 改写

```sh
git commit --amend                       # 只改信息（--no-edit 是只改内容）
git rebase -i <base>                     # 注意：把想改的那条标成 edit/reword，不是全动
```

`rebase -i` 最常见的两个失误：

- **`pick` 写成了 `drop`**：那不是"跳过"，是**删掉**。
- **范围选大了**：`git rebase -i --root` 会重写第一条提交，通常没必要。

### 4. 复查（别跳这一步）

```sh
git log --oneline -10                    # 信息对不对
git diff <改写前的那个 sha> HEAD          # 内容有没有被改掉（拿备份里的 sha 比）
git_state.py                             # 与远端的领先/落后变成什么样了
```

**`git diff <旧 sha> HEAD` 是这一步的关键**：改写应该只动历史形状，不动树的最终内容。

### 5. 推上去

```sh
git push --force-with-lease origin <分支>
```

`--force-with-lease` 而不是 `--force`：远端在你之后被人推过的话，它会被挡下来；
`--force` 会直接把别人的提交抹掉。基线分支（main / dev）永远不强推 —— 那不在"改写"的
范畴里，那是换主干。

### 6. 告诉别人

共享分支改写完，得有人去通知（或者接受他们下一次 pull 会撞上冲突）。
**这一步不是可选的**：「改完了没事」和「别人还没 pull」是两件事。

## 脱敏重写（这个仓库真做过一次）

顺序是：**备份 → 改写 → 逐项核验 → 强推 → 记档**。

- 改写前用 `git log --all -S"<敏感词>"` 确认它到底出现在哪些提交里（可能不止你记得的那次）。
- 改写后**再跑一遍同样的搜索**，确认命中数为 0 —— 这一步比"我改完了"有说服力得多。
- 顺带检查 tag 与其它引用：`git tag -l`、`git branch -a`，它们的指向也可能带着旧历史。
- 记档：把"改了什么、为什么、备份在哪"写进仓库的文档里（本仓的 `README.md` 就是这么做的）。

## 这个 skill 不做的事

- 不替你决定**该不该**改写 —— 那是取舍，不是计算。
- 不给"改写完就没事了"的保证：远端有别人的 clone 时，结论永远依赖于**他们的下一次操作**。
- 不用 `--force`（只用 `--force-with-lease`），不强推基线分支。
