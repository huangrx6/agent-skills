# 视觉设计规范

## 总原则（这一节是整份文档的核心）

> **不要追求"统一的颜色"，而要追求"统一的审美"。**
> **不要规定每一张图长什么样，而要规定每一张图为什么这样设计。**

这条之所以成立，是因为 Excalidraw 本身已经提供了 hand-drawn 风格、线条、填充、字体、
箭头、图形 —— **skill 不该重复规定"要手绘"**。它该加的那一层是**视觉判断**：

```text
Excalidraw         基础绘图能力（形状 / 箭头 / 字体 / 填充 / 手绘质感）
     ↓
本 skill           视觉判断（什么颜色 / 什么层级 / 什么布局 / 什么留白 / 哪里强调 / 哪里克制）
     ↓
高质量技术图
```

**所以"手绘风"不是这个 skill 的卖点，它是 Excalidraw 这个载体自带的。**
skill 的价值在 Visual Design / Information Design / Diagram Composition ——
换成 SVG 或 Canvas 渲染器，这一份规范仍然成立。

## 2.1 设计目标

在保持 Excalidraw 原生手绘特征的基础上追求：**好看 / 舒服 / 大气 / 专业 / 清晰 / 自然 / 有层次 / 耐看**。

整体观感应接近**经过设计的专业手绘信息图**，而不是 Excalidraw 默认图形的堆叠。

> **"好看 / 舒服 / 大气 / 专业"这四个词本身无法机械校验** —— 这一点必须说清楚，
> 否则就会有人以为跑完校验就等于做完了。校验能管的是"不出错"（不重叠、不溢出、
> 颜色在板内、连线够长）；**"好不好看"只能靠看真实渲染的图**。
>
> 这不是理论：P3（标签压线）和"标签压在节点上"两个缺陷，都是**校验全绿**时靠看图发现的。

## 2.2 不固定视觉主题（**总原则的落地机制**）

**不规定所有图用同一套颜色**，但也不能让模型自由发挥 —— 那正是这个 skill 一直在防的事。

机制：**主题是封闭枚举**，颜色查表得到。

```text
颜色 = THEMES[主题名][语义角色]     两个维度都是封闭枚举
```

| 主题 | 气质 | 典型用途 | 状态 |
| --- | --- | --- | --- |
| `morandi` | 柔和自然、去饱和、偏浅 | 技术架构、系统图 | **已实现（默认）** |
| `bright-clean` | 明亮清爽、白底 | 简单流程、说明图 | **已实现** |
| `dark-tech` | 深色底 + 浅色文字 | 科技主题 | **已实现** |
| `calm-tech` | 冷静科技 | 基础设施、AI 架构 | 候选，未实现 |
| `warm-human` | 温暖人文 | 产品流程 | 候选，未实现 |
| `neutral-elite` | 高级中性、克制 | 汇报材料 | 候选，未实现 |
| `minimal-mono` | 极简单色 | 概念图、草图 | 候选，未实现 |
| `accent-pop` | 中性底 + 少量高饱和强调 | 突出单一重点 | 候选，未实现 |

**没实现的只说"候选"，不写进 `THEMES`。** 写进枚举而没做出来，就是"指向一个空文件的指针"
—— 照着一份不存在的主题名去写规格，只会得到一个报错。

> 先前这里还写过一个 `soft-natural`，实际做出来时名字是 `morandi`（因为用户明确指定了
> 莫兰迪色系）。名字以 `THEMES` 为准，本节只是说明，**不复述取值表** —— 复述就会漂移。

未知主题名**判失败，不 fallback** —— 与 `kind` 同一条原则。

## 2.3 配色原则

**颜色用于建立层级和语义，不是用来填满画布。** 颜色首先回答：

哪些元素属于同一类别？哪些最重要？哪些是输入/输出？哪些是外部系统？哪些是基础设施？
哪些是主流程？哪些是辅助信息？

**数量克制**：1 个主色 + 1~2 个辅助色 + 1 个强调色 + 中性色。复杂图可以增加语义色，
但**避免彩虹式节点图**；两个元素没有明确语义区别时，不要只为了丰富而用不同颜色。

**色彩关系**：主色 → 辅助色 → 强调色 → 中性色。同一语义层级的元素用相近的色彩体系：

```text
✗ 服务 A = 蓝   服务 B = 紫   服务 C = 橙        （像三个不相干的系统）
✓ 服务 A = 主色浅   服务 B = 主色中浅   服务 C = 主色辅助   （一眼看出属于同一个系统）
```

## 2.4 色彩服务于内容

不同类型的图用不同的视觉策略 —— 这是**查表**，不是判断：

| 图类型 / 主题 | 倾向 | 默认主题 |
| --- | --- | --- |
| 技术架构 / 系统图 | 克制、稳定、冷静、高级、清晰 | `soft-natural` 或 `calm-tech` |
| 产品流程 | 明快、友好、有节奏 | `warm-human` 或 `bright-clean` |
| AI / 科技主题 | 蓝紫、青色、深色底、少量发光 | `calm-tech` 或 `dark-tech`（避免大面积霓虹） |
| 数据架构 / 数据流 | 强调**数据流向与层级**，颜色优先给"数据类型/来源/处理阶段/输出" | `soft-natural` |
| 思维导图 | 层级清晰、中心突出 | `bright-clean` 或 `minimal-mono` |
| 汇报材料 | 更规整、更高级 | `neutral-elite` |

## 2.5 背景

简单、干净、低干扰。白 / 暖白 / 浅灰 / 浅色主题背景 / 深色背景 —— **由主题决定**，
不是每次现选。允许极轻纹理、微弱渐变、极淡背景色块、区域背景，
但**不能影响文字阅读、节点识别、连线判断、信息层级**。

> 修正一处旧约束：`palette.py` 里的 `EXCLUDED_STYLES` 曾把"深色背景"整个排除。
> 那是从 PKB 笔记的偏好搬来的；本节允许 `dark-tech` 主题使用深色底。排除清单改为
> **只排除真正会破坏可读性的东西**（大面积霓虹、3D、海报风、商业宣传风）。

## 2.6 节点设计

避免形成大量标准化的"彩色 UI 卡片"。优先：**简洁 / 轻量 / 清晰 / 柔和 / 有适度视觉差异**。

形状可以用矩形、圆角矩形、圆形、菱形、胶囊、自定义手绘形状，
**但形状必须与语义有关**（机制：`kind` → 形状的封闭映射表）：

| 语义 | 形状 |
| --- | --- |
| 服务 / 模块 | 矩形 / 圆角矩形 |
| 数据库 / 存储 | 圆柱（数据库形状） |
| 判断 / 条件 | 菱形 |
| 用户 / 角色 | 椭圆 或 人物图标 |
| 消息 / 队列 | 圆角胶囊 |
| 外部系统 | 虚线边框矩形 |

**不要为了好看而随机改变节点形状。**

## 2.7 节点填充

克制。优先**浅色填充 + 清晰描边**，而不是高饱和大色块。

重点节点通过**封闭枚举**声明，而不是让模型"看着挑一个"：

```text
emphasis: normal | primary | muted     （规格里显式写，或由图类型推出）
```

到 `primary` 的手段：更明显的填充 / 更深的描边 / 更大的尺寸 / 强调色 / 标签 / 光晕。
到 `muted` 的手段：更淡的填充 / 更细的描边。

## 2.8 描边

**不默认使用纯黑。** 用与整体主题协调的深色中性色（深灰 / 蓝灰 / 棕灰 / 墨色；
深色主题则用对应的浅色线条）。描边的作用是**定义边界和结构**，不要让它成为视觉焦点。

（这一条已经落地并被量化：莫兰迪主题实测描边 vs 底色 2.19~2.48 —— 刻意**不**压到 3:1，
因为压下去六条描边会全变成近似的深灰、丢掉色相识别。）

## 2.9 连线

架构图最重要的视觉元素之一。优先：**清晰 / 简洁 / 有方向 / 少交叉 / 少回绕 / 层级明确**。

线型必须**有明确语义**（封闭枚举，不允许为了装饰而混用）：

| 线型 | 语义 |
| --- | --- |
| 实线 | 主流程 |
| 虚线 | 异步 / 可选 / 间接关系 |
| 箭头 | 数据 / 调用方向 |
| 双向箭头 | 双向通信 |

**P1（同点喷出）与 P3（标签压线）就发生在这一节，两条都已处理：**

- 同一节点有多条出边时不能全部从同一个锚点射出 —— 现在按扇出数在节点边缘**均分落点**，
  并按另一端的横向位置排序（往上的目标配上面的贴点，这会**直接减少交叉**）。
  单条边不铺开，仍取中点，所以老图观感不变。
- 标签位置要**避开所有连线**，而不只是避开自己那条：候选方向 × 递增退让量 × **沿边滑动**，
  取第一个干净的。注意 P11 的教训 —— 搜索逻辑一直是对的，是喂给它的障碍物错了。
- 连线**不许穿过别的节点**：绕行与校验见 2.10。

## 2.10 留白

**留白优先级高于填满画布。** 节点之间要留够空间，让用户能快速判断谁和谁有关系。
尤其避免：节点贴节点、线贴线、文字贴边。

复杂图拥挤时优先**增加画布 / 分区域 / 分层 / 调整布局**，而不是不断缩小元素。

**P2（线穿过节点）属于这一节，已经补上一整条链路：**

1. **绕行由脚本做**（`layout.avoid_nodes`）：绕不过去的线段，绕着障碍节点的包围盒推开 ——
   候选顺序是「小动作优先」（先试小幅偏移，再试绕盒子），这个顺序有实测依据：
   反过来试过大绕行会占掉别的边本来能用的空间，整体反而更差。
2. **推不开就报出来**（`check_layout.check_edges_through_nodes`）：这是纯几何判断
   （线段与矩形相交），完全可以机械检 —— 而它当时**一条校验都没有**，只能靠看图发现。
3. **它是可调项，不是硬门**：报出来之后调参会加大间距重跑（实测网络图跑了 5 轮，
   间距 70→150 / 120→240），**环绕不过去就不出图**会把密集图卡死。

阈值同"元素间隙"（≥ 12px），但"穿过"按"真的相交"判 —— 擦着 1px 过去不算穿过，
只是难看；绕行时才要求留出 12px 间隙。

## 2.11 构图

默认使用稳定、平衡、自然的构图。复杂架构图可以采用左→右、上→下、中心辐射、分层架构、
泳道、区域分组。**不要为了追求"艺术感"破坏信息阅读顺序。**

**P7（长宽比 5:1）与 P8（回边绕大圈）属于这一节**：当主轴很长而副轴很空时，
应考虑换方向（LR ↔ TB）或提示用户拆分；回边应贴着布局边缘走，而不是扫过整张图。

## 2.12 视觉重点

每张图应该有明确的**视觉中心**：用户第一眼就知道这张图最重要的东西是什么。
可以通过尺寸 / 位置 / 颜色 / 描边 / 留白 / 字体 / 层级共同实现。**避免所有节点都一样重要。**

**P4（无标题）与 P6（无层级）属于这一节，两条都已实现**：`title` 渲染在内容上方居中；
`emphasis: primary | normal | muted` 通过填充浓度与描边粗细建立层级。

注意这里**刻意没用"更大的尺寸"**这一手段：尺寸会进尺寸链（文字 → 盒子 → 坐标），
改它就得重新验证 12px 最小间隙那套阈值，而"哪几处必须一眼看到"本身不需要动几何。

## 2.13 字体

首先保证**清晰、自然、易读**。不要为了手绘风强制所有文字用夸张的手写字体。

| 场景 | 字体 |
| --- | --- |
| 普通架构图 | 清晰的无衬线字体 |
| 技术代码 / API | 等宽字体 |
| 概念图 / 产品草图 | 可以适当用夸张一点的 |

**字号固定 3 档（24 / 16 / 12），不给区间** —— 区间就是"让模型自己判断"，而它不该判断这个。

## 2.14 装饰

允许装饰，但**少而精**：小图标、标注、手绘箭头、强调圈、注释、小型背景元素。
所有装饰都要服务于**理解内容或增强视觉层级**。**不要添加无法解释其作用的装饰。**

图标遵循同一条纪律：**只允许一个库** —— 前作的失败模式正是"3 个图标源 → 风格混杂"。

因为它只扫含「见 / 参见」这类动词的行，而这句话用的是「遵循」。）

## 2.15 "大气感"的实现原则

"大气"**不是**元素越大、颜色越深、装饰越多，而是：

1. **大留白** —— 让画面呼吸
2. **大层级** —— 减少无意义的小节点
3. **强结构** —— 主次关系一眼可见
4. **克制颜色** —— 减少视觉噪声
5. **清晰路径** —— 阅读路线自然
6. **适当的不对称** —— 避免机械化，但不破坏平衡

## 2.16 不要过度手绘

底层已经是 Excalidraw，**不要再次刻意制造大量"假手绘"效果**。避免：所有线条严重弯曲、
所有框都故意歪斜、文字全部夸张手写体、大量水彩纹理 / 纸张噪点 / 涂鸦 / 装饰箭头。

目标是**保留 Excalidraw 的自然手绘感，同时提升视觉设计质量**，
而不是把技术架构图变成插画。

## 2.17 自适应视觉策略

生成前根据 **图表类型 + 内容主题 + 使用场景 + 信息复杂度 + 用户指定风格** 自动确定：
配色、节点样式、线条样式、字体、背景、层级、留白、装饰程度。

**机制是查表，不是"让模型看着办"**（见 2.4 的类型→主题表）。优先级：

```text
用户显式指定 theme  >  图类型 × 场景查表  >  默认 soft-natural
```

除非用户明确指定，否则不要固定一种视觉主题。

## 2.18 最终审美检查

生成后不能只检查"结构有没有错"，还要检查：

| 维度 | 能机械校验？ | 怎么查 |
| --- | --- | --- |
| **信息** 能否快速理解 / 主流程明确 / 节点关系清楚 | 部分 | 交叉数、连通性、标题存在性 |
| **视觉** 是否舒服 / 有视觉中心 / 颜色过多 / 局部拥挤 / 留白 / 噪声 | **部分** | 间隙、连线长度、**线是否穿节点**、标签是否压线、颜色数量 |
| **风格** 自然手绘感 / 专业 / 大气 / 过度装饰 / 统一设计体系 | **不能** | **只能看真实渲染的图** |

最后一行是这份文档最重要的诚实标注：**"是否好看"没有校验器。**
所以 `SKILL.md` 与 `references/validation.md` 都把"用眼睛看一遍"写成**硬性验收条件**，
而不是可选项 —— 上面 P2 和 P3 就是这么被发现的。
