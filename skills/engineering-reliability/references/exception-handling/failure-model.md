# 失败模型与全局异常处理

## 失败分类

| 类别 | category 枚举 | 含义 | 默认处理 |
| --- | --- | --- | --- |
| 输入错误 | `INPUT` | 语法、类型、格式、范围或必填字段不合法 | 返回准确 4xx，不重试 |
| 业务失败 | `BUSINESS` | 合法请求违反领域规则或资源当前状态 | 返回稳定业务错误码，通常不输出堆栈 |
| 认证与授权失败 | `AUTH` | 身份缺失、失效或权限不足 | 返回准确拒绝语义，不暴露校验细节 |
| 冲突与并发失败 | `CONFLICT` | 版本、锁、重复请求或状态冲突 | 返回冲突语义，仅在安全时重试 |
| 限流与过载 | `RATE_LIMIT` | 超出调用频率或并发配额 | 返回 429 与 Retry-After，调用方可限频重试 |
| 依赖失败 | `DEPENDENCY` | 数据库、缓存、RPC、队列或存储失败 | 归一化失败，隐藏实现细节 |
| 取消与超时 | （归入上游取消或 `DEPENDENCY`） | 调用方取消或截止时间耗尽 | 停止工作并传播取消 |
| 程序缺陷 | `SYSTEM` | 不变量破坏、非法状态或未预期运行时异常 | 对外兜底，对内完整记录并告警 |

`category` 枚举值必须与校验脚本的 `CATEGORIES` 集合一致（`INPUT`/`BUSINESS`/`AUTH`/`CONFLICT`/`RATE_LIMIT`/`DEPENDENCY`/`SYSTEM`）。取消与超时没有独立枚举值：上游取消不产生对外错误码；依赖侧超时归 `DEPENDENCY`。

## 捕获规则

仅在当前层能够承担至少一项职责时捕获：

- 恢复或提供已定义降级结果；
- 补偿或回滚；
- 转换为稳定的领域异常或依赖异常；
- 补充不重复的操作上下文；
- 使用可靠机制释放资源；
- 在 API、RPC、任务或消费者边界完成最终转换。

禁止仅为打印日志而捕获并重新抛出。未知失败发生后，不得返回空值、默认值或成功响应掩盖故障。

## 包装与传播

包装异常时必须：

- 说明失败的具体操作；
- 只加入安全且必要的对象上下文；
- 将原始异常保留为 `cause`；
- 保留调用栈与因果链；
- 避免多个层级重复添加相同语义。

优先使用“为订单预占库存失败”，而不是“操作失败”。

## 分层职责

| 层级 | 职责 |
| --- | --- |
| 领域层 | 表达预期业务规则失败，不包含传输协议逻辑 |
| 应用层 | 编排事务、补偿和用例上下文 |
| 基础设施层 | 归一化数据库、网络、缓存、存储和队列失败 |
| 入口边界 | 映射协议响应、透传链路标识并执行最终处置 |
| 错误码目录 | 维护错误码、状态、可重试性、责任方和生命周期 |

业务层不得直接构造 HTTP 错误响应。全局异常处理器不得包含具体业务判断。

## 全局异常处理器

每个执行入口应设置最终异常边界。处理器必须：

1. 识别已登记的预期失败；
2. 映射对外错误码和协议状态；
3. 创建或透传 `traceId`、`spanId` 或 `correlationId`；
4. 生成统一、安全的错误响应；
5. 清理内部实现细节和敏感信息；
6. 将未知失败统一映射为 `INTERNAL_ERROR`；
7. 保留运行时要求终止进程的致命行为。

处理器不得把所有异常统一返回 400、500 或 HTTP 200，也不得依据异常消息关键词推导映射。

## 资源清理

使用 `finally`、`defer`、上下文管理器或等效机制保证清理。

清理同时失败时，保留原始业务失败为主异常，将清理失败作为附加信息，不得覆盖原始原因。
