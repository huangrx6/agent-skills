# 日志事件、责任边界与级别

## 事件选择

记录事件前先判断它是否至少具有一种价值：

- 帮助定位故障；
- 表达关键运行状态变化；
- 支持容量、稳定性或业务运营分析；
- 形成安全或合规审计证据。

不得因为"以后可能有用"而默认记录完整请求、响应、对象或循环内逐项状态。

## 单点记录责任

同一失败通常只在承担最终结果责任的边界记录一次。

底层可以补充异常上下文后继续传播，但不应每层重复打印同一调用栈。只有发生新的运行事件时才再次记录，例如：

- 重试最终耗尽；
- 降级失败；
- 回滚或清理失败；
- 转入死信；
- 局部故障升级为服务级故障。

常见落地形态是"统一错误出口"：由唯一的总出口（全局异常处理器或请求边界中间件）统一输出最终失败日志，业务代码和中间层不重复打印，只负责补充上下文或透传。

异常处理规则本身由异常处理层负责；本技能只规定日志责任和记录方式。

## 日志级别

| 级别 | 使用场景 |
| --- | --- |
| DEBUG | 诊断分支、内部状态和开发调试信息，生产环境可关闭或采样 |
| INFO | 正常关键状态变化、生命周期和有价值的预期结果 |
| WARN | 操作仍可继续，但发生恢复、重试、降级、冲突或异常趋势 |
| ERROR | 当前操作最终失败，需要排查、告警或人工介入 |

级别反映运行影响，而不是代码是否进入 `catch`。

不单独推荐 TRACE 级别：更细粒度的调试信息并入 DEBUG；若使用 OpenTelemetry 标准且平台区分 TRACE，按下方映射表处理。

普通参数校验失败、资源不存在和预期业务拒绝通常不应记录为 ERROR。重复认证失败、疑似攻击等安全事件应进入安全日志或审计渠道。

### FATAL 级别

不单独引入 FATAL 级别。进程级致命错误使用 `ERROR` + 专用事件（如 `process.fatal`）+ 非零退出码表达，并写入 stderr。使用 OpenTelemetry 平台时映射到 severity 21。

### 级别与严重性数值映射

使用 OpenTelemetry 平台或需要数值严重性时，按标准值映射：

| 级别 | severity_number |
| --- | --- |
| TRACE | 1 |
| DEBUG | 5 |
| INFO | 9 |
| WARN | 13 |
| ERROR | 17 |
| FATAL（如平台需要） | 21 |

### 预期失败与安全事件的可见性习惯

- 预期业务失败（校验失败、拒绝、认证失败等）记录为 WARN + 稳定短码（如 `failure.reason=bad-credentials`），不输出完整堆栈；
- 但预期失败仍需可见性：统一事件化记录，成功与失败使用同一事件名（如 `authentication.succeeded` / `authentication.failed`），便于按事件聚合趋势和识别攻击模式；
- 同一类预期失败高频发生时用限频或采样，不逐条刷屏。

## 异常日志

未知异常最终逃逸时，内部日志应包含：

- 异常类型；
- 安全处理后的异常消息；
- 调用栈；
- 因果链；
- 操作、服务、环境与链路上下文。

使用标准异常字段名，避免各服务自创命名导致跨服务漂移：

| 字段 | 含义 |
| --- | --- |
| `exception.type` | 异常类型（类名/类型标识） |
| `exception.message` | 安全处理后的异常消息 |
| `exception.stacktrace` | 调用栈（按格式规范限制深度） |

以上三个对齐 OpenTelemetry 异常语义约定。因果链（Caused by / 嵌套异常）没有标准字段，通常嵌在 `exception.stacktrace` 的 "Caused by" 段落中，或由团队约定扩展字段记录；不要在不同服务中为因果链自创不同字段名。

预期业务失败通常只记录错误码、操作和必要业务上下文，不输出完整堆栈。

## 消息文本

日志消息应简洁描述事件，不承担机器解析契约。统计、检索和告警必须依赖稳定字段或事件类型，而不是自然语言片段。

使用"人读流"（控制台文本）时，可采用 `[模块] key=value` 前缀的可读约定（如 `[auth] result=SUCCESS principal=alice authType=password`）提升人工排查效率；同一事件的结构化字段仍必须进入机器读流（JSON）作为机器契约。可读文本形态不属于机器契约。
