## 默认格式

没有平台强制格式时，生产应用应优先输出 UTF-8 编码的 JSON Lines：

- 每个日志事件是一个完整 JSON 对象；
- 每条记录独占一行；
- 不输出 ANSI 颜色控制码；
- 不在同一日志流混用 JSON、普通文本和多种分隔格式；
- 换行、制表符等内容必须由 JSON 正确转义。

示例：

```json
{"timestamp":"2026-08-06T09:30:00.123Z","level":"INFO","event.name":"order.created","message":"订单创建完成","service.name":"order-service","trace_id":"..."}
```

只有在平台明确要求 RFC 5424、OTLP 或其他原生格式时才采用对应格式。

## 双流输出模式

允许"人读流 + 机器读流"并存，但必须满足：

- **人读流**（如控制台文本）：一行式可读文本，供人工排查；生产环境不输出 ANSI 颜色；可采用 `[模块] key=value` 前缀约定提升可读性；
- **机器读流**（如 JSON 文件/OTLP）：结构化字段，是唯一机器契约；
- 同一事件在两个流中各出现一次，形态固定（文本或 JSON），不得把同一条日志重复输出到同一流；
- 两个流的字段语义必须一致：人读流里的 `key=value` 必须来自同一事件的结构化字段，不得在文本流中拼接机器流里不存在的信息；
- 两个流使用同一级别阈值和同一上下文（trace/request 标识一致）；
- 级别筛选建议一致（ERROR 独立流、WARN/ERROR 分离等）时，规则要写明，避免人工排查时两处对不上。

不得在应用内部把同一事件复制到多个等价流造成重复采集（如同时写两个 JSON 文件流）。双流并存指的是形态不同（文本 vs 结构化），不是同一形态多份。

## 时间戳

时间戳必须：

- 表示事件实际发生时间；
- 包含时区；
- 跨系统集中采集时统一使用 UTC；
- 使用稳定的 RFC 3339/ISO 8601 表示；
- 精度至少满足故障排序要求，通常使用毫秒或更高精度；
- 不依赖本地化日期字符串。

采集链路可能产生明显延迟时，可同时记录：

- `timestamp`：事件发生时间；
- `observed_timestamp`：采集器观察到事件的时间。

服务节点必须进行时钟同步，并监控明显时钟漂移。

## 字段与类型

公共字段必须在字段目录中定义名称、类型、单位和是否必填。

要求：

- 同一字段不得在不同事件中混用字符串、数字和对象类型；
- 时长统一明确单位，优先使用 `duration_ms` 或标准遥测单位；
- 布尔值使用 JSON 布尔类型，不使用 `"yes"`、`"0"` 等文本代替；
- 计数和状态码使用数值类型；
- 复杂对象只在确有检索价值且大小受控时记录；
- 字段缺失与空字符串必须具有不同语义。

建议记录 `schema.version`，用于管理字段演进。

## 严重性数值

使用 OpenTelemetry 平台时，`severity_number` 与文本级别的映射见 [logging-model.md](logging-model.md) 的级别与严重性数值映射。文本级别与数值严重性必须一一对应，由日志 SDK 统一转换，不得在业务代码中手写数值。

## 消息与异常堆栈

`message` 用于人类阅读，不是机器解析契约。机器处理应依赖 `event.name`、错误码和结构化字段。

异常堆栈可以：

- 作为正确转义的字符串字段（`exception.stacktrace`）；
- 作为平台支持的标准异常字段；
- 由日志 SDK 以结构化异常对象输出。

不得把未转义多行堆栈直接写入单行日志流，导致一条事件被采集器识别为多条记录。

堆栈必须限制深度（例如 20-30 帧）和单帧消息长度：

- 未知异常的内部日志保留足够定位问题的深度；
- 截断时按帧截断而非整段丢弃，保留栈顶调用链；
- 平台支持时优先使用平台异常字段，让平台负责渲染；
- 已知库的深层内部帧可以折叠或省略。

## 记录大小

必须为单条日志设置合理的最大大小。

超出限制时：

- 优先删除非必要大字段；
- 对允许截断的字段执行截断；
- 增加 `log.truncated=true` 或等效标记；
- 不得把一条逻辑事件随意拆成无法关联的多条日志；
- 不得因日志序列化失败中断核心业务。

## 标准输出与标准错误

容器和托管运行环境通常应写入 stdout/stderr，由运行时、节点 Agent 或平台采集。

要求：

- 每次写入一个完整日志事件；
- 不在应用内部同时把同一事件复制到 stdout 和文件；
- stdout/stderr 的使用规则由团队统一，例如普通日志到 stdout、进程级致命错误到 stderr；
- 不依赖终端颜色、交互控制码或本地终端宽度。

## 文件输出

确需写文件时必须定义：

- 文件路径与目录所有者；
- 编码与格式；
- 文件权限；
- 活动文件命名；
- 轮转责任方；
- 重新打开文件句柄的机制；
- 轮转、压缩、保留和清理策略。

日志文件不得写入临时且会随容器消失的位置，除非平台已负责实时采集并允许丢失本地副本。

多实例部署时，活动文件名应包含实例唯一标识（如 `app.log.instance-3` 或 PID 后缀），避免多进程争写同一文件。

## Syslog 与 OTLP

使用 Syslog 时应遵循 RFC 5424 或平台明确支持的兼容格式，避免自定义不可解析报文。

使用 OpenTelemetry 时，应映射到其日志数据模型中的时间戳、严重性、Body、Resource、Attributes、TraceId、SpanId 和 EventName 等字段。

## Serverless 环境

Serverless（FaaS）环境的特殊性：

- 通常没有本地磁盘或不保证持久化，只能写 stdout/stderr 或直接投递日志平台；
- 平台对单条日志大小、写入速率和保留期有明确限制，必须按平台文档配置；
- 无文件轮转概念，滚动、压缩、保留与清理责任全部归平台，不写入 SKILL 的本地文件策略；
- 冷启动和并发实例多，日志应尽量小且少，避免按请求逐条 INFO 导致成本失控；
- 平台限制内无法满足审计或合规保留时，应显式投递到独立审计存储，而不是依赖平台默认保留；
- 不要在函数内维护长生命周期日志缓冲或后台刷盘线程。

## 兼容性

- 新增可选字段通常是兼容变更；
- 删除必填字段、改变字段类型或改变事件名语义属于破坏性变更；
- 字段重命名应提供过渡期；
- 不得要求查询、告警或程序长期解析自然语言消息。
