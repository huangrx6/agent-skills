# 报告可核验的结果

报告应让用户知道改了什么、为什么有用、验证到哪里。数字从本次命令结果取得，
不要复制 README 示例、旧会话成绩或未执行的计划。

## 不同证据证明不同事情

| 证据 | 能说明什么 |
| --- | --- |
| 结构与引用检查 | 文件格式和可识别目标符合机械规则 |
| 测试运行结果 | 本次实际执行用例的通过、失败、错误与跳过 |
| 浏览器/导出回读 | 对应环境和对应产物的实际表现 |
| 视觉审阅 | 具体页面上的排版、层级、可读性问题 |
| 文件与安装快照 | 当前读取到的工作区或安装目录状态 |

`Ran N tests` 包含跳过项，不等于 N 条通过；进程中断不能计作零失败或全绿。
缺失依赖可以让对应集成测试明确跳过，但交付依赖该功能时仍需在满足依赖的环境验证。
静态快照中的“测试文件数”不是用例数，更不是已通过数量。

## 如何写

先给结果，再列关键修改和验证命令的简洁摘要。失败与未验证项说明原因及影响。
必要时链接原始日志或文件，不要求每次把整段输出复制进对话。
命令未执行、外部服务没连接、截图没看过，就不要写成已经完成的验收。

`preflight.py` 只汇总它实际执行的三项检查。泄露词表未配置、安装器不可用、
脚本未在文档中出现等情况，要按输出的真实含义说明，不能改写成整体安全或无用。
