# skill README 模版

每个 skill 都要有一份 `README.md`，和它一起放在 skill 目录根下。
`SKILL.md` 是**给 Agent 看的规则**，`README.md` 是**给人看的详解** —— 两者受众不同，不要互相复制。

## 硬约束

| 约束 | 说明 |
| --- | --- |
| 位置 | `<skill>/README.md`，与 `SKILL.md` 同级 |
| 不重复规则 | 红线、触发条件、命令清单的**权威版本**在 `SKILL.md`；README 只解释「为什么」和「怎么用」，不另立一套 |
| 不写死本机路径 | 凭据 / vault / 配置一律说「从哪里解析」，不写具体路径（换机器只改一处） |
| 命令要能跑 | 「快速开始」里的命令必须是**现在就能跑**的，不是计划中的能力；未实现的能力归到「已知限制」 |
| 与 SKILL.md 同名同向 | 目录名 = frontmatter `name` = 标题里出现的名字 |

## 模版（照结构写，标题可按需增删）

```markdown
# <skill-name>

> 一句话：这个 skill 干什么。**不干什么**（把最容易误触发的邻近能力点掉）。

## 解决什么问题

2~4 句真实场景，带**具体触发语**（用户会怎么开口）。
写「以前怎么做、痛在哪」，不写抽象价值。

## 安装

\```sh
python3 tools/install_skills.py            # 默认软链
npx skills add <repo> --skill <skill-name> # 副本方式
\```

依赖：运行时用什么（**零依赖**就写明「只用 Python 标准库」）。

## 配置

| 配置项 | 从哪里读 | 说明 |
| --- | --- | --- |
| <凭据/路径> | `$ENV` → `~/.config/<x>/<y>` | 谁需要配、不配会怎样 |

首次配置的分步操作放这里或指向 `references/<x>.md`。

## 快速开始

\```sh
<3~6 条最常用的命令，带注释>
\```

预期输出示例（几行即可，**不要贴整段真实数据**）。

## 能力详解

| 能力 | 命令 / 入口 | 说明 |
| --- | --- | --- |
| <能力> | `<命令>` | 边界、默认值、注意点 |

细节手册见 `references/`（列出各文件负责什么）。

## 目录结构

\```text
<skill>/
├── SKILL.md          # 给 Agent 的规则（触发、红线、命令索引）
├── README.md         # 本文件
├── references/       # 细节手册
├── scripts/          # 确定性脚本
└── evals/            # 触发与行为评估
\```

## 边界（不该用它的时候）

与 `SKILL.md` 的 Do NOT 一致，用人话重述一遍，并指出**该用哪个 skill**。

## 验证

\```sh
<跑测试 / 校验的命令>
\```

说清楚「什么算通过」。

## 已知限制与未验证项

| 项 | 状态 |
| --- | --- |
| <还没做的> | 计划 / 不做 |
| <需要真实环境才能验的> | **未实测**，别当成已验证 |
```

## 写的时候容易犯的错

- **把 README 写成 SKILL.md 的副本** —— 两份东西必然漂移。README 讲「怎么用 + 为什么」，规则留给 SKILL.md。
- **把计划写成现状** —— 「快速开始」里出现还没实现的能力，等于对读者说谎。没做的进「已知限制」。
- **不写「不干什么」** —— 触发边界只写在 SKILL.md 里，人翻 README 时最容易误用。
- **贴大段真实数据** —— 真实项目名 / 客户名 / 内部系统名会被 `check_leakage.py` 拦下，示例要脱敏或合成。
