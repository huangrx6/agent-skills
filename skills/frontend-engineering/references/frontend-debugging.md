# 前端系统化根因调试手册（Systematic Frontend Debugging）

> **铁律：未经根因调查，严禁提出或写入任何修复代码。**  
> **NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST.**  
> 修症状就是制造下一个更隐蔽的 Bug。前端调试尤其容易诱发“加个 `!important` 看看 / 加个 `setTimeout` 试试 / 补个 `useEffect` 兜底”的赌博心态——严格按四阶段证据链推进。

---

## 何时必须严格执行本流程

- 任何渲染错位、样式被覆盖、主题失效、布局溢出或闪烁；
- 状态不同步、切页残留旧值、输入框丢焦点、列表跳动；
- 交互卡顿、掉帧、无限重渲染、异步请求乱序覆盖；
- 构建报错、水合不匹配（Hydration Mismatch）、测试失败。

**越是以下高压情境越不可跳过**：时间紧迫觉得“改一行就行”、之前已经试过 1–2 次修法但没根治、还没完全搞懂触发路径。

---

## 四阶段系统化根因调试法

每一阶段必须拿到明确产出后，才能进入下一阶段。

| 阶段 | 核心动作 | 通关标准 |
| --- | --- | --- |
| **1. 根因调查与采证** | 读完整报错、稳定复现、查最近改动、按边界插桩采样、逆向追踪数据流 | 掌握可复现事实与真实触发源（WHAT + WHY） |
| **2. 对照正常模式** | 找同仓表现正常的同类组件，逐项比对 DOM/CSS/生命周期/数据流 | 列出全部微小差异，不先入为主忽略 |
| **3. 单假设最小验证** | 写下单一明确假设，做最小单变量改动验证；不对立刻回退 | 假设被直接证实或证伪 |
| **4. 源头修复与回归** | 先写最小复现用例，从源头单点修复，跑回归验证；三连败触发架构熔断 | 缺陷根除、无连带破坏、有回归用例守护 |

---

### 第一阶段：根因调查与采证（Root Cause Investigation）

动手改任何一行修复代码之前，必须完成以下 5 步检查：

1. **完整读完报错与警告**：不要跳过 Console 警告（如 React duplicate key、hydration mismatch、invalid DOM nesting）；读完整错误栈，定位**第一条源头报错**而非级联引爆的最后一条。
2. **确认稳定最小复现**：精确记录触发条件——视口宽度、浅/暗主题、数据量（0 条 / 1 条 / 30+ 条 / 超长名称）、操作顺序。若暂时无法复现，继续采集证据而不是瞎猜。
3. **检查近期变更**：查看 `git diff` 与最近提交、新增依赖、CSS 引入顺序或配置变动。
4. **前端三类专项采证手段**：
   - **CSS 层叠 / 计算样式 / 特异性排查**：
     - 检查目标元素实际命中的 CSS 规则列表、来源文件与选择器特异性；
     - 用 `getComputedStyle(el)` 与盒模型尺寸核对 `display`、`min-width`、`min-height`、`flex-shrink`、`overflow`、`position`、`z-index`；
     - 全局搜索可疑类名，确认是否存在同名选择器后加载静默覆盖。
   - **React 重渲染与状态流排查**：
     - 定位到底是谁触发了重渲染（父组件 prop 新引用？组件内嵌套定义子组件？Context value 每次新建对象？）；
     - 检查是否用 `useEffect` 同步派生状态，或依赖数组漏写/过宽导致过时闭包与无限循环；
     - 检查是否存在受控与非受控输入混用，或切换目标未用 `key` 重置。
   - **异步竞态与多层链路边界插桩**：
     - 跨越 `UI 事件 → Hook/状态层 → API/IPC → 服务端/存储` 的问题，在**每一层边界**打印进出数据、请求序号与时序，跑一次拿齐证据看究竟在哪一层失真，再只针对故障层深挖。
5. **逆向追踪坏值源头**：看到组件渲染了错误值时，不要直接在渲染处写 `value ?? fallback` 掩盖；沿调用栈与 props/store 向上追，直到找到最初产生坏值的源头并从那里修复。

---

### 第二阶段：对照正常模式（Pattern Analysis）

1. **寻找同项目的正常对照**：找一个同仓库中功能相近但表现正常的组件、弹窗或页面。
2. **完整阅读参考实现**：逐行对照，不要扫一眼就下结论。
3. **逐项列出全部差异**：包括 DOM 包裹层级、容器 `min-width: 0` / `min-height: 0`、CSS 导入顺序、Provider 包装边界、初始化与复位时机——**不要假设“这点差异应该没关系”**。
4. **核对隐含前提**：检查该组件依赖哪些外部 Context、CSS 变量、事件监听或挂载时机。

---

### 第三阶段：单假设最小验证（Hypothesis & Minimal Testing）

1. **明确写下单一假设**：“我认为问题根因是 **X**，因为观察到的证据 **Y** 表明 **Z**。”
2. **单变量最小实验**：只改一个最小变量验证假设，**绝不同时改 3 处再一起测**（否则无法判断哪一处生效，还会引入新问题）。
3. **严格证伪回退**：
   - 假设成立 → 进入第四阶段做正式源头修复；
   - 假设不成立 → **立刻撤销本次验证改动**，带着新信息形成下一个假设，绝不把猜错的补丁留在代码里继续叠加。
4. **承认未知**：遇到没搞明白的浏览器或框架行为，明确说明“当前尚不明确 X，需要先查证/采证”，绝不装懂硬蒙。

---

### 第四阶段：源头修复、回归与三连败熔断（Implementation）

1. **先立最小复现回归用例**：能抽成纯逻辑/状态模型的，先写一条必败的 `*.spec.ts` / `*.spec.mjs` 复现用例；交互/样式问题则记录明确可复现的验证步骤。
2. **只做聚焦的单点源头修复**：
   - 样式冲突 → 拆清作用域前缀，不加 `!important`；
   - 切页残留状态 → 在生命周期源头重置或用 `key` 重建，不加 `setTimeout` 清空；
   - 请求乱序覆盖 → 加 `AbortController` + 请求序号守卫，不靠延长防抖碰运气；
   - 不在修 Bug 的同一次提交里夹带“顺手重构旁边旧代码”。
3. **完整验证**：确认回归用例转绿、既有测试无破坏、类型检查与构建通过、实际界面在目标主题与视口下表现正常。

---

## 三连败架构熔断原则（3-Strike Circuit Breaker）

**每次修复失败后先计数**：
- 若尝试次数 `< 3`：回到第一阶段，结合新证据重新分析；
- 若尝试次数 **`≥ 3`**：**立刻停止尝试第 4 次补丁！**

### 典型架构失衡信号
- 每修好一个现象，立刻在别处冒出新的错位或状态不同步；
- 每次修复都在同一个 `useEffect` 或 CSS 选择器上继续叠条件判断；
- 要想让当前修法生效，需要到处塞 ref、定时器或大规模绕弯。

### 熔断后必须做的事
停止修症状，退后一步质疑根本结构：
1. 状态归属是否放错了层级（应提升到 Provider 或彻底改为渲染期派生）？
2. 是否把本该分离的多个语义变体硬塞进了同一个充满布尔开关的巨型组件？
3. 两个模块是否错误耦合在了同一份全局 CSS 规则之下？
4. 整理已排除的假设与架构症结，**先与用户/协作方对齐结构调整方案，再动手改代码**。

---

## 危险信号（Red Flags）与协作纠偏信号

### 脑中闪过以下念头时，立刻刹车回到第一阶段
- “先快速打个补丁，回头再查原因”
- “试试改一下 X 看看能不能好”
- “顺便把三处可疑的地方一起改了跑一遍”
- “问题很简单，不用写回归用例/不用跑构建，我看一眼就行”
- “大概率是 X，直接改了吧”（没有实际采样证据）
- “已经试了两次，再试最后一次补丁吧”

### 收到用户以下反馈时，说明已偏离根因法，立刻回到第一阶段
- “你确定真的发生了吗？” → 未经验证就在猜；
- “加这个能帮我们看到什么证据？” → 缺边界采证；
- “别猜了” → 没拿到一手证据就在提修法；
- “停下来从底层想想” → 陷入修症状循环，需要质疑架构。

## 常见合理化借口对照表

| 常见借口 | 真实后果 | 正确做法 |
| --- | --- | --- |
| “加个 `!important` 马上好，省事” | 埋下层叠炸弹，后续主题切换与交互态全部失效 | 查计算样式与全局类名碰撞，拆清作用域前缀 |
| “加个 `setTimeout(..., 100)` 等 DOM 就绪再聚焦” | 不同机器与高负载下必成偶发闪烁与竞态 | 用事件回调、生命周期钩子或条件就绪回调 |
| “问题太简单，没必要走四阶段流程” | 简单 Bug 一样有根因；按流程查其实比瞎猜返工更快 | 用 1 分钟拿齐复现 + 证据再动手 |
| “先改完试通了再补测试” | 未先复现失败的用例往往测不到真正的触发路径 | 先立必败复现用例，再验证修复转绿 |
| “同时改几处更省时间” | 无法隔离哪一处有效，还把新 Bug 混进同一现场 | 单假设单变量验证，错即回退 |
| “文档太长，我大概照意思改写一下” | 一知半解的模式照抄最容易漏掉关键约束（如 `min-width: 0`） | 完整读完对应参考条目与边界条件再落地 |
| “已经改了两三次，再补一个判断就能过” | 3 次以上失败是架构信号，不是差一个 `if` | 触发三连败熔断，停止补丁并重审架构 |

---

## 当系统排查证明确实属于外部/环境/时序问题时

只有完整走完前两阶段并排除自身逻辑错误后，若确认问题源于外部接口抖动、浏览器差异或环境限制：
1. 如实记录已排查过的证据链；
2. 实现清晰的防御处理（超时、重试、取消、错误降级提示）；
3. 补充必要的可观测日志以便后续追踪。  
（经验提醒：绝大多数“找不到根因的玄学问题”，实际都源于第一阶段采证不完整。）
