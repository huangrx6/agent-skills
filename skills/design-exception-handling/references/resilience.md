# 超时、重试、取消与幂等

## 重试资格

只有同时满足以下条件时才允许自动重试：

1. 失败具有临时性；
2. 操作幂等，或具备幂等保护；
3. 再次执行不会放大副作用；
4. 调用链仍有剩余截止时间；
5. 尝试次数和总耗时均有上限。

可重试情况通常包括临时连接失败、连接重置、依赖短暂不可用、明确限流和可安全重试的并发冲突。

不得重试输入错误、权限拒绝、确定性业务失败、数据损坏、程序缺陷和无保护的非幂等写操作。

## 重试策略

必须明确：

- 最大尝试次数；
- 最大总耗时；
- 初始与最大等待时间；
- 指数倍率；
- 随机抖动；
- 可重试错误集合。

收到 `Retry-After` 时应遵循。每条调用链优先只设置一个明确重试层，避免网关、SDK、服务和任务多层放大重试。

重试放大（retry amplification）是主要风险：若网关、SDK、服务、任务各层独立重试 3 次，最坏情况下单次请求被放大为数十次下游调用，可能把局部故障放大为雪崩。应集中在一层重试，或用总预算（剩余截止时间）约束各层重试总量。

## 幂等保护

重试写操作时，至少使用一种机制：

- 幂等键；
- 唯一约束；
- 条件写入；
- 版本检查；
- 去重表；
- 请求状态查询；
- 事务性 outbox 或 inbox。

超时不能证明写操作失败。再次提交前，应查询状态或复用同一幂等键。

## 超时预算

为 HTTP/RPC、数据库、缓存、文件、对象存储、锁、消息和子进程显式设置超时。

总截止时间应覆盖连接、执行、等待和所有重试。向下游传递剩余预算，不得在每一层重新获得完整超时。

## 取消

上游取消应向支持取消的下游传播。收到取消后：

- 停止启动新工作；
- 中断可取消等待；
- 释放资源；
- 不把调用方取消当作服务端程序缺陷；
- 将清理失败或状态不一致作为独立故障处理。

## 熔断与降级

只有依赖持续失败且快速失败能够保护系统时才使用熔断。必须定义阈值、打开时长、半开探测、指标、告警和安全降级行为。

降级必须保持正确性。没有明确契约时，不得返回虚构或误导性数据。
