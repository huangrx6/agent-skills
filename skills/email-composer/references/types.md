# 类型、必填槽位与复合规则

类型决定主题行写法、必填信息、默认样式和追问重点。先定主类型，再判断是否复合。
类型不明确时不要猜着写，按 [questions.md](questions.md) 追问。

## 判定维度

| 维度 | 取值 | 作用 |
| --- | --- | --- |
| 用途 | 告知、请求、确认、汇报、交付、协调、商务、跟进、邀请、日常 | 决定主类型 |
| 对象 | 上级、同级、下级、跨部门、外部 | 决定称呼、语气与是否用 plain |
| 期望动作 | 仅知悉、回复、审批、确认、参会 | 决定结尾与待办 |
| 紧急度 | 普通、需尽快、紧急 | 决定是否用 alert |

主类型由「用途 + 期望动作」决定，不由措辞决定。例如「同步一下」但要求对方确认，
就是确认邮件；「通知」但要对方审批，就是申请/审批。

## 十个类型

| key | 中文 | 必填槽位 | 默认预设 |
| --- | --- | --- | --- |
| `notice` | 通知 | 事项、生效时间、影响范围、对方需做什么 | business |
| `approval` | 申请/审批 | 申请事项、依据、审批人、期望完成时间 | business |
| `confirm` | 确认 | 确认范围、明细、回复截止时间 | business |
| `report` | 汇报 | 周期、已完成、问题、下周计划 | report |
| `handover` | 交付/验收 | 交付物、验证结果、验收方式、验收人 | report |
| `coordination` | 协调/故障 | 问题、影响、所需支持、责任人 | alert |
| `business` | 商务 | 事项、条件、金额（如有）、下一步 | business |
| `followup` | 跟进 | 待办、截止时间、责任人 | business |
| `invitation` | 邀请 | 主题、时间、地点或链接、议程、参会人 | business |
| `daily` | 日常 | 要点 | plain |

Spec 的 `type` 可以写英文 key，也可以写中文（申请、审批、周报、故障等），脚本会归一化。
未识别的类型保持原样，校验会给警告；不要用未识别类型交付。

## 复合邮件

一封邮件同时承担多种用途时，`type` 写主类型，`secondary` 写次类型：

```yaml
type: approval
secondary: [handover, confirm]
```

- 主类型决定主题行前缀、默认预设和收件人最需要先看到的结论。
- 次类型只追加模块，不改主类型：交付说明用 paragraph/table，工时确认用 table/todo。
- 模块顺序按「结论 → 依据 → 明细 → 待办」排。不要把主类型的结论压到第二屏。
- 复合不等于堆信息。每个次类型至少对应一个可核对的模块；没有内容就不要挂名。

## 与预设的关系

默认对应关系见上表，实际选择顺序是：

1. Spec 的 `style` 明确指定。
2. `urgent: true` 或 `type: coordination` → alert。
3. `type: daily`，或 `audience` 含「外部 / 客户 / 甲方 / 供应商」→ plain。
4. `type` 为 report / handover → report。
5. `type` 为 approval / confirm / invitation / notice / business / followup → business。
6. 其余情况：表格 3 行以上或图片 2 张以上 → report，否则 business。

所以「上线申请 + 3 张图 + 工时表」仍是 business，不会因为图多就变成汇报样式。
用户指定品牌色或预设时，以用户为准；只改样式令牌，不改内容。

原始 HTML 模板不经过这套预设：它保留模板自带的版式，具体规则见
[templates.md](templates.md)。

## 缺少槽位时

- 槽位缺失会改变邮件结论（时间、金额、审批人、影响范围）→ 追问，不写。
- 槽位缺失只影响完整性（签名、抄送、附件名、图片地址）→ 用 `【待填：xxx】`，交付时列出。
- 能从材料推断的槽位直接推断，并在交付清单的「假设」里注明依据。
- 材料里的日期或数字互相矛盾时停止写作，先追问，不自行选一个。

各类型的追问重点与话术见 [questions.md](questions.md)。
