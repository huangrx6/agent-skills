# 从材料提取功能过程与接口清单

输入可以是接口文档、前后端代码、可读源码的 HTML 原型、截图、数据库表结构，
也可以只是一段需求。材料只提供证据，**不提供换算比例**。

## 先确定四件事

写规格前先固定：度量目的、范围、软件边界与层、功能用户。它们决定哪些数据移动
算 E/X（跨边界）而不是 R/W（边界内），也决定范围外的功能不进入本次计量。
这些字段直接写在 `measurement` 里，产出报告会带上。

## 五种材料的取证方式

| 材料 | 提取什么 | 陷阱 |
| --- | --- | --- |
| Swagger / OpenAPI | path+method、summary、入参、响应字段、tag | summary 为空时不要只取 path 末词当业务对象 |
| 后端路由 | 路由表、控制器方法、注释、包结构 | 中间件与健康检查不是业务功能；网关前缀不是业务对象 |
| 前端代码 | 页面/路由清单、每个页面的 API 调用、表单与表格字段 | 只搜 `axios` 会漏掉封装层；先枚举页面再逐页找调用 |
| HTML 原型（可读源码） | `data-page`、导航项、fetch/axios、表单与表头 | 原型里的模拟数据不是接口证据 |
| 截图 / 设计稿 | 页面上的操作与可见字段（表头、表单标签、指标名） | 入参/出参看不见，必须标待核实；可见字段可以直接用 |
| 数据库 DDL | 表、字段、说明、外键 | 表数 ≠ 功能过程数；物理表 ≠ 兴趣对象 |

截图路径的判据只有一句：**页面上看得见＝有证据；看不见＝待核实，不推测**。

## 接口与页面清单（inventory）

`coverage` 需要一个清单文件。它记录「素材里有什么」，不记录「应该拆多少」：

```json
{
  "version": 1,
  "source": "OpenAPI v3 + 前端路由（2026-10 抓取）",
  "pages": [
    {"id": "orders", "name": "订单列表", "evidence": "src/views/orders/List.vue:12",
     "endpoints": ["api-orders-list", "api-orders-detail"]},
    {"id": "empty", "name": "开发者中心", "evidence": "router.ts:88", "endpoints": []}
  ],
  "endpoints": [
    {"id": "api-orders-list", "l3": "订单管理", "method": "GET", "path": "/api/orders",
     "summary": "订单列表查询", "evidence": "openapi.json#/paths/~1api~1orders"},
    {"id": "api-orders-detail", "l3": "订单管理", "method": "GET", "path": "/api/orders/{id}",
     "summary": "订单详情查询", "evidence": "openapi.json#/paths/~1api~1orders~1{id}"}
  ]
}
```

字段约定：

- `id` 唯一，供规格引用，不由 path 自动生成（改名就断链）。
- `pages[].endpoints` 只能引用存在的接口 id；空数组表示该页面没有提取到接口。
- `endpoints[].process` 可选，表示接口侧已经知道归属；与规格 `evidence` 冲突时不自动选一个。

## 在规格里认领接口

```json
{"id": "FP-002", "name": "订单列表查询", "op": "queryList",
 "evidence": ["api-orders-list"], "movements": [...]}
```

`evidence` 是接口 id 数组，不是自然语言。自然语言证据仍写在 `source`
（需求章节、代码位置）。两者都要：`source` 说明需求依据，`evidence` 让覆盖可机器核对。

## 覆盖核对照什么

`cosmic.py coverage spec.json inventory.json`：

1. **未覆盖接口**：清单里有、没有任何过程认领。可能是范围外、重复接口，也可能是漏拆。
   报告按 `summary` 前四个字给出「可能对应」的候选，**只提示，不自动认领**。
2. **悬空证据**：规格引用了清单里不存在的 id。改名或删接口后最常见。
3. **空页面**：页面存在但没提取到接口。先判断是纯前端页还是提取遗漏。
4. **无接口被认领的页面**：有接口但都不属于本次范围，同样要确认。
5. **页面覆盖率**：有接口的页面 ÷ 总页面。低于 90% 时提示「素材可能不完整」，
   但这不是硬阈值——未提供的页面不属于遗漏，如实在报告里写清范围即可。

覆盖通过只证明清单与规格对得上，不证明清单完整，也不证明过程划分正确。

## 反向核对（接口 → 功能过程）

历史上真实发生过整块模块丢失：234 个接口只转出 283 个移动，分发服务器管理、
站内通知、操作日志、重试策略查询整块没进表。原因不是算错，而是聚合时只顺着模块
往下写，没有回头对数。

使用 `coverage` 时按两步做：

1. 先把清单里的接口尽量写上 `evidence`，跑一次，列出未覆盖项。
2. 对每个未覆盖接口问一句「这是范围外、重复，还是漏了？」。确认范围外的，从清单删除
   或标注；确认漏拆的，补过程再跑，直到未覆盖为 0 或剩余项都有书面理由。

高发遗漏区：独立子资源前缀（`/api/{entity}/{id}/{sub}`）、`PATCH` 状态切换、
汇总/统计类 GET、登录与认证接口、导出任务与异步重试接口。它们常被误并进列表查询，
或因为「不是业务功能」被跳过。

## 页面枚举先于函数搜索

从前端代码提取时，先列出全部页面/路由/菜单项，再逐页找渲染组件与 API 调用。
先搜函数会得到一堆调用点，但不知道漏了哪些页面。输出一张清单：

| 页面 | 渲染入口 | 接口数 | 判断 |
| --- | --- | --- | --- |
| 订单列表 | `views/orders/List.vue` | 2 | 有数据操作 |
| 开发者中心 | `views/dev/Index.vue` | 0 | 空占位，无后台交互 |

空占位页不算漏拆；有数据展示却没有接口调用，才需要回头查封装层。

## 只有需求文档时

不需要为了走流程先造一份接口清单。直接从需求章节引用功能用户、触发事件与数据组，
在 `source` 写章节号，把看不到的入参/出参标 `unverified`。接口清单是可选证据，
不是开工门槛。
