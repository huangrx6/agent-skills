# 拆分原则与反例

先确定度量范围、层、软件边界和功能用户，再根据功能用户需求识别过程与数据移动。
规范来源及适用范围见 [标准与参考来源](measurement-sources.md)。以下是分析步骤，不是定额表。

## 功能过程

每个过程应能追溯到功能用户需求，具有功能用户触发的事件，并完成对此事件的业务响应。
一个过程至少包含两个数据移动，有触发输入，并包含输出或写入；一个过程可有多个输入。
脚本以过程编号分组，不以 E 的出现次数分组，也不把表格最后一行的类型当成执行时序证明。

| 常见材料信号 | 正确的核查问题 | 不能自动推导的结论 |
| --- | --- | --- |
| 一次操作写主表、关联表 | 是否为同一触发下的完整响应？是否移动不同兴趣对象的数据？ | 一张表就是一个功能过程 |
| 列表与详情 | 是否存在独立触发、独立用户需求？ | 超过六个字段就必拆两条 |
| 导入、上传、预览、确认 | 是否分别有独立业务触发，还是一个过程的内部步骤？ | 导入固定 5 或 13 CFP |
| 采集、预计算、入库 | 是独立的功能需求，还是技术实现步骤？ | 指标固定拆成三条过程 |
| 多个看板面板、Tab | 是否为多个过程，或同一过程中的多个数据组？ | 面板/Tab 数直接乘三 |
| 启用与停用、角色视角 | 功能用户需求和数据移动是否实质不同？ | 换按钮、角色或数据值就另计过程 |
| 只读查询 | 数据由谁产生，是否在范围外？ | 本系统一定漏了写入功能 |
| 有手动新增 | 是否存在明确的导入导出需求？ | 自动补导入导出三件套 |
| 子资源接口 | 它是否由独立事件触发？ | URL 层级直接决定功能过程 |

例：提交申请同时保存申请和申请明细，在一个触发下可能是同一过程中的多个 W；
若用户另有独立“维护明细”需求，才分析另一个过程。物理表与兴趣对象不能直接画等号。

## 数据移动

- E：从边界外功能用户进入；X：向边界外功能用户输出。
- R/W：与边界内持久存储之间的读取/写入；删除持久数据也属于 W。
- 每个移动描述一个兴趣对象的数据组。判断依据是需求语义，不能仅按 SQL 次数计数。
- 同一过程同一兴趣对象同类移动通常只计一次；额外移动须有明确需求依据，记录在
  `repeat_reason`，由人工核对。更换数据值、循环次数或批量条数本身不增加 CFP。
- 数据运算、排序、格式转换不单独作为数据移动；确实涉及另一个数据移动时另行识别。
- 同一个数据组可以进入、写入、读取或输出。属性列相同并不自动表示重复计量。
- 单字段也可以描述有效数据组，不为满足“至少三个字段”而捏造属性。

## 容易漏计或错计的移动

- 需求要求向人类用户输出的纯错误/确认消息，在同一功能过程中合计一个 X，不按成功、失败或文案条数分别计点。携带订单编号、余额等业务数据的回执还需按兴趣对象核对数据组。
  仅对纯消息可用“错误/确认消息”作为表内占位对象名，它不代表另有业务实体。
- 仅导航、关闭窗口或改变显示方式的控制命令不单独计；取消订单、退订等实际改变业务数据的操作仍需分析，不能凭“取消”一词排除。分页参数作为真实查询入参可保留。
- 数据校验、换算、排序包含在关联的移动里，不单独计。一个移动只移动一个数据组。
- 改造已有系统时按**受影响的数据移动**计数（新增/修改/删除各 1 CFP），
  不是把过程重新计一遍；变更度量与新建立量不能混用。当前脚本汇总完整过程的移动数，不能直接当作变更 CFP；需另列新增/修改/删除移动与原需求对照。
- 复杂算法不因难度加分。与度量发起方另有约定时，按 LocalFP 在表外单独计量，
  CFP 与 LocalFP 分列并注明实际采用的标准版本，不硬写为 4.0，也不合成一个 CFP 总数。

本地送审表的句式、排序、命名惯例见 [命名与写法](naming-and-style.md)，
它们不改变以上判据。

## 操作名称不是定额

新增、修改、查询或导入都没有本工具预设的固定 CFP。逐项填写实际移动和数据组，
例如新增可能包括 E/R/W/X，审批可能包括 E/R/W；结果取决于真实需求。

## 范围差距分析

先计算材料支持的规模，再与用户目标比较。缺口可以推动需求核查，但不能反向制造功能。
将已确认项和候选项分别汇总；增加或删除真实需求时重新计量并说明来源变化。
需求未变而目标变动时，规格里的过程和移动应保持不变。
