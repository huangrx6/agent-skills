# 操作类型词表：给建议，不给定额

`op` 是可选的分类标签。它决定三件事：**默认描述句式**、**命名一致性提示**、
**`--order crud` 的排序类别**。它**不产生数据移动，也不改变 CFP**。

同一个操作名在不同需求下可以有完全不同的移动：

- 新增通常 `E→W`，但先查重就是 `E→R→W`，还要回执就是 `E→R→W→X`；
- 删除通常 `E→W`，但需要先读取约束再确认，就多一个 R；
- 查询通常 `E→R→X`，但外部数据进入边界时可能先有 W。

所以 `moves` 这一列是**没有相反证据时的提议**。规格里写了什么就计什么。
声明了 `op` 却与默认序列不同时，检查器提示补 `op_note` 说明依据；
不补也不会改数，只是 `--strict` 时会阻塞。

## 词表

| `op` | 名称 | 默认 | 触发方 | 排序类别 | 备注 |
| --- | --- | --- | --- | --- | --- |
| `query` | 查询 | E→R→X | 操作员 | 查询 | |
| `queryList` | 列表查询 | E→R→X | 操作员 | 查询 | 分页列表天然返回总数，不另拆 count |
| `queryDetail` | 详情查询 | E→R→X | 操作员 | 查询 | 与列表各有触发才拆，字段数不是判据 |
| `insert` | 新增 | E→W | 操作员 | 新增 | |
| `update` | 修改 | E→W | 操作员 | 修改 | |
| `delete` | 删除 | E→W | 操作员 | 删除 | 删除持久数据也属于 W |
| `import` | 导入 | E→W | 操作员 | 新增 | 导入是否拆四步见下 |
| `export` | 导出 | E→X | 操作员 | 查询 | |
| `download` | 下载 | E→X | 操作员 | 查询 | |
| `enable` | 启用 | E→W | 操作员 | 修改 | 启用/停用合并为一个过程 |
| `publish` | 发布 | E→W | 操作员 | 新增 | 发布/取消发布合并 |
| `up` | 上线 | E→W | 操作员 | 修改 | 上线/下线合并 |
| `pass` | 审批 | E→W | 操作员 | 修改 | 通过/驳回合并；意见与历史按真实接口判断 |
| `send` | 发送 | E→X | 操作员 | 其他 | 提醒/通知/同步/下发统按发送类 |
| `push` | 推送 | E→X | 操作员 | 其他 | |
| `collect` | 采集 | E→W | 定时任务 | 采集 | 指标三段式的第一段 |
| `stat` | 统计 | E→W | 定时任务 | 采集 | 第二段；采集必须在统计之前 |
| `chart` | 查看图表 | E→R→X | 操作员 | 指标查看 | 第三段 |
| `report` | 报表查询 | E→R→X | 操作员 | 指标查看 | 报表类第三段 |
| `verify` | 验证 | E→W→X | 操作员 | 其他 | 模拟调用等；按真实交互，不套定额 |
| `other` | 其他 | 无默认 | — | 其他 | 词表外的场景，需写明理由 |

排序类别只在 `build --order crud` 时生效，用于满足部分送审表的编排习惯：

`新增 → 修改 → 删除 → 查询 → 采集 → 统计 → 图表/报表 → 其他`

采集与统计属于同一类别但保持先后；报表类模块没有 CRUD 时不强行套这个顺序。

## 子过程描述的默认句式

作者省略 `description` 时按下面的模板生成；已有描述一律原样保留。

| 移动 | 模板 | 例（对象=订单，op=queryList） |
| --- | --- | --- |
| E | `输入{对象}{动作}请求` | 输入订单查询请求 |
| R | `读取{对象}信息` | 读取订单信息 |
| W | 新增/采集/统计 → `保存{对象}信息`；修改/启停/导入 → `更新{对象}信息`；删除 → `删除{对象}信息` | 保存订单信息 |
| X | `返回{对象}{动作}结果` | 返回订单查询结果 |

这是**项目送审偏好的写法**，不是 COSMIC 标准条文。另有实测被要求重写的旧模板句
（`接收…请求并校验输入数据`、`从数据存储读取…`、`将…数据写入数据存储`、
`向用户返回…结果`），检查器只提示并用 `normalize` 改写措辞，不改对象与属性。

## 指标三段式

一个指标通常对应三个过程：`{指标}数据采集`（E→W）→ `{指标}数据统计`（E→W）
→ `{指标}查看图表` 或 `{指标}报表查询`（E→R→X）。

- 采集与统计的功能用户通常是「定时任务」，在规格里如实写。
- 真实系统没有预计算、只做实时聚合时，不要为了凑三段式硬拆；规模小、实时可算的
  指标计入查询过程即可。判据是需求与实现，不是指标名称。
- 采集在统计之前，不代表统计一定要独立：只有结果被单独持久化的统计才需要 W。

## 导入四步不是默认动作

有的系统把导入拆成模板下载、文件上传、数据预览、确认执行四个独立触发，
那就是四个过程（2+2+3+2=9 个移动）。但如果一次请求完成校验与写入，
就是一个过程。**不要因为模块有新增就补导入导出**，也不要为了增加行数补。
依据只能是真实接口、页面或需求。

## 常见的合理偏离

| 规格写法 | 为什么会偏离默认 | 记录方式 |
| --- | --- | --- |
| `insert`：E→R→W→X | 新增前查重、完成后回执 | `op_note` 写清查重与回执的需求依据 |
| `delete`：E→R→W | 删除前读取关联约束 | `op_note` 写清约束来源 |
| `queryList`：E→R→X→W | 查询同时回写访问记录，且该写入在范围内 | `op_note` 说明回写需求；否则应移出范围 |
| `export`：E→R→X | 导出前读取模板或权限数据 | `op_note` 说明读取对象 |

偏离是正常现象。检查器只确保「偏离被写下来」，不让默认值反过来决定计量。
